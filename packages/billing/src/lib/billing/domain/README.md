# Contract billing calculation boundary

`calculateContractBilling` is the only document-level financial entry point for contract billing. Production and simulation loaders pass the same fully resolved, unpriced obligation union with an explicit `live` or `simulate` mode. Obligations contain storage-independent camel-case line, pricing, timing, service, and activity facts; they never contain an `IClientContractLine`, database activity row, `IBillingCharge`, or family compute-input object. Preloaded tax policies are supplied separately by key at the document boundary. The document engine privately translates normalized facts for the legacy arithmetic modules, dispatches fixed, hourly, usage, bucket, product/license, discount, and adjustment calculation, builds canonical lines and explanations, and owns tax and totals. The domain functions perform no database or network I/O and have no clock, random ID, numbering, audit, event, or persistence dependency.

Callers must never invoke `calculateContractCharge` or financial compute modules directly; those symbols are intentionally absent from the package/domain public barrels and are implementation details of the document engine. Production may provide explicitly scoped non-contract supplemental charges because project, material, and manual billing are outside this contract consolidation, but contract charges must always arrive unpriced. `assertLiveContractBillingResult` is the mandatory runtime guard at a persistence boundary. Simulation never receives a commit adapter; production retains its existing transaction, reconciliation, invoice finalization, audit, idempotency, and event stages around the pure result.

Charge results carry their explanation associations directly, so adapters never reconstruct charge keys. Discounts and adjustments also require an explicit execution mode. Production passes the guarded live document through `applyCanonicalLiveBillingResult`; that handoff preserves persistence identities and rich source rows while taking document totals only from the canonical calculation.

Future pricing, proration, tax, adjustment, schedule, charge-key, explanation, and rounding rules belong in this domain layer or one of the compute modules it exclusively dispatches. Do not add direct charge-family calls, financial formulas, or a parallel total pipeline to `BillingEngine` or simulator presentation code. Storage and scenario shapes are normalized before this boundary; persistence maps the canonical live result without recalculating money.
