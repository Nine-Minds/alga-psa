# Email provider security fixes: human review guide

Review this repair first for **initial and reconnect OAuth authorization with a fresh application secret**, **durable credential invalidation across endpoint changes (including environment fallbacks)**, and **private mail-target allowlist compatibility in every IMAP socket path**. Both original findings and their authorization boundaries are covered below.

## Finding 1: provider actions lacked the MSP authorization boundary

`packages/integrations/src/actions/email-actions/emailProviderActions.ts` now uses the existing `requireOutboundEmailAdmin(user, knex)` enforcement point from `mspOutboundEmailAccess.ts`. It guards `upsertEmailProvider`, `createEmailProvider` (intentionally in addition to its delegated upsert), `updateEmailProvider`, `deleteEmailProvider`, `resyncImapProvider`, `testEmailProviderConnection`, `retryMicrosoftSubscriptionRenewal`, and `getEmailProviders`. Both diagnostics actions also use that shared guard, rejecting client users before permission lookup. The direct API handlers in `server/src/app/api/email/imap/{resync,reconnect}/route.ts` and `server/src/app/api/email/oauth/imap/{initiate,callback}/route.ts` independently obtain the authenticated session and apply the same guard before provider reads, secret access, mutations, or outbound requests. Callback state is tenant-checked, but its `userId` is not an authorization input. Writes keep their permission-denied action result; operation, renewal, listing, and diagnostics results retain their established shapes.

Provider-list responses omit client secrets, refresh tokens, access tokens, and webhook verification tokens. The safe `oauth_authorization_status` field communicates `connected`, `not_connected`, or `reauthorization_required`; `ImapProviderForm` renders this field instead of inferring state from redacted token values.

Behavioral coverage is in `packages/integrations/src/actions/email-actions/emailProviderActions.authorization.test.ts`. It checks client denial across all ten exports, missing `ticket_settings:update` denial across the MSP entry points, no provider-table reads for denied callers, an empty unauthorized listing, and an authorized caller reaching provider work.

## Finding 2: configurable IMAP targets could receive credentials or open internal sockets

The reusable validation core is `shared/lib/net/outboundTarget.ts`, built as `@alga-psa/shared/lib/net/outboundTarget`. It normalizes hostnames, validates syntax and scheme, rejects localhost aliases, resolves all DNS answers, and blocks loopback, private, link-local, metadata, CGNAT, and reserved IPv4/IPv6 ranges. `server/src/lib/webhooks/ssrf.ts` delegates to it while retaining the webhook API and error class.

The action, auth-paused lifecycle recovery, inbound queue worker, and live `services/email-service` listener all use the shared IMAP host policy before OAuth refresh or `ImapFlow` construction. The policy checks every DNS answer, allows only IMAP ports 143/993, and returns one approved address. Every ImapFlow transport receives a lookup callback pinned to that address. OAuth token exchanges validate HTTPS port 443, disable redirects and environment proxy routing, and pin the HTTPS agent to the validated address. This also covers the authorization-code callback. Token endpoints never inherit the private IMAP exception. The listener discovery query loads the durable issuer marker and secret-key version, and active workers restart when the host, endpoint, binding, version, or OAuth credentials change. Cached listener access tokens are also rejected when their issuer marker does not match. See `docs/security/email-provider-private-target-allowlist.md` for the deployment-only `EMAIL_PROVIDER_IMAP_PRIVATE_TARGET_ALLOWLIST` contract. Private IMAP targets are denied by default; exact host/IP entries opt in RFC 1918 IPv4 and IPv6 unique-local destinations. The allowlist cannot permit loopback, link-local/metadata, CGNAT, or reserved addresses.

Migration `server/migrations/20261109180000_bind_imap_oauth_credentials_to_token_endpoint.cjs` adds the active issuer marker and secret-key version. `server/migrations/20261110090000_add_imap_oauth_reauthorization_status.cjs` stores the UI reauthorization state separately. On every token-endpoint change, `persistImapConfig` clears the active `oauth_credentials_token_url`, resets the secret-key version to 0, sets the separate reauthorization-required flag, and commits `NULL` for database `oauth_client_secret`, `refresh_token`, `access_token`, and expiry fields. This also discards old credentials resubmitted by a stale form. Returning to a previously used endpoint does not restore the marker. Every mailbox-token consumer rejects unbound credentials before secret lookup, including environment-backed legacy and endpoint-scoped fallbacks and cached access-token paths. Secret-store deletion remains best effort because a composite provider may expose read-only environment fallback values. The update returns a reconnect-required `setupError` after endpoint-change clearing commits.

Application client secrets and mailbox tokens have different authorization lifecycles. A new confidential OAuth client needs its application secret before it can obtain its first mailbox refresh token. After an endpoint change, save the newly entered client secret again at the unchanged endpoint, then reconnect the mailbox. Persistence accepts this fresh secret in the existing database field without restoring the mailbox-token binding. The shared `getImapOauthAuthorizationCredentials` resolver uses that configured value for an unbound authorization-code exchange and never reads secret-store fallbacks or old refresh tokens. A mismatched non-null issuer marker also blocks the database secret. Background refresh still requires an active matching issuer marker, even when a fresh application secret has been saved.

A successful callback with a new refresh token restores the active binding, stores endpoint-scoped secrets, and clears the reauthorization status. A callback that omits `refresh_token` can preserve an existing refresh token only when the prior active issuer marker matches the endpoint. Otherwise it returns HTTP 400 without reporting a successful connection or changing the binding. Same-endpoint version-0-to-1 migration preserves legacy secret-store or DB fallback credentials only when that prior active marker matches. This repair needs no additional migration beyond the two listed above.

## Limitations and operational impact

- Private IMAP configurations stop working by default until the deployment lists their exact host or IP in `EMAIL_PROVIDER_IMAP_PRIVATE_TARGET_ALLOWLIST`.
- The credential-binding migration treats the existing token URL as the binding for legacy credentials; it cannot determine whether an endpoint was changed before deployment. It prevents future forwarding but does not rotate credentials that may already have been exposed.
- The private allowlist intentionally permits an exact listed IMAP host to resolve to RFC 1918 or IPv6 unique-local addresses. Review deployments' DNS ownership and target reachability before adding entries.
- Live OAuth vendors and on-prem mail servers were not contacted. Authorization was exercised through the actual callback with a mock token endpoint and real tenant persistence.
- Microsoft and Google fixed token endpoints are unchanged.
