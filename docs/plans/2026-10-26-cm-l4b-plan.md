## 1. Intent

L4a made the *message* say who may read it. This card makes everything attached to a message follow the same answer, and lets the answer be changed later without rewriting history. Three things are genuinely new. **Files**: an attachment on shared work is written by an actor from the *other* organisation, so it cannot be a `documents` row in the customer's tenant (`documents.created_by` is `NOT NULL` with an FK to that tenant's `users` — verified in base), and it must not be reachable through the generic tenant download path, which knows nothing about conversation audiences. **Drafts**: a reply composed by a foreign actor must survive a reload — the text, the audience choice and the pending files — and must publish once. **Disclosure**: an organisation-private thread can be moved into the shared conversation with its files copied, behind a preview that names exactly what will become visible, and a durable transfer record. Native ticket attachments keep working exactly as they do today.

## 2. What changes (in this order)

1. **Attachment identity and storage.** `co_management_conversation_attachments` (own table, own `storage_path`, `content_hash`, `file_size` ≤ 25 MB, `status` pending→ready, `actor_tenant`+`actor_user_id`, `discarded_at`), squashed and re-dated. **Verified in `2d00cb6f0e`**: the reference deliberately creates no `external_files`/`documents` row — "generic tenant downloads do not enforce a conversation audience". `attachmentStoragePath.ts` owns the key convention; `archiveStorageProvider.ts` resolves the provider lazily because a static `@alga-psa/storage` import binds `fs` into the module graph reachable from client components (reference comment, verified).
2. **Parent resolver and thread kinds.** `packages/co-managed/src/attachmentParent.ts` (reference, verified): `{kind:'ticket'|'project_task', id}` → both parent columns, exactly one non-null. This is PLAN §5's named seam "attachment-parent resolver (L4b)". A `threadKind` registry (`ticket` only in this card) is where **L4c** registers `project_task`; L4b ports no task-thread branch.
3. **Staging through L4a's registry.** `server/src/lib/co-managed/attachmentStaging.ts` registers a file-stager into L4a's `registerCommentWriter`/file-stager plugin points (`server/src/components/co-managed/ticketCommentWriter.ts`, L4a plan §2.3) — L4b never adds a second comment writer and never writes `collaboration_audience`. Upload validates size/mime server-side (`attachmentUploadLimit.ts`), writes bytes, inserts the pending row, returns a draft handle.
4. **Drafts.** `co_management_conversation_drafts` (operation-scoped: `operation_id`, `customer_tenant`, `relationship_id`, `ticket_id`, `thread_id`, `actor_tenant`, `actor_user_id`, `audience`, `request` jsonb, file `manifest` jsonb, `request_hash`, status draft|published). Submit calls L4a's writer once, reconciles the file manifest to `ready`, and marks published in the same transaction; replay returns the original receipt. Discard releases the files to the sweeper. Reference shape verified.
5. **Read paths — one resolver, two transports.** `packages/co-managed/src/conversationAttachments.ts` exposes `resolveAttachmentAccess(reader, attachment)` = L4a's `isCommentAudienceVisible` + L2 resource authority + draft ownership. `server/src/app/api/co-management/attachments/[attachmentId]/route.ts` (MSP) and `server/src/app/api/client-portal/conversation-attachments/[attachmentId]/route.ts` (requester) are thin transports over it; both call an L0 adapter. Requester link sharing reuses base's `ticket_comment_attachment_challenges` (migration `20260904221253`, verified) rather than a second signed-URL scheme.
6. **Upload cleanup — one handler.** `coManagedUploadCleanupHandler` exists twice on the branch (DAG R14: "both copies go to L4b"). Ship one, in `packages/jobs`, registered through L0b's job registry with a `TenantSelector` wrapped in `filterServed`; its sweep has two adapters — base's `cleanupCommentAttachmentDrafts` (`server/src/lib/jobs/handlers/cleanupCommentAttachmentDrafts.ts`, verified: 24 h grace, 100/batch, FK-reference-aware, preserves shared storage) and the co-managed table. `cleanup_file_ids`/`cleanup_completed_at` make it idempotent.
7. **Disclosure.** `threadDisclosureAdmission.ts` (pure admission: actor, resource, command, hashed request) → `threadDisclosure.ts` `preview` (locks thread + comments + visible files + drafts, hashes a snapshot) → `disclose` (requires `expectedSnapshot` and `confirmed:true`, writes `co_management_thread_transfers` with `comment_map`+`manifest`, relabels the thread through L4a's audience validation, records metadata-only activity). `privateThreadDisclosure.ts` handles the MSP-private → shared direction: copy bytes into the customer tenant, map comment ids, mark the source `abandoned`, and let `privateThreadTransferCleanup.ts` retry removal (attempts, next attempt, error code). Same-tenant relabel touches no bytes.
8. **Archive files (substrate only).** `co_management_archive_files` + `archiveFiles.ts`: a copy-on-retain primitive (`retainFile({sourceTenant, fileId, hash}) → archive row`) that survives the source tenant's deletion. L4b builds the ability; **L7a decides what is retained.**
9. **UI.** `CoManagedCommentAttachments`, `SharedCommentAttachmentPicker`, `CoManagedAttachmentRemoval`, `CoManagedConversationDocument`, `CoManagedPortalAttachments`, `CoManagedThreadDisclosure`, `CoManagedTicketAttachmentsProvider` mount through L3a's conversation slot and L0a's UI slot registry — no `TicketDetails`/`CommentItem` hunk (L3a owns those).

## 3. Boundaries

- **Audience vocabulary, the thread column, the comment writer and the publication intent: L4a.** L4b adds no audience column, no outbox, no publication table; disclosure validates through L4a's resolver and publishes drafts through L4a's writer, so the existing `persistCommentPublication`/`dispatchCommentPublication` path (verified in base) stays the only durable intent.
- **Task conversations and requester task mail: L4c** (PLAN §5; DAG R7). L4b provides the parent resolver + thread-kind registry; L4c registers and implements.
- **Delivery of an attachment, inbound attachment transfer: L5** (DAG R14 — the hook is L0b's, the copy is L4b's primitive).
- **Departure/closure policy, archive reads and manifests: L7a.** **Portable export: L7b3** (via L7b1's registry, DAG R15). **Notification of a disclosure: L5.**
- **Do not port**: `cancelScheduledComment` losing `withdrawCommentAttachments` (T0 §4 #6 — base calls it at `commentActions.ts:820`, verified; keep it); the after-commit publication that drops durability for workflow/email comments (#8); any trigger on existing tables; legacy adapters for URLs that never shipped.
- **Split seam** (PLAN §6.4 lists thread disclosure as "kept, built last, splittable"): workstreams 1–6 are independently shippable; 7–8 depend only on 3–4. A split would be drawn between 6 and 7 without re-cutting any path.

## 4. Contracts L7a and L7b3 inherit (binding)

**L7a** — departure, closure, archive reads — inherits exactly four things and adds none:
1. `co_management_archive_files` row shape plus `archiveFiles.retainFile()` / `readArchivedFile()`: L7a chooses the set, L4b owns copying and hashing. An archive row must never point at customer storage that deletion will remove.
2. `attachmentParent` + `listConversationAttachments(parent)`: how closure enumerates the files that belong to one work item.
3. `co_management_thread_transfers` as the immutable record of what was disclosed; L7a reads it when composing closure evidence and **must not add columns** to it.
4. The rule that an `abandoned` transfer's cleanup is L4b's sweeper; L7a never deletes transfer artifacts.

**L7b3** — portable contributors — inherits reader primitives, not a registry entry (registering into L7b1's registry would be a downward dependency):
1. `listConversationDocumentsForExport(tenant, scope)` — attachment metadata only, no bytes.
2. `openAttachmentStream(attachment)` via the lazy provider, plus `content_hash` so the exporter can verify.
3. `attachmentRedactionPolicy` — `organization_private` content is never exported; a redacted attachment keeps a tombstone entry in the manifest.
4. `readArchivedFile()` for retained files.

## 5. Acceptance

- **A1 Audience inheritance**: a file is readable iff its parent comment is visible to the reader, across all three audiences and both transports; the requester's copied link is denied for a `shared_it` file (H §2 L4 step 4).
- **A2 Foreign author**: an MSP actor uploads to a customer-tenant comment; the row carries `actor_tenant`/`actor_user_id`, no `documents` row exists, the customer's own user downloads identical bytes (`content_hash`), and the generic document download route returns not-found for the file id.
- **A3 Draft lifecycle**: reload restores text + audience + pending files; discard releases them; the sweeper removes bytes exactly once (attempts recorded), and a document referenced elsewhere is preserved (base's guard, A3 test reuses it).
- **A4 Disclosure**: preview snapshot; concurrent edit ⇒ conflict, nothing written; confirm relabels the thread with one history entry; MSP-private → shared copies bytes and maps comments; a failure mid-copy leaves `abandoned` + retryable cleanup and **no half-visible thread**; `cm1:`-era clients cannot relabel (audience change is a thread command, not a text edit).
- **A5 Native neutrality**: a psa tenant's comment attachments, drafts, deletion and cleanup path are unchanged and cost **0** extra statements; no `co_management_*` table is touched on a native path (schema-absent gate). The disclosure command is absent, not hidden.
- **A6 Cross-card migration discipline**: L4b's only change to an L4a table is a nullable `disclosure_operation_id` on `co_management_private_threads` in **L4b's own** migration (never an edit to L4a's), without a cross-table FK — the invariant lives in app code (PLAN §3, no triggers).
- **A7 Evidence**: H §2 L4 steps 4, 7, 8 (attachment audience, draft restore, View read-only) plus the disclosure walkthrough (preview → confirm → history), plus Chapter 0 and Chapter N. **Infrastructure**: the recorded minutes need a shared ticket (L3), an audience-carrying conversation (L4a) and object storage; without them only the unit/integration evidence stands.
- **A8 Gates**: migration lint (all new tables; two additive columns), upgrade-order N-1, schema-absent, hot-path budget (comment attachment read/download), tenant-manifest coverage (L0b's manifest picks up every new table), generated artifacts.

## 6. Risks

- **A file leaks because a read path bypassed the audience.** Mitigation: one `resolveAttachmentAccess` used by both routes; the generic `/api/documents/*` path is proven closed (A2); no static storage import that would let a server component fetch bytes directly.
- **Disclosure half-applied.** Mitigation: prepared → published/abandoned state machine with `comment_map`/`manifest` and a snapshot hash; every retry is keyed by `operation_id`.
- **Byte duplication vs a pointer.** MSP-private → shared copies, so cleanup must not orphan bytes; same-tenant relabel copies nothing. Mitigation: `content_hash` verification plus the FK-reference-aware preservation rule inherited from base's cleanup.
- **Cross-card schema coupling.** L4b needs a column on L4a's private-thread table. Mitigation: additive nullable, no FK, guarded by `hasColumn`; A6.
- **Module graph.** Importing storage statically pulls Node builtins into client-reachable graphs. Mitigation: lazy provider (step 1), asserted by an image/worker boot check.
- **Draft publishes twice.** Mitigation: operation id + `request_hash`, status transition, and the comment writer's own receipt; replay returns the first receipt.
- **Shared files**: `ticketCommentAttachmentsIntegration.test.ts`, `ticketDocumentUpload.service.test.ts`, `documentAuthorization.ts` callers — additive changes only; base's attachment tests must pass unchanged.

## 7. Open design choices

- **Own attachment table vs extending `ticket_comment_attachments` — decided: own table.** Decisive reasons in base: `documents.created_by` is `NOT NULL` FK-bound to the tenant's `users` (a foreign actor cannot author one), and the generic download path has no audience concept. Extending base's table would still need document rows, so it would carry the same defect plus a hot-table migration.
- **Drafts server-side vs client-side — decided: server-side.** Verified: base stores attachment drafts but has no text-draft store, and a foreign actor's draft must survive a browser change and carry the audience decision plus file handles.
- **Where the disclosure control lives — open (leaning: the same audience control L4a adds on the thread header, opening a preview dialog; no separate page).** A second control would let a text edit and an audience change look alike.
- **Files per disclosure — open (leaning: bound the manifest like drafts do, 20 per operation)**, with the preview stating the count. A larger batch needs chunking, which needs its own receipt shape.
- **Same-tenant relabel of a thread that also has `organization_private` replies — open (leaning: refuse).** Replying audience is per-thread (L4a), so relabelling would make a private reply readable; the preview must show zeros for that case rather than silently widening.
- **Forced, not open**: audience lives on `comment_threads.collaboration_audience` with one resolver in `shared/lib/commentAudience.ts` and the comment-row publication intent reused (L4a, ratified); no new outbox; no triggers; migrations expand-only.
