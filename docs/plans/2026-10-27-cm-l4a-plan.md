# L4a — Conversation audiences, private threads & outbox

Reviewer question: *Does every message reach exactly the audience its author chose, on both sides of the relationship, with native comments unchanged?*

Base: `origin/main` @ `058d45c388` · Reference: `feature/co-managed-it` @ `2d00cb6f0e` · Remote card host (X670E) — no worktree on this host · Card `21527c39`, wave 4, hard parent L2, rebase after T0-4 and T0-8.

## Intent

A shared ticket has three readers, not two. Today a comment is `is_internal` or it is not, and that single boolean decides who may read it. Co-management needs a third answer: a note that both IT teams can read but the requester cannot, a note only the author's own organisation can read, and a reply aimed at the requester. This card introduces an explicit audience on the conversation thread, keeps the legacy internal/public semantics exactly where they are (a nullable column means "legacy"), puts the message bodies of organisation-private notes where their owner can retain them, and makes the comment write path say which audience it is writing to before it commits. It also settles where a confirmed comment's publication record lives, because a requester-visible message that silently fails to publish is a customer-facing loss.

## What changes

**1. Audience vocabulary — `shared/lib/commentAudience.ts` (new, pure).**
`CommentAudience = 'requester' | 'shared_it' | 'organization_private'`; `resolveCommentAudience({collaboration_audience, is_internal})` maps `NULL` to today's rule (`is_internal === false ? 'requester' : 'organization_private'`) and rejects inconsistent pairs; `isCommentAudienceVisible(audience, ownerTenant, actorTenant, requester)`; `commentAudienceSql(threadAlias, rootAlias, …)` as the read facet (inconsistent legacy rows resolve private); `CoManagedAudienceRequiredError` (`CO_MANAGED_AUDIENCE_REQUIRED`) for "choose an audience" rather than a silent default. Two rules are load-bearing: audience is an *additional* restriction after resource/principal authorization, and a legacy internal note must never become `shared_it` by inference.

**2. Write path — one writer, three callers.** `packages/co-managed/src/ticketCommentCreation.ts` + `ticketCommentMutation.ts` (new) hold the admitted create/edit/tombstone commands; `nativeThreadAudience(trx, tenant, {isInternal, authorType, audience})` is the native reducer (returns `{}` for `psa` after reading `tenants.product_code` **once**, and for internal notes/plain authors, so an ordinary note costs the same as today plus one cached lookup — see Risk 1). Call sites, in order: `shared/models/ticketModel.ts` `createComment` (base, L1473+, resolves the thread and inherits `thread.is_internal` from the parent today), `packages/tickets/src/actions/comment-actions/commentActions.ts` (base create/update/delete), `optimizedTicketActions.ts`, `ticketActions.ts`, `server/src/lib/api/services/TicketService.ts`, `server/src/lib/co-managed/{createTicketComment,mutateTicketComment}.ts` (new thin server adapters), and the four `server/src/lib/actions/coManaged*Comment*Actions.ts` entry points (each must call an L0 adapter — H §5 gate coverage).

**3. The plugin points later cards need (L4a owns, per PLAN §5 "file-stager registry and comment-writer plugin points").** `server/src/components/co-managed/ticketCommentWriter.ts` becomes a registry (`registerCommentWriter(kind, writer)`) that native and shared screens resolve through the L3a seam's `conversation` config; a `file-stager` registry alongside it. L4a registers only the plain-text writer; L4b registers attachments/drafts, L4c registers task conversations. No card may edit another's registration line.

**4. Storage placement.** Organisation-private notes created on shared work are retained in the *author's* tenant: `co_management_private_threads` (tenant, customer_tenant with `tenant <> customer_tenant`, relationship, qualified soft reference, root comment) and `co_management_private_comments` (body, display snapshots, revision, tombstone timestamp), both distributed, bodies never in the shared tenant. `co_management_private_command_receipts` makes a qualified command idempotent. `collaboration_actor_references` is **L2's** (its migration 20260906140000) — the `comments.actor_reference_id` FK in this card depends on L2 having landed, which is why L2 is a hard parent.

**5. Outbox — the Design Session decision (PLAN §6.2, default lean "reuse existing paths").**
Lean: **reuse the durable publication intent that already exists on the comment row.** Base stores `publish_state`, `scheduled_publish_event_id`, `comment_publication_payload`, `scheduled_publish_dispatched_at` (migrations `20260821170000`, `20260904221253`, verified in base) and `shared/lib/ticketCommentAttachments.ts` already exposes `persistCommentPublication`/`dispatchCommentPublication` (verified, L47-84) used by `TicketService` and `optimizedTicketActions`. L4a extends that payload with the audience and thread id and drops both new-table migrations (`co_management_event_outbox`, `co_management_event_consumers`) plus `conversationEventOutbox.ts`/`conversationEventConsumers.ts`. L5 then consumes the same intent rows for email and keeps its exactly-once proof there. If the session instead ratifies a separate pipeline, L4a must justify why the existing intent+reconcile path cannot carry an audience, and L5's kill-switch chapter changes with it.

**6. Order of work.** (a) audience helpers + reducer + tests; (b) `comments`/`comment_threads` columns and constraints (nullable add, then `NOT VALID` CHECK, then a separate `transaction:false` `VALIDATE`, index `CONCURRENTLY`); (c) private-thread tables + receipts; (d) `ticketModel.createComment` + actions + `TicketService` (writer before UI); (e) event schema (`TicketCommentAdded` audience/thread fields, additive and optional) and the search ACL/indexer facets; (f) UI: `TicketConversation.tsx` audience select replacing the Internal toggle (base has `isInternalToggle` at L206 and a `hideInternalTab` prop), `CommentItem.tsx` badge/change-audience, `BentoTimelineTile.tsx` composer, `TicketDetails(Container)` `audienceId` threading with the `onAddComment` confirmed-boolean that keeps a draft on unconfirmed publish; (g) client-portal read facets (`client-tickets.ts` requester predicate, tombstone redaction, parent masking); (h) retention + before-source-change (`sourceChangeRetention.ts`, calling L2's access-reduction retainer registry).

## Risks

- **Audience widens by accident.** A wrong default turns an internal note into a customer-visible one — the worst failure in this card. Mitigation: `nativeThreadAudience` fails closed in a `co_managed` workspace, legacy `NULL` never maps to `shared_it`, and A1 asserts the inconsistent-row case.
- **The `tenants` read in the reducer.** One lookup per native comment could breach the budget. Mitigation: resolve once per request/transaction and cache on the L0 context; A3 measures it.
- **Hot-table DDL.** `comments` and `comment_threads` are among the largest tables; a validating CHECK or non-concurrent index blocks writes. Mitigation: nullable adds, `NOT VALID` → `VALIDATE` in a separate `transaction:false` file, `CONCURRENTLY`, low-traffic window, recorded duration.
- **Outbox decision reversal.** If the session ratifies a separate pipeline after L5 has started, L5's consumers and kill-switch chapter change. Mitigation: settle it before any code (PLAN §6.2), record the decision in the charter, and keep the audience in the payload either way so the transport is replaceable.
- **Search leaks a private body.** `packages/search/src/acl.ts` and `indexers/ticket_comment.ts` must carry the same facet. Mitigation: reuse `commentAudienceSql` rather than a second predicate; `searchAcl.test.ts`/`searchIndexers.test.ts` extended.
- **Draft/attachment coupling arrives early.** L4b's registries are consumed by the composer this card rewrites. Mitigation: define the registry signatures here, ship an empty native stager, and let L4b register.

## Open design choices

- **Outbox vs existing intent (open until ratified here; leaning reuse).** PLAN §6.2 makes this the session's call with a lean to reuse; the evidence above (existing `persistCommentPublication` with a reconcile path) is why I lean that way.
- **Audience on thread only, or on each comment (forced: thread).** The reference CHECK ties `collaboration_audience` to `comment_threads.is_internal` and asserts replies against the parent; a per-comment audience would let a reply contradict its thread, so replies inherit.
- **Whether `organization_private` comments also get an inline copy in the shared tenant (leaning no).** Duplication would create two sources of truth for the tombstone rule.
- **Where the audience selector lives on the grid layout (open).** Leaning: the same composer slot as the entry layout, via L3a's `slots`, rather than a second control in the tile header.
- **Forced, not open:** audience is an extra restriction, not a grant (reference comment and L2's model); native text edits cannot relabel a thread; no triggers on `comments` (H §3); the upload-cleanup job is L5's or an `filterServed`-gated L4 job (H §2 L4 exclusions).

### Screens and tenants (who sees what, where)
- A shared ticket is **stored in the customer's co_managed workspace tenant**. Shared-IT and requester comments are rows in that tenant; an organization-private note is stored in its **author's** tenant (`co_management_private_*`) and is never read from, or copied to, any other tenant.
- **MSP sponsor persona (QA)**: `/msp/co-management/customer-tickets/[relationshipId]/[ticketId]` mounts `CoManagedSharedTicket`. It loads the conversation through `getCoManagedTicketConversationScreenAction` and posts through the registered writer; the composer offers exactly the audiences the server granted (`shared_it`, the MSP's own `organization_private`). Shared IT always goes through `createCoManagedTicketCommentAction`; an MSP private note goes through `saveCoManagedPrivateTicketCommentAction` into the MSP tenant.
- **Customer IT (Alice)**: `/msp/tickets/[id]` in her own co_managed workspace, wrapped by `CoManagedLocalTicketDataSourceProvider`. Requester and organization-private comments stay on the native path; shared threads load and post through the same session/writer. She never receives the MSP's private note because it lives in the MSP tenant and the loader never reads it.
- **Requester**: client portal `getClientTicketDetails`, `requester` audience only.
- **psa tenants** (including Kansas, and Emerald with the flag on but no entitlement): `/msp/tickets/[id]` renders the unchanged tree. The page calls `isCoManagedWorkspace` once; with no resolver registered it reads nothing, and for a psa tenant it costs at most one `tenants.product_code` read per process, then zero (`workspaceCheckBudget.test.ts`).
- Resolution/close: when `conversation.audiences` is set the dialog and the resolution toggle require an audience (native audiences only; no default).

### Flag gating points
- Native psa writes: `nativeThreadAudience` returns `{}` with zero SQL for psa tenants, internal notes and non-staff authors; co_managed with no audience fails closed (`CO_MANAGED_AUDIENCE_REQUIRED`).
- New server actions gate on the `co-managed` capability before DB work (contract test: server-actions/server-ui counts updated).
