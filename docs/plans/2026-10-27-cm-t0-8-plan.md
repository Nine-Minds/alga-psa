## 3. Design per item

### N1 — internal-mention leak (fix, no BC)
Today `internalNotificationSubscriber.ts` resolves @mentions (`extractMentionUserIds` ~L1277-1390,
`findMentionedUsers` ~L1394) and notifies every resolved user regardless of user type or comment
audience. A client-portal user mentioned in an internal-only comment therefore receives a notification
whose body previews the internal note.

Change, in the comment-added handler (~L1409 onwards), before notifications are written:
1. Resolve mentions as today.
2. Filter recipients by `isInteractiveUserType` (main's filter — **keep it**, do not replace it).
3. Filter out client-type users whenever the comment is internal-only. Portal users keep notifications
   for comments that are actually visible to them (public/portal audience) — this is a visibility
   filter, not a blanket client exclusion.
4. Never place the comment body preview into a notification for a recipient who cannot see the comment.

Test (new, `server/src/test/unit/internal-notifications/`): emit `TICKET_COMMENT_ADDED` for an internal
comment mentioning one internal and one client user → exactly one notification, addressed to the
internal user; the client user gets none and no preview text appears anywhere. Second case: a
portal-visible comment still notifies the mentioned client user, with the preview. Third case: an
inactive internal user stays excluded (proves the `isInteractiveUserType` filter survived the port).

### N2 — template escaping + compile fallback (BC: yes, release-noted)
`BaseTemplateProcessor.replaceTemplateVariables` (L36-53) is a per-variable regex replace over
`subject`/`html`/`text` (Database L177-179, Static L207-209), so any tenant-supplied value containing
`<`, `>`, `&` is injected raw into HTML mail.

Change:
1. Compile each template piece with Handlebars once per render. Render **`html` with escaping on**
   (double-stash escapes by default) and render `subject`/`text` with `{ noEscape: true }` — a subject
   line and a plain-text body must not gain `&amp;`.
2. Wrap compilation in `try/catch`. On a compile error: `logger.warn` with template id/tenant/field and
   the compile message, then fall back to the existing regex replace for that piece. A malformed
   tenant-customised template must degrade (unescaped legacy output), never throw and never block the
   send.
3. Audit `tenant_email_templates` before merge: compile every custom template body read-only and record
   the malformed ones in the review packet. The audit is evidence, **not** a migration and not a code
   path — PLAN §3 migrations rules mean no schema change here.

Tests (`packages/email/src/__tests__/templateProcessors.test.ts`): value `<script>alert(1)</script>`
renders escaped in HTML and verbatim in text/subject; a triple-stash template still injects markup;
an unclosed `{{#if}}` template renders via the legacy path and logs one warning (no throw).
Acceptance bar A: commit **one rendered escaped-email snapshot** (HTML fixture) used by the test.

### N3 — HTML-only replies thread (BC: yes, release-noted)
`processInboundEmailInApp.ts:396 hasSubstantiveReplyContent` decides whether a reply carries content
before the self-notification skip at L1151; an HTML-only reply with no plain-text part reads as empty and
is dropped as `skipped/self_notification`. `replyParser.trimHtmlAtBoundary` (L440) can also leave a
dangling `<div` when it cuts before a marker tag.

Change:
1. Export `htmlToVisibleText` (L278) from `replyParser.ts`.
2. In `hasSubstantiveReplyContent`, if no plain-text substance exists, test the HTML body's *visible*
   text (`htmlToVisibleText(...).trim()`), ignoring `&nbsp;`/whitespace-only bodies. Non-empty visible
   text ⇒ substantive ⇒ the reply threads.
3. In `trimHtmlAtBoundary`, cut at a tag boundary: if the cut would land inside a tag, back up to the
   start of that tag so the trimmed fragment is well-formed.

Tests: parser unit cases for (a) HTML-only body, (b) whitespace/`&nbsp;`-only body is **not**
substantive, (c) the trimmer never returns a fragment containing an unterminated tag; plus an inbound
integration case asserting the HTML-only reply produces a comment rather than `self_notification`.

### N4 — bounded Teams Graph calls (L)
`createTeamsMeeting.ts` (event POST and the onlineMeeting id lookup GET), `updateTeamsMeeting.ts` (PATCH)
and `deleteTeamsMeeting.ts` (DELETE) under `ee/packages/microsoft-teams/src/lib/meetings/` issue Graph
fetches with no timeout, so a stalled Graph call can hang the meeting job. (An earlier draft of this plan
named `packages/scheduling/.../teamsMeetingService.ts` and `packages/jobs` handlers; those are not where
the fetches live.) Add `signal: AbortSignal.timeout(30_000)` to every one of those fetches; the existing
`*WithResult` catch turns the abort into a failed outcome. **Keep main's error-body read** on non-2xx responses
(DO-NOT-PORT #5) — do not replace it with the reference's shorter error handling.

Tests (`ee/packages/microsoft-teams/src/lib/meetings/__tests__/graphCallTimeouts.test.ts`): every Graph
fetch (create POST, create lookup GET, update PATCH, delete DELETE) receives an `AbortSignal`; an abort
surfaces as a failed outcome rather than hanging or throwing; a non-2xx with a Graph error body still
surfaces that body.

### N5 — deterministic workflow run actor (BC: yes — attribution changes)
`resolveRunContext` joins every definition version for the tenant, so `.first()` picks an arbitrary
`published_by`. Add `wr.workflow_version = wdv.version` to the join (plus the existing tenant/run
predicates) so the actor is the publisher of the version the run actually used; keep the
`published_by ?? created_by` fallback.

Test (`shared/workflow/runtime/actions/__tests__/businessOperations.shared.actorResolution.db.test.ts`,
DB-backed): two workflow versions with different publishers; a run on v1 resolves to v1's publisher and a
run on v2 to v2's. Run it against Postgres directly (local stack: `DB_PORT=5472`), not through pgbouncer
(`6472`), which cannot serve the per-worker `test_database_N` the helper creates. This is a visible attribution change; call it out in the release note.

## 10. Evidence: `tenant_email_templates` audit (N2, read-only, no migration)

Run against the dev DB (`server` @ 127.0.0.1:6472, creds from `server/.env.local`; `server/.env` does not exist
in this worktree) inside `BEGIN READ ONLY ... ROLLBACK`. Method: `select tenant,name,language_code,subject,
html_content,text_content from tenant_email_templates`, then `Handlebars.compile(piece)({})` for every
subject/html/text, plus regex scans for triple-stash (`{{{`), block/partial openers (`{{#`, `{{/`, `{{^`, `{{>`),
and non-simple expressions (anything that is not a dotted identifier).

| Measure | Result |
|---|---|
| `tenant_email_templates` rows | **0** (0 tenants with customised templates) |
| Compile errors / triple-stash / block helpers / non-simple expressions | 0 / 0 / 0 / 0 (nothing to scan) |
| `system_email_templates` rows (control) | 505 |
| System templates that fail `Handlebars.compile` | **0** |
| System templates containing `{{{` | many (survey rating buttons, board notifications, ticket/project bodies) - these were already written for Handlebars and render correctly now; under the old regex path a `{{{x}}}` left stray braces |

Finding: the dev DB has no customised tenant templates, so the audit is vacuous here. **The same query must be
re-run against staging/production before merge**; the script is the query above (compile each piece, flag
failures). Any tenant template that fails to compile now degrades to the legacy replace with a
`logger.warn` (template id, tenant, field) instead of throwing, so a malformed row cannot block a send.
