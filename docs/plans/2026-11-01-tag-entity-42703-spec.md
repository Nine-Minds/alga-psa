# Spec — the REST tag path must not be able to name a column that is not there

Card `1275a53e` · "REST: adding a tag to a ticket returns 500 INTERNAL_CONFIGURATION" (YourColo
alga-2026-0002687, item 4, v1.6.9)

## 1. The shape

`POST /api/v1/tags/entity/{entityType}/{entityId}` → `ApiTagController.tagEntity` →
`TagService.tagEntityInTransaction` (`server/src/lib/api/services/TagService.ts`). The same tag added in
the UI works, because the UI uses a **server action** on a different code path. That asymmetry is the
whole finding: the REST path is the only consumer of this particular query, so a column it names can rot
without any interactive test noticing.

The failing statement is the read-back after the insert:

```ts
const created = await tenantDb(trx, tenant).table('tag_mappings as tm')
  .modify((query) => joinTagDefinitions(query, trx, tenant))
  .where('tm.mapping_id', mapping.mapping_id)
  .select('tm.mapping_id as tag_id', 'td.board_id', 'td.tag_text', 'tm.tagged_id',
          'tm.tagged_type', 'td.background_color', 'td.text_color', 'tm.tenant', 'tm.created_by')
  .first();
```

`INTERNAL_CONFIGURATION` is `apiMiddleware.ts`'s mapping of Postgres `42703`, and the middleware already
logs `Undefined database column (42703)` with table/column — so **the exact column is a log line, not a
hypothesis.** The candidates visible in that statement are `td.board_id` (tag *definitions* may not carry a
board) and `tm.created_by` (the mapping table's creator column, which `TagMapping.insert` populates from
`context.userId`). Either way the answer must come from the repro or the Loki line, not from reading.

## 2. Decision: reproduce, fix at source, and make the class fail in CI

### 2.1 Reproduce first (the card's own instruction)

1. Migrate a local database to head, seed a tenant + ticket, and call the REST route with an API key.
2. Capture the `42703` log line (table + column). Confirming from `information_schema.columns` that the
   named column is absent is the proof; if it *is* present locally, the difference is schema drift
   between `main` and the 1.6.9 appliance and the spec's §2.2 matters more, not less.
3. Check the sibling routes in the same controller for the same column: `bulk/tag` and the `PUT`
   replace-on-entity path, plus `untagEntity`/`replaceEntityTags`. The card asks for exactly this.

### 2.2 Fix at the source

Per column, decide which side is wrong and say so in the PR body:

- **Query wrong** (the column moved or never existed): select it from the table that owns it, or stop
  returning it — `TagResponse` should not promise a field the schema cannot supply. `joinTagDefinitions`
  is a local helper (`TagService.ts:62`); keeping column knowledge there is what lets the select drift
  silently, so the join and the select list should be generated from one description of the join.
- **Schema wrong** (the column should exist and the migration forgot it): add the migration, with a
  backfill, and prove the UI path still passes.

Prefer the first: a response shape wider than the schema is what invites this bug.

### 2.3 The general guard

Add a **schema-contract test** for the tagging path: on a migrated test database, run
`tagEntity` → read-back → `untagEntity` → `replaceEntityTags` inside a rolled-back transaction. Postgres
raises `42703` for a missing column, so the test fails in CI with the column name. That converts this
class — "a column named only by a REST path" — from a customer report into a red build. Make the helper
reusable so the sibling REST services can adopt it (the same class is on `64ebdeec` and `45d31de9`).

Additionally: the read-back should be **one query description**, not a select list plus a separate join
helper, so the two cannot disagree.

### 2.4 Integration test the card asks for

Tag a ticket **through the REST route** with an API key, then read the tag back through a second REST
call and assert text, colours, and `board_id` (or its honest absence). The UI path is not a substitute:
the whole defect is that only the REST path is affected.

## 3. Deliberately not doing

- **Not adding `created_by` with a default** to silence a missing column. If the insert does not supply
  it, a default hides who tagged what; if it does, the select can read it.
- **Not re-running the tag logic through the UI server action from the REST controller.** That would
  make the two paths converge on the *interactive* code, which has different authorization and
  transaction semantics; the REST service is the correct layer.
- **Not widening `INTERNAL_CONFIGURATION`.** `42703` is an internal fault; the fix is to make it
  impossible, and to keep the column name in the server log (and non-production responses) so the next
  report needs no log dig.

## 4. Tests

1. Schema-contract test for the tagging path (§2.3) — fails today, passes after the fix.
2. REST integration: tag → read back (asserting the fields the route promises).
3. Sibling routes: `bulk/tag` and `PUT` replace produce the same read-back shape.
4. Untag + replace leave no orphaned `tag_mappings` (the existing cleanup migration
   `20260209000000_cleanup_orphaned_tag_definitions.cjs` exists precisely because this happened before —
   assert the new path cannot create orphans).
5. `42703` anywhere still maps to INTERNAL_CONFIGURATION *and* logs table + column (operator contract).

## 5. Risks

- **`TagResponse` is a public API shape.** Narrowing it is a contract change — check the OpenAPI document
  and the API changelog, and land the narrowing with the version bump rather than silently.
- **Multi-tenant: the join helper takes `tenant` twice** (query + trx). The contract test must run on a
  tenant-scoped DB handle, or it will pass while a tenant-scoped query still fails.
- **The 1.6.9 appliance may differ from `main`.** If the column exists on `main` but not in 1.6.9, the
  deliverable is the guard plus a note on the upgrade path, not a code change that "fixes" nothing.
