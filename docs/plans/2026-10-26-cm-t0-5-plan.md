### 1.1 Per-item design (exact change, file, line)

#### O1 — Invitation auto sign-in sends the fields the provider reads

The credentials provider's `authorize` reads `email`, `password`, `userType` and `tenant` (`packages/auth/src/lib/nextAuthOptions.ts:1608-1720`). Both setup pages send `username`, a field the provider ignores, so `authorize` returns `null`: every invitee is bounced to a sign-in page **and** any session already in the browser survives, which is why a shared browser used to keep the previous user's workspace.

- `server/src/app/auth/team/setup/page.tsx:126-131` → `signIn('credentials', { email: result.username, password: formData.password, userType: 'internal', redirect: false })`.
- `server/src/app/auth/portal/setup/page.tsx:182-186` → same, with `userType: 'client'` and `...(tenantSlug ? { tenant: tenantSlug } : {})` (the slug is already read at `:77`).

On success the pages keep their existing `router.push` behaviour. A successful `signIn` writes a new session cookie over the old one, which is the whole fix for "the previous user stays signed in". No `signOut()` first: a pre-emptive sign-out would destroy the old session even when the invitee's sign-in fails, and would log the wrong user out of a workspace he still owns on another tab.

#### O7 — Internal login must not pick a tenant by luck

`packages/auth/src/actions/auth.tsx:161-166`: the internal branch still calls `User.findUserByEmailAndType(...)` and takes `.first()`. The client branch already resolves through `resolveUnscopedClientUser` (`:68-104`), which verifies the password against every match and throws `TenantRequiredError` (`code = 'TENANT_REQUIRED'`) when more than one **live** tenant authenticates.

Change: rename `resolveUnscopedClientUser` → `resolveUnscopedUser(normalizedEmail, password, userType)` and route both unscoped branches through it; delete the `.first()` internal call. A restored/inactive duplicate then cannot shadow the live account, and equal passwords across two live tenants are refused rather than coin-flipped. A wrong password still returns `null` (no tenant disclosure).

Nothing in the schema stops two live users of the same type sharing an email inside one tenant. When more than one of them verifies, the resolver orders them by `created_at`, then `user_id`, and takes the first. Both columns are immutable, so the same rows always give the same user, whatever order the database returns them in. The resolver reports that it already checked the password, so `authenticateUser` does not run bcrypt on the winner a second time.

**Known limit, not fixed here.** Same-tenant duplicate resolution takes no account-status input: two live internal rows sharing an email resolve to the oldest, which may be the more privileged one. It is deterministic and no worse than the `.first()` it replaces, and O7 refuses only cross-tenant ambiguity, so the resolution order is left as is.

Lookups normalize the email the way writers store it. `authenticateUser` and `userExists` use `normalizeLoginEmail` (`packages/auth/src/lib/security/loginEmail.ts`: trim, then lowercase), the same function login protection keys attempts on. On the write side, the user-row writers lowercase only (`packages/users/src/actions/user-actions/userActions.ts:653`, `registrationActions.ts:176`, `packages/users/src/services/UserInvitationService.ts:79`); only the invitation action trims its input first (`userInvitationActions.ts:96`). The trim on the read path is ours, and it is what makes a pasted `" user@example.com "` find a stored `user@example.com`. Do not "fix" the writers to match: the lookups are correct because the read path trims and then lowercases, and that read-side rule is the fix. A whitespace-only email counts as missing.

`TenantRequiredError` is a `CredentialsSignin` subclass and the provider's catch rethrows it (`:1852-1858`), so the code reaches the browser. The client portal already handles it (`ClientLoginForm.tsx:123-128`); **the MSP form does not**.

- `packages/auth/src/components/MspLoginForm.tsx:79-113`: add, before the generic `result?.error` branch and after `RATE_LIMITED`, a `result?.code === 'TENANT_REQUIRED'` branch that shows a "Contact Your Administrator" alert ("This email is used in more than one organization, so we can't tell which account to sign you in to. Contact your administrator for help signing in.") and does **not** refresh the captcha — the password was correct, so it is not a failed attempt (same reasoning as `ClientLoginForm.tsx:123`). Widen the `signIn` result with the cast that `ClientLoginForm` already uses so `code` is typed.
- Two new keys in `server/public/locales/*/msp/auth.json` under `signIn.errors`: `tenantRequiredTitle`, `tenantRequiredMessage`; regenerate the pseudo-locale (`node scripts/generate-pseudo-locales.cjs`).

There is deliberately **no** MSP org picker (see §3): enumerating tenant names to an unauthenticated caller is an information leak, and the MSP form has no tenant hint to send.

#### O8 — One cookie name for NextAuth, Express and the edge

Bug on main, two symptoms, one cause: `packages/auth/src/lib/session.ts:76-81` picks the `__Secure-` prefix through `isSecureCookieEnvironment()` (scheme-aware), while `server/src/lib/auth/sessionCookies.ts:65-76` picks it from `NODE_ENV` alone. On an http self-host (`NODE_ENV=production`, `NEXTAUTH_URL=http://…`):

1. Auth.js sets/reads `authjs.session-token`; edge middleware (`server/src/middleware.ts:393,524,581` → `sessionCookies.ts`) looks for `__Secure-authjs.session-token`, finds nothing, and treats every request as signed out;
2. `encodePortalSessionToken` uses `getSessionCookieName()` as the JWT **salt** (`sessionCookies.ts:167,177`); a different name is a different salt, so portal hand-off tokens cannot be decrypted.

Change:

- `packages/auth/src/lib/session.ts:15-51`: `getDevCookiePortSuffix()` → `getCookiePortSuffix()`. The first valid public URL (`NEXTAUTH_URL`, `APP_URL`, `NEXT_PUBLIC_APP_URL`) is authoritative: a public URL with a port scopes the cookies to that port; a port-less public URL means the scheme's default port even when the listener is `PORT=3000`. `PORT`/`APP_PORT`/`EXPOSE_SERVER_PORT` are a development fallback only.
- `withDevPortSuffix` puts the marker **before** `authjs`: `__Secure-authjs-port-8443.session-token`, `authjs-port-3003.pkce.code_verifier`. This is load-bearing. Auth.js reads *every* cookie whose name starts with its session-cookie name as a token chunk, `.3374` looks like a chunk index, and on the wrong runtime it decodes the token with the chunk salt, fails, and **deletes** the other runtime's cookie. A trailing `.3001` suffix (main's behaviour) is a cross-runtime session clearer; a `-port-` infix is inert. The middleware's chunk filter `name.startsWith(sessionCookieName + '.')` still matches (`server/src/middleware.ts:395`).
- `server/src/lib/auth/sessionCookies.ts`: delete `getDevCookiePortSuffix`, and implement `getSessionCookieName` / `getSessionCookieConfig` as straight delegations to `@alga-psa/auth/session` (the subpath export already exists and is already imported by `server/src/app/api/auth/session/route.ts:3`). The file keeps only `getSessionMaxAge`, `getNextAuthSecret`, `encodePortalSessionToken`.

**How agreement across the three runtimes is proven.** The three runtimes are (a) Auth.js in node — `nextAuthOptions.ts:140` `SESSION_COOKIE` plus the `withDevPortSuffix` cookie overrides at `:323-361`; (b) the Express-side API/portal-token issuer — `server/src/lib/auth/sessionCookies.ts`; (c) the edge middleware — `server/src/middleware.ts` and `packages/auth/src/nextauth/edge-auth.ts:8`, which both resolve through the same two import paths. After this change all three call one function, so agreement is a property of the import graph; it is *proven* by A2, which asserts, for each row of an environment matrix (dev + explicit port, prod http + port, prod https + port, prod https port-less), that the package name, the server name, the server config name and the token salt are one string, and by a round-trip: a token encoded by `encodePortalSessionToken` decodes with `@auth/core/jwt` under the package's name. A1's counterfactual test pins the reverse direction — a `.port`-suffixed cookie really is parsed, rejected and cleared as a production chunk, so the fix is the reason the collision stops.

**Why O8 and O9 ship in one deploy.** The nonce cookie is named by the same `withDevPortSuffix` (`nextAuthOptions.ts:361`), and O8 is what changes that function and its call sites. Ship them separately and an SSO login that starts under one image writes `authjs.nonce` under one derivation and is read back under another — every Microsoft login fails until both colours drain, on top of the logout O8 already forces. Together it is one cutover, one cookie name function, one logout.

#### O9 — Microsoft SSO verifies the ID token against a nonce

**What the check verifies, and against what.** Auth.js (`@auth/core/lib/actions/callback/oauth/checks.js`, `authorization-url.js`) mints a random nonce, seals it in an encrypted `authjs.nonce` cookie (15-minute life), and sends `nonce` on the authorization request. At the callback it decrypts that cookie and passes it as `expectedNonce` to `processAuthorizationCodeResponse`, which verifies the `nonce` claim of the **ID token returned by the token endpoint** — a token Entra minted for *this* authorization request and signed by Entra's keys, checked against issuer/audience/JWKS. `state` binds the callback to the browser and `pkce` binds the code to the client; only `nonce` binds the ID token to the request, so only `nonce` stops an ID token minted elsewhere being injected into this session. It verifies nothing about the access token or the Graph profile.

Change in `packages/auth/src/lib/nextAuthOptions.ts`:

- `buildAzureADProvider` config type (`:440`) widened to `Array<'pkce' | 'state' | 'nonce'>`.
- The Microsoft registration in `buildAuthOptions` (`:1585-1595`) `checks: ['pkce','state']` → `['pkce','state','nonce']`. On this base it is the only one: `buildTeamsAuthOptions` (`:2449`) calls `buildAuthOptions` with a Teams context, so the default and Teams option sets share it. The reference's env-only fallback `options` registration does not exist on main.
- `buildAzureADProvider` (`:444-482`): `checks` is a required field and both branches use `config.checks` as given. The simulator branch's `['pkce','state']` default and the Entra branch's conditional spread are gone, so a caller cannot drop `nonce` by omission. A single code path, no special case. The dev simulator mints an unsigned `id_token` (`packages/emulators/msgraph/src/core.ts:652`, header suffix `.emulator`), so nonce is *sent* there but cannot be *verified*; see the divergence table.

A1–A7 do not attempt an Entra round-trip. A4 builds the default and Teams option sets (and the simulator variant) and asserts every `azure-ad` provider declares `pkce`, `state` **and** `nonce` — behavioural, not a source grep, so a future provider refactor cannot pass by keeping a comment. It also uses the real `withDevPortSuffix` with a ported public URL and asserts the nonce, pkce, state, callback-url and csrf cookie names, so dropping the suffix from any of them fails.

#### O10 — No credentials in analytics URLs

Invitation (`/auth/team/setup?token=…`), portal setup, password reset (`?token=`/`?code=`), OAuth callbacks (`?state=`, `?ott=`) and signed asset URLs all carry live credentials in the query string. The browser PostHog init spreads `posthogConfig.defaultConfig` (`server/src/components/providers/PostHogProvider.tsx:52-56`), and the manual `$pageview` at `:19` sends `url` with the full search string, so today those values are stored in PostHog on the event, the person (`$set_once.$initial_current_url`) and autocapture hrefs.

- New `packages/analytics/src/lib/redactSecretUrls.ts`: `redactSecretQueryValues(text)` replaces the value of any query parameter whose name ends in `token|signature|credential` (so `X-Amz-Signature`, `X-Amz-Credential`, `X-Amz-Security-Token` and the same prefixed form other providers use), or is exactly `ott|otp|code|state|secret|password|sig|key|api_key`, with `redacted`, keeping the rest of the URL; `redactCaptureResult(result)` applies it to `properties`, `$set` and `$set_once` and is the `before_send` hook.
- `packages/analytics/src/config/posthog.config.ts:17-32`: `before_send: redactCaptureResult` in `defaultConfig`.
- `packages/analytics/src/client.ts:7`: export `redactSecretQueryValues` alongside `posthogConfig`.

**The fallback path must not leak.** A redactor that throws inside `before_send` is worse than no redactor: the SDK's error path still sends the event, and the obvious `catch { return result }` returns the *unredacted* object. So the hook is total: redaction is applied by walking the value graph (objects, arrays, `$elements_chain` strings) with a depth guard, a non-string leaf is passed through untouched, a cycle or an unexpected shape causes the **event to be dropped** (`return null`, PostHog discards it) rather than returned, and no branch logs the input. Returning `null` is the only fallback that cannot leak; a dropped analytics event is an acceptable cost, a leaked invitation token is not. `disable_session_recording: true` stays — recording would capture the address bar independently of `before_send`.

## 8. Deployment

Image order: **server only**, both colours drained to the new SHA. No migration, no worker image, no generated API/MCP artifact. `NEXTAUTH_SECRET` unchanged; nothing else to configure.

Release note (appliance / self-host):

- **One forced sign-out** on upgrade. The cookie name changes wherever the public URL carries an explicit port (e.g. `https://psa.example.com:8443` → `__Secure-authjs-port-8443.session-token`). On an http self-host this is not a loss: the middleware never saw the session before this fix.
- **One failed SSO attempt per in-flight login**: a Microsoft sign-in in progress at the moment of deploy has no `nonce` cookie and fails once; retrying works.
- **Duplicate emails are refused**: an internal email that exists in more than one organization with the same password now gets a "sign in with your organization's address" message instead of being signed into whichever tenant won the `.first()` race. Admins of affected installs should give those accounts distinct addresses.

Rollback: revert the image (one colour, no schema). The cost of a rollback is a second forced sign-out, not data loss. Do not roll back half of it: O8 and O9 go together (§1.1).

## Risks

| Risk | Mitigation |
|---|---|
| A forced logout on every appliance, and a second one if rolled back | release-noted; the alternative is a split cookie name, which is worse in both directions |
| Port-scoped cookies mean two ports on one host no longer share a session (previously they silently corrupted each other) | intended; documented; dev/worktrees rely on it |
| `TENANT_REQUIRED` on internal login can lock out a real user who cannot disambiguate | the message names the remedy (tenant-specific sign-in address, or an admin email change); the refusal only fires when the credentials genuinely match live users in two tenants |
| A dropped analytics event under the redactor's fallback | accepted deliberately: `null` is the only non-leaking fallback |
| Two live internal users in one tenant share an email; sign-in picks the oldest, which may be the more privileged | known limit, recorded in O7; deterministic and no worse than the `.first()` it replaces; out of O7's cross-tenant scope |
| A second Microsoft provider registration later ships without `nonce` | A4 fails; `buildAzureADProvider` also requires `checks` |
| Hand-porting into `nextAuthOptions.ts` (935 lines of main drift) | hunk-level apply + A4; the file is not restored whole |
| New i18n keys fail the untranslated-UI audit | keys added to all 9 real locales and the pseudo-locale in the same commit |
