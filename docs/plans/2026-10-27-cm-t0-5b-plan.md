# CM T0-5b: MSP multi-org sign-in recovery and SSO tenant audit (implementation plan)

- Card: de8907af-2397-404e-b4f8-bace5947d472 · PSA ticket alga-2026-0002894
- Follows: CM T0-5 (PR #3912, merged)
- Branch: `feature/cm-t0-5b-msp-multi-org-sign-in-recovery-sso-tena`
- Status: plan only. No code is in this commit.

## 1. Problem

T0-5/O7 changed `resolveUnscopedUser` (`packages/auth/src/actions/auth.tsx`). An unscoped password sign-in now refuses with `TENANT_REQUIRED` when the same email and password authenticate live users in more than one tenant. MSP sign-in has no way to name a tenant:

- `MspLoginForm` never sends `tenant`.
- `/auth/msp/signin` (`server/src/app/auth/msp/signin/page.tsx`) reads only `callbackUrl`.
- Vanity-domain tenant resolution (`portalDomain`) only applies to `userType === 'client'`.

Those internal users can no longer sign in with a password. T0-5 shipped a "Contact your administrator" alert as a stopgap.

The credentials provider (`nextAuthOptions.ts` `authorize`) already supports scoped sign-in. It accepts `credentials.tenant`, validates it with `isValidTenantSlug`, and calls `authenticateUser(..., { tenantSlug, requireTenantMatch: Boolean(tenantSlug) })`. `authenticateUser` resolves the slug with `getTenantIdBySlug`, looks the user up with `findUserByEmailTenantAndType`, and rejects any tenant mismatch. The missing piece is the MSP UI and page plumbing, plus a way for users to find out their tenant slugs.

## 2. Binding XO decisions

1. **One tenant-discovery mechanism**, parametrised by user type, sign-in path, link surface and email template. We do not fork an MSP copy of `requestTenantLoginLinksAction`. The contact gate stays client-portal only, as a precondition on the client profile.
2. **The response is always generic.** The action emails the mailbox owner one scoped sign-in link per organization. Each link uses the vanity domain from `resolveTenantAppBase(tenant, 'msp')` when there is one. Otherwise it uses the canonical `/auth/msp/signin?tenant=<slug>`. Links are scoped sign-in URLs, never login tokens: password, 2FA and captcha still apply.
3. **`?tenant` on `/auth/msp/signin` is validated server-side** and threaded `MspSignIn → MspLoginForm → signIn('credentials', { tenant })`. The page shows which organization is being signed into, with a link back to the unscoped page. There is no unauthenticated organization picker or tenant list anywhere.
   - *How this splits in practice:* no email exists when the page renders, so validation happens in two places. The **page** checks that the slug is well-formed (`isValidTenantSlug`) and resolves to an existing tenant. If it doesn't, the page silently redirects to the unscoped page and shows no name. The **credentials provider** checks that the email belongs to that tenant at submit time (`requireTenantMatch` → `findUserByEmailTenantAndType` scoped to the tenant). SSO gets the same check through the scoped resolution in §3.5.
4. **Rate-limit discovery per email** with `checkPasswordResetLimit`, and apply the same limit to the existing client-portal action. That action currently has no limit, which makes it a mail-bombing vector.
5. **SSO audit.** The verdict is in §4: **the ambiguity is real**, so the fix is in scope.

## 3. Behaviour by scope item

### 3.1 Generalised tenant discovery (scope 1 and 4)

**New engine:** `packages/auth/src/lib/tenantDiscovery/` (server-only).

- `profiles.ts` defines one `TenantDiscoveryProfile` per user type. A profile is a value, not a flag set:
  - `userType: 'client' | 'internal'`
  - `surface: AppSurface` (`'client_portal'` or `'msp'`, the value passed to `resolveTenantAppBase`)
  - `signInPath`: `/auth/client-portal/signin` or `/auth/msp/signin`
  - `templateName`: `'tenant-recovery'` or `'msp-tenant-recovery'`
  - `precondition?: (email) => Promise<boolean>`: the client profile sets this to the existing active-contact check (`isEmailAContact`, moved here unchanged). The internal profile leaves it unset.
- `requestTenantSignInLinks(profile, email, callbackUrl?)` runs this pipeline:
  1. Normalize the email with `normalizeLoginEmail`. If it is malformed, return the generic response.
  2. Call `checkPasswordResetLimit(email)`. If the limit is exceeded, log it and return the generic response without sending.
  3. Run `profile.precondition` if the profile has one.
  4. Find live users of `profile.userType` with this email, across tenants. The query is the existing `findClientUsersByEmail` generalised by user type: `is_inactive = false`, joined to `tenants.client_name`, and de-duplicated by tenant so a tenant with duplicate rows gets one link.
  5. If there are no users, return the generic response.
  6. For each tenant, build a link (`buildTenantSignInLink`, generalised from `buildPortalLoginLink`). Use `resolveTenantAppBase(tenant, profile.surface, { knex: admin })` to get the origin: the vanity domain when there is one, otherwise canonical.
     - Client profile: unchanged. A vanity link is bare, because the vanity host resolves the tenant. A canonical link gets `?tenant=<slug>`.
     - Internal profile: **always** append `?tenant=<slug>`, vanity or not. `authenticateUser` resolves a tenant from `portalDomain` only for `userType === 'client'`, so a bare MSP vanity link would hit `TENANT_REQUIRED` again. This is a profile field (`vanityScopesTenant: boolean`), not a branch.
     - `callbackUrl` is carried only if it is a same-origin relative path (`isValidResolverCallbackUrl`).
  7. Call `sendTenantRecoveryEmail(email, infos, { templateName: profile.templateName })`.
  8. Return the generic response. Errors are logged and swallowed to the same generic response, as today.
- The generic response is a single constant: `{ success: true, message: <generic> }`. It is identical whatever the outcome (rate limited, not a contact, no users, sent, or error).

**Server actions** (thin, `'use server'`):

- `packages/auth/src/actions/tenantDiscoveryActions.ts`: `requestMspSignInLinksAction(email, callbackUrl?)` calls the engine with the internal profile.
- `packages/client-portal/src/actions/portal-actions/tenantRecoveryActions.ts`: `requestTenantLoginLinksAction` keeps its name and signature, so `ClientPortalTenantDiscovery` is unchanged. Its body becomes a call to the engine with the client profile. The local helpers move to the engine. The client portal therefore gets the rate limit with no separate code path.

**Rate limit:** the limit reuses the existing in-memory `passwordResetLimiter` (3 per 15 min, 15 min block) **with the same per-email key**. This is deliberate: password reset and tenant discovery both send email to this address in response to an unauthenticated request. The threat is a flooded mailbox, so one budget per mailbox is the correct model. The side effect is that requesting links counts against password-reset requests for that address within the same 15 minutes. Because the limit is per email and does not depend on whether an account exists, being limited reveals nothing. We still return the generic response, per decision 2.

**Email copy:**

- `sendTenantRecoveryEmail` gains an optional `templateName`, defaulting to `'tenant-recovery'`. The fallback copy is chosen by template.
- New source-of-truth file `server/migrations/utils/templates/email/auth/mspTenantRecovery.cjs`, modelled on `tenantRecovery.cjs`. Copy: "sign in to {{platformName}} for each organization". It must not say "client portal". All languages that `tenantRecovery.cjs` ships are included (en, de, es, fr, it, nl, pl, pt, sv).
- New migration `server/migrations/2026102712xxxx_add_msp_tenant_recovery_email_template.cjs` registers the template and its subtype using the same helper as the auth templates.

### 3.2 `/auth/msp/signin?tenant=<slug>` (scope 2)

**Page** (`server/src/app/auth/msp/signin/page.tsx`):

1. Read `params.tenant`. If it is present but fails `isValidTenantSlug`, or `getTenantIdBySlug` finds no tenant, `redirect()` to `/auth/msp/signin`. Keep `callbackUrl` and drop `tenant`. Unknown and malformed slugs behave identically and render no name.
2. If the slug is valid, load the organization's display name from `tenants.client_name` through a small server helper (`getTenantDisplayNameBySlug`, next to `getTenantIdBySlug` in `@alga-psa/db`). Pass `{ slug, name }` as `scopedTenant` to `MspSignIn`. This matches the client-portal precedent, which already brands its sign-in page from `?tenant`. An MSP's slug is the same slug its clients see in their portal links, so showing the name discloses nothing a slug-holder did not already have.
3. Signed-in branch: if the session is for a different tenant than the one in `?tenant`, do not auto-redirect. Render the scoped sign-in. A successful sign-in replaces the session, as any sign-in does today. If the session is for the same tenant, keep the existing redirect to `callbackUrl`. The revoked-session and client-user branches are unchanged, except that the revoked branch also passes `scopedTenant`.

**`MspSignIn`:** takes `scopedTenant?: { slug: string; name: string }`.

- When `scopedTenant` is set, the card shows "Signing in to **{name}**" under the title.
- Below it is a "Not your organization? Sign in without choosing one" link to `/auth/msp/signin`, carrying `callbackUrl`.
- `MspSignIn` passes `tenantSlug={scopedTenant?.slug}` to `MspLoginForm`.

**`MspLoginForm`:** takes `tenantSlug?: string`.

- `signIn('credentials', { ..., ...(tenantSlug ? { tenant: tenantSlug } : {}) })`.
- `SsoProviderButtons` receives `tenantHint={tenantSlug}`.

**Provider:** no change is needed in `authorize`. It already lowercases and validates the slug and sets `requireTenantMatch`.

### 3.3 `TENANT_REQUIRED` offers the links (scope 3)

- `MspLoginForm`'s `TENANT_REQUIRED` branch stops raising the "Contact Your Administrator" alert. It sets local state `tenantRequired = true`.
- The form then renders an inline `Alert` (the standard component already imported):
  - Text: "This email is used in more than one organization. We can email you a sign-in link for each one."
  - A `Button` (`id="msp-send-org-links-button"`): "Email me sign-in links".
  - The button calls `requestMspSignInLinksAction(email, callbackUrl)` with the email already typed.
  - After the call, the alert switches to the generic confirmation: "If this email has accounts, we've sent sign-in links to it. Check your inbox." The button is then disabled.
  - The alert clears when the email field changes.
- The captcha is not refreshed. This is unchanged from T0-5: `TENANT_REQUIRED` is not a failed attempt.
- The alert is not shown on the scoped page. A scoped attempt cannot produce `TENANT_REQUIRED`, because `resolvedTenantId` is set.
- Retire the i18n keys `signIn.errors.tenantRequiredTitle` and `signIn.errors.tenantRequiredMessage`. Add keys under `signIn.tenantRequired.*` and `signIn.scopedTenant.*` in `server/public/locales/*/msp/auth.json` for every shipped locale, plus `xx`.

### 3.4 SSO tenant-required (consequence of §4)

- Add `'tenant_required'` to `OAUTH_MAPPING_FAILURE_CODES` (`packages/auth/src/lib/sso/types.ts`) with fallback copy. The existing `callbacks.signIn` → `resolveOAuthFailureRedirect` path redirects to `/auth/msp/signin?error=AccessDenied&reason=tenant_required&providerEmail=…` with no new routing.
- `MspSignIn`: for `reason === 'tenant_required'`, the existing `useEffect` alert explains the problem. `MspLoginForm` is seeded with `providerEmail` (if `initialEmail` is unset) and `tenantRequired = true`, so the same "Email me sign-in links" offer appears. The `providerEmail` came from the IdP that just proved ownership of it, but the action is generic and rate-limited either way, so it gains no special trust.

### 3.5 SSO fix (scope 5)

**One resolution engine for every sign-in path.** Extract `resolveUnscopedUser`'s logic into `packages/auth/src/lib/signInUserResolution.ts`:

```
resolveSignInUser({ email, userType, scopeTenantId?, verify }) -> { user?, verified } | throws TenantRequired
```

- **With `scopeTenantId`:** call `findUserByEmailTenantAndType(email, scopeTenantId, userType)`. Only that tenant is considered.
- **Without `scopeTenantId`:**
  1. Load `findUsersByEmailAndType`.
  2. Keep the live candidates (`!is_inactive`, plus `hashed_password` for the password verifier).
  3. Run `verify` on each.
  4. If verified candidates span more than one tenant, throw `TenantRequired`. If they span one tenant, resolve with `compareByCreationThenId`.
  5. If no candidate is live, return the sole or oldest candidate unverified, so the existing inactive and win-back paths still run.
- **Password** uses `verify = verifyPassword`. `resolveUnscopedUser` becomes a two-line call. Behaviour is identical: the T0-5 tests in `auth.tenantScoping.test.ts` must pass unchanged.
- **SSO** uses `verify = () => true`. The IdP has proved control of the mailbox, which every live account with that email shares equally. So for SSO, more than one tenant with a live account means the email is ambiguous, even where passwords differ. This is the correct reading: SSO has no second factor to narrow the candidates.

**Trusted SSO tenant scope.** Profile claims (Google `hd`, Entra `tid`/`tenant`/`domain`, a Keycloak `tenant` claim, OAuth `state.tenant`) are IdP- or client-controlled. They must never select an internal user's tenant. Scope comes only from server-issued, signed context:

1. **`MspSsoResolutionPayload` gains `scopeTenantId?: string`.** `/api/auth/msp/sso/resolve` reads `tenantSlug` from the body, which `SsoProviderButtons` already sends. It validates the slug with `isValidTenantSlug` + `getTenantIdBySlug` and signs the tenant into the resolution cookie. An invalid or unknown slug gets the existing generic failure. If discovery chose `source: 'tenant'` for a *different* tenant than the requested scope, the route uses app credentials (`source: 'app'`) when available and the generic failure otherwise. A scoped sign-in never runs through another tenant's IdP.
2. **When the resolution cookie has `source: 'tenant'`, its `tenantId` is the scope.** A tenant's own IdP credentials (Google, Entra or Keycloak secrets held per tenant, on a verified domain claim in EE) vouch only for that tenant's users. Today `.first()` can let tenant A's IdP assertion sign a shared email into tenant B. After this change it resolves in A or fails `no_matching_user`.
3. **Teams** (`buildTeamsAuthOptions(tenantId)`): `context.teamsTenantId` is the scope.

`getClientPortalSsoProfileHints` is generalised into `getSsoProfileHints(provider, context)`. It returns `{ userType, scopeTenantId? }` from the client-portal cookie, the MSP cookie or the Teams context, in that order. This removes the per-provider duplication in `mapGoogleProfile`, `mapKeycloakProfile` and the Azure `profile` closure, which each assemble hints today.

**Mappers:**

- **EE `locateUser`** (`ee/server/src/lib/auth/ssoProviders.ts`):
  - The internal branch calls `resolveSignInUser({ userType: 'internal', scopeTenantId, verify: alwaysTrue })`.
  - `TenantRequired` becomes `buildAuthFailureResult('tenant_required', …)`.
  - The dead "tenantHint fallback after `.first()`" is removed.
  - The client branch is unchanged: it already requires a tenant and resolves it scoped.
  - `mapOAuthProfileToExtendedUser` loses its post-hoc `tenantHint`/`vanityHostHint` re-derivation for internal users. The tenant is the resolved user's tenant.
- **CE `mapCeOAuthProfileToExtendedUser`:** same call, same failure code. CE is normally single-tenant, so this is a no-op there. It closes the hole on any multi-tenant CE.
- **`applyOAuthAccountHints`:** for internal users, `tenantIdFromHints` stops being able to fill `user.tenant`. The tenant is always set by the mapper. Client behaviour is unchanged.

**Account linking** (`ensureOAuthAccountLink`) needs no change. It is keyed by `user.tenant` after resolution, so it inherits the fix.

## 4. SSO audit verdict

**The ambiguity is real.** It is worse than the password case: there is no password check to narrow the candidates, and IdP-supplied hints cannot select a tenant.

Evidence:

- **EE** `ee/server/src/lib/auth/ssoProviders.ts` `locateUser`: for every non-client sign-in (`normalizedType === 'internal'`) it calls `findUserByEmailAndType(email, 'internal')`. That is `User.findUserByEmailAndType` (`packages/db/src/models/user.ts:117`): an unscoped `.where({ email, user_type }).first()` with no ORDER BY, so it returns whichever tenant the database yields. The tenant hint is consulted only *after* that lookup misses, which never happens when the email exists anywhere. Google, Microsoft (Entra) and Keycloak all go through this function (`mapGoogleProfile`, the Azure `profile` closure, and `mapKeycloakProfile` → `mapOAuthProfileToExtendedUser` → registry).
- **CE** `packages/auth/src/lib/sso/ceOAuthProfileMapper.ts:46`: `User.findUserByEmailAndType(normalizedEmail, 'internal')`. Same `.first()`.
- **The MSP resolution cookie is not used for user resolution.** `/api/auth/msp/sso/resolve` signs `tenantId` into `msp_sso_resolution`, but only `getOAuthSecrets` reads it (`nextAuthOptions.ts` ~1513), and only to pick credentials. The profile mappers read only the *client-portal* cookie (`getClientPortalSsoProfileHints`). A tenant-scoped IdP can therefore assert a shared email and land in another tenant (§3.5 item 2).
- **Teams:** `buildTeamsAuthOptions(tenantId)` scopes credentials only. The Azure profile closure ignores `teamsTenantId` when it resolves the user.
- **Account linking** (`ensureOAuthAccountLink`) does not resolve users. It reads and writes links under the already-chosen `user.tenant`, so it carries the wrong-tenant choice forward rather than causing it.
- **Client-portal SSO is not affected.** `locateUser`'s client branch requires a tenant (signed cookie, slug or vanity host) and calls `findUserByEmailTenantAndType`. `mapOAuthProfileToExtendedUser` then enforces `tenant_mismatch`.

## 7. Deliberately not done

- No unauthenticated organization picker, tenant list, or "which orgs does this email have" response, anywhere.
- No login tokens or magic links: the emailed links carry only a public slug.
- Nothing co-managed.
- No change to *who* may sign in: no new SSO-to-account auto-linking, and no resolving SSO users by existing provider-account link before email. Resolving by link first would be stronger; it is noted as a candidate follow-up.
- No distributed rate limiter. The existing in-memory `passwordResetLimiter` is reused as ordered (see risks).
- `findUserByEmailAndType` (`.first()`) is not removed. Other callers outside sign-in are not audited here. Its sign-in callers move to the engine.
- `applyOAuthAccountHints` can still set `user_type` from an id-token or state `user_type` claim. That is a separate type-trust question: noted for follow-up, not fixed here.

## 8. Risks

1. **Behaviour change for SSO users with live accounts in two tenants.** Unscoped Google, Microsoft or Keycloak sign-in will now refuse with `tenant_required` where it used to land in an arbitrary tenant. That is the intended fix, and the recovery path covers it: the links open the scoped page, where SSO is scoped through the signed cookie. Affected users must use an emailed link once per sign-in until we add a remembered-organization feature (not in scope). Before merge, a production count of internal emails live in more than one tenant would size the impact. The count is read-only and gives no reason to stop.
2. **Tenant-sourced IdPs become tenant-bound.** A user whose email domain is claimed by tenant A, but who only has an account in tenant B, can no longer sign in with A's IdP credentials. That was a cross-tenant trust gap, not a feature. Users in that position fall back to app-level SSO (when it is configured) or a password.
3. **The rate limiter is per process (`RateLimiterMemory`).** With N pods the effective limit is 3×N per 15 minutes per email. This is the same weakness password reset already has; this card does not widen it.
4. **Shared bucket with password reset.** Requesting links counts against password-reset requests for that address for 15 minutes. This is intended (§3.1) but visible to users.
5. **Email template migration.** It must ship every locale that `tenant-recovery` ships, or the fallback copy is used. Contract test: the template file has the same language set as `tenantRecovery.cjs`.

**Stop conditions** (none currently triggered): stop and escalate if implementation finds either of the following.

- A non-test caller relies on SSO resolving an internal user across tenants without scope. An example would be an automation that assumes `.first()`.
- `/auth/msp/signin` on an MSP vanity host turns out to strip or override `?tenant`. Today it does not: the page reads the query string the same way on every host.

**Already resolved here:** MSP vanity hosts do not resolve a tenant for internal credentials (`portalDomain` is client-only in `authenticateUser`). The plan therefore always appends `?tenant=<slug>` to MSP links, vanity links included (§3.1 step 6).
