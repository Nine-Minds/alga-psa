# CM L6a2 — Co-managed time, effort & billing modes (design session plan)

Card `b8d90b04-c1d2-40e3-b1ab-0b23b9c5aa57` · wave 5 · hard parents merged: L4a, L1b, L6a1 · soft: L3b1, L3c.
Reviewer question: "Can customer staff log operational time and MSP staff log billable time on shared work, with each side
billed correctly and nothing billed twice?"
Authority: `~/cm-redelivery/PLAN.md` §2–3, §5 and `manifests/L6a2.md` win over this plan.

## 1. Intent

Shared work produces two kinds of time that must never be mixed: MSP staff log **billable** time that flows to the MSP's
invoice, and customer staff log **operational** time that records effort but is never invoiced. Today `time_entries` has no
billing-mode concept at all — `billing_mode` is only ever read as a projection of the service catalog
(`packages/scheduling/src/actions/timeEntryCrudActions.ts:265`, `sc.billing_method as billing_mode`), so an entry is
billable if and only if it resolves to a billable service. This card adds an explicit per-entry mode plus the effort
arithmetic that lets both sides see one honest total, and registers a co-managed time source into L6a1's provider registry
so the native scheduling stack learns about shared work without any native file changing.

## 2. What changes

All wiring goes through seams that already belong to other cards. L6a2 adds modules and registers. Original intent was to
edit neither `packages/scheduling/**` nor `packages/billing/**`; the deploy-fix round (see "Ownership crossings" below) crossed
into both, narrowly, and every crossing is listed there.

Order of work (each step lands only after the one above it):

1. **Schema first** (three migrations, re-dated later than main's newest, currently `20261009*`):
   - `time_entries.billing_mode text NOT NULL DEFAULT 'commercial'` — metadata-only default, then a CHECK added
     `NOT VALID` and validated in a separate `transaction:false` file.
   - `work_item_type` CHECK widened **additively**: build the replacement from the live constraint definition
     (`server/migrations/20250602153500_add_interaction_work_item_type.cjs` shows the existing
     `time_entries_work_item_type_check`), add the new CHECK NOT VALID, validate, then drop the old one. Never hard-code a list.
   - `co_managed_time_work_references` (new table, tenant-distributed, unique `(tenant, entry_id)`), plus the participation
     marker migration. No triggers anywhere (DO-NOT-PORT #17).
2. **Write path as a provider**: `packages/co-managed/src/nativeTimeSheetCommand.ts`, `nativeTimeSheetLifecycle.ts`,
   `nativeTimeTracking.ts`, `timeEntryBillingMode.ts` implement L6a1's provider interface. L6a2 supplies the decision
   ("this entry is operational, no service, no contract line"); L6a1 owns the call site.
3. **Read path**: `nativeTimeRead.ts`, `nativeTimePeriod.ts`, `nativeTimeSheetList.ts`, `nativeTimeReview.ts`,
   `nativeTimeEntryAccess.ts`, `timeWorkItem.ts`, `timeWorkReference.ts`, `timeWorkSource.ts`, `timePeriodJob.ts`.
4. **Effort arithmetic**: `effortTotals.ts` (customer / MSP / combined from one entry set) and `timeParticipationEvidence.ts`
   (registers `retainCoManagedTimeParticipation` into L2's access-reduction retainer registry, per DAG-REPORT R2).
5. **Deletion/dispatch**: `nativeTimeDeletion.ts`, `nativeTimeDispatch.ts`, `nativeTimePeriodSettings.ts`,
   `timeBillingProfile.ts` (per-relationship billing profile: default mode, rounding).
6. **Server action + UI**: `server/src/lib/actions/coManagedTimeActions.ts`, then the client components
   `CoManagedTimeEntry.tsx`, `CoManagedTimeBillingProfile.tsx`, `CoManagedEffort.tsx`, `CoManagedEffortSummary.tsx`,
   `CoManagedProjectEffortProvider.tsx`, `useCoManagedSharedTimeConfig.ts`. Shared ticket screen files
   (`SharedTicketScreen.tsx`, `sharedTicketDataSource.tsx`, `CoManagedLocalTicketDataSourceProvider.tsx`) take only the
   time-capability hunks (33% each) — L3b2/L4a own the rest.
7. **Tests** (manifest list): `coManagedSharedStopwatchCases.ts`, `coManagedTimeBillingProfileCases.ts`,
   `coManagedInvoiceJourneyCases.ts`, and the six `server/src/test/unit/product/coManaged*` unit files.

**The stopwatch is not a second table.** Main already owns `time_tracking_sessions` / `time_tracking_session_segments`
(`server/migrations/20261009120000_create_time_tracking_sessions.cjs`, `packages/scheduling/src/actions/stopwatchActions.ts`).
Co-managed sessions extend that table — its `work_item_type` deliberately carries no CHECK — never a parallel session table.

- A2 `coManagedSharedStopwatchCases.ts` — start/stop on a shared ticket produces one entry with `work_item_type`

- A3 `coManagedInvoiceJourneyCases.ts` — an invoice for the shared ticket bills the 15-minute MSP entry and contains no
  operational row; **golden invoice for a plain PSA tenant is byte-identical** (this is the card's stated bar: "a native
  billing regression check (golden invoice identical)").
- A4 `coManagedTimeSnapshot.test.ts` — invoice snapshot of a co-managed entry validates (see R1).
- A5 Effort totals: 5 + 15 = 20, no double count, asserted per side and combined.
- A6 Global gates: migration lint (no triggers, NOT VALID/VALIDATE, re-dated); schema-absent neutrality (psa path never
  reads `co_managed_*`); hot-path query budget for "time entry create/approve" and "invoice generation" unchanged for a
  psa tenant; gate-coverage contract sees the new action and UI mounts; generated artifacts regenerated (OpenAPI must be
  additive: `billing_mode` optional in request, `service_id` still required for non-participating tenants).
- A7 Recorded guide: CT logs 5 operational minutes, MT logs 15 billable and invoices; Quick Invoice
  (`packages/billing/src/actions/ticketInvoiceActions.ts`, `QuickInvoiceTicketDialog.tsx`) also bills only the 15.
  **Decision (deploy-fix round): implemented.** The server path (`loadQuickInvoiceWork`, `validateContributedManualTimeSources`)
  already existed and needed no change; what was missing was the entry point on the MSP shared ticket. It is mounted in
  `CoManagedSharedTicket` through the existing `slots.timeSummary` seam (not `renderQuickInvoice`, because the shared ticket
  keeps `hideBilling` and `TicketDetails` gates `renderQuickInvoice` on billing, a gate pinned by a contract test). The dialog
  is only mounted when the workspace serves co-managed. Deduplication: the billed time entries are flagged `invoiced`, and the
  billable-items query only reads `invoiced = false`, approved, `billable_duration > 0`, service set, for the MSP's own
  `co_managed` work item; operational (customer) entries live in the customer tenant under another work item and are rejected
  as foreign ids. Covered by `coManagedTimeDeployFix.integration.test.ts`.
- No evidence ledger, census or completion verifier. If a check needs a fixture export or a second tenant that this card's
  environment does not have, say so in the charter instead of claiming a pass.

## 5. Risks

- **R1 snapshot whitelist**: `isValidInvoiceTimeSnapshot` (`packages/billing/src/lib/billing/invoiceTimeSnapshot.ts`)
  accepts `workItemType ∈ [null,'ticket','project_task','ad_hoc']`. If the snapshot copies `entry.work_item_type`, every
  co-managed invoice row fails validation. Mitigation: snapshot the *work item* type (a shared ticket is still `ticket`);
  prove it with A4 before touching any billing file. Widening the validator is T0-2's path, not this card's.
- **R2 CHECK widening**: dropping `time_entries_work_item_type_check` before validating the replacement leaves a window
  where an old reader inserts a value the new constraint rejects. Add-then-validate-then-drop, in that order, in separate
  migrations.
- **R3 optional `service_id`**: H §3 and the card bar require `service_id` to stay required for non-participating tenants.
  Make it conditional on participation **and** operational mode only, in the provider, not in a schema change.
- **R4 double count**: a shared entry visible to both relations must be counted once per side. Key the effort query on
  `entry_id`, not on the work item, and assert A5 for the combined column.
- **R5 tenancy**: use `tenantDb(...)` structural scoping (the pattern asserted by
  `packages/sla/src/services/__tests__/slaServiceTenantScoped.contract.test.ts` for the sibling package); never
  `.where({ tenant })`.
- **R6 i18n**: new UI strings need a namespace file under `server/public/locales/en/msp/` plus all locales and the `xx`
  pseudo-locale (`npm run test:i18n` regenerates and validates).
- **R7 hot path**: the effort/provider read is composed into the ticket screen; cache the participation lookup, and add no
  per-entry queries for psa tenants (PLAN §3 "0 extra queries steady-state").

## 6. Open design choices

- **Where the mode lives** (leaning: explicit `time_entries.billing_mode` column, as above). Reason: the invoice must be
  reproducible after a service is repriced or swapped; a derived value cannot be. A CHECK plus default keeps it
  backward-compatible.
- **May operational time later become billable?** (leaning: no in v1 — log a new commercial entry instead). Reason: a
  mutation would silently change an already-shown effort split and could retro-bill a customer's own note.
- **Retroactive effect of a billing-profile change** (leaning: applies to future entries only). Reason: the profile is a
  default, not a re-writer; anything else needs an audit story this card does not own.
- **Decided, not open**: no triggers on `time_entries`/`invoice_time_entries` (PLAN §3, DO-NOT-PORT #17); the effort split
  is read-only; no second stopwatch table (H §2 L6 excluded list).


## 7. Deploy-fix round (post-smoke repairs)

Five repairs on the existing branch, no migrations:

1. **Drawer empty strings.** The native drawer sends `''` for every blank optional field (`user_id`, `time_sheet_id`,
   `approval_status`, `service_id`, `contract_line_id`, `tax_region`, `tax_rate_id`, `entry_id`). `writeCoManagedTimeEntry` now
   normalises them once at the top (`normalizeCoManagedTimeEntryInput`) and resolves the owner as
   `existing?.user_id || entry.user_id || actor.user_id`.
2. **co_managed time sheets.** The seam gained an async `work.describeItem` / `work.listSheetItems` (see below), and the two native
   call sites that threw for an unknown work item type now ask the seam first.
3. **Operational, no-service save.** The seam gained `work.serviceOptional(type, id)`, answered per work item. The drawer reads it
   through the `isServiceOptionalForWorkItem` server action and never inspects the tenant. When it applies the service is optional,
   the entry is labelled operational and billable is off. The customer's own `/msp/tickets/<id>` view mounts the effort split.
4. **Quick Invoice** on the shared ticket (see A7).
5. **Minor.** Contract preview for `co_managed` uses the provider's `billingContext`; the billing profile picker is mounted with the
   effort split; `admitSave` records `ticketNumber` with `title`; REST `workItemTypeSchema` accepts `co_managed`, and
   `TimeEntryService` rejects it with the previous validation error unless a registered source handles the call (so a
   non-participating tenant, and today any REST caller, sees the same rejection as before). The stopwatch in the shared-ticket
   header is **not done** (see below).

Deviation: `work.resolveItem` is a pure synchronous seam (ticket id to work item) and stays a miss. Resolving a `co_managed` item
needs I/O (name and ticket number from `co_managed_time_work_references` plus the routing row), so a separate async
`describeItem` was added rather than making `resolveItem` async and touching every native caller.

Stopwatch: the session store books `ticket` and `project_task` only and `TicketStopwatchControls` returns null for any other type.
Making it book `co_managed` needs the stop/log launcher and `stopwatchCore` to learn a contributed type; that is a larger change
to `packages/scheduling` + `packages/tickets` than this repair round allows, so it is left out. It needs no new table (it extends
`time_tracking_sessions` / `_segments`).
