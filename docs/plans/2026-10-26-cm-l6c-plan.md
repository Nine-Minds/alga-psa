Card `f1f37359-21c3-48db-880e-acccd591ec5f` · wave 4 · hard parent L6a1 (merged) · soft L0c.
Reviewer question: "Can an MSP technician book, move and meet on a customer's shared work without touching a customer-private calendar, losing a meeting to a crash, or changing anything a plain PSA tenant sees?"
Authority: `~/cm-redelivery/PLAN.md` §2–§5 and `manifests/L6c.md` win over this plan. Reference `feature/co-managed-it @ 2d00cb6f0e`; the worktree is main (`058d45c388`), so every `packages/co-managed/**` path below is a new manifest file and every other path was read in the worktree.

## 1. Intent

Shared work is booked, not just discussed. A technician working a shared ticket or task must see the customer's calendar entries that concern the shared item, book and move an appointment on it, approve or decline the customer's appointment request, attach a Teams meeting to that appointment, and log the call that followed — against the customer's *native* records, never a parallel co-managed calendar. Today those surfaces are pure PSP: `packages/scheduling/src/actions/scheduleActions.ts` (1298 lines) and `appointmentRequestManagementActions.ts` (2123 lines) gate on `user_schedule` permissions inside the customer tenant, which no MSP user holds. This card supplies admitted co-managed read and command providers for schedule, appointment request, interaction and online meeting, plus the durable operation records that let Teams meeting creation and later calendar synchronisation survive a crash — registered so no native caller knows co-managed exists.

## 2. What changes, in order

Order is forced: durable records before anything writes them; reads before commands reuse their authorizer; provider adapters before the worker and EE surface can be wired.

1. **Schema first** (newest migration on main `20261025080000`, verified in worktree). `…_create_co_managed_meeting_creation_operations.cjs` (re-dated): one tenant-distributed table, `PRIMARY KEY (tenant, operation_id)`, partial unique index on `(tenant, appointment_request_id)` for live operations, due-index, status/JSONB CHECKs, and no FK to `appointment_requests`/`users` (recovery must outlive deletion of its source — keep the reference comment). The immutability trigger is allowed because the table is new.
2. `…_add_co_managed_meeting_sync_intents.cjs` touches the *existing* `online_meetings`, so it expands into three files: nullable columns + CHECK `NOT VALID`; a separate `transaction:false` `VALIDATE`; a third `transaction:false` `CREATE INDEX CONCURRENTLY` for `online_meetings_co_managed_sync_pending` (PLAN §3, H §3 rules 1/4). Each ALTER sets `lock_timeout = '2s'` with retry.
3. **Read/retain providers**: `nativeScheduleRead.ts`, `nativeScheduleRelations.ts`, `nativeAppointmentRequest.ts`, `nativeMeetingRead.ts`, `nativeInteractionRead.ts`. Each resolves a work root (ticket / project task / interaction / appointment request) through the authorization kernel, locks the actual rows, and returns a redacted-field list; this is the only place shared-work authority is decided.
4. **Commands**: `nativeScheduleCommand.ts` (create/update/delete, occurrence scope, all-day rule via `validateAllDayInterval`, refusal when time entries or a live `native_time_tracking_sessions` row point at the entry), `nativeAppointmentRequestCommand.ts` (decline/reschedule/associate), `nativeAppointmentApproval.ts` (approve with and without meeting), `nativeInteractionCommand.ts`. Every entry point starts with the participation gate plus `assertCoManagedOperationalWrite` from L0b's `packages/licensing/src/lib/co-managed-lifecycle.ts`; lapse semantics are L7a's, the call is ours.
5. **Native wiring**: `scheduleActions.ts` and `appointmentRequestManagementActions.ts` take only the dispatcher hunks their seams leave open (§6 choice 1); `interactionActions.ts`, `onlineMeetingActions.ts`, `InteractionDetails.tsx` and `EntryPopup.tsx` take the small admitted-read and `download_url` hunks.
6. **Meeting creation as a durable operation**: `meetingCreationOperation.ts` + `appointmentMeetingCreation.ts` (state machine prepared → uncertain → created → attached, with cleanup_pending), the scheduling adapter `packages/scheduling/src/lib/appointmentMeetingCreation.ts`, and the EE side `meetingCreationRecovery.ts`, `createTeamsMeeting.ts`, `deleteTeamsMeeting.ts`, `updateTeamsMeeting.ts` (operation id in Graph `transactionId` plus a singleValueExtendedProperties tag; GET-before-POST recovery). Keep the Graph `errorBody` that DNP #5 records as dropped when `resolveOnlineMeetingIdFromJoinUrl` moves out of `createTeamsMeeting.ts`.
7. **Calendar sync intents**: `nativeScheduleMeetingSync.ts` and `packages/scheduling/src/lib/scheduleMeetingSynchronization.ts` write an intent on the meeting row inside the schedule transaction; `packages/jobs/src/lib/handlers/teamsMeetingSweepHandler.ts` drains it. The sweep must import the reconciliation lazily and check participation *before* SQL, or the native Teams sweep for every tenant depends on `@alga-psa/co-managed` resolving (PLAN §3 images; DNP #22).
8. **Artifacts**: `server/src/lib/api/auth/meetingArtifactActor.ts`, the new `server/src/app/api/online-meetings/artifacts/[artifactId]/route.ts` (provider-derived URL, no bearer token on stored URLs, range passthrough), the recordings-route reroute, `packages/documents/src/lib/meetingDocumentAdmission.ts` and the `documentActions` wrapper hunk. The reference's blanket "any `x-api-key` goes to the co-managed path" is DNP #21: reroute only for a participating tenant and keep the native proxy otherwise.
9. **Types then tests**: `IOnlineMeetingView` / `IOnlineMeetingArtifactView` and `IInteraction.online_meeting` switch to the projection so provider and storage identities never reach the client; `WorkItemType` already carries `co_managed` from L3a, so the two `Record<WorkItemType, string>` maps (`scheduleChipInk.ts`, `AgentScheduleView.tsx`) typecheck.

## 5. Risks

- **R1 seam mismatch with L6a1.** If its registry has no schedule/appointment verb, the manifest's call-site hunks double up. Mitigation: implement the providers first, run them against L6a1's contract test, and raise a registry amendment before merge rather than editing native call sites twice.
- **R2 native calendar regression.** `includeMaster: true` changes what every recurring series shows (T0 §1 T-hold). Mitigation: not ported; the file keeps main's occurrence semantics.
- **R3 locking an existing table.** `online_meetings` is read on the ticket screen and by the sweep, so an inline CHECK or index blocks writes. Mitigation: the three-file split, `lock_timeout`, `CONCURRENTLY`.
- **R4 duplicate or lost meetings.** A Graph POST can commit while the response is lost. Mitigation: commit `uncertain` before the call, tag the event with the operation id, recover by GET before retrying, and never record an approval that claims a meeting it does not have. Approve-without-meeting stays the operator's explicit choice — `approve_without_meeting` already exists at `packages/scheduling/src/schemas/appointmentRequestSchemas.ts:46` (verified in base).
- **R5 worker coupling.** A top-level co-managed import in `teamsMeetingSweepHandler` turns a co-managed bug into a Teams outage and breaks worker boot. Mitigation: dynamic import after the participation check, plus A5.
- **R6 artifact authorization.** The `x-api-key` reroute and the per-read participation probe are DNP #21/#17. Mitigation: participation-gated reroute, cached lookup, native proxy untouched for everyone else.
- **R7 tenancy.** Every provider runs on `tenantDb(trx, tenant)`, never `.where({ tenant })`; the new table is tenant-scoped and distributed; a meeting id alone never authorises a cross-tenant read.
- **R8 disclosure at rest.** `approval_input` and `creation_target` hold subject, contact email and organiser identity. Mitigation: never store a token or secret (only `credential_kind` + `credential_id`) and complete or abandon rows so the sweep stops selecting them.
- **R9 T0-4 dependency.** The `documentActions` wrapper passes an admission hook to `authorizeAndRedactDocuments`; that sixth parameter belongs to T0-4's `shared/lib/documentAuthorization.ts` (verified in base at five parameters). If T0-4 lands without it, report — do not edit outside this manifest.

## 6. Open design choices

- **Where the schedule seam is invoked** — leaning: register the providers into L6a1's registry and take *zero* `scheduleActions.ts` hunks even though the manifest lists the file. Reason: PLAN §5 says later cards register and do not edit the same hunks, and the manifest is "heuristic; verify while implementing". Settle at Design Session when L6a1's contract is on screen.
- **Sync intents as columns vs a small table** — leaning columns on `online_meetings`, because the existing sweep already scans that table and nullable columns are metadata-only. Open because it puts co-managed state on a hot native table; a join table is the fallback if review objects.
- **Meeting creation inside the approval transaction** — leaning: operation committed in the transaction, provider call after commit, recovery in the sweep. It is the only shape where a crash cannot both lose the meeting and report success.
- **Recording-route gating** — leaning: keep the native `/api/online-meetings/…` URLs and gate on cached participation instead of inventing a co-managed URL prefix, so existing links and the native proxy keep working.
- **Interactions on opportunities** — leaning: excluded, as in the reference. An opportunity is pipeline, not shared work; keep the exclusion and say so in the guide.
- **Decided, not open**: no triggers on existing tables (PLAN §3); two new tables only; no new SLA, export or notification machinery (H §2); lapse stays in L7a.
