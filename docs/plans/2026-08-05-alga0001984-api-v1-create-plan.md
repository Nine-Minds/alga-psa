# API v1 Invoice and Contract Create Repair Plan

## Goal

Make API-key-authenticated `POST /api/v1/invoices` and `POST /api/v1/contracts` succeed without hidden audit-column failures or silently discarded contract fields, while improving the error returned for future undefined-column defects.

## Design decisions

- Establish API-key user context at the shared v1 controller boundary so downstream `withAuth` actions see the authenticated API-key identity. Reuse the existing API-key AsyncLocalStorage mechanism rather than adding endpoint-specific authentication bypasses.
- Make audit-field filtering explicitly target-aware. Hand-written inserts into `contracts` and `invoices` must filter against the table actually receiving the row, not a service's default table.
- Preserve the existing database schema: do not add audit-user columns merely to accommodate generic stamping.
- Tighten create schemas around caller-owned input. Contract create fields must be accepted and propagated deliberately; invoice item fields generated by the server must not be required from the caller.
- Map PostgreSQL `42703` to a diagnostic API error without leaking SQL or secrets.

## Implementation

1. In the shared API v1 authentication/controller path, wrap authenticated API-key execution in `runWithApiKeyUser` alongside tenant context. Add a behavioral test proving a downstream `withAuth` action resolves the API-key user.
2. Extend the BaseService audit helper with an explicit target-table option (or equivalent reusable helper), preserving current callers. Use it in `ContractLineService.createContract` for `contracts` and in `InvoiceService` for `invoices` before inserts.
3. Correct `createContractSchema` and its service mapping so supported client, start-date, and end-date inputs are neither stripped nor ignored. Prefer strict validation once the complete supported shape is represented.
4. Correct invoice-create item validation so server-assigned `invoice_id` and calculated `total_price` are not mandatory client inputs; retain validation for actual caller-supplied item data.
5. Add `42703` handling in the central API error mapper with a stable, meaningful public code/message and internal logging of the underlying database detail.

## Behavioral verification

- Exercise both POST endpoints with a real API key and valid payloads; assert successful persisted records and correct tenant/user attribution where the target schema supports it.
- Prove contract client/date fields survive validation and persistence.
- Prove invoice items can be created without client-supplied generated fields and totals are calculated server-side.
- Exercise API-key context through a `withAuth` dependency.
- Exercise the error mapper with a representative undefined-column database error and assert the sanitized public response.
- Run focused unit/integration suites plus the affected server typecheck. Do not substitute source-string assertions for runtime behavior.

## Guardrails

- Do not broaden session/API-key trust beyond the authenticated request scope.
- Do not alter unrelated catalog-service overrides or asset-route middleware.
- Do not expose SQL identifiers, statements, credentials, or stack traces in the public error response.
- Keep changes scoped to the shared mechanisms and the two affected create flows.
