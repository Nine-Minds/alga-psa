# T0-3 — Time & scheduling API fixes

Reviewer question: *Do the time-sheet API, the period generator and the project-hours recompute stop failing, stop being callable from a browser, and stop losing updates — with no co-managed code involved?*

Base: `origin/main` @ `058d45c388` · Reference: `feature/co-managed-it` @ `2d00cb6f0e` · Remote card host (X670E) — no worktree on this host · Card `96a54e05`, wave 1, no parents. Standalone: land straight to main, no flag, no schema.

## Intent

Three defects sit in code every tenant runs, and none of them needs co-management to matter. Creating a time sheet over REST fails because the service writes `created_at`/`updated_at` into a table that has neither column; the same create accepts a `user_id` for someone else without the act-on-behalf check every other delegated write performs. The nightly period generator is an exported `'use server'` function that takes its settings from the caller, so a browser can drive it, and the calendar arithmetic for yearly profiles and inclusive month ends lives in two places that disagree. And two technicians saving time against the same task can silently lose one of the two `actual_hours` recomputes because nothing locks the task row. This card fixes exactly those three things, with the tests that prove each one red on main and green here.

## What changes

**T1 — REST time-sheet create/update (`server/src/lib/api/services/TimeSheetService.ts`).**
Base `create()` spreads caller data and then adds `created_at: new Date(), updated_at: new Date()` (verified in base, L344-351) while `update()` adds `updated_at` (verified, L403-407). `time_sheets` has no such columns — the table is `(tenant, id, user_id, period_id, approval_status, submitted_at, approved_at, approved_by)` (verified in base, `202409071803_initial_schema.cjs` L549-563) and the same file's list layer already acknowledges it ("time_sheets has no created_at column", L133-134, L169). Fix: delete those keys from both payloads, keep the existing re-fetch-after-commit behaviour and `publishUnregisteredEventType` calls untouched. Add the delegation check on create: when `data.user_id` is supplied and differs from `context.userId`, run `assertCanActOnBehalf(actor, tenant, subjectUserId, db)` from `packages/scheduling/src/actions/timeEntryDelegationAuth.ts` (verified in base, L76) before the insert, so a sheet cannot be opened on another user's behalf without `time_sheet` manager rights. This is a **backward-compatible API behaviour change**: an API key that could previously create a sheet for anyone now cannot. Changelog entry required.

**T3 — project-hours lost update (`packages/db/src/services/projectTaskActualHours.ts`).**
Base recomputes `actual_hours` from a grouped `SUM` and then updates each `project_tasks` row with no lock (verified in base: the module has no `forUpdate`/`forShare`, L21-41). Two concurrent saves each read the pre-commit total and write back a stale sum. Fix: sort the task ids (stable) and take `FOR UPDATE` on the affected `project_tasks` rows inside the caller's transaction before computing totals, so the recompute serialises per task rather than per tenant. Signature and callers unchanged; behaviour unchanged for a single writer.

**T2 — period cadence and the browser-callable generator (`packages/scheduling/src/lib/timePeriodCadence.ts` new; `actions/timePeriodsActions.ts`; `server/src/lib/jobs/tenantPeriodMaintenance.ts`).**
Base exports `createNextTimePeriod(settings, daysThreshold, options)` from a `'use server'` module (verified: `timePeriodsActions.ts` L3 `'use server'`, L823 export), and the nightly job imports it from that action module (`server/src/lib/jobs/tenantPeriodMaintenance.ts` L4, verified). Fix: (a) add `timePeriodCadence.ts` with `endOfConfiguredTimePeriod(start, setting)` and `isTimePeriodSettingApplicable(start, setting)` as the single reading of `end_day` (last **included** day for months → stored end is `end_day + 1`; `end_day_of_month` on yearly profiles stays exclusive), `start_day`/`start_month` alignment and the effective-date window; (b) make `getNextPeriodStart` call it, including yearly start alignment instead of `currentStart.add({years})`; (c) delete the exported `createNextTimePeriod` from the action module and move the job-facing body into `lib/timePeriodAutomation.ts` (`createNextTimePeriod(db, identity, daysThreshold)`), so no unauthenticated caller can pass settings and only a job identity or an admitted action reaches it. Every remaining internal caller goes through `createTimePeriodsThrough` (existing, `lib/timePeriodMaterialization.ts`).

**Order of work**: T1 (isolated, small, one integration test) → T3 (one module, one concurrency test) → T2 (touches a `@ts-nocheck` action file, a job, and an existing test that imports the deleted export) → changelog. Rebase daily: `TimeSheetService.ts` changed 13 times in 11 days on main (T0-standalone §3), so hand-port, never restore a whole file.

- **A2 Act-on-behalf** (same file): an API principal without `time_sheet` manager rights gets a forbidden/denied error when creating for another user; a manager succeeds; creating for self is unchanged.
- **A3 T3 concurrency** (new, `server/src/test/integration/timeEntryProjectHours.concurrency.integration.test.ts`): two overlapping saves for the same task over separate connections produce the arithmetic sum, not the last writer's sum. Deterministic (barrier between read and write), not sleep-based.

- **A5 Job path**: `tenantPeriodMaintenance` generates through `timePeriodAutomation` under a tenant context; the existing suspension-gates contract test stays green.
- **A6 Gates**: no migrations (so migration lint, upgrade-order, schema-absent are trivially green — say so); generated artifacts regenerated (OpenAPI must show **no** request/response shape change; the act-on-behalf rule is a 403 not a schema change); `npm run generate:artifacts && git diff --exit-code`.

## Risks

- **Main churn.** `TimeSheetService.ts` is one of main's hottest files; a whole-file restore would revert unrelated work. Mitigation: hand-port two hunks, review the diff against `origin/main` only.
- **Act-on-behalf breaks an integration.** A customer's API key that created sheets for technicians now fails. Mitigation: changelog + release note; the check mirrors the existing per-entry delegation path, and the error names the missing permission. This is the item T0 §3 already flags as "API changelog".
- **T3 lock scope.** `FOR UPDATE` on `project_tasks` inside a time-save transaction widens the lock held while bucket/hour-block work runs. Mitigation: lock only the sorted affected task ids, at the end of the recompute path, and keep the transaction short; the concurrency test also asserts no deadlock when two entries touch two tasks in opposite order.
- **T2 is behaviour-visible.** Changing `getNextPeriodStart` alters generated period boundaries for yearly profiles. Mitigation: keep the month/week arithmetic identical, cover yearly alignment and inclusive month ends with explicit tests, and note the change in the release note (T0-standalone: "minor (suggester output)").
- **`@ts-nocheck` file.** `timePeriodsActions.ts` is `// @ts-nocheck` (verified L1-2), so a wrong call compiles. Mitigation: type the new cadence module strictly and keep the action's body thin.
- **Shared test file.** `server/src/test/infrastructure/time-periods/timePeriods.test.ts` is also in L6a1's manifest. Mitigation: T0-3 lands first (wave 1 before wave 3) and L6a1 rebases on it.
- **Fixture/test-context coupling.** `server/test-utils/testContext.ts` carries a comment about `createNextTimePeriod` needing a tenant context (verified in base). Moving the function must not silently change what the shared test context seeds; run the full `server/src/test/infrastructure/time-periods` suite, not just the new cases.
- **Silent API contract drift.** Removing a column that was never stored is invisible until a client asserts on the response. Mitigation: the integration test asserts the response body shape explicitly, and the OpenAPI diff must be empty.

## Open design choices

- **Job-facing entry point name (open, leaning `createNextTimePeriod(db, identity, daysThreshold)` in `lib/timePeriodAutomation.ts`).** The alternative is keeping the function in the actions module but dropping `'use server'`; leaning the module move because the job should not import a browser-callable surface at all.
- **Strictness of the act-on-behalf check (open, leaning full `assertCanActOnBehalf`).** The narrower alternative is `hasPermission(user,'time_sheet','update')` plus a same-client check; leaning the shared helper so a sheet and its entries cannot disagree about who may act for whom.
- **T3 lock granularity (decided, leaning the task rows).** A `pg_advisory_xact_lock` per task was considered; rejected because it does not compose with the caller's own row locks on `project_tasks`.
- **Forced, not open:** no co-managed import or flag (card contents, T0 §3); `TimeEntryService` contract resolution out of scope (B-API-1 held); the weekly/monthly arithmetic must not change (release-note risk classification).
