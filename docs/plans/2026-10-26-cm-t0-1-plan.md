## 4. B1 — where the rate is resolved, and the arithmetic

**Decision: one pure resolver in the compute layer, one precedence order, engine supplies facts only.**

`resolveHourlyContractTerms(line, serviceConfig, isSystemManagedDefault)` lives in `computeTimeBasedCharges.ts` and returns `{ minimumMinutes, roundUpMinutes, contractRate }`. Reason: the compute function is the single point both the live path and the obligation round-trip pass through (`calculateContractCharge.ts:683`), so resolution placed there cannot be bypassed by the second pass; putting it in the engine would leave the round-trip free to re-derive different terms.

Rate precedence, entry to weakest:

1. `entry.custom_rate` (`computeTimeBasedCharges.ts:270`) — an explicit per-entry override, unchanged.
2. `userTypeRates.get(entry.user_type)` (`:262-268`) — negotiated per role, unchanged.
3. **`terms.contractRate`** = `serviceConfig.config.hourly_rate` when positive, else `serviceConfig.config.custom_rate` — new.
4. `entry.currency_rate` (`:272`), the `service_prices` row in the contract currency — the catalog list price, now the third fallback rather than the second.
5. Otherwise throw `Missing pricing for time entry …` (`:276-281`) — unchanged.

Why contract rate outranks catalog: the contract row is the negotiated price, the catalog row is the list price; billing at list when a contract exists is the defect. Why `custom_rate` outranks `hourly_rate` inside step 3 is the opposite: `hourly_rate` is the wizard's normalised rate, `custom_rate` is only populated when the picker fell back to a manual figure.

`hourly_rate: null` must survive loading (`billingEngine.ts:5723-5726` currently coerces to `0`, which would make every contract with no wizard rate bill at zero). `positiveOrUndefined` rejects `0`, `null`, `NaN` and negatives, so a stored `0` falls through to the catalog price exactly like an unset rate.

**Minimum and rounding precedence: line wins, per-service copy is the fallback.** `minutesOrNull` treats `null`/`undefined` as "unset" but keeps `0` as a real value, so:
- line `15`, per-service `0` → 15 (the reported bug: the wizard writes line 15/15 and per-service 0/0);
- line absent, per-service `30` → 30 (pre-existing contracts keep working);
- line `0`, per-service `30` → 0. An explicit 0 means "no minimum"; it is not a signal to consult the other copy. This is the one semantic worth a test and a review note, see §13.

System-managed default lines bypass everything: `{0, 0, undefined}`, i.e. raw minutes at the catalog price, because a default line has no negotiated terms (`computeTimeBasedCharges.ts:227-229` already computes `isSystemManagedDefault`).

**Wizard 15/15.** The line rows already write `?? 15` (`contractWizardActions.ts:1008-1009`, `:1101-1102`, `:2109-2110`, `:2233-2234`); the per-service copies write `?? 0` (`:1057-1058`, `:1144-1145`, `:2141-2142`, `:2262-2263`). Both physical columns default to 15 (`server/migrations/20251008000001_rename_billing_to_contracts.cjs:1043-1044`, `:1065-1067`), so the `?? 0` is what creates the disagreement. Aligning the four sites to `?? 15` fixes **new** contracts; the line-wins precedence fixes **existing** ones without a backfill.

**Worked example** (fixture in `compute.test.ts`): contract line 15/15, contract rate $100.00/hr = `10000` cents, per-service copy 0/0, no `service_prices` row, entry of 1 billable minute.
```
durationMinutes = max(1, 15) = 15          (minimum, minimumApplied = true)
roundUpMinutes  = 15 → 15 % 15 = 0         (no rounding needed)
duration        = 15/60 = 0.25 h
rate            = min > 0 → 10000
total           = Math.round(0.25 × 10000) = 2500 cents = $25.00
```
The guide 09 review block is 17 entries of 1, 6 and 15 minutes (6 + 5 + 6), every one of which lands on the 15-minute minimum: `17 × 2500 = 42500` cents = **$425.00**. On main this set throws `Missing pricing` (no catalog price) or, with a catalog price present, bills 39 raw minutes = $15.00 at $100/hr and ignores both terms.

## 5. B1 — rounding

**Decision: minutes round up per entry to the line increment, after the minimum; money rounds once per entry to the nearest cent; nothing rounds again per line or per invoice.**

- Minute rounding is `durationMinutes += increment - (durationMinutes % increment)` (`computeTimeBasedCharges.ts:242-250`), i.e. ceiling to a multiple of the increment. Ceiling, not nearest, because that is what `round_up_to_nearest` has always meant here and what the contract-authoring screen says.
- Composition order is **minimum first, then round up**, unchanged from main's per-service behaviour. So the billed minutes are the smallest multiple of the increment that is at least the minimum. With minimum 20 and increment 15, a 1-minute entry bills 20 → 30 minutes; with minimum 15 and increment 15, it bills 15. Preserving this order is deliberate: contracts that already worked under per-service terms must not change amount, and reordering would be a second, unreviewed billing change inside a defect fix.
- Money is `Math.round(hours × rate)` once, as `entryTotal` (`:318`); `rate` is `Math.ceil`ed from the stored value (`:288`) so a fractional stored rate cannot produce sub-cent line prices. Example of the money step: line minimum 0, increment 1, 25 minutes, $100/hr → `25/60 × 10000 = 4166.67` → `4167` = **$41.67**.
- Double-rounding is prevented structurally, not by tolerance: (a) the obligation is computed exactly once — `calculateContractBilling` → `calculateNormalizedContractCharge` → `computeTimeBasedCharges` (`calculateContractCharge.ts:669-685`) — and the facts round-trip is now lossless for `custom_rate` and line terms; (b) the persisted `invoice_charges.net_amount` is `charge.total` verbatim (`invoiceGeneration.ts:566-568`), and `calculateNetAmount`'s `round(quantity × rate)` (`services/invoiceService.ts:647-668`) is only reached by manual items; (c) when overtime splits an entry into two segments, the first segment is rounded and the remainder is forced onto the last (`:373-381`), so segments sum to `entryTotal` exactly.

## 6. B3 — the exact off-by-one

Current predicate, both arms of `getUnresolvedChargeReview` (`packages/billing/src/actions/unresolvedChargeActions.ts:139-140` and `:163-164`):

```
te.start_time >= input.windowStart
te.start_time <  input.windowEnd        -- exclusive
```

The dashboard builds an **inclusive** range — `endDate = new Date()`, `startDate = subDays(endDate, 30)`, both `format(..., 'yyyy-MM-dd')` (`ClientContractLineDashboard.tsx:184-191`) — and hands `dateRange.endDate` straight to the review (`:357-361`). An entry worked today has `start_time` inside today, `today < today` is false, so it is excluded; it appears tomorrow when `windowEnd` becomes tomorrow. **Fix:** `windowEnd: format(addDays(parseISO(dateRange.endDate), 1), 'yyyy-MM-dd')`, so `today < tomorrow` includes all of today and nothing after it.

Timezone/DST hazard, and the chosen resolution. `time_entries.start_time` is `timestamptz` (`server/migrations/202409071803_initial_schema.cjs:569`); the action compares it to a bare `yyyy-MM-dd` string, which PostgreSQL casts using the **session** timezone, in practice UTC. Two consequences:
1. The window is a UTC day range, but "today" is the **viewer's** calendar day (the date is formatted in browser local time, and the dashboard has no tenant timezone anywhere in its inputs — it receives `clientId` only). For a viewer west of UTC, `windowEnd = tomorrow` as UTC midnight is `today 19:00` local at UTC-5, so entries logged late this evening still fall outside. For viewers east of UTC the window overshoots into tomorrow morning local instead.
2. `addDays(parseISO('yyyy-MM-dd'), 1)` in date-fns preserves the local wall-clock time, so the date string increments by exactly one calendar day across a DST boundary; the 23/25-hour day appears only in the server-side UTC cast, not in the string arithmetic.

Resolution: keep the `+1 day` fix and document the window as "viewer-local calendar days, resolved at UTC midnight", because (a) it is the same convention every other action this dashboard calls already uses (`getHoursByServiceType` compares `start_time >= startDate` / `<= endDate` against the same strings), (b) a tenant-timezone-correct window needs a timezone the component does not have, and inventing a second date convention inside a defect fix would make the next reader trust neither. The tenant-TZ window is listed as a non-goal with a follow-up.

Note the second, unrelated boundary defect left in place: `subDays(endDate, 30)` yields **31** inclusive dates, and `getHoursByServiceType` uses `<= endDate`, which covers only the first instant of the end day. After this card the review panel includes all of today while the hours panel effectively includes none of it. That is pre-existing inconsistency, out of scope, and named in §9.

## 7. B4 — what leaves `client_id` behind

`billing_profile_autopay` is created by the EE-only migration `ee/server/migrations/20260926091000_create_autopay_tables.cjs`: primary key `(tenant, billing_profile_id)`, a FK to `client_billing_profiles` with `ON DELETE CASCADE`, and a redundant `client_id` FK to `clients`. `AutopayService.enroll` writes `client_id: profile.client_id` (`ee/server/src/lib/payments/AutopayService.ts:50`).

A client merge moves profiles by inserting them under the target and archiving the source shell (`clientMergeEngine.ts:665-678`), then re-stamps every table in `PROFILE_HISTORY_TABLES` from `source.clientId` to `target.clientId` (`:681-699`). `billing_profile_autopay` is not in that list (`clientMergePlan.ts:540-551`), so the row keeps `client_id = <archived source>` while its `billing_profile_id` now belongs to the target profile. The source client row is not deleted (it becomes a shell with a system-managed default), so no FK breaks and no cascade fires — which is exactly why nobody noticed.

**Cleanup:** add `{ table: 'billing_profile_autopay', label: 'autopay authorization', editionOptional: true }` to `PROFILE_HISTORY_TABLES`, add `editionOptional?: boolean` to that array's element type, and guard both loops with `entry.editionOptional && !(await tableInstalled(trx, entry.table))` → count 0 and skip. `editionOptional` is required: `PROFILE_HISTORY_TABLES` is iterated with an unconditional `UPDATE` and `countRows`, so on a CE database a bare entry would abort the whole merge transaction on a missing relation — the failure mode `tableInstalled`'s own comment describes (`clientMergeEngine.ts:256-263`).

**Referential/audit consequences.** The stale key breaks the invariant the rest of the schema leans on — `profile.client_id == row.client_id` — and it breaks the classification contract enforced by `clientMerge.integration.test.ts:998-1032` (TM019): every `public` table with a `client_id` column must appear in one of the four merge matrices. On any EE-migrated database that test fails today, which confirms the bug independently of the reference commit. No current reader joins autopay on `client_id` — every read keys on `billing_profile_id` (`AutopayService.ts:64,87,104,144,185,246`, `:340`; `SavedPaymentMethodService.ts:97,109`) — so the practical exposure is latent rather than visible: an export, an audit query, or the next `client_id`-keyed autopay report attributes a live enrollment to a tombstone. Re-stamping is the correct direction (the collision argument in the reference comment holds: one autopay row per profile, so no unique violation on `(tenant, billing_profile_id)`), and no backfill is needed for already-merged clients — see §13.

## 14. Risks / open questions

1. **Tenants priced under the buggy path are not repaired, only re-priced going forward.** Existing uninvoiced time will re-price at the contract terms on the next run; already-issued invoices stay as issued. Whether that requires a one-time delta report to affected customers or a credit note is a commercial decision, not a code one — the preview in §13 produces the numbers, and the answer should be decided before rollout, not after.
2. **Line `0` overriding per-service `30`.** An operator who set the line to 0 while the per-service copy carried 30 loses the minimum. Believed rare (the wizard always writes 15) but unverified; the delta preview's largest negative deltas are exactly this population and must be inspected individually.
3. **The contract rate displacing a deliberately-added catalog price.** Main's only way to price a contract service without an hourly rate was to add a `service_prices` row (the workaround the defect forced). For those tenants the catalog row becomes dead weight and the invoice now follows the contract line. If a tenant's catalog price was higher than its contract rate, invoices go **down**; if lower, they go **up**. Both directions appear in the delta list, which is why the preview is mandatory rather than advisory.
4. **`contractWizardActions` four-site change is untested behaviourally.** No wizard test asserts the per-service 0/15 split today. A9 covers the engine; the wizard is covered only by the wiring tests' source-text assertions. Consider a narrow action-level assertion on the inserted row, and accept the cost if the wizard's transaction harness makes that expensive — the precedence fix is what actually protects existing data.
5. **B3's date convention is UTC days, viewer-local "today".** The panel is right for a UTC viewer and right about the day count only at UTC noon; the tenant-timezone fix is a separate card (§9.4). Do not let the review of this card reopen it as a defect.
6. **Autopay rows on already-merged clients stay stale.** The fix prevents new tombstones; existing ones remain until a merge is re-run (impossible) or a one-off `UPDATE billing_profile_autopay bpa SET client_id = p.client_id FROM client_billing_profiles p WHERE …` is run per tenant. That update is safe by the same profile-ownership argument, but it is a data write with no test coverage on real merge history — decide whether it ships as a separate, explicitly-announced maintenance action or not at all. Default: not at all in this card.
7. **`billing_profile_autopay` is EE-only, so A12/A13 are skipped on CE CI.** Guard the test with `hasTable` (as the reference does) and make sure the EE lane actually runs it; a green CE lane proves nothing about B4. Unverified which CI lanes build the CE+EE overlay — confirm before claiming the card is covered.
8. **Manifest ownership overlap with L1a** (§1). If L1a lands first, its `clientMergePlan` hunks will include the same region and this card's autopay row has to be re-applied on top. Land T0-1 first, or coordinate the hunk split explicitly.
