# CM L6b — Organization SLA on shared work (design session plan)

Card `ba08b26c-13ed-429c-be90-e328c54be061` · wave 6 · hard parents merged: L5, L1b · soft: L3b2.
Reviewer question: "Does the MSP's SLA clock run, pause and resume correctly as work moves between the two organizations?"
Authority: `~/cm-redelivery/PLAN.md` §2–3, §5 and `manifests/L6b.md` win over this plan.

## 1. Intent

A shared ticket carries two promises at once: the customer's own native SLA, unchanged, and the MSP's promise about the
work it accepted. The second promise only exists while the MSP holds the ticket — it starts when the customer escalates,
pauses when the MSP hands back, and resumes without losing elapsed time. This card builds that clock as a *second, parallel*
obligation on the same ticket, driven by lifecycle transitions rather than by the existing SLA write path, so a plain PSA
tenant's SLA behaviour cannot move by a single row.

## 2. What changes

Ordered; the pure clock lands before anything that persists or notifies.

1. **Migrations** (three, new tables, dated after L5's `20261031090100`, tenant-distributed with `tenant` in every unique index):
   `20261031090200_create_organization_sla_obligations` (obligations + events), `20261031090300_create_co_managed_sla_priority_mappings`,
   `20261031090400_create_organization_sla_notification_events`. They go into the tenant-deletion/export table manifest and
   `packages/db/src/lib/tenantTableMetadata.ts` (four tables; golden count 586 = main's 582 + 4). The recipient-receipt table and the
   email-retry-state migration were dropped: L5's `co_management_deliveries` ledger carries recipients, retry state and
   unknown-outcome reconciliation (delivery kinds `sla_in_app`, `sla_email`).
2. **Clock as a pure module**: `shared/lib/sla/organizationSlaClock.ts` — given an obligation row, a transition and an
   injected `now`, return the next state (running / paused / met / breached) and the accumulated elapsed minutes. No knex,
   no `Date.now()`, no i18n. Business hours and holidays come from the same helpers the native clock uses
   (`packages/sla/src/utils/holidayUtils.ts`, `normalizeHolidayRows`) — note it already carries a
   `// LEVERAGE: pattern holiday-date-normalize` marker; do not add a second date normaliser.
3. **Store and lock**: `shared/lib/sla/organizationSlaStore.ts` (`organizationSlaStore`, `organizationSlaLock`) with
   `packages/sla/src/services/organizationSlaStore.ts` / `organizationSlaClock.ts` / `slaPolicyResolver.ts` as thin
   re-exports so the package surface matches the existing `@alga-psa/sla/services` shape. Serialisation copies
   `packages/sla/src/services/slaLock.ts` (`acquireTicketSlaLock`, `pg_advisory_xact_lock` keyed on `sla:<tenant>:<ticket>`)
   — reuse the same advisory-lock key family so an org-clock write and a native SLA write on the same ticket serialise
   against each other rather than racing.
4. **Transition handlers** (`packages/co-managed/src/ticketSla.ts`, `ticketSlaRead.ts`): `applyCoManagedTicketSlaTransition`,
   `recordCoManagedTicketResolution/Reopened/FirstResponse`, `syncCoManagedTicketAwaitingClientSla`. These are **registered**
   into L0b's ticket-lifecycle hook registry (resolved / reopened / awaitingClient / firstResponse / handoff-or-closure);
   the reference code calls `ticketSla` directly from `commentActions`, `TicketService`, `ticketActions` and eight other
   call sites — that is DAG-REPORT R1's inversion and must not be ported. `server/src/lib/eventBus/subscribers/slaSubscriber.ts`
   stays untouched for psa tenants.
5. **Priority mapping and read model**: `packages/co-managed/src/ticketSlaRead.ts` plus the mapping CRUD behind
   `server/src/app/msp/co-management/sla/page.tsx` and `CoManagedSlaPolicyPanel.tsx`. The panel hangs in L0a's UI slot
   registry; the ticket display takes only L6b's hunks of `CoManagedTicketSection.tsx` (50%, shared with L3b2).
6. **Notifications** through L5's delivery ledger (no parallel pipeline): `slaNotification.ts` (authorization + fanout),
   `slaDeliveries.ts` (enqueue/list `sla_in_app` / `sla_email` rows), `storedSlaNotification.ts`,
   `packages/notifications/src/lib/coManagedSlaNotifications.ts` (event -> pending ledger rows) + `coManagedSlaPresentation.ts`,
   delivery runner `server/src/lib/notifications/coManagedSlaDelivery.ts` (in-app via `createNotificationFromTemplateInternal`'s
   ledger option, email via `sendEventEmail`'s ledger option, existing `sla-warning`/`sla-breach` templates).
7. **Observation job as data**: `packages/jobs/src/lib/handlers/coManagedSlaObservationHandler.ts`, registered with
   `registerMaintenanceJob` at tenant scope in `packages/jobs/src/lib/maintenanceJobFanout.ts` (+19) with a `tenants`
   filter built from `filterServed` so **psa tenants are excluded before any SQL against new tables**; the server-side
   registration lands in `server/src/lib/jobs/registerAllHandlers.ts` (+7).
8. **Second backend, last and splittable** (card: "the second backend (Temporal EE) is in scope, last, splittable (scope
   smell #5)"): a new implementation of `packages/sla/src/services/backends/ISlaBackend.ts` behind
   `SlaBackendFactory.ts`, selected only when the tenant participates. If it does not land, the CE pg-boss backend
   (`PgBossSlaBackend.ts`) is the card's delivery and the guide says so.

- **Customer-side native SLA**: unchanged (card: "OUT OF SCOPE … Customer-side native SLA (unchanged)"). No edit to

- **Ticket write call sites** (`commentActions`, `TicketService`, `ticketActions`, `optimizedTicketActions`,
  `ticketHandoffs`, `client-tickets`, `workflowTicketMutation`, `publishScheduledComment`): L0b (lifecycle registry) and
  L0c (write admission). This card registers handlers; it does not touch those files (PLAN §5 hot-seam table).
- **The policy resolver and holiday extraction**: already landed behaviour-neutral in L0b ("Behaviour-neutral
  slaPolicyResolver/holidayRows extraction already landed in L0b").
- **Outbox and delivery pipeline design**: L5. If L5 chose the existing notification paths (PLAN §6.2 default lean: reuse
  where they fit), this card adds templates and a transport, not a queue.
- **Ticket screen composition and the co-managed section shell**: L3a / L3b2 / L1b.
- **Lapse turning SLA off**: L7a (read-only state), consumed here as a participation signal only.

## 5. Risks

- **R1 double-start on redelivery**: a duplicated `TICKET_UPDATED`/handoff event starts a second obligation. Mitigation:
  unique `(tenant, ticket_id)` on the active obligation + the advisory lock + idempotent transition application.
- **R2 pause/resume arithmetic**: recomputing elapsed from timestamps loses paused intervals when a ticket sits in a third
  state. Mitigation: persist accumulated paused duration and the last transition timestamp; A1 pins the arithmetic.
- **R3 mapping change retargeting**: changing customer-High → MSP-P1 must not move an open ticket's target (H §2 L6 step 3).
  Mitigation: snapshot the resolved target duration onto the obligation row at start; mapping edits only affect new starts.
- **R4 hot path**: registering into the lifecycle registry must not add queries for non-participating tenants, and the
  `slaSubscriber` path must stay untouched. Mitigation: cached participation check, and the query-budget entry as the gate.
- **R5 Citus**: obligations must be distributed with `tenant` in the primary key and all unique indexes, created empty
  (see the pattern in `server/migrations/20261009120000_create_time_tracking_sessions.cjs`, including
  `ensureTenantDistribution`).
- **R6 business-calendar choice**: if the MSP clock accidentally reads the customer's business hours, targets silently
  shift by hours. Mitigation: the org clock resolves its calendar from `organization_sla_policy` only, tested with a
  divergent calendar fixture.
- **R7 i18n**: panel, breach templates and notification copy need the locale namespaces + `xx` pseudo-locale regeneration.
- **R8 second backend**: adding the Temporal backend late can tempt a hot-path import in `SlaBackendFactory`. Mitigation:
  factory selection per tenant, CE default, and the boot-isolation gate.

## 6. Open design choices

- **Whose calendar the MSP clock uses** (leaning: the MSP's own business hours from the org policy). Reason: it is the
  MSP's promise; using the customer's calendar would make a 4-hour target mean different things per client.
- **Obligation shape** (leaning: one row per (ticket, party), state machine, no per-escalation history rows in v1). Reason:
  the display needs current state; history can be derived from the transition log L5 already keeps.
- **At-risk notification cadence** (leaning: one at-risk and one breach per obligation, deduped by the receipt row). Reason:
  avoids a mail storm on a flapping ticket without a full policy engine.
- **Decided, not open**: one backend ships first (pg-boss CE), second backend last and splittable (card scope); new minute
  job gated by `filterServed` (card deployment note); no new outbox pipeline unless L4a/L5 chose one (PLAN §6.2).
