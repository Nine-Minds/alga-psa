### 2.2 One route root: `/msp/co-managed`

The reference splits by *side* (`/msp/co-managed` = sponsor, `/msp/co-management` = customer access panel). This card
splits by *relationship surface* inside one root. The page renders by side: `psa` → sponsor overview,
`co_managed` → the customer's own relationship home. The read model already carries the discriminant
(`CoManagedManagementTarget.side === 'customer' | 'sponsor'`).

| Route | Side | Behaviour (`psa` / `co_managed` / `algadesk`) | Owner |
|---|---|---|---|
| `/msp/co-managed` | sponsor overview **or** customer relationship home | `allowed` / `allowed` / `not_found` | **L1b** |
| `/msp/co-managed?clientId=<uuid>` | sponsor deep link into the provisioning panel | same rule (query, not a segment — a client page is the canonical place for a client) | **L1b** |
| `/msp/co-managed/access` | shared-board access policy, both sides | reserved now, rule `allowed`/`allowed`/`not_found` | L2 |
| `/msp/co-managed/tasks` | shared project tasks | reserved | L3b2 |
| `/msp/co-managed/archive` | shared-work archive | reserved | L7a |
| `/msp/co-managed/providers` | customer-owned mail/identity | reserved | L9 |
| `/msp/co-managed/upgrade`, `/export`, `/departure` | independence, export, ending | reserved | L8a / L7a / L7a |

`/msp/co-managed` is allowed for `psa` **by the product surface** even for a tenant that is not admitted. That is
correct layering: the product surface answers *"what shape is this product"*; the capability gate answers *"may this
tenant use it"*. §4 gives the route the gate adapter.

**Dropping `/msp/co-management` is safe, and it is not a redirect.** Nothing has ever served that path: the reference
shipped it on an unmerged branch, `main` has no `app/msp/co-management` directory, and the branch's own adapter
(`CoManagedLegacyRedirect`) exists only to resolve legacy *operation-id* URLs that were never issued to a customer
outside the evidence environment. PLAN §1 forbids porting "legacy adapters for URLs that never shipped" and H §3 lists
the same for `/msp/co-managed/tickets` + `queueView`. Consequence: a stale bookmarked `/msp/co-management` from the
internal review build 404s. That is acceptable and is stated in the review guide (Chapter 0 checks it as a non-tenant).
The board should know it is a hard cut, not a soft one.

Two registry truths this card must preserve:

- Menu items are filtered by the **product**, never by the capability
  (`filterMenuSectionsByProduct`, `productSurfaceRegistry.ts:371–397`). A `psa` tenant's `/msp/co-managed` is
  `allowed`, so only the capability gate can hide the group. The slot's `isAvailable` therefore reads the capability,
  not the product.
- `server/src/app/msp/billing/layout.tsx:8-15` already calls `enforceServerProductRoute({ pathname: '/msp/billing' })`.
  Quotes (`?tab=quotes`) and accounting exports (`?tab=accounting-exports`) are tabs of that page
  (`menuConfig.ts:464–518`), and there is no `/msp/quotes` or `/msp/accounting` route. So **one** `co_managed: 'not_found'`
  entry in L0a's `msp_upgrade_boundary` rule makes billing, quotes and accounting absent from the nav *and* 404 on
  direct URL before any page data loads. This card adds no route guards; it adds the test that proves it (A5).

### 2.3 The summary/header composition state machine

One pure function, `resolveClientRelationshipSummary(view, selection)`, is the only place the phase is decided.
Everything user-visible (header summary, tab title, status card) reads its output; nothing re-derives it.

Order matters. First match wins.

| # | Condition | `phase` | Header renders | Action |
|---|---|---|---|---|
| 0 | capability unavailable / `view === null` (read denied, load failed first time) | `absent` | nothing — the ordinary client header | — |
| 1 | `view.inconsistent && relationships.every(r => r.ended) && !selected` | `attention` | "Co-managed record needs attention" | none (a second setup must not be offered) |
| 2 | `!selected && setupOpen` (no live **and** no retained relationship; cancelled-only lands here) | `not_enabled` | "Co-managed IT not enabled" | "Enable co-managed IT" **iff** `view.canSetUp` |
| 3 | `!selected && relationships.length > 0` (several live, or ended history with no default) | `selection_required` | "Multiple co-managed relationships" or "This relationship has ended. Retained history…" | "Choose relationship" / "View history" |
| 4 | `selected.ended` | `ended` | state label + "Ended {date}" | "View history" |
| 5 | `selected && !selected.ended` | `live` | state label + "N of M technician seats" (or "N allocated" when usage is withheld) | "Manage" |

`setupOpen = !view.inconsistent && relationships.every(r => r.ended && !r.retained)` — **computed once, in the view
model**, not in the component.

The acceptance states map onto this table exactly, which is why the tests are a table too (A1/A2):

| Acceptance case | Row | What the test asserts |
|---|---|---|
| no relationship, authorized | 2, `canSetUp: true` | text + one action, and the action is the only entry to setup |
| no relationship, unauthorized | 2, `canSetUp: false` | text, **no** action, no disabled affordance, no query for setup options |
| active | 5 | state + seats + exactly one action |
| ended | 4 | `Ended {date}` + history action; never "not enabled" |
| one live + one ended | 5 | the live relationship wins; **no** chooser in the header (the tab holds the selector) |
| several live | 3 | "Multiple…" + chooser action; never an implicit first/last pick |
| cancelled-only | 2 | treated as never set up (a cancelled setup does not block a new one), Enable offered when authorized |

`canSetUp` never comes from this card. It is L1a's:

```
canSetUp = setupOpen                                   // nothing live and nothing retained, !inconsistent
        && view.canManage                              // co_management:manage
        && canManageCoManagedClient(db, actor, clientId) // tier-aware:
                                                         //   owner.plan === 'pro'
                                                         //   OR entitlement.source === 'self_host' && capacity > 0
                                                         //   AND client+board visible under local record policy
```

**If the management-policy module is not present** (the state of this worktree, §9): the header/tab half of the card
does not start. The card is written so the split is visible rather than papered over — `CoManagedClientIntegration`
takes its view model from a single import in `WorkspaceProviders.tsx:46-59`; when that import does not exist the app
does not build, which is the correct failure for a missing hard parent. It is never faked with a client-side guess, and
`canSetUp` is never recomputed locally to "unblock" the build.

### 2.4 Overview: what the MSP sees

`/msp/co-managed` for a sponsored `psa` tenant:

1. **Seat pool tile** — `available / allocated / committed / total`, read-only, from `getCoManagedSponsorSeatSummary`
   (`co_management:read`, entitlement + allocations; no purchase fields, no `account_management` requirement).
2. **Clients tile** — `CoManagedClientOverviewTable` (`CoManagedClientOverviewTable.tsx`): client name (a link, never an
   id), workspace name, state chip, seat usage ("2 of 3 technician seats" / "3 allocated" / "Seats released"), Manage or
   View details. Search + pagination as in the reference.
3. **Provisioning tile** — `CoManagedProvisioningPanel`, entered with `?clientId=`.
4. Empty state: "No co-managed clients" plus the pool numbers — the reference page's "empty overview with N seats
   available" is exactly this.
5. A failed read says so (`role="alert"`); it never renders as an empty list.

Nothing else. No purchase CTA (L8a), no shared-work rail (L3b2/L7a links go in when those routes exist — the reference's
`SharedWorkTile` links to three routes this card does not own).

For a `co_managed` customer the same route renders: sponsor name, relationship state, seats used/allocated,
**relationship event history**, and (from L2) the access panel entry. It never renders a client list.

### 2.5 Relationship event history (new)

`getCoManagedRelationshipHistory({ relationshipId })` → newest first, bounded (50 rows, cursor = revision):

| Column | Source | Rule |
|---|---|---|
| When | `created_at` | tenant date/time formatting (`useFormatters`) |
| What | `event_type` | translated label; unknown type falls back to the raw type, never hidden |
| Who | `actor_tenant === relationship.tenant` | "You" vs the other party's workspace name — **no user id, no email** |
| Revision | `revision` | monotonic counter, shown so two same-second events order honestly |

Authorization: the customer reads its own relationship; the sponsor reads a relationship it sponsors and can see the
client for (`co_management:read` + local record policy). Scope snapshots stay off this list (they can carry board names);
the L2 access panel owns scope.

### 2.6 The menu group, via the L0a slot

The L0a contract this card consumes (if L0a's shapes differ, adapt in `coManagedMenu.ts` only):

```ts
// packages/ui/src/capability/uiSlotRegistry.ts  (L0a)
export interface UiSlotAvailabilityContext {
  capability(key: 'co-managed'): { available: boolean; loading: boolean };
  productCode: ProductCode;
  permissions: readonly string[];
}
export interface UiSlotContribution<T> {
  id: string; slot: UiSlotKey; order?: number;
  isAvailable(ctx: UiSlotAvailabilityContext): boolean;
  build(ctx: UiSlotAvailabilityContext): T;
}
export function registerUiSlot<T>(c: UiSlotContribution<T>): void;   // idempotent by id
export function resolveUiSlots<T>(slot: UiSlotKey, ctx: UiSlotAvailabilityContext): T[];
```

`server/src/config/coManagedMenu.ts` contributes one `NavigationSection`-shaped group:

- `id: 'co-managed-it'`, slot `UI_SLOTS.MspNavigationGroup`, `order: 60` (between Clients and Opportunities —
  `menuConfig.ts:147–158`).
- `isAvailable`: `capability('co-managed').available && permissions.includes('co_management:read')`.
- `build`: group `nav.coManaged` with one item today — `nav.coManagedOverview` → `/msp/co-managed`
  (`requiredPermission: 'co_management:read'`). Later cards append to the same slot; **this card does not edit the
  sidebar for them.**

`SidebarWithFeatureFlags.tsx:209-241` gains one line, inside the existing `useMemo`:

```ts
const baseSections = useNavigationSections ? originalSections : [{ title: '', items: legacyMenuItems }];
// contributed groups join the base list, then flow through the *existing* chain:
// edition → feature/tier → permission → product.  A contribution cannot skip a filter.
const sectionsWithSlots = [...baseSections, ...resolveUiSlots(UI_SLOTS.MspNavigationGroup, ctx)];
```

Open risks, stated early:

1. **The two seams could drift** (§10): a card could add a client tab through the render-prop and a menu item through a
   static menuConfig row. Mitigation: A8's coverage contract enumerates UI-slot mounts, and this card leaves no
   co-managed row in `menuConfig.ts` for anyone to copy.
2. **`canSetUp` is tier-aware in L1a, and tier is L8a's commercial surface.** If L8a changes what "Pro" means, the
   Enable affordance changes without this card's tests noticing. Mitigation: A2 asserts the *composition* per
   `canSetUp` value, never the tier rule; the tier rule is tested where it lives.
3. **Seat usage is withheld** (`usedSeats: null`) when the reader lacks per-relationship manage authority, so the same
   row can read "3 allocated" or "2 of 3" depending on the viewer. That is intentional (aggregate customer state is
   not leaked to a read-only sponsor user) and is asserted in A9 rather than "fixed".
4. **The `co_managed` product surface is a large matrix owned by L0a**; this card only tests it. A gap in L0a's rules
   shows up here as a failed A5, which is the right place for it to surface but the wrong place to fix it — the fix
   goes back to L0a's registry, not into a co-managed page guard.
5. **`/msp/co-managed` for a `psa` tenant with the capability on but no entitlement** must still 404. The capability
   gate, not the product surface, is the only thing standing between a curious admin and an empty sponsor overview that
   would render "0 seats, no clients" — acceptable to *show* only for an admitted tenant. A2/A4 pin the closed case;
   the review guide records it as Emerald.
