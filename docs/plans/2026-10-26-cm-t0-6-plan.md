## 2b. Design: token, room auth, transport

### Token issue — `GET /api/notifications/live-token`
1. `getApiKeyUserOverride()` present → 401 (a machine principal must never mint a browser room token).
2. `getSession()` → `session.session_id`, `session.user.{tenant,id,user_type}`; missing any → 401. `getSession` has already proven the
   session is live (not revoked, owner matches, canonical `user_type`, `sessions` row reachable) — that is the whole reason the signer
   needs no SQL.
3. `issueNotificationLiveToken({ tenant, userId, sessionId, userType }, { now = Date.now(), ttl = 300, sessionExpiresAt })`:
   UUID-checks all three ids, `userType ∈ {internal, client}`, `exp = min(now/1000 + 300, sessionExpiresAt/1000)`, refuses `exp <= iat`.
4. Claims: `{ scope: 'notification-signals', tenantId, userId, sessionId, iat, exp, jti: randomUUID() }`, `HS256`,
   `audience: 'notification-signals'`. Response `{ token, expiresAt, tenant, userId }`, `Cache-Control: no-store, private`.
5. Signer is pure (secret + clock injected) → the issue/skew matrix is unit-testable with no DB and no Next runtime.

`getHocuspocusJwtSecret()` (`server/src/lib/hocuspocusJwt.ts:5-24`) throws in production when `HOCUSPOCUS_JWT_SECRET` is unset, and
`hocuspocus/hocuspocusJwtSecret.js` mirrors it. Both images already share that secret for ticket rooms — no new secret to provision.

### Token verify — `validateNotificationSignalRoom(roomName, request, { now })`
Room `notification-signals:<tenant>:<user>`: exactly 3 parts, prefix match, both ids UUIDs. `token` from the query string only.
`jwt.verify(token, secret, { algorithms: ['HS256'], audience: 'notification-signals', clockTolerance: 60 })`, then all of:
`claims.scope === 'notification-signals'`; `claims.tenantId === parts[1]`; `claims.userId === parts[2]`; `claims.sessionId` is a UUID;
`exp`/`iat` are safe integers; `0 < exp - iat <= 300`; `iat <= now + 60`; `exp >= now - 60`. Returns
`{ status:'ok', tenantId, userId, sessionId, expiresAt: exp*1000 }`.

Skew rule, stated once: **lifetime is measured only from the claims** (`exp - iat`), so a fast or slow issuer cannot make a 5-minute
token look like an hour. **Absolute instants** (which do compare two clocks) get ±60 s leeway, because web and hocuspocus are separate
containers. A token is therefore accepted up to 60 s after it expires and up to 60 s before its `iat` — both bounded by the duration cap.

### Why a forged join cannot work
- The room's two ids are unguessable-but-public UUIDs; the signature is the only thing that binds them. A token for
  `<tenant>:<alice>` carries `userId: alice`, and the validator compares **both** room segments to the claims — renaming the room to
  `:bob` fails, keeping `:alice` and presenting bob's token fails.
- Tokens can only be minted from a live browser session, resolved server-side from the cookie. Arbitrary `tenantId`/`userId` query or
  body parameters are never read (`route.ts` reads no input at all).
- `audience` + `scope` are `notification-signals`, so a ticket-room token (the only other hocuspocus token) cannot be replayed into a
  notification room, and vice versa.
- The room is read-only (`data.connection.readOnly = true`) and carries **no inbox content**: `notification.created|read|all_read|
  unread_count` collapse to the constant `{type:'notifications.changed'}`; the ring is the only payload and is delivered with
  `broadcastStateless`, filtered per connection by tenant/user/`expiresAt`, never written to a Yjs map. So even a legitimately joined
  connection cannot read another user's bodies — bodies come from `getNotificationsAction` under the reader's own session.

### Legacy room during the window — `validateLegacyNotificationRoom` (async)
Pre-signal bundles send no token, but their upgrade request carries the browser's session cookie. With the window open:
1. A `?token=` that is present is verified exactly as for a signal room.
2. Otherwise the `Cookie` header (and nothing else from the socket) is sent to `NOTIFICATION_LIVE_TOKEN_URL`
   (`redirect: 'manual'`, 5 s timeout). The web resolves it with `getSession()` — revocation, owner and user type included — and
   mints a signal token for **that session's** user.
3. That token goes through the same `verifyNotificationToken` against the legacy room: tenant **and** user must match.
4. No cookie, no URL, non-2xx, unreachable web, malformed body, or a token for anyone else → refused.

The verdict is memoised per (upgrade request, room), so the server gate and `NotificationExtension.onLegacyConnect` share one
exchange — keyed by room as well, because one hocuspocus socket can multiplex several documents. An admitted legacy connection is
read-only and carries the same `deadline` (exp + 60 s) and close timer as a signal connection, so it re-proves its session on
reconnect. The legacy maps still hold bodies, but only the owner's own verified sessions can join the room that holds them.

### Transport
`NotificationExtension` subscribes **once** to `pSubscribe('<prefix>internal-notifications:*')` (reference) instead of one channel per
room, re-subscribes on `ready` after a Redis reconnect, and on each message finds `instance.documents.get('notification-signals:…')`
and calls `broadcastStateless(payload, filter)`. No document → drop. `beforeHandleMessage` re-checks `expiresAt` (defence in depth;
the room is read-only, so clients should not send anything).

Client: every `connect()` fetches a **fresh** token, verifies the response's `tenant`/`userId` against the hook's scope (a stale or
cross-user token is refused), opens the room with `parameters: { token }`, and treats `onStateless` as "refresh now" (inbox) or
"fold the ring". Rotation is scheduled at `expiresAt - 15s`; any failure backs off 1 s → 30 s.

## 8. Deployment

No migrations, no flag-on prerequisites, no provenance chain (this card is not capability-gated). `HOCUSPOCUS_JWT_SECRET` must already
be set identically for web and hocuspocus (it is, for ticket rooms).

Image order — the only order that never leaves a client without a socket:
1. **hocuspocus** (this PR's bridge image). It validates `notification-signals:` and, by default, **refuses** `notifications:`.
   To keep tabs that are already open on the old bundle ringing, ops opens the window with `HOCUSPOCUS_LEGACY_NOTIFICATION_ROOMS=true`
   **and** `NOTIFICATION_LIVE_TOKEN_URL=https://<host>/api/notifications/live-token` (same shape as `COLLAB_PERSIST_API_URL`). Legacy
   joins are authenticated by the tab's own session cookie (§2b); without the URL every legacy join is refused (fails closed).
   With the flag open, both room types (new = signals, legacy = maps) are served from the same process and the same Redis event — that is
   what "accepting both room types" means in code: two `onConnect` branches and one `handleMessage` fanning into `broadcastStateless`
   (signals) and, for legacy rooms, the existing per-channel map writer.
2. **web/server** (this PR). New hook asks for a token, joins `notification-signals:`, ignores maps. Old tabs keep their legacy socket
   until they reload; new tabs never touch the legacy room.
3. **Window close** (same train, ≤1 h): drop `HOCUSPOCUS_LEGACY_NOTIFICATION_ROOMS`; then delete the legacy branch, the flag and the
   legacy map tests in the follow-up PR.

Residual gap and how it is bounded: a tab still running the pre-deploy bundle when the flag closes loses its socket; because the hook
enables polling only while disconnected (`useInternalNotifications.ts:153-158`), its bell falls back to the 30 s poll and its ring is
lost until reload. Ops note: close the window after a normal working day and tell users to reload; step 3 is the only place a gap can
appear, and it appears exactly once per stale tab.

Rollback order (important): reopen `HOCUSPOCUS_LEGACY_NOTIFICATION_ROOMS=true` **first**, then roll the web image back — otherwise the
old web bundle has no usable room. Rolling back hocuspocus alone (to a build with neither validator) is safe at any point: the new hook
falls back to polling and re-auths when the new hocuspocus returns.

Generated artifacts touched: none. Migrations: none, so no `migration-lint`, no N-1 schema question.

## Risks

1. **Stale-tab ring gap at window close** (§8) — the one place this card can produce a gap. Mitigation: window stays open through a
   working day; the ops note asks for a reload; bell still updates over polling.
2. **Rotation churn** — 2 sockets/tab × one rotation per 285 s ≈ 0.4 reconnects/min/tab (vs ≈2/min on the branch at 55 s). Hocuspocus
   logs one line per join; a rolling restart re-auths every tab within one backoff. Accepted.
3. **Socket carries no content any more** — the bell's freshness is now `getNotificationsAction` latency. A signal-triggered read that
   fails clears the list (visible change from main's stale-but-present Yjs data). Deliberate: stale shared content is the defect.
4. **Ring depends on a live socket** (`IncomingCallProvider` disables polling). A dropped socket delays a ring by ≤ the 1 s backoff;
   a tab reload restores it. Verified in R2.
5. **Clock skew** — ±60 s tolerance plus a claim-only duration cap; a host whose clock is off by more than 60 s will see 401s from
   `jwt.verify` and must be fixed, not tolerated silently.
6. **Do-not-port drift** — the branch hunks for `markAsRead` error propagation, `NotificationsSection` caching, `NotificationAccumulator`
   and the delivery wrapper must not ride along. The divergence table is the checklist for `git diff 2d00cb6f0e -- <paths>`.
7. **Revocation is bounded, not immediate** (R4) — `sessionId` is shape-checked, never looked up, so a revoked session's socket lives
   until the shipped hook's next rotation (≤ 285 s) or, at worst, hocuspocus's `exp + 60 s` close (≤ 6 min). Accepted: the socket
   carries no inbox content, and a per-message session lookup in hocuspocus would add a DB dependency to the relay.
8. **Legacy window depends on the web** — with the window open, each legacy join costs one `GET /api/notifications/live-token` from
   hocuspocus. If the web is down or `NOTIFICATION_LIVE_TOKEN_URL` is wrong, legacy joins are refused (fail closed) and stale tabs
   fall back to the 30 s poll, i.e. the same outcome as closing the window early.
