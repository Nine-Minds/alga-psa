## 1. Intent

A shared ticket was one record with two readers; a shared project is a *tree* of records the customer already owns. The project, its phases and its tasks live in the customer's workspace, and the customer's own staff stay assigned to them. The MSP gets a second, narrower thing: a **participation reference** in its own tenant that says "this task is shared with me, I am the MSP assignee, here is the revision I last saw". From that row the MSP gets a queue (working vs oversight, assigned to me or my teams), a qualified editor (name, status, due date) that cannot silently overwrite a customer-side change, a change history with organisation-qualified authors, and a search that cannot become a side door around the grant. The customer's native task screens keep working exactly as they do for a plain PSA tenant — the shared row is an *additional* authority check, never a replacement.

## 3. Boundaries

- **Project sharing grant (Collaborate/View), the read model, redaction and the retainer registry: L2.** L3c consumes `sharedWorkRead`, `customerWork`, `conversationPolicy`, `project` scopes; it defines none of them.
- **Task conversations, requester task conversation, task comment audiences: L4c** (PLAN §5; DAG R7: "An attachment-parent resolver and a thread-kind registry in L4b, which L4c registers into"). L3c ships *access admission* for task comments (step 7) and no composer, no audience control.
- **Shared-ticket screens and the Customer Tickets queue: L3b2**; **attachments on tasks: L4b**; **task time and effort: L6a2**; **SLA on shared tasks: L6b**; **delivery of any notification: L5** — L3c emits through L0b's event registry only.
- **Do not port**: `getProjectTreeData`'s lost self-heal (T0 §4 #4) — not this card's file, keep main's version if a hunk touches it; `withTaskCommentAccess`'s 1000-id cap (#18, fixed above); the branch's `TaskForm` rewrites beyond the 3-line hunk.
- **Out of scope**: bulk task actions, CSV of shared tasks, task duplication/move across phases, and project-level editing (the reference touches none; H §2 L3 lists CSV/bulk as ticket-queue follow-ups, not tasks).

## 4. Acceptance

- **A1 Revision guard**: two concurrent shared edits → the second returns a conflict with a fresh snapshot and writes nothing; a customer-side edit between load and save also conflicts; replay of the same operation id is a no-op (idempotent by `request_hash`, app-code enforced — no triggers, PLAN §3).
- **A2 Assignee separation**: MSP assignment changes only the reference row; `project_tasks.assigned_to` and `task_resources` are byte-identical before and after.
- **A3 Queue reader**: working vs oversight, `assigned=me|my_teams`, workspace narrowing never widens to "all", duplicate task names disambiguated by project name.
- **A4 Search**: redaction truth table over aliases (`title`/`task_name`/`values.task_name`), counts and cursor consistent with the page, requester (`user_type='client'`) sees no project-task rows (reference returns `whereRaw('false')` for task notes — verified), and a revoked grant removes the rows entirely.
- **A5 Native neutrality**: a psa tenant's project list, task form, task update and project search cost **0** extra statements and render identically (budget snapshot, H §5); `TaskForm` and `projects/page.tsx` diffs are additive.
- **A6 Comment-access fix**: a project with >1000 tasks still shows correct comment counts on the board (regression test for T0 §4 #18).
- **A7 Evidence**: H §2 L3 step 9 in full — MT edits a task name and status from Shared Tasks, the customer's native task view shows a qualified author, CA removes the project grant and MT's task URL fails on reload — plus guide 06's queue/assignment walkthrough, plus Chapter 0 (Kansas and Emerald unchanged) and Chapter N (kill switch: routes 404, references intact).
- **A8 Gates**: migration lint, upgrade-order N-1, schema-absent neutrality (no `co_management_*` read on a psa project path), hot-path budget (project search, task update), tenant-manifest coverage, generated artifacts.

## 5. Risks

- **Customer-side drift is invisible to `revision`.** `revision` only counts shared commands. Mitigation: compare the task's `updated_at` inside the same `FOR UPDATE` read (A1 tests both directions); never trust a client-supplied timestamp.
- **Foreign actor writing a customer task.** `project_tasks.assigned_to` FKs a customer user, and `created_at`/audit columns expect local identities. Mitigation: the MSP assignee never lands on the customer row; writes carry L2's actor reference; the audit entry is written in the customer tenant with a qualified author.
- **Search redaction by inference.** Two visible fields can reconstruct a hidden one (title + subtitle + body aliases). Mitigation: the reference's explicit alias list per type, plus the property test over every alias pair; carry the LEVERAGE marker so the next card does not add a fourth alias silently.
- **Stale display snapshots.** `assignee_name`/`organization_name` are denormalised. Mitigation: refresh in the same transaction as any assignment or edit, and on read compare `source_updated_at`; a stale row renders the reference's stored name rather than a query to the customer tenant (latency and cross-tenant read budget).
- **Grant revocation mid-session.** Mitigation: every action re-asserts L2 authority inside its transaction; the page fails on reload (A7), and the queue simply loses the row.
- **Shared files.** `TaskForm.tsx` (split with L0c), `searchActions.ts`, `runAppSearch.ts`, `query.ts`, `tenantTableMetadata.ts`, `projects/page.tsx` — hunk-only 3-way apply, diff against main, never whole-file restore (PLAN §1).
- **Search wrapper changes latency for psa tenants.** `withProjectSearchAccess` opens a transaction per search. Mitigation: short-circuit before the transaction when the tenant is not served (`filterServed` / capability check), asserted by A5's statement count.

## 6. Open design choices

- **Editing on a View grant — decided: no.** S8 gives the customer two sharing levels; View is read-only by construction, so the editor only exists for Collaborate (and L2's `visibilityMode` does not weaken it).
- **MSP assignee on the customer's task — decided: no** (separate column on the reference row, A2). Two assignees, two organisations, one task; writing an MSP user id into a customer `users` FK is not representable.
- **Search scope — decided: tenant-local, authority-narrowed** (step 6). A federated MSP search across customer workspaces would need per-tenant ACL evaluation and a merged cursor; nothing in the card's bar requires it, and it can be added later without a schema change because each workspace's index already carries its own ACL columns.
- **Task comments in the queue's comment count — open (leaning: show the count only where the reader may read at least the thread root).** The count is a side channel when the body is redacted.
- **Project-level shared editing (name, status, dates) — open, leaning out of scope.** The manifest has no project edit path; adding one would need its own revision guard and audit vocabulary.
- **`serves` vs `admits` per surface — decided: every L3c surface uses `serves`** (PLAN §2: `admits` = *may start* — provision, purchase, entry points — and needs flag AND eligibility; `serves` = *keep serving existing state* through durable participation (relationship, entitlement row, or `product_code='co_managed'`) and is sticky so a flag flip never strands a workspace). L3c starts nothing: the queue, project/task routes, edit/assign/history actions, shared search, and the two native-path short-circuits (project search, board comment counts) all operate on relationships and workspaces that already exist, so they gate on `serves`. Consequence, tested in `coManagedL3cNeutrality`: a participating tenant with `release-v2-0-feature` off is still served; the flag alone never changes behaviour. Native hot paths (PLAN §3) check `serves` and then the cached `isCoManagedWorkspace` (60s TTL), so a psa tenant pays 0 extra statements in steady state. `FORCE_CAPABILITIES=co-managed:off` is the kill switch and 404s every route.
- **Idempotency (A1) — decided: audit-log `details`, no schema column.** `operation_id` + `request_hash` + receipt are written into the customer-tenant audit row (via L2 `sharedWorkAudit`) in the same transaction as the edit/assignment; replays are found under the reference-row `FOR UPDATE` lock, so they serialise. Same id with a different request hash is refused as an opaque shared-work denial. App code only, no triggers.
- **Forced, not open**: reference table is MSP-owned with `tenant <> customer_tenant` and no cross-tenant FK (reference shape); no triggers; migrations expand-only and re-dated (PLAN §3).
