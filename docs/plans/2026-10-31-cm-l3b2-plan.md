# CM L3b2 — Shared ticket screen & Customer Tickets UI

Card: `707029bf-228d-45d3-9729-5dcab8f9578a` · wave 5 · ships dark behind `release-v2-0-feature`
via the co-managed capability gate. Supersedes 964ce5e0 / PR #3363.

Reviewer question this design answers: **is working a shared ticket on the native ticket screen as
natural as working a native one, and does the Customer Tickets queue scale?**

## What ships

### 1. The shared ticket is the native ticket screen

A shared ticket opens the **same** screen as a native one (grid/table and entry/detail), with the
co-managed composition providing: the customer identity + relationship context, the shared-work
callouts, the affordance badges, and the co-managed section slot (conversation/comments writers already
exist: `server/src/components/co-managed/sharedConversationSession.ts`,
`ticketCommentWriter.ts`). The standalone route survives as a deep link and redirect target, but is no
longer the working surface — the queue row navigates to the native screen with the shared reference as
context.

Composition rules:

- **The native screen is untouched.** No co-managed branch inside `MspClientTickets.tsx`; the section is
  a provider-supplied node, so flag-off and flag-on-without-entitlement render exactly today's screen
  (PLAN §2–3 neutrality).
- **One read per surface.** The screen resolves the shared reference through the same admitted read the
  detail page uses (`readCoManaged...` via its action), so a denial renders the native "not found" path
  rather than a half-populated screen.
- **No actor-scoped reload / intent recovery.** Explicitly dropped (scope smell #12): navigation is
  plain links plus the existing server re-admission on each load.

### 2. Callouts and badges (capability-driven affordances)

Affordances are derived from the effective capability resolution for the tenant, not from client-side
flags:

| affordance | shown when | where |
|---|---|---|
| "Shared by <customer>" callout + relationship badge | the ticket is a shared reference and `serves(tenant)` | above the title |
| "Customer-visible" marker on the comment composer | the writer path is customer-visible | composer header |
| read-only banner, no write controls | the reader holds read but not the co-managed write capability | replaces composer/actions |
| hand-back action | `canHandBack` for that row (server-computed) | row + detail header |

`canHandBack` is computed server-side once per relationship per request (same shape as the previous
attempt: derive from the relationship's state and the reader's capability, never from a client guess). The
read-only viewer case is the acceptance bar's "read-only viewer sees no write controls" — enforced by the
capability, asserted by a component test.

### 3. Customer Tickets queue — scale the three missing pieces

The queue already pages; what it lacks is exactly what makes it usable at volume:

- **Workspace filter**: a filter over the shared workspaces (customer tenants) the caller can read now.
  Options come from the same admitted read, not from a separate tenant list, so a workspace the caller may
  not read never appears as a filter value. Filter state lives in the URL (`?workspace=…`) so the page is
  linkable and the export uses the same parameters as the view.
- **Pagination**: keep the server-side cursor/page semantics (`hasMore` + page size); make the page state
  URL-derived too, so back/forward and deep links behave. No client-side accumulation.
- **CSV export**: `exportCoManagedCustomerTicketsAction` reusing `readCoManagedTicketQueue` with the same
  filters, streamed as `text/csv` with the *masked* projection — a redacted field must be absent from the
  CSV exactly as it is absent from the table (the L3a redaction path is the authority; the exporter adds no
  new query). Export is a capability-checked action, not a client-side serialisation of loaded rows, so
  "download everything" cannot outrun the page size.
- **Plain bulk handback** (in scope, last): select rows → "Hand back to customer" → one server action that
  re-admits each reference and reports per-row outcomes (handed back / denied / already returned). No
  queue machinery, no retry loops: partial results are surfaced, not retried automatically.

### 4. Kill switch and neutrality

- Flag off ⇒ the native screen is byte-for-byte today's composition (no provider node, no filters in the
  queue route).
- `FORCE_CAPABILITIES=co-managed:off` ⇒ the shared-ticket section, queue filters/export and bulk handback
  all disappear; the standalone route still answers 404 the way it does today.
- No migrations (card's deployment note).

## Order of work

1. Composition seam: provider node + the shared-reference context on the native screen; neutral when the
   capability does not serve. (Smallest reversible slice; proves the seam.)
2. Callouts/badges + read-only viewer, driven by the resolved capability.
3. Queue: workspace filter → URL-derived pagination → CSV export (each behind the same capability gate).
4. Bulk handback, last, with per-row outcome reporting.

## Tests (the card's acceptance bar, nothing more)

- **A. Component tests for capability-driven affordances**: write controls present for a writer, absent
  for a read-only viewer; callout/badge shown for a shared reference and hidden for a native ticket.
- **Queue**: filter narrows rows and is reflected in the URL; pagination respects `hasMore`; export returns
  the same masked rows and columns as the visible table (assert a redacted field is absent from the CSV).
- **Native screen unchanged**: the existing ticket-screen tests still pass with the flag off and with the
  flag on without entitlement.

## Deliberately not doing

- SLA callouts (L6b) and effort widgets (L6a2) — owned elsewhere; they compose via capabilities and are not
  grounds to fail this card.
- No `queueView` legacy redirects (scope smell #15).
- No evidence media, ledger or census machinery in the PR.
- No retry/intent-recovery state machine for the actor-scoped reload (scope smell #12).

## Risks

- **The seam's neutrality is the whole contract.** If composing the section requires a conditional inside
  the native screen, the flag-off guarantee is gone; the provider node must be inert when the capability
  does not serve. This is the first thing to prove (step 1), not the last.
- **Export/redaction drift**: the exporter must call the admitted read, never a second query, or the CSV
  becomes a side channel around L3a masking (the same class of bug just fixed in the co-managed ticket
  queue's relationships).
- **Filter options leaking workspace identity**: derive the workspace list from the admitted read; a tenant
  the caller cannot read must not appear as a filter value, even as a label.
- **Rebase:** depends on L3a/L3b1 (merged). L4a may move `msp-composition`; re-cut by path per PLAN §1
  (3-way apply hunks, never whole-file restore).
