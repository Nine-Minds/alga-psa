# L4c — Task conversations & requester task threads (design charter)

Card 8f27fd37. Reference `feature/co-managed-it @ 2d00cb6f0e`. Hard parents: L4b, L3c (PLAN §5, wave 6). Rebase after
L6a2 (soft). Capability-gated: every entry point below is `admits`-gated, and reads/writes must be `serves`-gated.

## 1. Intent
A project task is a place where an MSP tech and a customer's staff talk about shared work — and today it is an
MSP-internal comment box: every comment is visible to every internal reader, authors are unqualified, deletes destroy
the reply chain, and a portal contact has no way to discuss a task at all. This card gives task comments the same
conversation rules the ticket side gets in L4a/L4b — organisation-private audience threads, qualified author labels,
edit/delete tombstones that preserve replies, reactions that respect the audience — and adds a requester-facing task
thread in the client portal so a contact can reply on a task without gaining internal visibility. It is the task-shaped
sibling of the ticket conversation, reusing L4a's comment-writer plugin points and L4b's attachment-parent and
thread-kind seams rather than inventing new ones.

## 3. Boundaries
- **Not the write-admission choke point.** The 5 `assertCoManagedOperationalWrite` lines are L0c's (manifest `L0c.md`:
  "assertCoManagedOperationalWrite in create/update/delete/reaction"). L4c takes only its own 115-line hunk.
- **Not the attachment engine.** L4b owns the attachment-parent resolver, storage paths, download routes and limits;
  L4c only registers the task kind and adds parent columns (DAG-REPORT R7).
- **Not the outbox.** L4a owns the outbox, consumers and tables; L4c registers an event source (R3).
- **Not the disclosure mechanism.** L4b owns thread disclosure; the L4c migration is the task variant registering into
  it. Disclosure *is* splittable-last inside L4b (PLAN §6.4); if it is cut there, L4c ships the migration dormant.
- **No email for requester task threads.** PLAN keeps conversations (PLAN §6.4) but the requester-task *mail* is
  deferred (A-capabilities smell #14). Portal + in-app only.
- **Not search soft-delete.** T0-9a owns C7. If the 4 lines in `project_task_comment.ts` turn out to be C7's deleted/
  scheduled filter, drop them.
- No native ticket-screen edits (L3a owns `TicketDetails`/`Bento`/`CommentItem`); no flag checks against
  `release-v1-6-feature` (DNP #24) — use `useCapability('co-managed')` for the conversation button.

## 5. Risks
1. **DNP #18 regression** is the single most likely defect: an access filter expressed as an id-list breaks board
   counts. Enforce with an explicit >1000-task case.
2. **Requester identity**: `project_task_comments.user_id` is a users FK on base. A contact-authored row needs a
   nullable user, an author kind, and portal scoping that cannot be widened accidentally. N-1 code writes rows with no
   author kind — default it in the reader.
3. **Redaction done in the UI only** leaks through the REST service and the search indexer. One redaction function,
   called by all three.
4. **Citus**: `project_task_comments` is distributed; adding FKs to a new table must include the tenant column, and
   `CREATE INDEX CONCURRENTLY` needs `transaction:false` in the migration exports.
5. **Shared hunks**: `taskCommentService` (L0c) and `CoManagedProjectTaskEditor` (L3c, L6a2) — a whole-file restore
   would revert two cards.
6. **Table-manifest coverage**: any new table must appear in `packages/db/src/lib/tenantTableMetadata.ts` and the
   tenant-deletion activity. Neither file is in this manifest (see open choices).

## 6. Open design choices
- **Decided (PLAN §5):** parents L4b + L3c; L6a2 is soft, so do not block on it. **Decided (PLAN §6.4):** requester
  task conversations are in scope and built last inside the card, splittable at Design Session — so the plan keeps them
  behind a single commit boundary.
- **Decided (DAG-REPORT R3/R7):** the event source and thread-kind registrations belong to this card; the engines belong
  to L4a/L4b.
- **Open — table registration.** If the attachment-parent or disclosure migration creates a new tenant-scoped table, the
  PLAN §5 table-manifest gate fails while the binding manifest lists no `tenantTableMetadata` row for L4c. **Leaning**
  amend the manifest with the two registration rows and land them here, rather than deferring to L7a.
- **Open —** does a requester thread live on the task (one thread per task per contact) or per contact? **Leaning**
  per task with contact attribution, matching ticket-side requester visibility.
- **Open —** reactions across audiences: hide reaction counts from non-audience readers, or hide the reactor only.
  **Leaning** hide the reactor label, keep the count inside the audience.
