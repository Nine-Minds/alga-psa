# L8b — Independent upgrade & restored-workspace activation

Reviewer question: *Can a customer end co-management by buying its own PSA licence, and can a restored workspace be switched back on with credentials it owns, without a double charge, a half-closed relationship, or an activation that skips the restore's quarantine?*

Base: `origin/main` @ `058d45c388` · Reference: `feature/co-managed-it` @ `2d00cb6f0e` · Worktree: `feature/cm-l8b-independent-upgrade-restored-workspace-activation` · Card `9815b21f`, wave 7, hard parents L7a + L7b2 + L8a.

## Intent

Co-management ends one of three ways: the MSP leaves, the customer leaves, or the customer buys its own product. This card is the third. A customer administrator, who is a legitimate administrator of their workspace but not of the MSP's estate, purchases a PSA seat entitlement for their own tenant — monthly or yearly, through the same Stripe account-of-record — and the workspace becomes a plain `psa` tenant: the relationship closes through L7a's closure, the MSP's allocation is released once, and the customer keeps their own data. The same transition has a second entrance. A workspace restored from a portable export (L7b2) sits suspended with every user inactive and every automation paused; this card is the only way to bring it back, and it accepts only a licence or subscription the *customer* owns, never the source installation's credentials.

## What changes

**1. Domain — `packages/co-managed/src/{independentUpgrade,upgradePurchase,independentUpgradeScreen}.ts` (new).**
`withUpgradeAdmission` snapshots the actor, validates `operationId`/`expectedRevision` as UUID/int, takes locks in the same order as operational admission (`co_managed_entitlements` → sponsor `tenants` → relationship → customer `tenants`), and derives a request `fingerprint`. The completing work runs inside one transaction: L7a's `closeCoManagedRelationship` → `finalizeCoManagedArchive` (+ manifest hash) → entitlement write → `product_code='psa'` flip → receipt in `co_managed_independent_upgrades`. A retry with the same `operationId` returns the stored receipt without re-closing or contacting Stripe; a changed request raises `UPGRADE_CHANGED`. `prepareCoManagedUpgradePurchase` refuses a second pending purchase, refuses a workspace that already has a non-addon PSA subscription, and refuses `quantity` below `countCoManagedCommittedSeats`.

**2. Hosted payment — `ee/server/src/lib/stripe/{coManagedUpgradeCheckout,coManagedIndependentEntitlement}.ts` (new) + `packages/licensing/src/lib/hosted-psa-upgrade.ts` (new).**
Embedded checkout via `PaymentIntent` client secret (no redirect), customer ownership proved by `metadata.tenant_id` + `source=co_managed_independent_upgrade` (never by email). `retainHostedPsaUpgradeCandidate` re-reads the tenant's own subscription under `FOR SHARE`, requires exactly one active non-addon, non-`subscription_kind=co_managed` subscription, and a price id from the configured PSA price list; the fingerprint is compared again inside the completing transaction. **Register the payment handler into L8a's Stripe payment-event registry** (DAG-REPORT R16; PLAN §5 "Stripe payment-event registry (L8a)"). Do not edit `ee/server/src/lib/stripe/StripeService.ts` — L8a owns its 215 lines.

**3. Activation of a restored workspace — `ee/server/src/lib/co-managed/portableWorkspaceActivation.ts` (new) + `server/scripts/restore-portable-workspace.ts` (shared with L7b2, 50%).**
`admit()` requires, under an advisory lock keyed on the tenant: a `portable_workspace_restores` row, `tenants.product_code='psa'`, `suspended_at` set with `suspended_reason='portable_restore_pending_activation'`, every user `is_inactive IS TRUE`, and the restored administrator still carrying `hashed_password='!portable-restore-disabled'`. `requirePausedDispatch()` refuses activation while workflow definitions, maintenance schedules, scheduled comments, live meetings or auto-approval remain armed. Activation then sets a *new* administrator password (`validatePassword` + `hashPassword`, base paths), records the entitlement (`tenant_license` when `license_state` exists, else `hosted_subscription`), and writes one immutable receipt to `portable_workspace_activations`. Source passwords, sessions, MFA bindings and the source installation's licence can never satisfy it.

**4. Upgrade execution through the existing workflow — extend, do not fork.**
`ee/temporal-workflows/src/workflows/tenant-product-upgrade-workflow.ts` and `.../activities/product-upgrade-activities.ts` exist in base as an eight-step hosted upgrade. Add an optional serialisable `coManaged` input and one activity `product_upgrade_co_managed` that takes the early return; the AlgaDesk step sequence is never entered. Errors `CO_MANAGED_SHARED_WORK_FORBIDDEN`, `INVALID_UPGRADE`, `UPGRADE_CHANGED`, `PAID_ENTITLEMENT_REQUIRED`, `INSUFFICIENT_PSA_SEATS` become `ApplicationFailure.nonRetryable`. Split `.../db/co-managed-{hosted-upgrade,upgrade-operations}.ts` (new) from `.../db/product-upgrade-operations.ts` (+`initializeIndependentPsa`), so the hosted reader lives outside any transaction.

**5. UI — `server/src/app/msp/co-management/upgrade/page.tsx` + `CoManagedUpgrade{,Billing,Purchase}.tsx`.** Purchase renders only when the price ids are configured (`STRIPE_ALGAPSA_USER_PRICE_ID`, `..._ANNUAL_PRICE_ID`); otherwise the entry point is absent and the route is gated. Amounts use the standard currency components and the workspace's configured currency — no literal `"USD"` (AGENTS). Resume replaces a second purchase when a pending one exists.

**6. Migrations — squashed, guarded, three new tables.**
`co_managed_independent_upgrades`, `co_managed_upgrade_purchases`, `portable_workspace_activations`: `hasTable`+`IF NOT EXISTS`, `ensureTenantDistribution`, FKs added only if absent, `CREATE UNIQUE INDEX IF NOT EXISTS co_upgrade_one_pending_purchase`. **Fix the reference's state CHECK**: it admits `('preparing','checkout','paid','expired')` while the domain type and queries use `payment_failed`, so a failed payment would violate the constraint. Build the CHECK from the full state list. Immutability triggers are allowed on these *new* tables (H §3 rule 6) only as defence in depth; the same invariant must also be asserted in `independentUpgrade` and tested. Activation receipt FK → `portable_workspace_restores` (L7b2).

## Boundaries

- **L8a owns** capacity/pool purchase, the Stripe subscription kind (`metadata.subscription_kind='co_managed'`), the payment-event registry and `StripeService.ts`. L8b registers one handler and one page section; it never writes a subscription itself outside the shared Stripe helper.
- **L7a owns** closure, archive finalisation and the allocation release. L8b *calls* them; it does not reimplement, and "released once" is proved by L7a's receipt, not a new counter.
- **L7b1/L7b2 own** export, restore and the restore decision. L8b owns only *activation* — the state after restore, and `restore-portable-workspace.ts --inspect` remains L7b2's (H §2 L7 excludes the activation wizard; this card is it, and it is a CLI + route, not a wizard).
- **L1a owns** relationship state and `co_managed_entitlements`; **L2** owns the trust/authorization model that closure reduces.
- **Excluded by authority**: the degradation/recovery matrix (ci:F019–F026) and a live production price — production stays configuration-gated so purchase UI renders only with a configured price (H §2 L8 acceptance/deployment).
- **Not ported**: no down-migration (receipts are retained, `down` throws if rows exist); no `assertPsaOnlyTenantAccess`-style product shutdowns; no second upgrade workflow.

## Acceptance

- **A1 Receipt idempotency**: same `operationId` twice ⇒ one closure, one allocation release, one receipt; changed quantity/interval ⇒ refusal with no charge.
- **A2 Capacity granted only after verification**: a `payment_failed`/`checkout.session.expired` event leaves the tenant `co_managed` and writes `payment_failed` (this is the CHECK bug's regression test).
- **A3 Entitlement isolation**: `retainHostedPsaUpgradeCandidate` refuses a subscription whose metadata carries `subscription_kind=co_managed` and refuses two candidate subscriptions; `psa` tenants' subscriptions untouched.
- **A4 Activation quarantine**: activation fails for (a) a tenant without the restore marker, (b) a tenant with one active user, (c) a tenant with an armed workflow/schedule/scheduled comment, (d) a source password; passes only with a customer-owned licence and a policy-compliant new password.
- **A5 Workflow**: `tenantProductUpgradeWorkflow` without `coManaged` runs the same eight steps in the same order (existing tests unchanged); with it, exactly one step runs and a non-retryable code is not retried.
- **A6 Gates**: migration lint, upgrade-order (N-1), generated artifacts, image boot isolation — all green. Evidence: H §2 L8 step 6 (upgrade) and the activation CLI; steps 1–5/7–8 are L8a's and are not this card's bar.
- **Infrastructure this card lacks**: no real Stripe price in production and no live Entra/Stripe tenant — CI uses Stripe test mode plus the local emulator, and the guide must say the upgrade was exercised against test mode.

## Risks

- **Double charge on resume.** Stripe idempotency keys expire (~24 h); a late retry can create a second customer or session. Mitigation: purchase row keyed by `operationId`, `23h` staleness refusal with "needs provider reconciliation", and customer lookup by tenant metadata with an ambiguity error rather than a guess.
- **Half-upgrade.** Entitlement written, product not flipped (or the reverse) if the transaction boundary is wrong. Mitigation: one transaction for entitlement + flip + receipt; provider reads strictly before it; A1 proves retry safety.
- **Activation on a non-isolated tenant.** A `psa` tenant that merely looks suspended could be reactivated with imported credentials. Mitigation: the exact `suspended_reason` marker, the disabled-password sentinel, all-users-inactive and paused-dispatch checks, each with a failing test.
- **Cross-package import.** `portableWorkspaceActivation.ts` reaches into `ee/temporal-workflows/src/db/product-upgrade-operations` by relative path (reference does). Mitigation: keep one import behind `initializeIndependentPsa` and mark `// LEVERAGE: friction temporal-db-import — activation needs the seed initialiser, which belongs in a shared package`; do not copy the module.
- **Worker ordering.** The server must not start the `coManaged` branch until the Temporal worker that knows the activity is deployed (PLAN §3, worker deploys last). Mitigation: the branch is only reachable for a tenant that participates, and the activity name is versioned (`product_upgrade_co_managed`); flag-on requires every image to report the SHA.
- **Receipt table without a reader.** Rows are written but only the route reads them. Mitigation: the route and the CLI both read the receipt, and A1 asserts the same row.

## Open design choices

- **Hosted upgrade entry point (open, leaning existing workflow + one activity).** The alternative is a dedicated `coManagedIndependentUpgradeWorkflow`; leaning is the optional branch because Temporal history and the status query already exist and a second workflow duplicates the `runStep` scaffolding.
- **Self-host vs hosted selection (open, leaning `license_state` presence as the switch).** That is what the reference does and it matches L8a's rule that a hosted subscription cannot replace installation licensing; the alternative (an explicit product config) adds a mode for one binary.
- **Where the activation receipt is surfaced (open).** Leaning: the CLI prints it and the upgrade page links to it read-only; no new admin screen.
- **Forced, not open:** register into L8a's payment-event registry and do not touch `StripeService.ts` (DAG-REPORT R16, PLAN §5); no down-migration; purchase UI absent without a configured price (H §2 L8); activation is a CLI + route, not a wizard (H §2 L7 exclusion); currency via standard components (AGENTS).
