## 0. Decisions (Design Session, 2026-10-27)

| # | Decision | Source |
|---|---|---|
| D1 | **"Submit for review" does NOT hide an already-published article from the portal.** It stays visible until the next publish. | XO, binding (PLAN §6.3) |
| D2 | `documents.is_client_visible` on a KB document is **derived from article state, never set independently**: `visible ⇔ status = 'published' ∧ audience ∈ {client, public}`. One pure function owns the rule. Every KB write that changes `status` or `audience` (server actions **and** REST service) re-derives it under a row lock. | design |
| D3 | D1 is implemented by **not demoting a published article** in `submitForReview`: it keeps `status='published'` (so the portal KB page, which filters `status='published'`, keeps showing it, and D2 keeps the flag true). Reviewer rows are written as usual. Drafts still move to `review`. | design, follows from D1+D2 |
| D4 | The manifest's migration `20260906110000_add_kb_import_batch_identity.cjs`, `KBImportDialog.tsx`, `kbArticleImportHandler.ts` and the import/recovery tests belong to **KB import recovery** (`batch_id`, resume, `paused`/`retry_required` driven by `getCoManagedOperationalState`). That is not C1/C2/C3/C7 and is co-managed lifecycle machinery, so it is **not ported**. The card's single migration slot is used for the C1 data repair instead (§5). | design; PLAN wins over manifest |
| D5 | C7 is fixed at **both** ends: the indexers stop emitting deleted/unpublished rows, and the query-time ACL verifiers refuse them. The verifier half covers rows already in the index before the nightly reconcile prunes them, so C7 needs no migration. | design |
| D6 | C3 reads `tickets.attributes.description`. If it is a BlockNote document, its blocks are spliced under "Problem" (formatting kept); if it is plain text, it becomes a paragraph. Create-from-ticket runs in one transaction in both the action and the REST service; the event publishes after commit (main's existing pattern). | design |

### What the defect actually is on main (read before the video)

- The portal KB page (`packages/client-portal/src/actions/client-portal-actions/client-kb.ts`) filters on
  `kb_articles.status='published' AND audience IN ('client','public')`. It **already** follows an audience change on main.
- What does not follow is the document flag. `publishArticle`/REST `publish` set `documents.is_client_visible=true` for
  client/public and **never clear it**; `updateArticle`/REST `update` never touch it. So a published client article switched
  to `internal` (or set back to `draft`/`review` through `updateArticle`) keeps `is_client_visible=true`. That flag is what the
  rest of the product trusts: the authorization kernel's `client_visible_only` bundle constraint
  (`bundleProvider.ts:89`), the portal document surfaces (`client-documents.ts`, `clientDocumentAccess.ts`), and the
  "visible to clients" indicator in the MSP Documents list (`DocumentListView.tsx:149`) for the `/Knowledge Base` folder.
  The reverse also happens: internal→client on a published article leaves the flag `false`.
- So the C1 fix restores one source of truth for the portal ("visibility follows the article"). The guide and video
  demonstrate it on the document flag, not only on the portal KB page.

## 3. Per-item design

### C1 — audience/status change re-derives portal visibility
- `shared/models/kbArticleModel.ts`:
  - `isKbArticleClientVisible({ status, audience }): boolean` — the rule in D2, nothing else.
  - `syncKbArticleClientVisibility(trx, tenant, article)` — writes `documents.is_client_visible` (+ `updated_at`) for the
    article's `document_id` only when it differs. Takes the post-write row so callers cannot pass stale state.
- Every write path locks the article row first (`.forUpdate()` on the `kb_articles` read inside the transaction), applies its
  change, then calls the sync with the merged `{status, audience}`. Sites: actions `updateArticle`, `publishArticle`,
  `archiveArticle`, `submitForReview`; REST `update`, `publish`, `archive` (REST methods get a private
  `withArticleWrite(context, work)` = `withTransaction(getDbForContext(context), trx => work(trx, {...context, db: trx}))`).
  `publish` of an `internal` article now actively sets `false` (repairs a stale `true`).
- `createKbArticle` writes `is_client_visible: false` explicitly (new articles are drafts).
- D3: `submitForReview` reads the locked row; if `status === 'published'` it does not change `status` (and so visibility is unchanged);
  otherwise it sets `status='review'` and syncs (→ `false`). The MSP UI only offers "Submit for Review" on drafts
  (`KBArticleEditor.tsx:435`, `KBPublishingControls.tsx:131`, `KBArticleList.tsx:443`), so D3 changes no visible MSP flow; it governs the
  server action and API callers.
- Existing drifted rows: §5 migration.

### C2 — reviewer can be re-requested
- `submitForReview` runs in one transaction (today it is four autocommit statements: status update, validate, delete, insert —
  a failed validation leaves the article in `review`). Order: lock article → dedupe `reviewerUserIds` → validate users →
  delete **pending** rows for reviewers no longer selected → insert with
  `.onConflict(['tenant','article_id','user_id']).merge(['review_status','assigned_by','assigned_at','reviewed_at','review_notes'])`
  resetting to `pending`, `reviewed_at=null`, `review_notes=null`. Non-pending rows for deselected reviewers stay (review history).
- `completeReview` locks the article row before updating the reviewer row, so both actions take locks in the same order
  (article → reviewer) and cannot deadlock.

### C3 — create-from-ticket uses the real description, atomically
- `buildKbArticleContentFromTicket(ticket)` in the shared model: title, "Problem" heading + description blocks from
  `ticket.attributes.description` (BlockNote JSON → blocks; string → paragraph; empty → today's placeholder text), "Resolution"
  heading + today's placeholder. Used by the action and the REST service (removes the two divergent copies).
- Action: `withTransaction(knex, trx => createKbArticle(trx, ...))`, then `publishKbArticleCreated` after it returns.
  `createArticle` gets the same wrapper (same atomicity defect: document insert, block insert, article insert are autocommit
  today with a best-effort cleanup that leaks `document_block_content`).
- REST: `create` and `createFromTicket` run in `withArticleWrite`; `createFromTicket` calls the inner create with the trx context.

### C7 — deleted/unpublished comments out of search
- Indexers: `ticket_comment` base query adds `whereNull('c.deleted_at')` + `where('c.publish_state','published')`;
  `project_task_comment` adds `whereNull('pc.deleted_at')`. Because the subscriber's upsert path deletes the index row when
  `loadOne` returns null, a soft-delete/cancel event now removes the row, and the nightly reconcile's
  `deleteRowsMissingFromSource` prunes rows already indexed.
- A scheduled comment is indexed when it publishes: `publishScheduledCommentHandler` emits `TICKET_COMMENT_ADDED` after the
  `scheduled→published` transition (`:35`, `:91-107`).
- ACL verifiers (`acl.ts`): `ticket_comment` adds `whereNull('deleted_at')` + `where('publish_state','published')`;
  `project_task_comment` adds `whereNull('ptc.deleted_at')`. Read-time safety for rows not yet pruned.
- `reindexTicketComments`/`reindexProjectTaskComments` (parent rename/move) delete on null instead of skipping.

## 5. Migrations
One file, `server/migrations/<ts>_repair_kb_document_client_visibility.cjs`, `<ts>` re-dated after the newest migration on main
**including T0-11's** at implementation time. **Chosen: `20261027100000_repair_kb_document_client_visibility.cjs`** (after main's newest, `20261027090100_add_stripe_subscription_item_id.cjs`, at rebase onto `e6c1f94cdf`).
- **Hide-only data repair**: per tenant (distinct `kb_articles.tenant`), one statement routed to that tenant's shard:
  `UPDATE documents d SET is_client_visible=false, updated_at=now() FROM kb_articles ka WHERE d.tenant=? AND ka.tenant=? AND
  d.document_id=ka.document_id AND d.is_client_visible AND NOT (ka.status='published' AND ka.audience IN ('client','public'))`.
- Never sets anything to `true` (a migration never exposes content; published client articles with a stale `false` are repaired
  by their next write, and the portal KB page does not read the flag).
- No DDL, so expand-only by construction; `exports.config = { transaction: false }` with one transaction per tenant; idempotent
  (second run updates 0 rows); Citus-safe (co-located join on the distribution column, tenant-pinned); N-1 compatible (old code
  can only re-introduce drift in the blue/green window, which the new code repairs on the next write). `down` is a no-op.
- Pre-deploy query for the release note: count of affected KB documents per tenant (same predicate as `SELECT count(*)`).

## 8. Deployment
- One image set; the migration is safe to run before or after the web rollout (hide-only, idempotent).
- **Release note — KB visibility**: "A knowledge base article's client visibility now always follows its status and audience.
  Changing a published article's audience to Internal, or moving it back to Draft, removes it from the client portal and from
  document views that show client-visible documents; changing it to Client or Public on a published article shows it again.
  Submitting an already-published article for review keeps it visible until it is published again. During the upgrade, internal,

## 12. Risks
1. ~~T0-11 not merged~~ — resolved: merged at `09c9768a91`, rebased.
2. D1/D3 is a behaviour change versus main for API/action callers: today `submitForReview` on a published article demotes it to
   `review`, which hides it from the portal KB page. After this card it stays `published`. The article will not appear in the MSP
   "Review" tab (that tab lists `status='review'`), only its reviewer rows change. Acceptable because no MSP UI offers this transition;
   flagged so the XO can overrule.
3. There is no versioning: content edits to a published article are live immediately, so "stays visible until the new version is
   published" means "stays visible, with its current content". D1 does not introduce drafts-of-published.
4. Migration hides KB documents that admins may have flagged client-visible by hand on purpose while the article is internal.
   Mitigated by the per-tenant pre-deploy count in the release note; the portal KB page never relied on the flag.
5. Reviewer-question wording vs main: the portal KB **page** already follows audience on main; the defect is the document flag.
   The video must show the flag/Documents surface, or R1 will look green on main.
