## 1. Intent

Delivery is one decision, made once. When a customer escalates, an audience-restricted message is posted, or a requester answers mail, the system must decide **who is entitled to know, on which channel**, and then deliver exactly once — surviving a worker kill, a replayed event, a re-delivered inbound message, and a revoked sharing grant. Today the product already has most of the machinery for one tenant talking to itself: a durable comment-publication intent, an inbound durable inbox/outbox with consumer dedupe, a reply-token threading lookup, per-recipient email claims, and a template-driven in-app notification table. This card makes that machinery speak for two organisations, adds the one ledger it cannot express (non-comment delivery: escalation routing, task comment, assignment), and teaches inbound mail to admit a *qualified* reply token and stamp the audience the reply belongs to. It does not build a second notification backend (§2 of H describes the branch's five delivery tables plus its own outbox as exactly that; `// LEVERAGE: friction notification-backend`).

## 2. What changes (in this order)

1. **One claim protocol, two tables.** Extract base's claim/finish pair (`server/src/lib/notifications/ticketCommentAttachmentEmail.ts:149-159`, `claimCommentEmailDelivery`/`finishCommentEmailDelivery`, backed by `ticket_comment_email_deliveries`, migrations `20260904210725` + `20260904221253`, **verified in base**) into `shared/lib/deliveryLedger.ts` as `claim(trx, {ledger, key, recipient})` / `finish(...)`. Base keeps its table and its behaviour (a pure refactor, covered by the existing tests). Co-managed deliveries get ONE table `co_management_deliveries` (tenant, `delivery_kind`, `source_id`, recipient_kind, recipient, state, attempts, next_attempt_at, last_error, error_code, requires_reconciliation) with `UNIQUE(tenant, delivery_kind, source_id, recipient)`. Replaces the reference's `in_app_receipts`, `notification_deliveries`, `email_deliveries`, `customer_email_deliveries`, `requester_email_deliveries`, `requester_task_email_deliveries`, `ticket_routing_notifications` — 7 tables → 1.
2. **No outbox.** L4a's ratification (PLAN §6.2, "reuse existing paths") means the outbox is base's comment-publication intent: `comments.publish_state` / `scheduled_publish_event_id` / `comment_publication_payload` plus `persistCommentPublication` / `dispatchCommentPublication` (`shared/lib/ticketCommentAttachments.ts:47-84`) and the reconcile sweep already in `publishScheduledCommentHandler.ts` (**verified in base**). L5 consumes those intent rows; it adds none. `co_management_event_outbox` / `co_management_event_consumers` and the `conversationEventOutbox*` modules are dropped (divergence rows).
3. **Recipient resolution, once.** `packages/co-managed/src/deliveryRecipients.ts`: `(event, audience) → recipients[]` where each recipient carries `{tenant, kind: 'msp_user'|'customer_user'|'requester_contact'|'team', id, address}`. Audience comes only from L4a's `resolveCommentAudience`/`shared/lib/commentAudience.ts`; `organization_private` never yields a recipient in the other tenant. In-app recipients reuse `filterRecipientsWhoCanReadTicket` (`server/src/lib/notifications/boardNotificationAudience.ts`, verified). Escalation routing recipients come from L3b1's handoff receipt, not from a new ticket query.
4. **Senders — extend, never parallelise.** Comment email stays in `server/src/lib/eventBus/subscribers/ticketEmailSubscriber.ts` (base already resolves suppression via `shouldSendInternalTicketEmail`/`shouldSendContactFacingTicketEmail`, L94-120) and task comment email in `projectEmailSubscriber.ts` (`TASK_COMMENT_ADDED` handler, L1606+; both **verified in base**). L5 adds an audience-aware recipient/template step and a ledger claim; the served gate is evaluated once per event through `filterServed` (L1a, PLAN §2) and short-circuits before any co-managed SQL. The three reference subscribers (`coManagedCommentEmailSubscriber`, `coManagedCustomerCommentEmailSubscriber`, `coManagedRequesterCommentEmailSubscriber`) collapse into that one step.
5. **One genuinely new subscriber.** `server/src/lib/eventBus/subscribers/coManagedRoutingSubscriber.ts` for events base has no subscriber for (escalation received / returned / assignment), registered in `subscribers/index.ts` (declarative list, verified in base) via L0b's native event registry (DAG R3). In-app effect and email effect both write `co_management_deliveries` rows. In-app is transactional: claim row, `createNotificationRowFromTemplate` (`packages/notifications/src/actions/internal-notification-actions/createNotificationCore.ts:247`, verified), mark `sent`, all in one transaction — atomic, so a retried event inserts nothing.
6. **Requester mail and reply tokens.** Base already has `email_reply_tokens` (migration `20250310120000`), marker application (`sendEventEmail.ts:532-552`) and token lookup `findTicketByReplyToken(token, tenant)` inside `processInboundEmailInApp.ts:1679` (**verified in base**). Reuse both: no token table. `requesterReplyTokens.ts` / `customerReplyTokens.ts` become namespaced adapters minting `cm2:`-prefixed tokens stored in `email_reply_tokens.metadata` as `{namespace:'cm', version:2, relationshipId, grantGeneration, threadId}`. A version-1 (`cm1:`) token, or a token whose `grantGeneration` no longer matches the live relationship, is refused *before* any comment write. Replaces `co_management_requester_reply_tokens` / `co_management_customer_reply_tokens`.
7. **Inbound admission.** One hook registered into L0b's inbound-email registry (`shared/services/email/processInboundEmailInApp.ts` — L5 takes the qualified-admission hunk only; the shared-file hunks next to L0b/T0-8 are 3-way applied, PLAN §1). It resolves the token, asserts participation and audience, stamps `collaboration_audience` on the created comment through L4a's writer, and maps the outcome to base's durable inbox terminal states (including quarantine). Duplicate replay is caught by base's existing dedupe (`inboundEmailConsumerDedupe`, `inboundEmailDurableStore`) — no new receipt table.
8. **Recovery.** One handler, registered as a descriptor in L0b's job registry (DAG R18) and selected by a `TenantSelector` (`packages/jobs/src/lib/maintenanceJobFanout.ts`, verified in base) wrapped in `filterServed`. It sweeps stale `co_management_deliveries` rows, never blind-resends an unknown provider outcome (same rule as base's `COMMENT_DELIVERY_RECONCILIATION_REQUIRED`, verified), and re-expires scheduled comments through the existing `publishScheduledCommentHandler`.
9. **Notification catalog.** Co-managed categories/subtypes/templates are global rows (`internal_notification_categories|subtypes|templates`, migration `20251031160000`, verified). Additive migration seeds them and the listing action behind `packages/notifications/src/components/settings/InternalNotificationCategories.tsx` filters by capability, so an unserved tenant's settings are unchanged (H §2 L5 requirement). No per-tenant permission or reference backfill (PLAN §3).

## 4. Acceptance

- **A1 Exactly-once**: consumer crash at each step of the routing subscriber; replayed `TICKET_COMMENT_ADDED`; duplicate inbound message. Ledger shows one `sent` row per (kind, source, recipient) and one comment. (H §2 L5 A1, steps 4 and 6.)
- **A2 Claim protocol parity**: base's `ticket_comment_email_deliveries` tests stay green after the extraction — the refactor is behaviour-preserving (unit test at the ledger seam plus the existing integration test).
- **A3 Token admission**: `cm2:` round trip; `cm1:` refused; revoked grant generation refused without a comment; malformed token falls through to thread-header matching, which base already implements (**verified: `matchedBy: 'reply_token' | 'thread_headers'`**).
- **A4 Inbound neutrality**: main's `replyParser` golden corpus and the inbound journey tests pass unchanged for a psa tenant; the log shows the gate skipping before any `co_management_*` query (H §2 L5 step 7).
- **A5 Fanout scoping**: every selector is `filterServed`-wrapped; the tick with participation serves only served tenants (step 8). No unscoped scan of a new table before gating.
- **A6 Hot path**: comment add/edit/delete and inbound reply cost **0** extra statements for a psa tenant (budget snapshot, H §5). The audience check must reuse rows already loaded by the subscriber.
- **A7 Catalog neutrality**: Kansas's notification settings list is byte-identical to main; Emerald's too.
- **A8 Kill switch**: `FORCE_CAPABILITIES=co-managed:off` → rows accumulate, nothing sends, nothing drains; lift → drains once (step 9).
- **A9 Gates**: migration lint (both migrations new-table/lookup-seed only), upgrade-order N-1, schema-absent neutrality, image-boot isolation (email-service, workflow-worker, Temporal worker boot with `@alga-psa/co-managed` unresolvable), generated artifacts. **Needs infrastructure the card does not itself provide**: GreenMail, the email-service and workflow-worker images, and the worker-kill step. ## 5. Risks

- **Double send.** Native subscriber and co-managed subscriber both mailing a shared ticket's comment is the worst outcome. Mitigation: one served decision per event, taken before recipient resolution; A1 asserts a single ledger row *and* a single provider send; the native path is unmodified for non-served tenants.
- **Requester leaks an internal note.** Mitigation: recipients and template derive from `resolveCommentAudience` only, never from `is_internal`; a negative test asserts an `organization_private` comment produces no requester recipient.
- **Hot-path cost of the audience read.** `ticketEmailSubscriber` and `internalNotificationSubscriber` are hot. Mitigation: read `collaboration_audience` from the thread row the subscriber already fetches; A6 measures; the L0 fast path absorbs the tenant lookup.
- **`filterServed` is L1a's, not base's.** Mitigation: treat it as a hard interface; if L1a's shape differs, adapt in one module (`deliveryGate.ts`) rather than at call sites.
- **Reconciliation vs duplicate.** An unknown provider outcome must never auto-resend (base already refuses: verified). Mitigation: `requires_reconciliation` state plus an operator-visible count; the sweeper only retries `failed`/`pending`.
- **Token reuse after revocation.** Mitigation: generation check before any write, plus the `unique(token)` constraint base already has.
- **Global catalog rows.** Mitigation: capability filter in the listing action and a neutrality assertion (A7); no tenant backfill.
- **Image ordering.** Producers write rows only for served tenants; an older worker leaves rows waiting (PLAN §3). Mitigation: the guide's kill-switch chapter plus provenance check across all four images before flag-on.

## 6. Open design choices

- **One ledger vs two — decided: one new ledger for every co-managed delivery**, base's ledger untouched for native. A single table cannot absorb `ticket_comment_email_deliveries` in place: its PK `(tenant, comment_id, recipient)` cannot be widened on an existing distributed table (migration lint refuses `DROP`/`RENAME` on existing tables, H §5). The extraction in step 1 keeps one *protocol*; the ledger is chosen by served state, so exactly one writer owns each send.
- **In-app store — decided: base `internal_notifications`** (it already carries `delivery_status`/`delivery_attempts`, plus the push hook in `eventBus/initialize.ts` and read state). No receipt table.
- **Reply tokens — decided: no new table**; namespace + generation in `metadata`, version prefix in the token. Reopens only if a token must resolve to a *different* tenant than the sending one, which the qualified design forbids.
- **Escalation in-app notification shape — open (leaning: one notification per routing event, no digest).** Base's `NotificationAccumulator` (Redis, 30 s window) stays untouched for ticket-update accumulation; aggregating routing events would hide the "N awaiting your reply" signal L3b2 renders.
- **Rejection channel for a revoked token — open (leaning: one acknowledgement mail to the sender via the workspace's provider, no comment, no MSP copy).** H §2 L5 step 5 says "rejected visibly"; a silent drop fails that, an inbound error would loop.
- **Forced, not open**: no triggers on existing tables, no down-migration in prod (PLAN §3); the outbox decision is L4a's and already ratified (PLAN §6.2); the V2 consumer must not always start (T0 §4 #20).
