Reviewer question: "Can project statuses and tasks be reordered without unique-index
collisions or nested server actions, and are project events published only after commit?"

## Goal
Port the Co-Managed branch's project status and ordering fixes to main as one
standalone change. No feature flag, capability or migration.

## Outcomes
- Swapping two project statuses or two tasks never trips a unique-index collision.
- No server action calls another server action.
- The unauthenticated ordering endpoints are gone.
- Project events publish only after their transaction commits.

## 2. Divergence from reference
- Kept main's `getProjectTreeData` status-mapping self-heal. The manifest's "drop status-mapping seeding from tree read" hunk is not ported (DO-NOT-PORT #4).
- `reorderTask` and `reorderPhase` take the reference's in-transaction repair, but without `withCoManagedOperationalTransaction`. That is the co-managed coupling, and it is stripped.
- `projectTaskActions.ts` imports the module-level publishers under `…Now` aliases. The reference imports them unaliased, and that let a destructure of the wrong name publish inside the transaction in `addTaskResourceAction` and `moveTaskToPhase`.
- Not ported: `client-project-details.ts` and `projectBillingEngine.test.ts`. Their hunks (storage `persistRelatedRecords`, a `billing_work` union) do not support C4-C6 or S4.

## Release note
Project and project-task events (PROJECT_CREATED, PROJECT_UPDATED, PROJECT_DELETED, PROJECT_TASK_*) now publish after the writing transaction commits, never inside it. A rolled-back change no longer emits an event, and consumers always see committed rows.
