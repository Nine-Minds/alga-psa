# L9 — Customer-owned integrations (email, identity, directory)

Reviewer question: *Can the customer run its own mail and sign-in without touching, or reaching, the MSP's integrations?*

Base: `origin/main` @ `058d45c388` · Reference: `feature/co-managed-it` @ `2d00cb6f0e` · Remote card host (X670E) — no worktree on this host · Card `33833ced`, wave 3, hard parent L1a, rebase after T0-5.

## Intent

A co-managed customer workspace must be self-sufficient for the two integrations that decide whether the workspace can operate at all: the mailbox its requesters write to, and the identity its staff sign in with. Today both are MSP-owned in one way or another — email provider credentials are edited at `/msp/settings/integrations`, which the product boundary closes for any non-PSA product, and staff sign-in is only reachable through the MSP's SSO application. This card gives the customer a provider surface that is *the same PSA workbench* (no fork, no second credential store), lets the customer's own Google/Microsoft application be used for its staff and its mail, and keeps every other integration family — RMM, accounting, payments — closed to that workspace. The MSP's own provider settings are untouched.

## What changes

**1. One product-neutral entry path instead of a hardcoded route.** `PROVIDER_SETUP_ENTRY_PATH` (and `MAILBOX_SETUP_ENTRY_PATH`) in `@alga-psa/types`, resolved by product code. Reason: base hardcodes `/msp/settings/integrations?category=providers` in `packages/integrations/src/components/email/EmailProviderConfiguration.tsx:589` and twice in `MicrosoftProviderForm.tsx` (verified in base) — a URL that is `not_found` for `co_managed`. Replace the three literals; do not add a second component.

**2. The provider surface — `server/src/app/msp/co-management/providers/page.tsx` (new) + `server/src/components/co-managed/CoManagedProviderSetup.tsx` (new).** A thin shell (back link, heading, card) around the existing `ProviderCredentialsWorkbench` (`packages/integrations/src/components/settings/integrations/ProviderCredentialsWorkbench.tsx`, verified in base). No persistence, no relaxed guard: RBAC stays `system_settings:update` inside the provider actions, tenant ownership and secret redaction stay the actions' own. **This route must call the L0 serving adapter** (`serves`/`withCapability`, `notFound` when unserved): H §5's gate-coverage contract matches `app/msp/co-man*` by AST. The reference page deliberately omits the boundary with a long comment; that comment is not authoritative — the gate is.

**3. The allow/deny matrix, expressed in the registry that already exists.** `server/src/lib/productSurfaceRegistry.ts` (verified in base) types every rule as `Record<ProductCode, …>`, and `PRODUCT_CODES` is `['psa','algadesk']` (`packages/types/src/constants/productCodes.ts`). Adding `co_managed` (L0a) makes the compiler demand a decision per rule; L9 states it: `/msp/co-management/providers` allowed; `/msp/settings/integrations`, `/msp/integrations` and every `category=` under them (`rmm`, `accounting`, `payment*`) `not_found`. The matrix is asserted as data (a table test), not prose.

**4. Identity: the customer's own OIDC application.** `packages/auth/src/lib/nextAuthOptions.ts` — take **only** the `product_code` typing hunk: import `ProductCode`, widen `TenantSubscriptionInfo.product_code`, and stop collapsing the tenant row with `tenantRecord?.product_code === 'algadesk' ? 'algadesk' : 'psa'` (base, `fetchTenantSubscriptionInfo`) so a co-managed tenant is not reported as `psa` on its session. Do **not** take the adjacent `resolveSelfHostEffectiveTier`/`resolveTenantTier` hunks in the same diff: they return `'essentials'` on any error (DO-NOT-PORT #14). `ee/server/src/lib/actions/auth/ssoPreferences.ts` + `ConnectSsoClient.tsx`/`ConnectSsoWrapper.tsx` — `canConfigureSsoProvidersAction` (`hasPermission(user,'system_settings','update')`) so the profile offers "set up your provider" instead of "ask your administrator", linking through `PROVIDER_SETUP_ENTRY_PATH`.

**5. Evidence-grade OIDC without a live Entra tenant.** `packages/auth/src/lib/sso/microsoftSsoEmulator.ts` — replace the hand-rolled OAuth branch with signed OIDC via `buildMicrosoftSsoEmulatorProvider`, and add `packages/emulators/msgraph/src/entraOidc.ts` + `wire.ts` discovery/JWKS/token endpoints. Base already has the deny-by-default gate (`isMicrosoftSsoEmulatorEnabled`, production hard-locked; verified in base), so this only changes the *shape* of the simulated provider to signed OIDC with `state`/`pkce`/`nonce`, which is what the guide's step 3 needs.

**6. Order of work.** (a) types constants + registry matrix + route + shell ⇒ matrix test and gate-coverage green; (b) entry-path literals; (c) `product_code` typing hunk + its contract test; (d) profile "configure providers" affordance; (e) emulator OIDC; (f) fixture slice `scripts/dev/co-managed-fixtures/l9.ts` declaring `requires: ['l1a']`; (g) guide.

**7. What the guide actually shows** (mapping to H §2 L9's seven steps, so the fixture is built once): step 1 the matrix — Google and Microsoft offered, RMM/accounting/payment absent because the integrations root is not-found; step 2 credentials entered in the shared workbench; step 3 staff OIDC lands in the customer workspace (the emulator's signed token, `aud` = the tenant's client id); step 4 an inbound message becomes a customer-owned ticket, MSP queue unchanged unless escalated (L5's routing decides that, L9 only proves the mailbox is the customer's); step 5 a requester-audience reply leaves through the customer's provider (headers prove it); step 6 credential revocation surfaces a visible failure in the provider list; step 7 the MSP's own settings are byte-identical before and after. Chapter 0 (Kansas, flag off) and chapter N (`FORCE_CAPABILITIES=co-managed:off` ⇒ `/msp/co-management/providers` not-found with data intact) close it.

## Boundaries

- **No directory provisioning or sync.** Drop the `ee/server/src/lib/scim/service.ts` hunks (`lockCoManagedSeatScope`/`assertCoManagedSeatAdmission`) even though the manifest lists them: H §2 L9 acceptance says "**Excluded:** directory provisioning and sync (no customer entry point exists; deferred)", and PLAN §6.4 lists directory/SCIM sync as scope kept but built last and splittable. If SCIM later ships, it is its own card registering into L1a's admission primitive.
- **L1a owns seat admission.** `packages/users/src/lib/internalUserLicenseGuard.ts` (verified in base; branch adds the `product_code === 'co_managed'` branch to `assertCoManagedSeatAdmission`). L9 adds no admission code; step 3 demonstrates that a staff user admitted under L1a lands in the *customer* workspace.
- **L0a owns the gate, middleware and product-surface registry shape**; L9 fills in one rule and one adapter call, and never uses raw `useFeatureFlag('release-v2-0-feature')`.
- **T0-5 owns sign-in correctness** (O1, O7, O8, O9, O10) — including the O9 `nonce` fix that this card's emulator must remain compatible with by working through `buildAzureADProvider`, not around it.
- **L5 owns requester email delivery**; L9 proves the customer's *provider* carries it (step 5 headers), not the delivery pipeline.
- **L8a/L8b own commercial entitlement**; L9 grants no capacity and reads no pool.
- **Not ported**: the `resolveSelfHostEffectiveTier` rewrite (#14), `next.config.mjs` dev-origin assertion (#23), any `assertPsaOnlyTenantAccess`-style product shutdown of AlgaDesk (#21).

## Acceptance

- **A1 Allow/deny matrix** (table test over `MSP_ROUTE_RULES`): for `co_managed` — providers `allowed`; integrations root, `category=rmm|accounting|payment*` `not_found`. For `psa` unchanged; for `algadesk` unchanged.
- **A2 Gate coverage**: `app/msp/co-management/providers` calls an L0 adapter (AST pass); closed state renders not-found with data intact.
- **A3 OIDC tenant routing**: `nextAuthOptions.productCodeMapping.test.ts` and `mspContract.test.ts` green; a co-managed tenant's session reports `product_code: 'co_managed'`, not `psa`, and lands on the customer workspace, never the MSP shell.
- **A4 Seat admission on SSO**: the staff user admitted under L1a signs in; seat count is unchanged by sign-in (sign-in must not consume a second seat) and an over-allocation is refused at creation, not at login.
- **A5 Provider-neutrality for the MSP**: `MicrosoftIntegrationSettings.contract.test.tsx` and `providersFirst` tests green; MR's `/msp/settings/integrations` shows the same providers before and after.
- **A6 Evidence**: H §2 L9 recorded steps 1–7, with the OIDC emulator and GreenMail. Directory sync is not shown (excluded).
- **No migrations in this card** (manifest carries none) — the expand-only and schema-absent gates are trivially satisfied; say that in the PR rather than leaving it implicit.

## Risks

- **The new route becomes an ungated door.** A co-management route that renders for any tenant exposes the workbench (harmless for `psa`, wrong for `algadesk`). Mitigation: A2 plus the existing `not_found` rule for `algadesk`.
- **Two entry paths drift.** If `PROVIDER_SETUP_ENTRY_PATH` is added but the old literal survives somewhere, co-managed users hit a 404 from a link. Mitigation: grep-based contract test that the literal `/msp/settings/integrations?category=providers` appears nowhere in `packages/integrations` client components.
- **`product_code` widening leaks.** Widening the session's product code touches tier/licence presentation. Mitigation: only the typing and passthrough hunk; the licensing hunks are refused with citation, and `sessionExpiry`/`mspContract` tests must pass without re-baselining.
- **Emulator reaches production.** The gate is deny-by-default and hard-locked on `NODE_ENV=production` (verified in base), but a signed-OIDC emulator is a bigger surface than the old profile-fetch branch. Mitigation: keep the gate function exactly as-is, add a test that production + `MICROSOFT_SSO_EMULATOR_MODE=true` still returns false, and pin `iss`/`aud` to the simulator issuer.
- **Production flag-on without a real app registration** shows a workbench that cannot complete consent. Mitigation: H §2 L9 deployment — flag-on waits for a real app registration; the guide runs in the test app only.

## Open design choices

- **Where the entry path is resolved (open, leaning a typed constant + server-side product lookup).** A constant in `@alga-psa/types` keeps client bundles free of server code; the alternative is a compute-on-render link prop threaded down. Leaning constant, because four call sites need it and a prop would be re-plumbed per surface.
- **Whether the provider route reuses `/msp/settings/email` chrome (open, leaning no).** The shell is 20 lines; reusing the email settings page would drag the denied integration categories into a `co_managed` render path.
- **Emulator OIDC token lifetime/claims (open).** Leaning: one 5-minute token, `aud` = the tenant's configured client id, no refresh, so the guide cannot accidentally prove a path production does not have.
- **Forced, not open:** the gate adapter on the new route (H §5); no SCIM (H §2 L9 excluded, PLAN §6.4); only the `product_code` hunk from `nextAuthOptions` (#14); no new credential store — the workbench and its actions are the ones PSA uses.
