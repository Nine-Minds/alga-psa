## Repair round findings

- `ticketRecordAuthorization.ts` now owns the authorization context and shared SQL compiler call used by both optimized ticket lists and search. Search resolves that context once, compiles the ticket and live-comment-parent predicates, and uses the same predicate for exact type counts and cursor pages.
- Supported ticket/comment policies bypass the candidate scan. Other object types continue through their existing verifier and are merged with the direct ticket page. Unsupported ticket rules batch-load source rows and reuse the request context with the record evaluator. Resolution failures deny ticket and comment hits.
- Production-schema PostgreSQL regressions call the real principal resolver, shared compiler, ticket evaluator, bundle resolver and search request path. They compare unrestricted/restrictive decisions, exercise live ticket/comment parents, requester audience, deleted/scheduled comments, cross-tenant comments, mixed search types, unsupported constraints, and resolver failure. The 100-result public limit regression follows 205 mixed rows over 100/100/5 results and terminates its stable cursor.
- The reproducible production-path benchmark runs the real resolver, SQL compiler, and baseline evaluator against production `tickets` UUID columns and `app_search_index`: baseline `5cdc72b0d450943c6b92b0f7fb856920f89e44e7` and revised implementation, PostgreSQL 15.4, 500 matches (50 readable, 450 denied), one warmup, five measured samples, concurrency 1. It counts all Knex query events during the request. A second compiled-path measurement increases matches from 150 to 500 and verifies the request SQL count stays bounded.
- Repair round commit `86abc71008a370b0765ac850fb8642ea48daa953` closes the mixed-search gap. It compiles project, phase, task, task-comment, document, workflow-task and status verifier semantics into the same SQL path used for pages and exact counts, and directly admits types that only rely on existing index ACL metadata. Custom registered verifiers without a compiled predicate still scan in batches and deny on verifier failure.
- The identical mixed PostgreSQL benchmark harness was executed against baseline `bdca35983cc22c75f9b07ffd797aedc8463b2129` and repair `86abc71008a370b0765ac850fb8642ea48daa953`: PostgreSQL 15.4, 500 tickets, 50 comments, 500 projects, and one stale project index row; concurrency 1, one warmup, five measured requests. Mixed page SQL fell from 516/517 statements to 9/10. Project growth from 150 to 500 matched source records increased baseline statements from 160 to 515; repaired requests stayed at 10. See [benchmark.md](evidence/benchmark.md#mixed-search-repair-round) for raw samples and commands, and [review-guide.md](evidence/review-guide.md) for reviewer checks.
- Follow-up document-search repair: the built-in document verifier is now registered with an equivalent tenant-scoped SQL compiler. It requires a live source document, and for scoped principals uses `NOT EXISTS` over client associations to deny if any linked client is outside scope. Its UUID cast is guarded on the index value so the source UUID column remains indexable. The compiler is attached to the verifier registration; replacing the verifier without a compiler drops the built-in predicate and correctly uses fallback. The production-path harness measures 150/500/1,500 candidates for internal and client-portal contexts across typeahead and full search; statement counts remain 10/10/10 internally and 3/3/3 for the portal, with zero standalone document/association verifier SELECTs. Full result walks terminate with exact totals. See the repaired section in [benchmark.md](evidence/benchmark.md#repaired-sql-filtered-document-search-at-150-500-and-1500-candidates).
