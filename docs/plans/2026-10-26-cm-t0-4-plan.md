### S1 — document-content IDOR

**Site.** `server/src/app/api/documents/[documentId]/content/route.ts:68-74` (the only check is `hasPermission(user,'document','read')`)
then `:79-100` reads `documents`, `document_block_content` and `document_content` by raw id and `:151-189` returns them.

**Wrong behaviour.** `document:read` is a *type* permission, not an instance permission. Any authenticated tenant user — including a
client-portal user of another client — can fetch the block/text body of any document in the tenant by guessing or replaying a
`documentId`. The route never consults the document authorization kernel that every other document path already uses.

**Minimal correct check.** Resolve the document through the existing shared engine before reading anything:

```ts
const authorizedDocument = await withTransaction(knex, (trx: Knex.Transaction) =>
  getAuthorizedDocumentById(trx, tenantId as string, currentUser as any, documentId));
if (!authorizedDocument) {
  return NextResponse.json({ error: 'Document not found' }, { status: 404 });
}
```

`getAuthorizedDocumentById` already exists on main (`packages/documents/src/actions/documentActions.ts:320-336`) and runs
`authorizeAndRedactDocuments`, so client visibility, `same_client`, user/team assignment, and comment-attachment lifecycle all apply.
Imports added: `withTransaction` from `@alga-psa/db`, `Knex` type, `getAuthorizedDocumentById` from
`@alga-psa/documents/actions/documentActions`. 404 (not 403) is deliberate: the caller must not learn the id exists.

The response is then built from `authorizedDocument` rather than by re-reading `documents`. The kernel deletes each field in
`decision.redactedFields` from the record it returns, so the route serves only what the decision leaves in place. Document metadata
is projected from the authorized record, so a redacted metadata field is absent. The block and text bodies are the document's
`content` field, so they are read only when `content` survives redaction; otherwise the content section comes back empty. The
download hint follows `file_id` the same way.

**Regression test.** New `server/src/test/integration/documentContentAuthorization.integration.test.ts`, harness modelled on
`clientPortalDocuments.integration.test.ts` (`createTenant`/`createClient`/`createUser`, `setupCommonMocks`, mocked
`server/src/lib/db` `createTenantKnex`):
1. client-portal user of client A requests a `is_client_visible` document associated with client B → **404**, body has no
   `SECRET-CONTENT`;
2. client-portal user requests a `is_client_visible=false` document → **404**;
3. positive control: the document's own client and an internal technician → **200** with `SECRET-CONTENT` (proves the denies are
   not a harness artefact);
4. `is_client_visible=true` document the client created itself (no associations) stays readable via the `own` rule (no over-blocking). A visible document with no association and a different creator is denied to clients by the existing kernel (`own`/`same_client`), unchanged by this card.

5. a kernel decision that carries `redactedFields: ['content','document_name','mime_type']` (bundle rule resolver stubbed at
   `resolveBundleNarrowingRulesForEvaluation`, so the real kernel produces the redaction) → **200**, and the body has no
   `SECRET-CONTENT`, name or MIME type. Control: redacting only `document_name` still serves the content.

Red on main: cases 1 and 2 return 200 with the block content; case 3/4 pass on both. Case 5 is red on any route that re-reads raw
rows after authorizing (including this branch's first cut, `04bf106afc`). Green on the PR: 404/404/200/200/200.

**Residual risk.** The authorization decision and the content reads are in different transactions, so a permission revoked between
them is still served once (bounded by one request). The route still accepts an API key (`:44-58`) — the API-key user is now
authorized as that user, which is the intent, but an API key minted for a client-portal contact is still refused earlier by
`assertInternalApiUser`. Withdrawn *comment attachments* are covered as far as `canReadCommentAttachment` is consulted by the
kernel; the full attachment sweep belongs to the attachment card.

### S3 — RBAC request-cache key is not principal-qualified

**Site.** `packages/authorization/src/kernel/engine.ts:50-53`.

**Wrong behaviour.** The request-local cache key is
`` `rbac:${input.subject.userId}:${input.resource.type}:${input.resource.action}` ``. A consolidated request that evaluates several
principals (a different tenant, a different `userType`, `apiKeyId`, `agentId`, or `roleIds` for the same `userId`) reuses the first
principal's grant or denial for the rest. One principal per request is the norm today, so this is latent — but it is exactly the
shape a cross-workspace leak takes.

**Minimal correct check.** Qualify the key with the whole subject:

```ts
`rbac:${JSON.stringify([input.subject, input.resource.type, input.resource.action])}`
```

Two comments explaining why, as on the reference.

**Regression test.** New `packages/authorization/src/__tests__/kernel.tenantCache.test.ts` (ported verbatim, no co-managed coupling):
- `it.each(['grant-first','deny-first'])`: one `userId` in two tenants, `rbacEvaluator` grants only the `msp` tenant; each tenant's
  `authorizeResource` **and** `authorizeMutation` must return its own answer and the evaluator must run exactly twice. Red on main:
  the second tenant reuses the first decision (one call).
- `it.each` over `{userType:'client'}`, `{apiKeyId}`, `{subjectType:'agent',agentId}`, `{roleIds}`: decision must not be reused when
  the principal context changes. Red on main for every case.

**Residual risk.** `JSON.stringify` of the subject is insertion-order sensitive: two logically identical subjects built differently
now miss the cache. That errs toward extra RBAC queries, never toward a leaked grant. Do not "fix" it by sorting later without a
test; if the extra queries ever matter, the key should become an explicit canonical join of the principal fields.

### S4 — orphaned unauthenticated ordering endpoints

**Sites.** `packages/projects/src/lib/orderingService.ts:18-39` (`reorderProjectTask`) and `:44-63` (`reorderProjectPhase`) — `'use server'`
exports wrapped in `withAuth` that take `_user` and write `project_tasks` / `project_phases` with **no permission check and no
`project_task:update` gate**; `server/src/lib/services/orderingService.ts:55-73` and `:75-91` — static methods that do the same writes
using the *ambient* tenant from `createTenantKnex()` with no caller at all.

**Wrong behaviour.** A Next.js `'use server'` export is a network endpoint. `withAuth` only proves *someone* is signed in; the module
performs a cross-task/cross-phase reorder for any internal or portal session, and rewrites `project_status_mapping_id` as a side
effect. The static class methods are unreachable but stay compiled, tenant-context-dependent and free for the next caller to use.
Nothing imports `packages/projects/src/lib/orderingService.ts` (`grep -rn "lib/orderingService" packages/ server/` finds it only as
itself). The only importer of the server file is `server/src/lib/api/services/ProjectService.ts:45`, which uses **only**
`generateKeyForPosition` (`:592, :601, :755, :764`) — never the `reorder*` methods.

**Minimal correct check.** Delete, do not gate. `packages/projects/src/lib/orderingService.ts` goes entirely. In
`server/src/lib/services/orderingService.ts` remove `reorderProjectTask` and `reorderProjectPhase` and keep
`generateInitialKeys`/`generateKeyForPosition` (pure, no DB, used by `ProjectService`). The real, authorized reorder paths are
`projectTaskActions.reorderTask` / `projectActions.reorderPhase` (C5's card).

**Regression test.** New `packages/projects/tests/orderingServiceAuthorization.contract.test.ts` (source-reading contract test, same
shape as `packages/documents/tests/documentContent.authorization.contract.test.ts`):
- `expect(existsSync('packages/projects/src/lib/orderingService.ts')).toBe(false)`;
- the server file's source contains no `reorderProjectTask`, no `reorderProjectPhase`, and no `tenantDb(...).table('project_Tasks'|'project_phases')`
  write;
- positive guard: it still exports `generateKeyForPosition` and `generateInitialKeys`, and `ProjectService.ts` still imports them —
  so a future "cleanup" cannot delete the helpers.

Red on main: the first three assertions fail (both files still exist with both write methods).

**Residual risk.** Deleting a `'use server'` export is invisible to a build; the contract test is the only thing that keeps it gone.
Any already-built client bundle that imported it (none in this repo) would 500. The authorized reorder paths still lack the
cross-phase neighbour check — that is C5, a different card.

### S5 — comment update/delete authorship + field whitelist (+ the `TICKET_COMMENT_UPDATED` guard)

**Site.** `packages/tickets/src/actions/comment-actions/commentActions.ts`
- `:556-591` — the author check only fires `if (comment.user_id && …)`, i.e. only when the **request body** carries `user_id`, and it
  then looks up *that* user's `user_type`; `:615-620` spreads the whole request body into `Comment.update`;
- `:645-676` — `TICKET_COMMENT_UPDATED` is published only `if (updatedComment && comment.user_id && …)`, so once the body-supplied
  `user_id` stops being trusted the event silently stops (port hazard R4);
- `:731-741` — `deleteComment` checks only `is_system_generated`; any session can delete any comment.

**Wrong behaviour.** `updateComment(id, {note})` — no `user_id` in the body — passes the authorship check unconditionally, and the
spread also lets the caller rewrite `created_at`, `user_id`, `author_type`, `deleted_at` and `publish_state` (the model strips only
`bundle_mirror_source`, see `packages/tickets/src/models/comment.ts:283-290`). `deleteComment(id)` needs no claim at all. The UI
restricts all of this; the server does not. The REST path already gets it right
(`server/src/lib/api/services/TicketService.ts:2864-2900`: author, or author-less comment plus `ticket:update`, and a
`note`/`updated_at`-only update) — this item makes the action match the already-correct REST rule.

**Minimal correct check.** One helper, used by both actions:

```ts
async function assertMayChangeComment(trx: Knex.Transaction, user: { user_id: string; user_type: string }, existing: IComment): Promise<void> {
  if (existing.user_id === user.user_id) return;
  if (existing.user_id == null && isMspPrincipalUserType(user.user_type)
      && await hasPermission(user as any, 'ticket', 'update', trx)) return;
  throw new Error('You can only edit your own comments');
}
```

`updateComment`: call it right after the system-generated check, then build the patch explicitly —
`note`, `is_resolution`, and `is_internal` **only when the caller is an internal principal**; delete the old `:556-591` block and the
old `is_internal` validation. The new rule replaces it: a non-MSP caller who submits an `is_internal` that differs from the stored
value is refused with main's own `'Only MSP users can set comments as internal'`. Resubmitting the unchanged value is accepted, as
on main.
`deleteComment`: after `:741`, `if (existingComment) await assertMayChangeComment(trx, user, existingComment);`.
`TICKET_COMMENT_UPDATED`: change the guard to `if (updatedComment && commentTenant)` and resolve the actor as
`.where({ user_id: comment.user_id ?? updatedComment.user_id ?? user.user_id })` and `userId: user.user_id` in the payload;
keep main's `try/catch` and `publishEvent` (do not adopt the reference's `publishNativeCommentEvent`). Keep main's post-commit
`TICKET_COMMENT_DELETED` publish in `deleteComment` and keep `withdrawCommentAttachments` in `cancelScheduledComment`
(DO-NOT-PORT 6).

**Regression test.** New case in `server/src/test/integration/commentActionsThreading.integration.test.ts` (ported from the
reference, +43 lines), no co-managed coupling:
1. a different internal user calls `updateComment(id,{note})` → resolves to `{actionError:'You can only edit your own comments'}` and
   the stored note is unchanged; the same for `deleteComment(id)`;
2. the author calls `updateComment` with smuggled `created_at`, `user_id`, `deleted_at`, `publish_state` → note changes, everything
   else does not;
3. a comment with `user_id = NULL` (inbound email) is editable by an internal user;
4. **the same squash:** the author's edit publishes `TICKET_COMMENT_UPDATED` with `payload.userId === author.user_id` — this is the
   assertion that catches a port of `cac0f6d556` without the guard hunk;
5. deny side of case 3: with `hasPermission` answering false for `ticket:update`, a different internal user is refused on both
   `updateComment` and `deleteComment` for an author-less comment, and the comment is unchanged. This is red if the guard falls back
   to "any internal user";
6. a client user who submits `is_internal: true` on their own comment gets `{actionError:'Only MSP users can set comments as
   internal'}` and the stored flag stays false. Control: the same client resubmitting `is_internal: false` with a text edit is
   accepted.

Red on main: 1 succeeds (and deletes), 2 rewrites `user_id`/`created_at`, 4 publishes nothing. Green on the PR: all six.
Existing T027/T028 in that file are the positive control that ordinary comment creation still works.

**Residual risk.** Internal users lose the ability to edit a colleague's comment (the reference keeps the same narrowing; the UI
already forbids it). Comments authored by a `service` principal count as "internal" for the author-less repair path. The REST
`PUT /api/v1/tickets/[id]/comments/[commentId]` path already enforces the rule but does **not** publish `TICKET_COMMENT_UPDATED`;
that pre-existing gap is out of scope. Mobile comment edit goes through the REST path, so it inherits the rule.

### S6 — project task comments have no read permission

**Site.** `packages/projects/src/actions/projectTaskCommentActions.ts:101-114` — `getTaskComments(_user, {tenant}, taskId)` passes `_user`
and calls `listTaskCommentsWithDb`. The sibling read actions in the same file already gate (`:162-164` `getTaskCommentCount`,
`:186-188` `getTaskCommentCountsBatch`).

**Wrong behaviour.** Any authenticated session in the tenant can read every comment — including internal-only discussion — of any
project task by id, with no `project_task:read`.

**Minimal correct check.** Mirror the sibling exactly:

```ts
if (!await hasPermission(user, 'project_task', 'read')) {
  throw new Error('Permission denied: cannot read task comments');
}
```

Rename `_user` → `user`. Do **not** port the branch's `withTaskCommentAccess` (it caps at 1000 ids and breaks board comment counts,
DO-NOT-PORT 18).

**Regression test.** New `packages/projects/tests/taskCommentReadAuthorization.test.ts` (unit, no DB): mock `@alga-psa/auth` `withAuth`,
`@alga-psa/auth/rbac` `hasPermission`, `@alga-psa/db` `createTenantKnex`, and `../src/lib/taskComments/taskCommentService`
`listTaskCommentsWithDb`.
1. `hasPermission → false` ⇒ resolves to a `permissionError`, and `listTaskCommentsWithDb` never called;
2. `hasPermission → true`, called with `('project_task','read')` ⇒ the service result is returned.

Red on main: case 1 returns the comment list and calls the service. Green on the PR: 1 errors, 2 unchanged.
Control: `projectTaskCommentThreading.integration.test.ts` T026 must stay green (its user has the permission).

**Residual risk.** One permission for all task comments: there is no per-task or per-client narrowing, so a user with
`project_task:read` for one client can read any task's comments in the tenant. Per-task scoping is a product change, not a fix.

### S7 — file download runs outside the tenant context

**Site.** `server/src/app/api/files/[fileId]/download/route.ts:39` — `StorageService.downloadFile(fileId)`.

**Wrong behaviour.** The route authorizes the document in the session tenant (`:24-37`), then calls
`StorageService.downloadFile`, which internally calls `createTenantKnex()` **with no tenant**
(`packages/storage/src/StorageService.ts:428`) and resolves the file record and storage provider from ambient context. Inside a
request that context is whatever the middleware left behind (or nothing), so the read is not pinned to the tenant that was
authorized: it fails, or — the dangerous case — resolves against another tenant's context left on the async chain.

**Minimal correct check.**

```ts
const result = await runWithTenant(tenant, () => StorageService.downloadFile(fileId));
```

`runWithTenant` is already available from `@alga-psa/db`; the import at `:6` gains it. Nothing else changes: the authorization in
`:24-37` stays as is.

**Regression test.** New `server/src/test/unit/api/fileDownloadTenantContext.test.ts` (ported verbatim): mocks `@alga-psa/db` with an
`AsyncLocalStorage`-backed `runWithTenant`, and the storage mock throws unless `tenantContext.getStore()` is the authenticated
tenant.
1. a request made from an unrelated ambient context (`tenantContext.run('unrelated-request', …)`) returns 200 with the bytes, the
   store is restored to `'unrelated-request'` afterwards, and `downloadFile` is called once with the file id;
2. unauthenticated ⇒ 401, missing document ⇒ 404, not permitted ⇒ 404, and storage is never touched in any of them.

Red on main: `downloadFile` throws `tenant context not found` ⇒ 500 (and case 2's "storage not called" still passes, which is why
case 1 is the discriminating one). Green on the PR: 200 + byte-for-byte body.

**Residual risk.** `StorageService.downloadFile` remains ambient-context-dependent; this route now supplies the context, but any
future caller can repeat the mistake. Guarding that belongs at the storage layer (pass the tenant explicitly), which is out of this
card. Authorization still uses `canAccessDocument` rather than the kernel — a narrower check than S1's, unchanged here by design.

## Risks

1. **A too-narrow author check breaks support workflows.** Internal users can no longer edit a colleague's comment; the UI already
   forbids it, but the ticket screen is a hot path. Mitigated by the positive control in A4 and by matching the REST rule that
   already ships. Watch: no new `actionError` rates on comment update after deploy.
2. **R4 port hazard.** Porting `cac0f6d556` without the guard-removal hunk silently stops `TICKET_COMMENT_UPDATED` (no edit
   notifications, no search reindex). A4 case 4 fails loudly if the hunk is dropped — it must be in the *same squash*.
3. **The content route's new 404 is customer-visible.** Any client that relied on `document:read` alone (e.g. a script hitting the
   content endpoint for a document it never legitimately had) starts failing. That is the intent; call it out in the release note.
4. **Deleting a `'use server'` module is invisible to the compiler.** Only A3 keeps it gone; if A3 is ever relaxed, the endpoint is
   back with the next `git restore`.
5. **Cache-key format change is a behaviour edge.** It can only add RBAC evaluations, never remove one, but a caller that relied on
   request-local reuse across different subjects will now be slower — intended.
6. **Still not authorized after this card:** per-task/per-client comment scoping (S6), attachment-state sweeps on every download
   route (S1 covers only the content route's own read), the `cancel-tracking` endpoint, REST comment-edit notifications, storage's
   ambient tenant dependency, and all S-hold items (portal `contact_visibility`, licence `aud` binding, MCP OIDC).
