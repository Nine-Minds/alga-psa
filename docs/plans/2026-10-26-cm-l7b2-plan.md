# CM L7b2 — Portable restore (design session plan)

Card `df290180-b686-46c1-a16f-b5b96361544a` · wave 6 · hard parent merged: L7b1 · soft: L5.
Reviewer question: "Can an exported workspace be restored into a fresh tenant?"
Authority: `~/cm-redelivery/PLAN.md` §2–3, §5 and `manifests/L7b2.md` win over this plan.

## 1. Intent

L7b1 makes a workspace exportable as a signed, passphrase-protected archive. This card is the other half: take that archive
and reconstitute a working tenant — records, attachment bytes, credential secrets — into an installation that has no prior
co-managed state, and prove the result is a normal tenant whose tickets, files and users open. It is deliberately a
one-way, offline, operator-run path (`server/scripts/restore-portable-workspace.ts`), not a UI and not an activation
workflow: nothing in the product links to it, so a restore can never be triggered from a tenant that is still live.

## 2. What changes

Ordered; each step depends on the one above.

1. **Migrations** (three, re-dated past main's newest; guard with `hasTable`/`IF NOT EXISTS`, no triggers, no backfills):
   - `*_create_portable_restore_suspensions.cjs` — the durable marker that a tenant is mid-restore, so background intake and
     workers do not write into a half-populated workspace.
   - `*_create_portable_workspace_restores.cjs` — one receipt per restore attempt; the idempotency key.
   - `*_create_portable_workspace_restore_uploads.cjs` — upload/promotion attempts with their outcome, for cleanup and audit.
   All three are new co-managed tables and must be added to the L0 tenant-deletion/export table manifest (gate: manifest
   coverage) and registered as tenant-scoped in `packages/db/src/lib/tenantTableMetadata.ts`.
2. **Records and database restore**: `packages/co-managed/src/portableWorkspaceRestoreFiles.ts` (archive layout, manifest
   verification, per-file classification) and `ee/server/src/lib/co-managed/portableWorkspaceRestoreDatabase.ts` (ordered
   inserts in FK-safe order, tenant rewrite of every row, sequence/identity and citation-safe idempotency). EE-only because
   it drives the EE database helpers.
3. **Bytes and uploads**: `packages/co-managed/src/portableRestoreUploads.ts` (stage → verify hash → promote into the
   storage provider), `ee/server/src/lib/co-managed/portableWorkspaceRestoreUploads.ts` (3-line EE shim that injects the EE
   storage provider). Staging happens before promotion so a failed restore leaves no half-visible file.
4. **Secrets**: `ee/server/src/lib/co-managed/portableWorkspaceRestoreVault.ts` — decrypt the archive's secret section with
   the operator passphrase, re-wrap into this installation's secret store via `@alga-psa/core/secrets`. Never write a
   decrypted secret to a log, temp file or error message; never accept a passphrase from argv (stdin or env only).
5. **Identity and authority**: `packages/co-managed/src/portableRestoreInstallationAuthority.ts` +
   `ee/server/src/lib/co-managed/portableRestoreInstallationAuthority.ts` — refuse if the target installation already holds a
   co-managed relationship, entitlement or restore receipt for that workspace, so a restore cannot overwrite live state.
6. **Operator entry point**: `server/scripts/restore-portable-workspace.ts` (`--inspect` prints the manifest and exclusions;
   `--apply` performs the restore; `--resume` re-runs from the receipt). Matches the surrounding script style in
   `server/scripts/` (`create-tenant.ts`, `rollback-tenant.ts`).
7. **Job and startup wiring, last** (both files are shared hot seams — hunk-level only):
   - L0b registers the cleanup job as data in `server/src/lib/jobs/portableRestoreJobs.ts`; startup scheduling stays dark
     until restore upload rows exist and the co-managed capability is not forced off.
   - `packages/jobs/src/lib/handlers/portableRestoreUploadCleanupHandler.ts` performs the expiry sweep and refuses before
     SQL when the kill switch is off. Worker boot remains isolated from the optional co-managed package.

## 3. Boundaries

- **The export side** — archive format, contributor registry, what is included/excluded: L7b1 (hard parent; PLAN §5 "export
  contributor registry" is its seam). This card consumes the format; it must not change it.
- **Activation, billing and the customer-facing "restored workspace" purchase**: L8b (card description: "OUT OF SCOPE …
  Activation billing (L8b)"). No activation wizard exists and none is built here (H §2 L7 excluded list).
- **Per-domain exporters** (time, schedule, meetings, conversations, documents): L7b3.
- **Relationship closure / departure before a restore**: L7a. This card never closes or opens a relationship.
- **`tenants_suspended_reason_check`**: widened by L7a, not here (see R2).
- **Any evidence/ledger machinery**: excluded by PLAN §1 and the card's rules.

## 5. Risks

- **R1 partial restore**: a crash between record insert and byte promotion leaves a tenant that looks restored. Mitigation:
  the suspension marker plus receipt state machine (`staged → promoted → verified`), and `--resume` keyed on the receipt;
  promotion after verification only.
- **R2 suspension surface**: if the suspension marker reuses `tenants.suspended_at` / `tenants_suspended_reason_check` it
  collides with L7a, which owns that CHECK widening (H §2 L7 deployment). Mitigation: a dedicated co-managed restore flag
  (see open choice), or coordinate the reason value list with L7a before writing the migration.
- **R3 tenancy rewrite**: every row's `tenant` must be rewritten to the target; a missed table silently leaks another
  workspace's data. Mitigation: the file list is driven by L7b1's contributor registry, and A2 asserts that the set of
  written tables equals the set in the archive manifest — not a hand-list.
- **R4 EE/CE parity**: four of the modules are under `ee/server`; the CE build must still boot. Guard the imports and let
  A7's boot-isolation gate prove it.
- **R5 `initializeApp.ts` is main-changed**: whole-file restore would revert main. Take only the recovery-start hunk with
  `git apply --3way` and reconcile.
- **R6 uploads staging size**: temp staging can fill a disk on a large export. Cap the staged bytes, document the cap in the
  charter (H §2 L7 asks for a documented cap) and let the cleanup handler reclaim stale staging.
- **R7 credentials**: an operator passphrase in argv lands in shell history and process lists. stdin/env only, and the CLI
  must refuse `--passphrase=`.

## 6. Open design choices

- **Restore target** (leaning: fresh installation with zero co-managed rows only). Reason: the archive carries ids; any
  existing row set invites merge semantics this card does not own.
- **Where the suspension marker lives** (leaning: a co-managed restore row, not `tenants.suspended_at`). Reason: R2, and a
  tenant suspension has product-wide meaning that a restore should not borrow.
- **Receipt granularity** (leaning: one receipt per (workspace, attempt), resume in place). Reason: idempotency proof for
  the acceptance bar without a new event log.
- **Decided, not open**: no activation UI (H §2 L7 excluded list); no checked-in archive fixtures (PLAN §1); the CLI is
  operator-only and hidden from the product surface registry.

## 7. Charter (H §4 template) — delivery record

**Question answered.** Can an L7b1 export be restored into a fresh installation? The isolated PostgreSQL and local-storage
round trip covers a ticket, a native file row and its bytes, deterministic identity remapping, uploader ownership, receipts,
idempotency and promotion recovery. Browser review remains a separate human step; this card does not record a walkthrough.

**Shipped dark.** Everything is behind `release-v2-0-feature` via the co-managed capability gate;
`FORCE_CAPABILITIES=co-managed:off` disables it (the CLI refuses before reading any secret). Flag off: no new hot-path queries,
nothing reachable from the UI. The only hot-path hunk is a guarded dynamic import in `server/src/lib/initializeApp.ts`.

**Migrations (expand-only, idempotent, no triggers, no backfills; after current main's `20261101120000`).**
- `20261102120000_create_portable_restore_suspensions`
- `20261102120100_create_portable_workspace_restores`
- `20261102120200_create_portable_workspace_restore_uploads`

All three are in `tenantTableMetadata.ts`, the L0 deletion manifest, tenant-scoped migration helper and temporal deletion
activity (current-main baseline 584 → 587).

**Staged-bytes cap.** Default 16 GiB (`PORTABLE_RESTORE_DEFAULT_STAGED_BYTES_CAP`), override `--max-staged-bytes`.
Checked at prepare and again before any provider write. Uploads are journaled with an attempt fence and a 35-minute expiry;
the sweeper job reclaims stale staging.

**§6 resolutions.**
- Restore target: fresh installation only (no rows in `co_management_relationships`, `co_managed_entitlements` or other tenants' receipts); otherwise refused. Installation authority = superuser or database owner.
- Suspension marker: dedicated `portable_restore_suspensions` table (`portable_restore_in_progress` → `portable_restore_pending_activation`). `tenants.suspended_at` and its CHECK are untouched.
- Receipt granularity: one receipt per (workspace, attempt), state `staged → promoted → verified`, resumed in place with `--resume`.

**Secrets.** Passphrase from stdin, hidden prompt or `ALGA_PORTABLE_RESTORE_PASSPHRASE` only (removed from `process.env` after
reading); `--passphrase=` is rejected; errors are bounded to a phase name. A wrong passphrase fails closed.

**Divergences from the reference / L7b1.**
- Additive `restorePortableCredentialVault` in `ee/server/src/lib/credentials/portable.ts`; the export side is unchanged.
- Restore is driven by the v2 manifest and a fail-closed `PortableRestoreProfile` registry. The merged L7b1 `files`
  contributor exports `external_files` plus blobs named `file:<file_id>`; L7b2 registers its production profile and binder.
  The binder reuses the deterministic remapped file identity and uploader reference, then promotes bytes through the native
  storage path. Document records and their links remain L7b3.
- The L0b job registry exists and is used (`defineJob`). Registration lives in `server/src/lib/jobs/portableRestoreJobs.ts`
  because a contract test forbids `@alga-psa/co-managed` imports under `packages/jobs/src`.

**Neutrality while dark (round 2).** The re-delivery PLAN (`~/cm-redelivery/PLAN.md`) states, line 64: "Flag off ⇒ no behaviour
change for any tenant. Flag on without entitlement ⇒ still none." and, line 59, adapters for "jobs (skip before SQL)". An
always-defined 15-minute system cron is a behaviour change on every installation (a scheduled row and a periodic run), so the
PLAN does not permit it. `registerPortableRestoreJobs` is therefore async and defines the job only when it is not forced off
(`forcedValue(FORCE_CAPABILITIES, 'co-managed')`) and `portable_workspace_restore_uploads` exists and holds at least one row.
Server startup registers the production descriptor before CE convergence; the EE Temporal scheduler process independently
registers the same shared schedule row before its convergence because its registry is process-local. Nothing is scheduled
while dark, and EE removes a previously persisted cleanup schedule when the journal is absent or the capability is forced off;
the startup cost is an existence/data probe in the process that owns the scheduler. The handler itself still skips
before SQL when forced off. The sweep appears on the first scheduler start after a restore has journaled bytes; until then an
abandoned attempt waits for that start (a resumed restore stages under a fresh attempt id and does not reclaim the old one).
The optional descriptor import and journal probe are failure-isolated: an error is reported but native CE and EE schedules
still converge. EE leaves a previously persisted restore schedule untouched when probe state is unknown; a later successful
probe can enable or remove it according to journal and kill-switch state.

Each upload attempt initializes `next_cleanup_at` to its fixed 35-minute expiry before any provider write. Cleanup also treats
legacy NULL deadlines as due, then rechecks expiry and native references while holding the tenant lock: an unexpired live
upload is deferred to its expiry, a referenced object is retained, and an expired unreferenced interrupted upload is deleted.
This lets maintenance recover both newly created attempts and rows left by the prior NULL-default behavior.

Scheduler regression coverage runs the full `ee/temporal-workflows/src/schedules/__tests__` suite, including cases where
the optional journal probe fails, and a CE behavioral test forces the optional descriptor import to fail while confirming
native convergence continues. The server and EE project typechecks pass. The offline webpack production build completes;
the Turbopack build path still reports its existing `@product/service-principals/entry` import-map resolution errors.

**Verification.** `server/src/test/integration/coManagedPortableRestoreRoundTrip.integration.test.ts` runs against the migrated
Postgres test database and isolated local storage. It uses the real L7b1 contributor registry, the production `files` exporter,
the production restore profile/binder, native SQL and a sealed archive created in the test. The test uses only the export
admission seam as a fixture because the same installation cannot both retain a source relationship and satisfy the fresh
installation guard; permission provisioning and `hasCoManagedLocalPermission` are real. One ordered scenario covers all three
migrations down/up/up; wrong passphrase and non-fresh refusal; real ticket and file export; matching source/destination bytes;
destination uploader and native metadata; no duplicate `external_files` rows; staging cap before provider writes; upload cleanup;
promotion failure rolling receipt, suspension and native rows back; successful apply and verified receipt; resumed verification
and idempotent apply/resume; and unchanged unrelated-tenant data.

Bugs this surfaced and fixed: (1) destination UUIDs were random per preparation, so a resumed restore wrote rows whose ids
disagreed with the administrator id already stored on the `staged` receipt; allocation is now a deterministic function of
(archive sha256, destination, stage, order). (2) The L7b1 work catalog selected four columns of `project_task_comments`
(`actor_reference_id`, `actor_display_name`, `actor_organization_name`, `collaboration_revision`) and a reference on them that no
migration creates, so the export failed on any real Postgres; the catalog and reference now match the schema (nothing consumed them).

The test fixture builds manifests directly from contributor-owned fixture records instead of invoking the production collector
with a fake actor/database. This keeps unit fixtures out of the parent's tenant authorization contract; the integration test
exercises the production files contributor and real local-permission lookup.

**Deploy-fix round (D1-D4).** Supersedes the round-2 text above where they differ. (D1) The CLI loads the EE restore modules with a dynamic
`import()`, and `ee/server/tsconfig.json` maps `@alga-psa/storage` to source (the package's exports are import-only), so the documented
command runs. (D2) `BaseStorageProvider.getLocationIdentity()` is implemented (sha256 of local resolved basePath, or s3 region/bucket/endpoint).
(D3) The remap references are the manifest's declared edges plus the destination's actual FKs between included tables (read by the same
metadata reader as the graph check); declared, external, polymorphic, conditional and qualified-actor columns always win. (D4) **Option (a):**
a brand-new destination gets no durable receipt or suspension until promotion: both are inserted inside the promotion transaction, as
`promoted`, so any failure before commit rolls them back; uploaded bytes are recovered by the journal and cleanup job. `staged` remains only
for receipts written by earlier builds (still resumable). Freshness is checked before bytes are staged and again inside promotion.
Verification counts now include rows projected into native tables (handoff history -> `ticket_audit_logs`).
