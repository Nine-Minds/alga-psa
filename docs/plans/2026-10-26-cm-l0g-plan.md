## 2. Decision 1 — `scripts/ci/migration-lint.mjs`: rules 1–8

**Engine.** Two layers. (a) JS structure via the TypeScript compiler API (`ts.createSourceFile` on each `.cjs`; `typescript` is already a root devDependency at `package.json:282`), which yields call expressions, object literals for `exports.config`, and `const` initialisers so `const TABLE = 'comments'` resolves. (b) A hand-rolled SQL statement splitter over every `knex.raw(<template>)` whose substitutions all resolve to literals; it must handle `$$...$$` dollar quoting (used by `20261009140000_time_entries_end_time_not_null.cjs`), single-quoted strings, and `--`/`/* */` comments. Unresolved substitutions produce a `*-UNRESOLVED` violation, not a skip.

**"Existing table" set.** Derived offline from the merge-base commit's migrations by running the same SQL classifier over `git show <base>:server/migrations/*.cjs` and `ee/server/migrations/*.cjs`, cached at `.cache/migration-schema/<sha>.json`, recomputed when the base SHA changes. No database is needed, so the lint runs in ~30 s. Limitation stated in §11: a table created by `setup/create_database.js` or by a seed would be invisible; `tenants` and `comments` are created by `server/migrations/202409071803_initial_schema.cjs`, so the important ones are covered.

|---|---|---|---|---|---|

| 3 | On existing tables: `SET NOT NULL`, `ALTER COLUMN ... TYPE`, `DROP TABLE`, `DROP COLUMN`, `RENAME TO`/`RENAME COLUMN`, and `DROP CONSTRAINT` for a name not added `NOT VALID` earlier in the same file | statement kind + object kind; `DROP POLICY`/`DROP INDEX`/`DROP TRIGGER` explicitly not matched | `ALTER TABLE time_entries ALTER COLUMN end_time SET NOT NULL` | the guarded Citus-shard pattern with an annotation, or no statement | `DROP CONSTRAINT IF EXISTS` followed by an add of the *same* name (main's invariant-preserving pattern) must pass; name matching is by literal only |

| 7 | DDL without an idempotency guard: `CREATE TABLE`/`CREATE INDEX`/`ADD COLUMN` need `IF NOT EXISTS`; `ADD CONSTRAINT` needs a preceding `DROP CONSTRAINT IF EXISTS <same name>` in the same file | statement text + same-file name lookup | `ALTER TABLE x ADD COLUMN y int` | `ADD COLUMN IF NOT EXISTS` | `knex.schema.hasTable(...)` early return is accepted as an alternative guard only when it precedes the statement in the same function |
| 8 | Writes to global reference data: `INSERT`/`UPDATE`/`DELETE` on `permissions`, `role_permissions`, `internal_notification_categories`, `internal_notification_subtypes`, `internal_notification_templates`; any call to `reconcileAllTenants(`/`syncPermissionCatalog(` from a migration | literal table set + call-name match | `INSERT INTO permissions ...` | none — this rule is annotation-only | the table list is explicit, so a new global catalog table escapes; §11 proposes extending it |

**Escape hatch.** Syntax: `// migration-lint: allow <rule-id> — <reason>` on the offending line or the line immediately above it, where `<rule-id>` is `1`..`8` or `*-UNRESOLVED`. `applyAnnotations()` in `scripts/lib/migration-lint.mjs` matches the comment against the violation's `(file, line, rule)`, requires a reason of ≥12 non-space characters after the em dash, rejects `allow all`, and rejects a mismatched rule id. There is no other suppression: no config allowlist, no environment variable. The CLI prints `N annotation(s)` in the job summary and every annotation is a visible added comment in the diff — the annotation *is* the review control, because the lint cannot judge intent. Any author may write one; rule 2/3 annotations on `comments`, `time_entries`, `tickets` or `project_task_comments` additionally require an explicit reviewer note in the PR body (stated in the annotation text).

**CLI contract.** `node scripts/ci/migration-lint.mjs [--base <ref>] [--files <glob>…] [--json]`. Default base is `origin/main`; the changed set is `git diff --name-status --diff-filter=AMR <base>...HEAD -- server/migrations ee/server/migrations` for the PR gate (added, modified and renamed files; the new path of a rename is linted), and `--files` exists so the A2 audit and the fixture tests can point at arbitrary files without a git range. Exit `0` clean, `1` violations, `2` the lint could not decide (missing base ref, unparseable file, unresolved substitution that is not annotated). `2` is deliberately distinct from `1` because it means "the tool failed", not "the migration is unsafe", and the job summary says which. Output is one line per violation, `file:line: R<rule> <message>`, followed by `N violation(s), M annotation(s), K file(s) scanned`. `--json` emits the same data for the tests; no other consumer exists.

**PR-mode scope (A/M/R) and decisions (repair round, alga-2026-0002848).** PR mode lints every migration the PR adds (`A`), modifies (`M`) or renames (`R`); `D` is not handled. M/R files are scanned whole, not by hunk, so touching an old file requires annotating any violation already in it (fail closed). Decisions:
- *Rule 6 for M:* a modified file keeps its original timestamp, so it is exempt from the "not later than base" check only.
- *Rule 6 for R:* a rename that keeps the timestamp is exempt like M. A rename that changes the timestamp is a new migration name to knex and is treated as an added file (full R6 check, current context, with the old path removed from the base facts).
- *Duplicates:* the duplicate-timestamp check runs once over the whole change set (A, M and R together). A collision between two files that were both already on base (`20261020120000` x2, `20261013120000` x2) is inherited and is not reported when the PR merely touches them; a collision with an added or timestamp-changed file is.
- *Context for M/R:* judged with the as-of-own-timestamp context the audit uses (`contextFromFacts(baseFacts, { asOf: true })`), so a table the file itself creates is not "existing" for that file, and a touched file in the newest-34 window is judged exactly as the main audit judges it. Added files keep the current context. Output lists M/R files as `<file>: modified` / `<file>: renamed from <old>`; `filesScanned` includes them.

**Fixture tree** (each rule has both sides, and the meta-test refuses a rule with only one):

## 3. Decision 2 — the upgrade-order job

One new script, `scripts/ci/upgrade-order.mjs`, one new job (`upgrade-order`) in `ci-safety-gates.yml`.

1. `actions/checkout` with `fetch-depth: 0`; Node 22; `npm ci --ignore-scripts` (needed for `pg`, `knex`, `tsx`).
2. Baseline = `github.event.pull_request.base.sha` (main on push). Fail if the SHA is not an ancestor of `origin/main`, so a stacked PR cannot compare against another stacked branch.
3. `prepareUpgradeSchema({ repository, commit: baseSha, destination: $RUNNER_TEMP/base, edition: 'ee' })` from the existing `scripts/lib/upgrade-schema-source.mjs`. Then `git archive baseSha server/seeds ee/server/seeds | tar -x -C $RUNNER_TEMP/base` — this library does not extract seeds, and the gate needs "schema + seed".
4. Postgres service: the pinned `pgvector` image from `.github/workflows/pinned-images.yml` (not `citusdata/citus`). Rationale: the EE AI migrations guard on `pg_available_extensions`, the Citus path is already covered fresh-install by `citus-migration-smoke.yml`, and the subject here is *ordering and compatibility*, not distribution. `CREATE DATABASE upgrade_order`, app role `app_user`.
5. Run the baseline's combined migrations (CE then EE, as `.github/workflows/citus-migration-smoke.yml` does), then `npx knex seed:run --knexfile knexfile.cjs --env migration` with `SEEDS_DIR=./seeds/dev` from `$RUNNER_TEMP/base/server`. Snapshot `pg_class`/`information_schema.columns`/`pg_constraint` into `$RUNNER_TEMP/before.json`, and `knex_migrations` into `before-ledger.json`.
6. Apply the PR's migrations: build a combined directory in `$RUNNER_TEMP/pr-migrations` (CE files, EE overlay, both `utils/`, same recipe as `scripts/merge-migrations.sh`) and `npx knex migrate:latest` with `MIGRATIONS_DIR` pointed at it.
7. Structural N-1 assertions (in `scripts/ci/upgrade-order.mjs`): every baseline ledger row still present with unchanged `name` and `batch`; every baseline column still present with an equal-or-wider type (`numeric` precision must not shrink, `varchar(n)` must not shrink, `text`→`varchar` counts as narrowing); every baseline constraint still present; no baseline table gone. This is the check that actually encodes "old code still runs".
8. Behavioural N-1 smoke: materialise the baseline *release tree* (`git archive baseSha` into `$RUNNER_TEMP/release`, `node_modules` symlinked from the PR tree — the same trick `prepareUpgradeSchema`'s caller already uses in `scripts/run-supported-upgrade.ts`), then `npx vitest run` over a pinned list in `scripts/ci/upgrade-order-smoke.json` (paths that must exist at the baseline commit, else the job fails with a config error rather than silently skipping). Initial list targeted at read paths over the tables the migrations touch: `server/src/test/integration/...` for tickets, comments, time entries, contracts and invoices.
9. Timeout 12 min, target ~8. On failure print: baseline SHA, the first failing assertion ("column `comments.x` removed at `server/migrations/2026..._y.cjs`"), and the sentence *"the release at `<sha>` would break on this schema during blue/green"*.

The prior release is therefore **the merge base of the PR, by SHA** — not a floating tag and not `v1.5.0`. `v1.5.0` stays the baseline for the existing e2e supported-upgrade gate; L0g's gate must be about the code that is live in production *this week*. The `upgrade-baseline.json` pin is deliberately not changed.

## 4. Decision 3 — `generate:artifacts` and the drift check

New scripts in `package.json`:

```json
"generate:openapi": "npx tsx sdk/scripts/generate-openapi.ts --edition ce --output sdk/docs/openapi && npx tsx sdk/scripts/generate-openapi.ts --edition ee --output sdk/docs/openapi",
"generate:pseudo-locales": "node scripts/generate-pseudo-locales.cjs",
"generate:artifacts": "npm run generate:openapi && npm run mcp:registry:generate && npm run generate:pseudo-locales",
"artifacts:check": "node scripts/ci/artifact-drift.mjs",
"lint:migrations": "node scripts/ci/migration-lint.mjs",
"budget:hot-path": "cd server && npx vitest run src/test/contract/hotPathQueryBudget.db.test.ts",
"budget:hot-path:record": "HOT_PATH_BUDGET_RECORD=1 npm run budget:hot-path"
```

Order matters: the chat registry is generated *from* the OpenAPI JSON (`ee/scripts/generate-chat-registry.mjs` reads `sdk/docs/openapi/alga-openapi.{ce,ee}.json`), so OpenAPI must run first. The CE run writes `alga-openapi.{json,yaml}` as an alias as well; both are in the checked set.

`scripts/ci/artifact-drift.mjs` does two things and fails on either:

1. **Drift.** Runs `git status --porcelain` over `sdk/docs/openapi/`, `server/src/lib/mcp/registry.generated.ts`, `ee/server/src/chat/registry/apiRegistry.generated.ts`, `server/public/locales/xx`, `server/public/locales/yy`. Any modified or untracked file is a failure with `::error file=<path>` plus `git diff --stat` and the first 120 lines of `git diff` in `$GITHUB_STEP_SUMMARY`. The job runs the generators itself; it never trusts the PR's committed output.
2. **Additivity.** Parses `git show HEAD:<spec>` and the regenerated spec as JSON and fails on any removed path, operation, schema, property, required-field relaxation or enum value removal. This is the machine-readable half of PLAN §3 ("changes must be additive"). Suppression is a reviewed data file `scripts/ci/artifact-drift-allow.json` (`{path, pointer, reason}`), never a code comment — JSON cannot carry one.

The `.yaml` files are compared by regeneration only (byte equality after `YAML.stringify`), not structurally; if the serializer ever proves non-deterministic the fix is to drop `.yaml` from the checked set, not to normalise the diff (see §11).

## 5. Decision 4 — the hot-path query-budget harness

**Placement.** `server/src/test/contract/hotPathScenario.ts` (steps), `hotPathQueryBudget.test.ts` (runner), `hotPathQueryBudget.json` (snapshot). H §5 names `scripts/review/hot-path-scenario.ts` "shared with the recorder"; PLAN §4 removes the recorder (board pipeline, no evidence media), so a vitest file under `server/src/test/contract/` is the honest home: it gets `createTestDbConnection`, `vi.mock` of `@alga-psa/db`, and the repo's existing integration fixtures for free. Recorded as a divergence.

**Listener.** `db.on('query', ...)` on the connection the test hands to the mocked `createTenantKnex`/`getConnection` (the pattern already used in `server/src/test/integration/calendar/getProvidersQueryCount.integration.test.ts`). Per emitted event: normalise whitespace, count 1 statement, extract leading verb, extract the first table after `from|into|update|join`, and record `locks += 1` when `/for\s+(update|share|no key update|key share)/i` matches. The knex `query` event is parameterised (`?` placeholders with a separate bindings array), so parameter values never enter the snapshot — that is the primary stability mechanism, not post-hoc scrubbing. Additionally normalise: `$1..$n`→`?`, quoted vs unquoted identifiers, and drop `BEGIN`/`COMMIT`/`SAVEPOINT`.

**Steps** (each wrapped in one outer transaction that is rolled back, so the fixture is identical every run): `withAuth` request; tier check; ticket list; ticket open; ticket update; board move; comment add; comment edit; comment delete; scheduled-comment enqueue; time entry create; time entry approve; invoice generation; portal ticket view; inbound reply handling; maintenance-fanout tick. Each step is a function returning `{statements, locks}`; steps run sequentially in one tenant so cache warm-up is deterministic. Three consecutive runs per step within the same process must agree (`statements` and `locks`); disagreement fails as **`UNSTABLE`**, a distinct message from **`BUDGET EXCEEDED`**, because the remedies differ (fix the scenario vs. approve a snapshot).

**Snapshot format** (`server/src/test/contract/hotPathQueryBudget.json`):

```json
{ "schemaVersion": 1, "scenario": "psa-canonical-v1", "edge": "ce",
  "steps": [{ "name": "ticket.list", "statements": 7, "locks": 0 }],
  "totals": { "statements": 0, "locks": 0 },
  "denylist": ["^co_managed_", "^co_management_", "^sla_organization_", "^native_time_tracking_", "^tenant_license_state$"],
  "notes": "raising a number requires this file in the PR diff" }
```

Assertions: every step's counts are ≤ the snapshot (increases fail; decreases rewrite the snapshot in the same PR), and no captured statement's table matches `denylist`. Later cards append patterns to `denylist`; the array is the extension point named in the card brief.

## 6. Decision 5 — CI wiring

One new workflow, `.github/workflows/ci-safety-gates.yml`, four jobs, all `runs-on: ubuntu-latest`, all on `pull_request` (target `main`) **and** `push: branches: [main]`. No `paths:` filters: each gate is dominated by `npm ci` (1–2 min with the npm cache) and a path filter on a safety gate is a way to not run it. `concurrency` cancels superseded PR runs.

| Job | Needs | Wall clock (target) | Caching |
|---|---|---|---|
| `migration-lint` (+ rules self-tests) | node, git history (`fetch-depth: 0` for the base SHA) | 2 min | `setup-node` npm cache |
| `artifact-drift` | node, full `node_modules` (`generate:openapi` imports `server/src/lib/api/openapi`) | 5 min | npm cache |
| `upgrade-order` | postgres service, node | 8–10 min | npm cache; no Docker builds |
| `hot-path-budget` | postgres service (pgvector image, migrated schema), node, nx-built workspace packages | 8–10 min | npm cache; `nx` local cache for the built packages |

`citus-migration-smoke.yml` keeps its current trigger and gains nothing; the upgrade-order job states in its header that Citus distribution coverage remains there.

**Attribution.** Two mechanisms, neither of which needs labels. (a) Every failure is emitted as a GitHub file annotation, so the reviewer lands on the offending migration or artifact. (b) `scripts/ci/attribute-card.mjs` reads `docs/cards/co-managed/*.md` §1 path tables (the charter format in H §4 makes them machine-readable) and prints `owned by card <Lx>` for the failing path in the job summary. If the path matches no charter, it prints `owned by no card — check the manifest` and still fails. PR labels are not used because `card-ids.json` lives outside the repo and CI cannot be trusted to read it.

Sketch of the shape (job bodies abbreviated; the `upgrade-order` and `hot-path-budget` jobs each declare the pinned pgvector service, create `upgrade_order`/`budget` databases and the `app_user` role before the node step):

```yaml
name: CI safety gates
on:
  pull_request: { branches: [main] }
  push: { branches: [main] }
concurrency:
  group: ci-safety-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
jobs:
  migration-lint:
    steps: [checkout(fetch-depth: 0), node 22, npm ci --ignore-scripts,
            node --test scripts/tests/migration-lint.test.mjs,
            node scripts/ci/migration-lint.mjs --base origin/main]
  artifact-drift:
    steps: [checkout, node 22, npm ci --ignore-scripts, npm run artifacts:check]
  upgrade-order:
    timeout-minutes: 12
    steps: [checkout(fetch-depth: 0), node 22, npm ci,
            node scripts/ci/upgrade-order.mjs]
  hot-path-budget:
    timeout-minutes: 15
    steps: [checkout, node 22, npm ci, nx build-deps server, npm run budget:hot-path]
```

## 7. Decision 6 — test plan mapped to acceptance bar A

| Bar item | Proof | Where |

| A1 each rule has a failing and a passing fixture | table-driven `node --test`; a meta-assertion that rules `1..8` each appear in `fixtures/migration-lint/<rule>/fail/` and `.../pass/`; each assertion also checks the emitted rule id and line number | `scripts/tests/migration-lint.test.mjs`, `scripts/tests/fixtures/migration-lint/**` |

## 8. Decision 7 — sequencing

1. **`scripts/lib/migration-lint.mjs` + CLI + fixtures first.** It is pure, DB-free, and the annotation pass over main's newest migrations is the input to every later card that adds a migration. Nothing depends on it, but everything after it benefits.
2. **`generate:artifacts` + `artifact-drift.mjs` second.** Independent of the lint; the only order constraint is OpenAPI before the chat registry. It also fixes a real gap today: the chat registry is generated from an OpenAPI file that nothing verifies is current.
3. **`upgrade-order.mjs` third.** It reuses `prepareUpgradeSchema` and establishes the "how do we get a migrated DB in a job" recipe that the budget harness copies.
4. **The query budget last.** It must not merge without a stable snapshot, or `main` inherits a flaky required check. Its only hard dependency is a migrated DB in CI (step 3) and a canonical fixture.

Safe partial merges: (1) alone, (1+2) alone, and (1+2+3) alone are each green on `main` with no effect on product code. The workflow file can land with jobs that do not yet exist only if the jobs are added in the same commit as their scripts; do not land a job that no-ops on a missing script.

   - rule 8: `20261013042016_add_ticket_template_permissions.cjs` (calls `reconcileAllTenants`, grants `ticket_template` permissions to every PSA tenant).

   `20261010120000_collapse_...` may produce several findings in one file; if the annotation count per file exceeds 3 the plan's fallback is a reviewed baseline file, not a louder comment.
2. **False positives from the SQL splitter.** Migrations build SQL with interpolated table names in loops (`for (const table of TABLES)` in `20261010000000_...`) and with `run_command_on_shards(?, $$...$$)`. The first is caught by executing literal-only `for...of` arrays (the TypeScript AST makes this mechanical); the second is caught by the dollar-quote rule. Neither is proven against all 1141 CE files until A2 runs.
3. **Rule 5 is a heuristic.** It cannot tell a keyed single-row update from a full-table rewrite. It will require annotations that "feel" unnecessary. That is the cost of not shipping an explain-plan analyser; the alternative (a `UPDATE ... WHERE pk = ?` exemption) is a name-shaped guess.
4. **The behavioural N-1 step (§3.8) is the risky one.** Symbolic-linking the PR's `node_modules` into an archived release tree is proven for *migrations* (that is what `scripts/run-supported-upgrade.ts` does) but unproven for *vitest suites* that import workspace packages. Rate it explicitly; if it does not work in the first spike, substitute a pinned psql read-path script and record that substitution as a divergence needing reviewer sign-off.
5. **`prepareUpgradeSchema` refuses to extract seeds.** Verified by reading it (only migrations and `utils/` are copied). §3.3 works around this with a second `git archive`; the alternative — changing the shared library — would touch the e2e gate.
6. **Determinism of `sdk/scripts/generate-openapi.ts`.** It reads `package.json` for the version and walks a registry whose ordering was not verified here. If two runs differ, `artifact-drift` fails for a reason that is not the PR's fault. First implementation step is to run it twice on an unmodified checkout.
7. **Base-SHA drift.** `pull_request.base.sha` moves when `main` advances, so a red upgrade-order job may be caused by a migration merged to `main` after the PR was opened. The failure text names the SHA; the fix is a rebase, and the job summary says so.
8. **Budget snapshot flakiness on shared runners.** Counts are per-step and transaction-scoped, so autovacuum cannot appear, but a step that lazily initialises a cache on first use will differ between run 1 and runs 2–3. The `UNSTABLE` message distinguishes this from a real regression; a warm-up call before recording is the likely fix.
9. **`docs/cards/co-managed/` does not exist yet.** `attribute-card.mjs` degrades to "owned by no card" until the first card charter lands. That is a soft dependency on L0a/L0b landing their charters.
10. **Manifest absence.** `~/cm-redelivery/manifests/L0g.md` is missing, so §1 is unverified against the authority the brief names. Reconcile before implementation; treat any path in §1 that the real manifest does not list as out of scope.
