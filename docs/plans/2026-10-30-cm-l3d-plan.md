## 4. The seam

`ProjectDataSource` mirrors `TicketDataSource` (L3a), because the same screen must serve two very different
authority models without the screen knowing which:

```ts
export type ProjectDataSourceKind = 'native' | 'co-managed-shared';

export interface ProjectDataSource {
  kind: ProjectDataSourceKind;
  project: { get(): Promise<ProjectHeader> };
  tasks: {
    list(phaseId?: string): Promise<ProjectTaskRow[]>;
    get(taskId: string): Promise<ProjectTaskDetail | null>;
    tree(): Promise<ProjectTreeData>;
    commentCounts(taskIds: string[]): Promise<Record<string, number>>;
  };
  options: { statuses(): Promise<TaskStatus[]>;
             priorities(): Promise<Priority[]>;
             types(): Promise<TaskType[]>; };
  people:  { users(): Promise<TeamMember[]>; clients(): Promise<Client[]>; };
  phases:  { list(): Promise<Phase[]>; customStatusCounts(): Promise<Record<string, number>> };
  editTask(request: ProjectTaskEditRequest): Promise<ProjectTaskEditResult>;
  updateProject(patch: ProjectUpdatePatch): Promise<void>;
  refresh(): Promise<void>;
  screen: ProjectScreenBehavior;
}

export interface ProjectScreenBehavior {
  readOnly: boolean;
  frozenFields: readonly string[];   // rendered, disabled, and explained
  hiddenFields: readonly string[];   // not shared with this viewer
  hideCreate: boolean;
  hidePhaseMoves: boolean;
  hideKanbanDrag: boolean;
  backHref: string;                  // back to the Shared Tasks queue
  slots: ProjectScreenSlots;         // conversations, timeSummary — null until L4c/L6a2
}
```

Two properties carry the acceptance bar:

1. **Native is a lazy forwarder.** `nativeProjectDataSource` is a frozen singleton whose every method calls
   the action it replaces, nothing more. Neutrality is therefore structural: a PSA tenant's screen issues the
   same statements it issues today, and the budget snapshot can assert 0 extra.
2. **The shared implementation throws rather than guesses.** `createCoManagedSharedProjectDataSource` starts
   from a `NO_PROJECT_CAPABILITIES` base in which every unoverridden method throws `CoManagedReadOnlyProjectError`
   — the same shape as `sharedTicketDataSource.ts`. Anything the card does not explicitly implement is a loud
   failure, never a silent native call that would read or write the MSP's own tenant.

### 4.1 Reads

The shared implementation's `project`, `tasks`, `phases` and `people` groups call new verbs in
`coManagedProjectTaskActions.ts` that wrap `getCoManagedSharedWorkSummary` and
`listCoManagedSharedProjectTasks`. They never call `getProject`, `getProjectTaskData`, `getProjectTreeData`
or `getTaskById`: those are `withAuth` + `createTenantKnex(viewerTenant)` and would answer for the MSP's own
tenant, which is exactly the leak this card exists to prevent.

Field visibility comes from `visibleCoManagedFields` (`packages/co-managed/src/sharedWorkRead.ts`) turned into
`screen.hiddenFields` / `screen.frozenFields`, so the drawer renders what the customer shared and explains the
rest — the screen stays full-fidelity even where the data is not.

### 4.2 Writes

Every write resolves to one of three outcomes, decided in the seam, not in the component:

| Native call site | Shared-mode behaviour |
|---|---|
| `TaskForm` submit | `editTask({ expectedRevision, expectedTaskUpdatedAt, patch })` → `projectTaskEditing.edit`, which owns the allowlist (`task_name`, `project_status_mapping_id`, `due_date`), the reference-row lock, the replay hash, revision drift and `updated_at` drift |
| Kanban drag (`updateTaskStatus`) | routed through the same `editTask` (status is admitted); a drift or revision conflict surfaces as the editor's conflict reload, not a lost write |
| Reorder / phase move / delete / create | **frozen** — `hideKanbanDrag`, `hidePhaseMoves`, `hideCreate`; there is no admission for them, so the screen must not offer them |
| `updateProject`, checklist, tags, resources, ticket links, dependencies | **frozen** — rendered read-only with the reason, never dropped |

The rule the card states is enforced literally: **a field that is not admitted causes a refusal, not a
discard.** `editTask` returns `refusedFields`, the form lists them, and nothing else is submitted. That is why
the seam carries `ProjectTaskEditRequest` rather than a loose patch.

### 4.3 Neutrality

`ProjectDataSourceProvider` defaults to `nativeProjectDataSource`, so any mount that does not opt in is
byte-for-byte today's behaviour. Shared mode exists only under `/msp/co-management/…`, behind both the server
`serves` gate and the client `useCapability('co-managed')`, and disappears entirely under
`FORCE_CAPABILITIES=co-managed:off`.

## 7. Acceptance bar

Automated (green at HEAD):
- **A1 seam contract** — `nativeProjectDataSource` satisfies `ProjectDataSource` and forwards every method to
  the named action (unit test with mocked actions; no method may be a stub).
- **A2 refusal, not discard** — submitting a non-admitted field in shared mode returns `refusedFields`, issues
  no write, and the form shows it; a test asserts no `updateTask*` action is reachable from shared mode.
- **A3 admission** — a shared-mode edit reaches `projectTaskEditing.edit` and the L3c guarantees still hold:
  reference-row lock, revision conflict, `updated_at` drift conflict, status-mapping-belongs-to-project.
- **A4 scope** — an out-of-scope project id and an out-of-scope task id are unreachable through every seam
  method (not merely hidden in the UI).
- **A5 neutrality** — a PSA tenant's project page, task form and task update issue the same statement count as
  `main` (budget snapshot), under flag off and flag on without entitlement.

Recorded (fingerprint-fresh): the review guide's walkthrough — open a shared project in the real screen, move a
task on the board, edit it in the native drawer, confirm a non-shared field is read-only, confirm an
out-of-scope project is invisible.

Global gates: all of H §5 — no new registry or budget entries, since no capability or event is added.

Explicit exclusions: conversations and effort in the drawer are slots, not implementations (L4c, L6a2).

## 11. Risks and traps

1. **The silent-native fallback.** Any seam method left unoverridden that falls through to a native action reads
   the MSP's tenant. Mitigated structurally by the throwing base plus A1/A4.
2. **`TaskForm` submits everything.** It carries description, checklist, tags, resources, ticket links and
   dependencies. In shared mode those are frozen and must be refused loudly, or a save will appear to succeed
   while changing nothing.
3. **Dragging bypasses the guard.** Native `updateTaskStatus` and `reorderPhase` are unguarded server actions.
   Drag is only safe because it is re-pointed at `editTask`; reorder and phase moves are frozen rather than
   re-pointed, because there is no admission for them.
4. **Two loaders.** `ProjectPage` loads through a client `useEffect` while `generateMetadata` uses the native
   `getProject` in RSC. The shared route must not call that RSC path with a customer project id.
5. **Cache separation.** Native actions `revalidatePath('/msp/projects')`; the shared route must not reuse those
   entries, and the `serves` gate must short-circuit before any `co_management_*` query so neutrality holds.
