## 0. Where the branch stands

The branch head is `04ea4a8ff5`, which is `origin/main` itself: **no L0b code exists yet.** This plan is written
against main as it is at that commit. Every `file:line` below was read from the worktree at that commit.

L0b is a refactor with zero behaviour change. It opens five seams that L1 (conversation ids) and L3 (navigator)
plug into. Nothing here is gated, because nothing here is visible. The `ticket-conversations` capability (L0a) is not
consulted.

## 1. What does not change

- **Rendered output.** For every tenant (native PSA, co-managed workspace, client portal), the DOM, element ids,
  `data-automation-id`s, labels, ordering and focus behaviour of the classic conversation, the Bento timeline,
  `CommentItem` and the reply composers are identical to main. That includes known oddities that a later card may
  fix but this one must not:
  - `TicketConversation.tsx:885/889` (`Switch id=${compId}-internal-toggle`, `Label htmlFor=${id}-internal-toggle`).
    The ids diverge when `id` is unset.
  - `TicketConversation.tsx:912` has the same `htmlFor` mismatch for the resolution toggle.
  - Classic and Bento use different locale keys for the same words (`tickets.conversation.closeStatus` versus
    `bento.timeline.closeStatus`).
- **Write semantics.** Every `comment_threads` row written by a migrated site has the same columns and values.
  Publication payloads stay byte for byte, including `collaboration_audience` and `thread_id` labelling, and the
  scheduled-comment `comment_publication_payload`. The SQL statements and their order within the transaction are
  unchanged.
- **Schema.** No migration, no new table, no new column. Nothing goes into tenant metadata, the manifest or deletion.
- **Hot paths.** No new query on any path. With no thread-insert contributor registered (the only state on main after
  this card), the shared insert function issues exactly the statements the call sites issue today.
  `hotPathQueryBudget.json` is not re-recorded, and these entries must stay green unchanged: `comment.add` 23/3,
  `ticket.open` 32/0, `portal.ticketView` 15/0.
- **Locale.** No key is added, removed or renamed. Strings stay in the files that render them. If a string moves with
  the code that renders it, the `t()` call keeps its key and namespace.
- **Public surface.** These keep their current exported signatures, because a test or another package imports them:
  - `buildTicketThreadTabState` (pinned by `ticketConversationThreadTabs.test.ts`; also referenced in
    `client-tickets.ts:476`)
  - `TicketConversation` and `BentoTimelineTile` props
  - `CommentItem` props (additive only)
  - `InlineReplyComposer` props

## 2. Seams

### Seam 1: one composer controller shared by classic and Bento

**Today.** Each surface owns its own copy of composer state:
- `TicketConversation.tsx:203–486`: `isInternalToggle` boolean; audience fields `configuredAudiences`,
  `useAudienceComposer`, `offeredAudiences`, `chosenAudience`, `audienceMissing`, `handleAudienceChange`; resolution,
  close status, notification suppression, schedule and Cc/Bcc state; the submit argument builder (387–398); the reset
  on success (399–408); tab-driven seeding (351–362, 467–477); the dirty guard (279–296).
- `bento/BentoTimelineTile.tsx:471–550, 792–846`: the same logic with `composerVisibility: 'client' | 'internal'`,
  seeded from `defaultReplyInternal` rather than a tab.

The copies have drifted. A shared controller has to reproduce each surface's current rule, not unify them:

| Rule | Classic | Bento |
|---|---|---|
| Audience select shown | `audiences != null && !hideInternalTab` | `audiences != null` |
| Visibility seed on open | active tab (Internal, or All plus `defaultReplyInternal`) | `defaultReplyInternal` |
| Tab change while open | re-seeds visibility and resolution | n/a |
| Schedule validity checks internal | no (schedule hidden when internal) | yes (`!isClientComposer ||`) |
| Send disabled without typed draft | no | yes (`!hasDraft`) |
| Portal (`hideInternalTab`) submit | `onAddNewComment(false, isResolution)` | n/a |
| Close-status/suppression reset | on editor close or resolution off | on resolution off |

**Seam.** The plan is a headless controller plus small shared parts. Each host keeps its own layout JSX.
- `packages/tickets/src/components/ticket/composer/useTicketCommentComposer.ts` is the one owner of:
  - visibility and audience state;
  - resolution, close status and suppression;
  - schedule (instant plus validity) and Cc/Bcc drafts;
  - the `onAddNewComment` argument tuple, including the conditional trailing audience argument;
  - the success reset and the open/seed and discard transitions;
  - the prefill handle (Seam 2).
- **Host policy is passed in as data, not as mode flags.**
  - `seedVisibility(): 'client' | 'internal'` is called on open and when the seed inputs change. Classic passes its tab
    rule; Bento passes `defaultReplyInternal`.
  - `audienceSelectable: boolean` is the host's existing condition.
  - `requireTypedDraft: boolean` is Bento's `hasDraft` gate.
  - `portalSubmit` is the classic portal tuple.
- `ComposerAudienceOrVisibility` renders `CommentAudienceSelect` when audiences are configured, and the host's own
  visibility control otherwise, passed as a child. This keeps "audience replaces internal" in one place, while the
  classic `Switch` and the Bento segmented buttons stay byte-identical.
- **Dirty guard.** `useComposerDirtyGuard(open, content)` goes in `packages/ui/src/editor/` (next to
  `hasEditorContent`) and wraps `hasEditorContent`, `useRegisterDismissGuard` and `useRegisterUnsavedChanges`. All
  three sites use it: classic, Bento and `InlineReplyComposer.tsx:85`. It belongs in `packages/ui` because
  `InlineReplyComposer` cannot import from `packages/tickets`.

**Markers resolved:** `pattern composer-dirty-guard` at `TicketConversation.tsx:282`, `BentoTimelineTile.tsx:524` and
`InlineReplyComposer.tsx:85`. The duplicated audience-select logic that MAIN-FOUNDATION §7 describes carries no marker
of its own; it is removed by this seam.

**Also removed:** the dead `handleAddNewComment` at `TicketConversation.tsx:444–465`. It is defined and never called,
so removing it changes no behaviour.

> **Flag for the captain: "one composer component".** The card asks for one composer *component* used by both
> surfaces. The two composers render different DOM: avatar, toggle row, a labelled segmented control versus a
> `Switch`, button order and labels, schedule placement, and locale keys. A single rendered component would change
> visible output, which the card says to raise rather than ship. This plan puts the logic in one place (controller
> plus the audience part) and leaves layout in each host. Default: proceed this way. Converging the two layouts is a
> visible change for a later card, likely L3 when the navigator brings its own composer.

### Seam 2: composer prefill (`base-composer-prefill`)

**Today.** There is no initial-content seam. Both composers mount `TextEditor` with `initialContent={DEFAULT_BLOCK}`
and `key={editorKey}`:
- `TicketConversation.tsx:983–988` and `BentoTimelineTile.tsx:936–941`
- `editorKey` and the draft content are owned by `TicketDetails.tsx:1439, 2045` and passed down via
  `onNewCommentContentChange`.

`TextEditor` already exposes `editorRef` (`packages/ui/src/editor/TextEditor.tsx:86`) and uses `replaceBlocks`, so no
editor change is needed.

**Seam.** The controller exposes a `TicketComposerHandle`. Each host publishes it through a new optional prop,
`composerHandleRef?: Ref<TicketComposerHandle>`, on `TicketConversation` and `BentoTimelineTile` (via
`useImperativeHandle`). With the prop unset, nothing changes.

```ts
interface TicketComposerPrefill {
  content: PartialBlock[];
  visibility?: 'client' | 'internal';
  audience?: ComposerAudience;
  resolution?: boolean;
}
interface TicketComposerHandle {
  prefill(p: TicketComposerPrefill, opts?: { replace?: boolean }): { ok: true } | { ok: false; reason: 'dirty' | 'read-only' };
  isOpen(): boolean;
  hasContent(): boolean;
}
```

Semantics:
- `prefill` opens the composer if it is closed, keeping the current placement or defaulting to `top`.
- It writes the content through `editorRef.replaceBlocks`, or falls back to seeding `initialContent` before mount.
- It calls the host's `onNewCommentContentChange(content)`, so `TicketDetails` submits what is shown.
- It marks the draft dirty, so both guards engage and Bento's Send is enabled.
- It applies visibility, audience and resolution through the controller's own setters, so the existing rules hold:
  - an audience outside `offeredAudiences` is dropped;
  - a resolution never offers `shared_it`;
  - an audience implies its `is_internal`.
- It never overwrites typed text: a dirty composer returns `dirty` unless `replace: true`.
- It never shows a confirmation. Whether to ask is the caller's UI, not this seam's.

No caller exists on main after this card, so no behaviour changes. L5d (AI), L5e (share) and L6 (synthesis) are the
first callers.

**Marker resolved:** `friction base-composer-prefill` at `server/src/components/co-managed/CoManagedDraftRestore.tsx:23`.

> **Flag.** Making `CoManagedDraftRestore` restore into the editor instead of its own panel is a visible co-managed
> change, so it is not done here. The marker comment is replaced by a plain note that names the new handle as the
> adoption path. The friction itself, the missing seam, is gone.

### Seam 3: data-driven thread tabs

**Today.**
- `ticketConversationThreadTabs.ts:18–43` partitions thread groups by `root.is_internal` into fixed
  all/client/internal/resolution buckets.
- `TicketConversation.tsx:150–153` hard-codes the tab ids.
- `TicketConversation.tsx:792–849` hand-builds the four tabs, including:
  - external child-ticket comments on Client only;
  - headings on Internal and Resolution;
  - the client portal subset `[baseTabs[0], baseTabs[3]]`.

**Seam.**
- A `TicketThreadTabDefinition` list: `id`, `containerId`, label key plus default, optional heading key, a group
  predicate `includes(group, ctx)`, `portal: boolean`, and optional `trailing` content (the external comments).
- `NATIVE_THREAD_TABS` reproduces today's four tabs exactly: ids, `ReflectionContainer` ids and labels, count format
  `Label (n)`, the portal "All excludes internal" rule, and resolution including internal threads only off-portal.
- A generic `buildThreadTabs(groups, tabs, ctx)` returns `{ id, comments, count }[]`. `buildTicketThreadTabState`
  stays as a thin adapter over `NATIVE_THREAD_TABS`, with the same signature and return shape, so its test and the
  `client-tickets.ts` reference are untouched.
- The tab list is read from the data source as `conversation.threadTabs?`, defaulting to `NATIVE_THREAD_TABS`. The
  native data source and the co-managed provider set nothing, so the tabs stay as they are. L3 supplies
  per-conversation tabs through this field.

**Marker resolved:** none exists. MAIN-FOUNDATION §7 lists the hard-coded tabs as a gap, not a LEVERAGE marker.

> **Flag.** Bento has no thread tabs. Its lane filters (`BentoTimelineTile.tsx:452–461`: everything, reply, time,
> system, alert) are a different, timeline-wide dimension and stay as they are. The navigator (L3) decides how
> conversations appear in Bento.

### Seam 4: per-comment and per-thread inline slots (`conversation-inline-slots`)

**Today.** `CommentItem` (`CommentItem.tsx:47–88` props) has no content slot. `TicketConversation` (`renderCommentItem`
604–690, `renderThreadGroup` 701–711) and Bento (`renderThreadComment` 868–902) give hosts no way to place content
inside a comment or at a thread's head. Co-managed works around this with a side panel
(`CoManagedConversationFiles.tsx:35`), which resolves `ticket.conversation.comment-attachments` and
`ticket.conversation.thread-header` UI slots outside the conversation.

**Seam.**
- Extend `TicketScreenSlots` (`packages/tickets/src/lib/ticketDataSource.ts:395`) with two optional render functions,
  following the existing `appSection` and `timeSummary` pattern:
  - `commentInline?(args: { comment; threadRoot; variant: 'default' | 'compact' })`
  - `threadHeader?(args: { group; variant })`
- `CommentItem` gains an additive `inlineSlot?: ReactNode` prop, rendered at one fixed position inside the bubble,
  after the body and before reactions. Nothing is rendered, not even a wrapper element, when it is
  `null`/`undefined`.
- Classic and Bento call the slot functions when the data source defines them. Classic renders the thread header
  inside `renderThreadGroup`; Bento renders it in `renderThreadComment` for the root.
- The native data source and the co-managed provider define neither function, so the DOM is unchanged.

**Marker resolved:** `friction conversation-inline-slots` at `CoManagedConversationFiles.tsx:35`.

> **Flag.** As with Seam 2, moving the co-managed files and disclosure into the bubble is a visible co-managed change,
> left for a later card. The marker becomes a plain note that names `slots.commentInline` and `slots.threadHeader`.

**Seam.** `shared/lib/commentThreadInsert.ts`, next to `nativeThreadAudience` in `shared/lib/commentAudience.ts`:

```ts
type ThreadAudienceSource =
  | { kind: 'native'; isInternal: boolean; authorType: string | null | undefined; requested: string | null | undefined }
  | { kind: 'resolved'; isInternal: boolean; audience: { collaboration_audience?: CommentAudience } }; // Comment.insert's co-managed command path

interface CommentThreadIntent {} // open; L1 augments it with { conversationId?: string } via declaration merging

insertCommentThread(trx, tenant, {
  threadId, ticketId, rootCommentId, createdBy, at, audience: ThreadAudienceSource, intent?: CommentThreadIntent,

registerCommentThreadInsertContributor(c: (trx, tenant, row, intent) => Promise<Record<string, unknown>> | Record<string, unknown>)
```

- The function resolves the audience exactly as each site does today: `nativeThreadAudience` (zero SQL for native
  tenants) or the pre-resolved co-managed value. It then inserts the same row through `tenantDb`/`tenantScopedTable`
  and returns the applied audience.
- **Hook for L1.** Contributors run in registration order and merge extra columns into the row. With none registered
  the function does no extra work: no query, no column. L1 registers one that maps `intent.conversationId` to
  `conversation_id` and owns that column's migration. The same module-level registry idiom as
  `registerCommentEventContributor` (`packages/db/src/lib/commentEventRegistry.ts:72`) is used, so L1 adds a
  registration and never re-edits the four call sites.
- Reply handling (`lockLabelledThreadAudience` / `assertReplyAudience`, plus the `reply_count` bump at
  `ticketModel.ts:1809`) stays at the sites. It is a different shape and out of the marker's scope.
- **Verify while implementing.** `ticketModel.ts` uses `db = tenantDb(trx, tenant)` (e.g. `:1644`), while `comment.ts`
  and `TicketService.ts` use `tenantScopedTable`. Confirm both produce the same `INSERT` statement before unifying; the
  hot-path budget test pins the statement count, not the text.

**Marker resolved:** `pattern thread-audience-insert` at all four sites, plus the marker text's stale "5 sites" claim.
