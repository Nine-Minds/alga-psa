# TC L0a — `ticket-conversations` capability gate on `release-v2-0-feature`

Card 783961f4 · PSA ticket alga-2026-0003159 · Ticket Conversations re-delivery, wave 1.
Authority: `~/tc-redelivery/PLAN.md` (§2, §3, §6, §7.3) wins; manifest `manifests/L0a.md`; `MAIN-FOUNDATION.md` §1.

**Reviewer question.** Can ticket conversations be switched on per tenant with `release-v2-0-feature`, and off
everywhere with one kill switch, without touching co-managed or any other tenant?

## 1. Captain decision (Design Session)

PLAN §7.3: **eligibility = every tenant (the flag alone admits); participation = the tenant has at least one non-default
named conversation.** Default: yes. In L0a this means:

- eligibility is registered as a constant `true`, so `admits = forced ?? release-v2-0-feature(tenant)`;
- participation is **left unregistered**, so `serves = forced ?? false` (reason `resolver-unregistered`). L1 registers
  the resolver when the containers table exists. No tenant is served after L0a, so nothing reads conversation state.

## 2. Deliverables

### D1. Capability key and registry seed

- **Where now.** `packages/core/src/lib/capability.ts:26` `export type CapabilityKey = 'co-managed'`; the seed is in
  `registry()` at `:212-219` (`gates.set('co-managed', …)`); `gateFor` throws `UnknownCapabilityError` for an unseeded key (`:222`).
- **Change.** Replace the single literal with one declarative table that is the source for the type, the seed and
  the bootstrap list:
  ```ts
  const CAPABILITY_SEEDS = {
    'co-managed':           { featureFlag: 'release-v2-0-feature' },
    'ticket-conversations': { featureFlag: 'release-v2-0-feature', eligibility: everyTenant },
  } as const satisfies Record<string, Omit<CapabilityGateDefinition, 'capability'>>;
  export type CapabilityKey = keyof typeof CAPABILITY_SEEDS;
  export const CAPABILITY_KEYS = Object.keys(CAPABILITY_SEEDS) as readonly CapabilityKey[];
  ```
  `registry()` seeds every entry. `everyTenant = async () => true` is a pure constant with no SQL.
- **Why the eligibility is seeded in core rather than registered from a package at boot.** The co-managed resolvers
  are an import side effect of `packages/co-managed/src/capability.ts:79`. If ticket-conversations followed that
  pattern, any process that did not import the registering module (email-service, a job runner, the Temporal worker)
  would answer `resolver-unregistered` → `admits=false` while the web server answered `true`. Because "every tenant"
  needs no data access, seeding it in the pure entry gives every process the same answer. Participation (SQL, L1)
  is still registered by the owning package, as for co-managed.
- **Seam.** `CAPABILITY_KEYS` becomes the list consumers iterate; adding a capability means adding a row.
- **Does not change.** The `admits`/`serves` semantics, the cache, `FORCE_CAPABILITIES` grammar, `registerCapabilityGate`
  merge rules, and the co-managed seed values. The header comment at `capability.ts:12` ("The release flag alone never
  admits anything") becomes false for this key and is reworded to "admits = flag AND eligibility; a capability whose
  eligibility is every tenant is admitted by the flag alone".
- **`resetCapabilityRegistry`** (`packages/core/src/capability/testing.ts`) must re-seed from the same table, so tests
  that reset the registry still see the `ticket-conversations` eligibility.

### D2. Bootstrap driven by the registry

- **Where now.** `server/src/lib/capability/bootstrap.ts:13` `const CAPABILITIES: readonly CapabilityKey[] = ['co-managed']`.
- **Change.** Iterate `CAPABILITY_KEYS`. The flag set is already deduplicated (`:31`), so both capabilities share one
  `evaluateFeatureFlag('release-v2-0-feature')` per request. Output gains `capability:ticket-conversations` and
  `capability:ticket-conversations:admit`.
- **Cost per request for a tenant.** The extra `admits` reaches `evaluateFeatureFlag` for a flag the bootstrap has just
  evaluated, so it is answered from the 60 s flag cache: no extra PostHog call. Eligibility is constant (0 SQL).
  `serves` is `resolver-unregistered` (0 SQL). The net cost is one extra in-memory decision per request.
- **Does not change.** The root-layout wiring, the PostHog `initialFeatureFlags` path, the anonymous `{}` result, and
  the error handling for each key (one failing key never drops the other).

### D3. Probe route for any key

- **Where now.** `server/src/app/api/v1/capabilities/co-managed/route.ts:14` hard-codes `CAPABILITY`. The middleware
  exempts only that exact path from the API-key check (`server/src/middleware.ts:263-268`, `exactApiKeySkipPaths`).
- **Change.** Move the handler to `server/src/app/api/v1/capabilities/[key]/route.ts`. Validate `params.key` with an
  `isCapabilityKey` guard exported beside `CAPABILITY_KEYS`. An unknown key returns the same `notFoundResponse()` a
  closed capability gets, so the probe still cannot reveal which capabilities exist. Replace the two co-managed
  literals in `exactApiKeySkipPaths` with entries generated from `CAPABILITY_KEYS` (with and without a trailing
  slash). The exemption stays exact-match: `/api/v1/capabilities`, `/…/other`, `/…/co-managed/extra` and
  `/…/co-managed-evil` still require an API key.
- **Does not change.** The response body, `Cache-Control: no-store`, 401 for no session, 404 for client-portal users,
  or 404 for a closed capability. The `/api/v1/capabilities/co-managed` URL stays byte-for-byte compatible (review R3).
- **Mismatch with the brief.** The card scope names the route but not the middleware. Without the exemption, R1/R2
  would answer the API-key 401 instead of reaching the handler. The exemption is part of this deliverable.
- **Edge-runtime check.** The middleware runs on the edge. If importing `CAPABILITY_KEYS` from the pure entry pulls
  `features`/`logger-universal` into the edge bundle, move the key table into a dependency-free module

## 4. Deployment

No migrations, no new tables (nothing to register in tenant metadata or the manifest), no new env vars

with the capability closed there is no behaviour change and no extra hot-path query.

## 5. Risks

1. **The shared flag.** Turning `release-v2-0-feature` on for a tenant now admits ticket conversations **and** shows the
   projects Timeline (`packages/projects/src/components/ProjectDetail.tsx:306` reads it raw). Co-managed is unaffected
   because it still needs an entitlement. This is the captain's decision (PLAN §2), so make it visible in D9.
2. **Admitted-but-not-served is the steady state until L1.** UI built before L1 that renders existing state on
   `enabled` would show nothing. Entry points must use `admitted`, and rendering must use `admitted || enabled` (PLAN §2).
3. **The "flag alone never admits" invariant was relied on.** Search for code or docs that assume a flag-on tenant without
   an entitlement is closed for every capability (`docs/features/feature-flags.md:46`, review guides). These remain
   true for co-managed only, and the wording should say so.
4. **Bootstrap PostHog budget under `flag-unavailable`** (D8). It depends on the flag layer caching unavailable results.
   It is verified by test, not assumed.
5. **Edge bundle** for the middleware import (D3).
6. **Pinned glob counts** for families whose directories do not exist yet (D7). A glob that is too broad silently
   matches unrelated "conversation" code. A count of 0 at L0a is the guard.
7. **Seam symbol change** (D4). It is limited to non-co-managed capabilities, so no existing global slot is renamed.

## 6. Out of scope

Any conversation data model, UI or behaviour; the participation resolver (L1); UI-slot contributions or mounts for
conversations (L3); the `release-v1-6-feature` flag sites in manifest Area 13. They belonged to the old branch,
PLAN §2 voids that flag, and Rule B already bans it repo-wide.
