### 2.1 `capabilityGate` API

```ts
// packages/core/src/lib/capability.ts
export type CapabilityKey = 'co-managed';
export type CapabilityMode = 'admits' | 'serves';

export type CapabilityReason =
  | 'forced-on' | 'forced-off' | 'forced-malformed'
  | 'flag-off' | 'flag-unavailable'
  | 'not-eligible' | 'eligibility-error'
  | 'not-participating' | 'participation-error'
  | 'resolver-unregistered';

export interface CapabilityDecision {
  capability: CapabilityKey;
  admitted: boolean;      // admits(): may start (provision, purchase, entry points)
  served: boolean;        // serves(): keep serving existing state (reads, workers, inbound)
  forced: 'on' | 'off' | null;
  reasons: { admitted: CapabilityReason; served: CapabilityReason };
}

export type EligibilityResolver = (ctx: { tenantId: string }) => Promise<boolean>;
export type ParticipationResolver = (ctx: { tenantIds: readonly string[] }) => Promise<ReadonlySet<string>>;

export interface CapabilityGateDefinition {
  capability: CapabilityKey;
  /** The rollout flag. Evaluated tenant-only; never a user context. */
  featureFlag: string;                       // 'release-v2-0-feature'
  eligibility?: EligibilityResolver;         // absent = not eligible (L1a registers)
  participation?: ParticipationResolver;     // absent = not participating (L1a registers)
}

export function registerCapabilityGate(def: CapabilityGateDefinition): void;
export function registerCapabilityEligibility(capability: CapabilityKey, resolver: EligibilityResolver | null): void;
export function registerCapabilityParticipation(capability: CapabilityKey, resolver: ParticipationResolver | null): void;
export function invalidateCapability(capability: CapabilityKey, tenantId?: string): void;
// Test-only hatches clearCapabilityCache() / resetCapabilityRegistry() live in
// packages/core/src/capability/testing.ts (not a package export; contract Rule E).

export async function admits(capability: CapabilityKey, tenantId: string): Promise<CapabilityDecision>;
export async function serves(capability: CapabilityKey, tenantId: string): Promise<CapabilityDecision>;
export async function filterServed(capability: CapabilityKey, tenantIds: readonly string[]): Promise<string[]>;
export async function evaluateCapability(capability: CapabilityKey, tenantId: string): Promise<CapabilityDecision>;

export class UnknownCapabilityError extends Error {}   // programmer error -> throws
```

Decisions and reasons:

- **One decision object, not two booleans.** Adapters need a reason for the probe and for the "closed because unregistered" vs "closed because ineligible" distinction that the review guide has to show; and the bar explicitly tests `admits` vs `serves` divergence, which is unreadable as two loose calls.
- **`admits` = forced, else `isFeatureFlagEnabled(featureFlag, { tenantId })` AND `eligibility({ tenantId })`.** Before calling the flag, `admits` short-circuits to `resolver-unregistered` when no eligibility resolver exists. That is what makes L0a's own deployment invisible even where PostHog is on (PLAN §2), and it means the gate itself performs **zero** PostHog evaluations and **zero** SQL for any tenant. (The root-layout bootstrap still evaluates the raw flag for the Timeline; its cost is stated in "Audit round 1" below.)
- **`serves` = forced, else `participation({ tenantIds: [tenantId] })`.** No flag term. A flag flip can therefore never strand a workspace, and a PostHog outage can never close reads.
- **`filterServed` = the batch form of `serves`.** One `participation` call for the misses; ordered, de-duplicated output; input order preserved.
- **Fail-closed is the default on resolver throw, per branch.** A throwing eligibility resolver yields `not-eligible`; a throwing participation resolver yields `not-participating`; a throwing flag checker yields `flag-off` (with reason `flag-unavailable`). The throw never escapes `admits`/`serves`: a gate that 500s leaks the existence of a closed feature and turns a PostHog incident into an application outage — the opposite of the neutrality contract. Each downgrade logs `warn` once per cache window (`capability_decision_failed` with `capability`, `tenantId`, `mode`, resolver name, error message) and never logs the resolved value.
- **Unknown capability key throws `UnknownCapabilityError`**; an unregistered *resolver* on a known key is data, not a bug, and closes.
- **`registerCapabilityEligibility`/`Participation` are separate from the gate definition** so L1a adds SQL without editing the gate constant, and so the default (`undefined`) is expressible without a "not yet" flag.

### 2.2 Caching

- Cache key: `` `${capability}|${mode}|${tenantId}|${forceFingerprint}` ``, where `forceFingerprint` is `f:on`, `f:off` or `-`. Including the forced value means flipping the kill switch is never masked by a warm cache entry.
- TTL: `Number(process.env.CAPABILITY_CACHE_TTL_MS ?? 30_000)`, clamped to `0..300_000`. 30 s is half of `FeatureFlags`' own 60 s default (`packages/core/src/lib/featureFlagRuntime.ts`), so a flag flip is observable within one flag-cache window, and a participation change cannot outlive two windows. `0` disables caching (tests, and the flag-off integration suite, which must not inherit a warm "closed" entry from an earlier case).
- `filterServed` fills and reads the *same* per-tenant `serves` entries, so a fanout batch warms the per-message path and steady-state `psa` traffic is one cached `false` per tenant per TTL, zero queries.
- Invalidation: (a) TTL; (b) `invalidateCapability(key, tenantId)` exported for L1a's participation writers (relationship end, allocation release, tenant deletion); (c) `FORCE_CAPABILITIES` is re-parsed whenever the raw string changes, so a deployment env change is observed without a code change (a restart, not a live toggle — see §11).
- **Tenant-only distinctId.** `admits` calls the flag checker with `{ tenantId }` and no `userId`, so `FeatureFlags.getDistinctId` yields `tenant_<id>`, not a hashed user id. This is what makes the decision identical for every user of a tenant, which the server/client parity bar requires.
- **PostHog is structurally unreachable from `filterServed`.** `serves`/`filterServed` contain no reference to the flag evaluator at all — the only call into `@alga-psa/core`'s checker is inside `admits`. Enforcement is threefold: (1) source shape (no call site exists); (2) a unit test that registers a throwing flag checker and asserts `filterServed` still resolves and the checker is never invoked; (3) the AST contract forbids `isFeatureFlagEnabled`/`featureFlagRuntime` imports in `packages/jobs`, `packages/core/src/lib/capability.ts`'s worker exports, and any co-managed worker entry point.

### 2.3 `FORCE_CAPABILITIES`

- Grammar: `key:value[,key:value]*`, keys `[a-z0-9][a-z0-9-]*`, values `on|off` case-insensitive. No variants: capabilities are boolean. Whitespace trimmed; empty entries ignored. Undefined/empty string yields no forces.
- Parser: `parseForcedCapabilities(raw)` → `{ values: Partial<Record<string, boolean>>, malformed: string[] }`, plus `forcedValue(raw, capability)` and `forceFingerprint`. One module, no Node imports, so client and server share the exact function (`@alga-psa/core/capability`).
- Server reads `FORCE_CAPABILITIES` (runtime env). Client reads `NEXT_PUBLIC_FORCE_CAPABILITIES` **only as a fallback when the bootstrap map has no key**; a bootstrapped value always wins, so a stale build-time variable cannot override a server kill switch. In a production build the client fallback logs a single `console.warn` and is ignored (PLAN §2: `NEXT_PUBLIC_*` is inlined at build time and is not a kill switch).
- Precedence: forced > (flag AND eligibility) for `admits`; forced > participation for `serves`. `on` bypasses both resolvers and the flag — that is what makes it usable for self-host/dev/CI without a PostHog account.
- A malformed value for a **configured gate key** (`co-managed:maybe`) forces `off` with reason `forced-malformed` and one warn line. An operator clearly tried to configure it; a typo must never admit. Unknown keys are ignored silently so a later card's key does not crash an older image.
- Parity test: a matrix over `raw ∈ {'', 'co-managed:on', 'co-managed:off', 'co-managed:maybe', 'co-managed:ON'}` × `gate registered/unregistered` × `bootstrap key present/absent`, asserting the server decision and the client hook decision are equal in every cell, and that malformed input closes both.

### 2.5 Client bootstrap

`server/src/app/layout.tsx` renders `<PostHogProvider>` with no props today (line 213). `server/src/components/providers/PostHogProvider.tsx` already accepts `initialFeatureFlags` and already wraps children in `FeatureFlagBootstrapProvider` (imported from `@alga-psa/ui/hooks`), and passes the same map into `posthog.init({ bootstrap: { featureFlags } })`. That existing plumbing is why this card adds no provider.

L0a computes the map per request in `server/src/lib/capability/bootstrap.ts` (React `cache()`, same dedupe pattern as `server/src/lib/feature-flags/serverFeatureFlags.tsx`):

```ts
{
  'release-v2-0-feature': <server-evaluated tenant flag>,   // Timeline reads this without flicker
  'capability:co-managed': <served>,
  'capability:co-managed:admit': <admitted>,
}
```

The Timeline and `admits` share one flag, so L0a evaluates it once per tenant per cache window and reuses the value for both consumers. With no eligibility resolver registered, `admits` short-circuits before the flag and does **not** trigger a second evaluation; `serves` never evaluates it at all.

`useCapability(key)` vs `useFeatureFlag(key)`:

- `useCapability` reads only `FeatureFlagBootstrapContext` (extracted to `packages/ui/src/capability/bootstrapContext.tsx`; `useFeatureFlag.tsx` re-exports `FeatureFlagBootstrapProvider` and `useFeatureFlagBootstrap` so `PostHogProvider` and `@alga-psa/ui/hooks` keep working). It never imports `posthog-js/react`, never subscribes to `onFeatureFlags`, and never re-evaluates. Missing key ⇒ `enabled: false, admitted: false, resolved: false` (fail closed, and the caller can tell "closed" from "not bootstrapped").
- `useFeatureFlag` keeps its PostHog re-evaluation after mount, now also reporting `resolved` (X6 port: forced, bootstrapped or PostHog-answered; `false` when PostHog is blocked or still loading). `resolved` is what lets a whole-screen gate distinguish "flag off" from "we do not know".
- `ProjectDetail.tsx:298` needs no edit: bootstrap is consulted before PostHog, so the Timeline renders on first paint from the server value and only a later PostHog update can change it.

### 2.8 `/api/v1/capabilities/co-managed`

`server/src/app/api/v1/capabilities/co-managed/route.ts`, `export const runtime = 'nodejs'`, `dynamic = 'force-dynamic'`. Session-authenticated via `getSession()` (precedent `server/src/app/api/v1/feature-flags/route.ts`); no session ⇒ 401 `{error:'Unauthorized'}`; a client-portal (non-interactive) session ⇒ the same 404 shape as adapter 2. The tenant always comes from the session; the route accepts no query parameters and no body — a `?tenant=` would be a tenancy oracle.

```json
{
  "capability": "co-managed",
  "tenantId": "<session tenant>",
  "admitted": false,
  "served": false,
  "forced": null,
  "reasons": { "admitted": "resolver-unregistered", "served": "resolver-unregistered" },
  "resolvers": { "eligibility": "unregistered", "participation": "unregistered" },
  "featureFlag": { "key": "release-v2-0-feature", "value": false },
  "evaluatedAt": "2026-10-26T12:00:00.000Z"
}
```

`Cache-Control: no-store`. It reveals only the caller's own tenant's decision and reasons. It deliberately reveals no resolver SQL, no row ids or entitlement amounts, no user identity, no other tenant's state, no PostHog token or person properties, and no capability list (later capabilities are not enumerable through this route).

Deliberately **not** doing, with reasons:

- No `CoManagedFeatureBoundary` and no `CoManagedWorkspaceBoundary`: the reference component is a raw-flag boundary; the gate plus `useCapability` replaces it, and the workspace boundary belongs to the card that ships a workspace (L1a).

- No change to `useFeatureFlag`'s PostHog precedence after mount: the bootstrap is a first-paint and offline-PostHog fix, not a new authority.
- No gate call in `middleware.ts`: edge runtime, per-request, and it would gate product *routing*, which is the product surface registry's job; gating in middleware would also 404 for tenants whose product code the DB cannot yet hold.

## Risks / open questions

1. **Per-process TTL vs multi-tenant correctness on a long-lived worker.** `services/workflow-worker` and `ee/temporal-workflows` are long-lived processes serving every tenant; a 30 s `serves` cache means a relationship ended at T can still be served until T+30 s in that process. Mitigation: `CAPABILITY_CACHE_TTL_MS` (workers can run at 0 or 5 s) and L1a's `invalidateCapability` on relationship end. Open: whether a fanout that begins before and finishes after a relationship ends must re-check per item — L1a's decision, but the batch form of `filterServed` is the seam for it.
2. **Can the cache leak across tenants?** The key is `capability|mode|tenantId|forceFingerprint` with no user or request component, and there is no `"*"`/anonymous entry, so a bleed requires a caller passing another tenant's id — which is an authorization bug above the gate. A test asserts two tenants with opposite decisions never share an entry. Residual risk: `filterServed` writes back per-tenant entries derived from a batch query; a resolver that returns the wrong tenant set would poison entries for one TTL. Mitigation: resolvers must return a subset of the input ids and the gate intersects defensively.
3. **`DISABLE_FEATURE_FLAGS=true` still returns `true` from `isFeatureFlagEnabled`** (`packages/core/src/lib/features.ts`). In L0a this is harmless because eligibility is unregistered; from L1a onward, E2E runs would admit *every* tenant with an entitlement row. Not a bug in the gate (the eligibility term is what protects us) but it must stay that way; a test pins "flag disabled does not imply admitted".
4. **Root-layout bootstrap cost.** One flag evaluation per tenant per 60 s per process (for the Timeline value) plus one `tenants` read per tenant per 5 min, and the layout is `force-dynamic` on every request. At L0a the eligibility short-circuit keeps the *capability decision* at zero evaluations; from L1a it is one PostHog call plus one eligibility read per tenant per 30 s. Unverified: whether `initializeApp.ts` (which registers the flag checker at line 51) is guaranteed to run before the first root-layout render; the gate treats a missing checker as flag-off, so the failure mode is a wrongly closed capability, not an open one.
5. **`admits` depends on a flag checker the Temporal worker never registers** (grep finds no `registerFeatureFlagChecker` under `ee/temporal-workflows`), while `services/workflow-worker` does register the PostHog-backed one (`services/workflow-worker/src/index.ts:51`). Any worker code that calls `admits` will therefore behave differently between workers. Rule: workers call `serves`/`filterServed` only; the AST contract (Rule D + entry-point scanning) is the enforcement, and the plan asks the reviewer to treat a worker `admits` call as a defect.
6. **Temporal skip sentinel contract.** Returning `{skipped:true}` instead of throwing keeps workflows alive, but a workflow that assumes the activity's effect happened will proceed silently. L5/L6 must handle the sentinel explicitly; L0a can only type it and document it.
7. **`Force` semantics for `serves`.** `FORCE_CAPABILITIES=co-managed:on` serves *every* tenant, including a `psa` tenant with no relationship. That is intended for self-host/dev/CI, but it means the switch is strictly more powerful than any resolver; it must remain unavailable to the commercial control plane (env only, never a settings UI).
8. **`co_managed` in the TS union before the DB accepts it.** *(Corrected in audit round 2; the earlier text claimed `resolveProductCode` maps `co_managed` to `psa`, which stopped being true when this card widened `PRODUCT_CODES`.)* `resolveProductCode('co_managed')` is valid and returns `co_managed`. In L0a the DB `CHECK` refuses the value, so such a tenant can only exist if L1a's migration has run and the image is then rolled back to L0a (blue/green N-1). What an L0a-only image does with that tenant:
   - session `product_code` is `co_managed` (`nextAuthOptions` reads through `resolveProductCode`); `getTenantProduct` returns `co_managed` (no `ProductAccessError`);
   - routes follow the `co_managed` column of `productSurfaceRegistry`: help-desk routes allowed, PSA-only routes and every unmatched route `not_found`, settings limited to the help-desk tab allow-list, PSA-only APIs denied, nothing in API metadata. That is strictly narrower than PSA, so it fails closed;
   - UI branches written as `productCode === 'algadesk'` (25 sites) take their PSA path for `co_managed`. Links they render to excluded pages land on the registry's `not_found`. The UI is inconsistent, but no surface opens;
   - the capability gate does not read `product_code`. With no participation resolver (L0a), `serves` is closed, so no co-managed surface appears unless `FORCE_CAPABILITIES=co-managed:on`.
   Ordering stays L0a → L1a. Rolling L1a back to L0a with co-managed tenants present gives the help-desk-shaped surface above, never PSA.
9. **`@alga-psa/core` gaining `next` as a peer dependency** is a new edge in a package every worker imports. The subpath split is the guard, but a future `export *` from `src/index.ts` that re-exports `capability/server` would reintroduce the worker-boot crash; the boot test (A6) and Rule D are the tripwires, and `src/index.ts` must not be touched by this card.
