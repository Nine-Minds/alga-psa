# TC T1: the V2 durable inbound stager drops MIME headers (design plan)

Card: a9bd7c01 "TC T1 · V2 durable inbound stager drops MIME headers (standalone fix)". PSA ticket alga-2026-0003160.
Wave 1 of the Ticket Conversations re-delivery (`~/tc-redelivery/PLAN.md`). It has no hard parents, and L4 depends on it.
This is a bug fix. It is **not** capability-gated, and it is not conversation-specific.

Baseline: this plan describes main @ `0184722cd6`, which is also the card branch HEAD when this was written. **No implementation
commits exist on the branch yet** (see §8, mismatch 1).

## 1. The defect

`EmailMessageDetails.headers` is how inbound security decisions see the wire headers. The two inbound paths disagree:

| Path | Where the MIME becomes `EmailMessageDetails` | `headers` | List-rewrite recovery |
|---|---|---|---|
| V1 (Redis pointer queue) | `shared/services/email/unifiedInboundEmailQueueJobProcessor.ts:329` `mapParsedMimeToEmailMessageDetails`, bag built inline at `:355-391`, set at `:440` | populated | yes (`:355`) |
| V2 (durable) | `shared/services/email/inboundEmailSourceStager.ts:112` `parseStagedMimeIntoEmailDetails`, object literal `:143-196` | **never set** | **no** (`from` copied raw at `:136`, `:157-160`) |

What breaks on V2 because `headers` is undefined:

- **Sender authentication.** `processInboundEmailInApp.ts:964-967` looks up `authentication-results`, finds nothing, and
  `verifySenderAuthentication` returns `null`. `allowsContactSenderAttribution(null)` is false, so every contact match
  for a correctly authenticated sender is discarded (`:972`). Internal-user attribution fails closed the same way.
- **List-rewrite recovery.** `x-resolved-original-sender` is never set, so `isVerifiedListRewrite` (`:968`) is always
  false, and `from` stays the list address (`'Jane' via support <support@lists…>`) instead of the recovered author.
- **The Microsoft same-org check.** `isMicrosoftIntraOrgSender(provider, headers)` (`senderAuthVerification.ts:128-137`)
  returns false when there are no headers, so M365 intra-tenant mail fails both gates.
- **Automated-message and loop detection.** `detectAutomatedInboundMessage` (`automatedMessage.ts:109-112`, used by
  `notificationLoopDetection.ts:262,408`) and `extractRelevantInboundHeaders` (`automatedMessage.ts:86`) see no
  `auto-submitted`/`precedence`/… headers on V2. Auto-replies are not suppressed there, and the forensic header snapshot is empty.
  The card description does not mention this. It is fixed by the same change and called out in §6.

Main already knows about the defect: `server/src/test/integration/clientReplyResponseState.integration.test.ts:68-74`
mocks `allowsContactSenderAttribution` to `true`, with the comment "parseStagedMimeIntoEmailDetails drops message headers".

The other V2 callers of the stager are `inboundEmailCoreProcessor.ts:182` (the processing path), `inboundEmailArtifactWorker.ts:141`
and `inboundEmailIngressStagingWorker.ts:431`. All of them get the fix through the one function.

## 2. Two header views exist today, and they differ on purpose

Main builds a header bag in two places, and they are **not** interchangeable:

| | V1 downstream bag (`unifiedInboundEmailQueueJobProcessor.ts:358-379`) | List-rewrite bag (`shared/lib/email/listRewriteSender.ts:208-242`, private `extractHeaderBag`) |
|---|---|---|
| Source | mailparser `parsed.headers` Map (decoded, unfolded) | `parsed.headerLines` (raw lines), falling back to the Map |
| Repeated headers | all values, `\n`-joined in wire order | **first (topmost) occurrence only** |
| Structured headers (`from`, `reply-to`, `sender`, `to`…) | dropped (Map values are objects) | present as raw strings |
| `x-resolved-*` / `x-list-*` from the wire | stripped | not stripped (never read by `computeListRewriteSender`) |
| Consumer | `EmailMessageDetails.headers` → `verifySenderAuthentication` (splits on `\n`, trusts `blocks[0]` only, `senderAuthVerification.ts:70-78`), `isMicrosoftIntraOrgSender`, automated-message detection | `computeListRewriteSender` → `authResultsTrustDomain` (`listRewriteSender.ts:72-106`) |

**Security constraint.** `authResultsTrustDomain` scans *everything* in its bag for an aligned pass. It is safe only because
the bag holds the topmost `Authentication-Results`, the one stamped by our receiving MTA. Feeding it the V1-style
`\n`-joined value would let an attacker-stamped lower `Authentication-Results` block (for example
`dmarc=pass header.from=evil.example`) vouch for a forged `X-Original-Sender: ceo@evil.example`. So the
card's instruction to replace `extractHeaderBag` with "one shared header-bag helper" has to keep this as a separate
**topmost projection**. It must not merge it into the joined bag. Without that rule the refactor would be a trust regression.

## 3. Design: one module, two projections, one entry point

New module **`shared/lib/email/inboundHeaderBag.ts`**. It is the only place that turns a mailparser `ParsedMail` into
header data. `listRewriteSender.ts` becomes pure trust logic with no knowledge of mailparser's shape.

```ts
// Downstream bag for EmailMessageDetails.headers: from the parsed.headers Map, lower-case names,
// wire x-resolved-*/x-list-* dropped first, string values as-is, string[] values '\n'-joined in wire order,
// other (structured) values dropped. Byte-for-byte what V1 builds today.
export function buildInboundHeaderBag(parsed: any): Record<string, string>;

// Trust bag for list-rewrite recovery: the current extractHeaderBag moved here verbatim
// (headerLines first occurrence wins, Map fallback), plus the same wire x-resolved-*/x-list-* strip.
export function buildTopmostHeaderBag(parsed: any): HeaderBag;

// Single entry point both paths call once per message.
export function resolveInboundHeaders(parsed: any): {
  headers: Record<string, string> | undefined;   // undefined when empty (as V1 today)
  listRewrite: ListRewriteResolution | null;
  from: { email: string; name?: string };        // recovered author when listRewrite, else parsed From
};

// Same contract as today's listRewriteSender export (env flag INBOUND_RESOLVE_LIST_ORIGINAL_SENDER honoured).
export function resolveListRewriteSender(parsed: any): ListRewriteResolution | null;
```

`resolveInboundHeaders` = `resolveListRewriteSender(parsed)` over `buildTopmostHeaderBag`. Then `buildInboundHeaderBag`.
Then, only when `listRewrite` is set, it adds `x-list-address`, `x-resolved-original-sender` and `x-resolved-original-sender-via`. The
`from` name rule stays V1's: `listRewrite.sender.name || parsedFrom.name || undefined`.

**Import direction (acyclic):** `inboundHeaderBag.ts` → `listRewriteSender.ts` (`computeListRewriteSender`,
`HeaderBag`, `ListRewriteResolution`). `listRewriteSender.ts` loses `extractHeaderBag`, `resolveListRewriteSender` and the
env-flag helper, which move to the new module. It keeps `computeListRewriteSender` (pure) and its types. This differs from the
reference (§8, mismatch 3), which left `listRewriteSender.ts` untouched and so left the duplicate in place.

### Deliberately unchanged

- **V1 output.** The V1 downstream bag, the `from` resolution and the recovery log stay byte-identical. The topmost projection is the
  current `extractHeaderBag` moved verbatim. The added strip there is a no-op, because `computeListRewriteSender` never reads
  `x-resolved-*`/`x-list-*` keys. This is checked by the parity test (T4) and the existing V1 tests (§4).
- `verifySenderAuthentication`, `computeListRewriteSender`, `isMicrosoftIntraOrgSender`, `processInboundEmailInApp.ts`,
  the `EmailMessageDetails` type (`Record<string,string>`), and the Gmail adapter path (it supplies its own record).
- No capability gate, no flag, no migration, no new table, no new query. `UNIFIED_INBOUND_EMAIL_DURABLE_MODE` gating is
  untouched.
- **Nothing conversation-specific.** The reference 6H test hunks for `ticket_conversation_email_routes` (in
  `imapWebhookHandoff`, `googleWebhookUnifiedQueue`, `microsoftWebhookUnifiedQueue` and the
  `unifiedInboundEmailQueueJobProcessor.fetch` test) are **not ported**. That table does not exist on main, and routing on it is L4's.

## 5. Review guide outline

- **Chapter 0, neutrality.** With the durable mode `off` (default) for a flag-off tenant and a co-managed tenant, inbound reply via
  GreenMail → V1 path, same ticket/comment/attribution as main; `inbound.replyHandling` budget green.
- **R1, reproduce on main.** With `UNIFIED_INBOUND_EMAIL_DURABLE_MODE=enforce`, a reply carrying an aligned
  `Authentication-Results` → sender auth evaluates `null` (contact match discarded; diagnostics show it).
- **R2, the fix.** Same reply on the PR → aligned result, contact attributed. A list-rewrite reply → recovered author.
- **R3.** T1–T7 red→green.
- **Final chapter, kill switch.** Not applicable: the card adds no gated entry point. Say so explicitly; do not invent one.
- No video. The behaviour is not user-visible beyond attribution, and R1/R2 are shown in logs/DB.

## 6. Deployment and who is affected

- No migrations, no new tables, nothing for tenant metadata/manifest/deletion.
- `UNIFIED_INBOUND_EMAIL_DURABLE_MODE` is **process-wide** (`shared/services/email/inboundEmailDurableStore.ts:47-48`), not
  per-tenant, and the webhooks divert to V2 only in `enforce` (`packages/integrations/src/webhooks/email/imap.ts:122-147`,
  likewise `googleWebhookHandler.ts:~304`). In `shadow`, V2 parses and stages, but legacy effects are authoritative. **Every
  tenant served by an `enforce` deployment** changes; nobody else does. The variable does not appear in `~/nm-kube-config` or
  the repo helm charts, so hosted runs `off` as far as this host shows. **The PR must confirm the set of deployments with
  the captain** (e2e has an enforce-conditional spec, `e2e-tests/tests/inbound-email.spec.ts:377`).
- What changes for those tenants (all of it is V1 parity):
  - sender auth now evaluates the real headers, so contact and internal attribution work for aligned senders;
  - verified list-rewrite mail is attributed to the recovered author, and the ingress envelope `from` (`buildEnvelope`,
    `inboundEmailIngressStagingWorker.ts:468-481`) records that author;
  - M365 intra-org mail is trusted;
  - automated-message and loop detection start suppressing auto-replies on V2.
- Zero-disruption (PLAN §3): no capability involved, no hot-path query added, N-1 safe (pure code).

## 7. Risks

1. **Trust regression if the projections are merged.** See §2, guarded by T7 and the module doc.
2. **Behaviour shift for `enforce` tenants** (§6). This is the intended fix. Mail that used to fail closed now attributes or suppresses.
3. **V1 drift during the 3-way apply.** `unifiedInboundEmailQueueJobProcessor.ts` changed on main since the reference
   (123 lines). Apply the hunk with `git apply --3way` and check it against main, never by whole-file restore. Guarded by T4 and the V1 suite.
4. **Moving `resolveListRewriteSender`** changes an export path. Main has only one caller (V1, rewired here) plus its test.
   Grep before the move.

## 8. Where the code and the orders disagree

1. **The XO order says "the implementation already exists at this HEAD".** It does not. Branch HEAD = `origin/main`
   `0184722cd6`, with no card commits and the working tree clean apart from an unrelated `package-lock.json`. This plan is written against main.
2. **The manifest says "Include the regression tests the reference added".** The reference 6H test hunks are all about
   `ticket_conversation_email_routes` durable routing (conversation work, L4). The reference added **no** V2 header
   regression test. T1–T7 are new work.
3. **The card says to replace "listRewriteSender.ts's private extractHeaderBag".** The reference did not do this. Its helper only
   replaced V1's inline bag, so a second bag builder stayed. A naive merge is unsafe (§2). This plan keeps one module
   with two named projections.
4. The reference helper's doc comment cites `inboundNamedConversationEmail.ts` and named-conversation admission. Neither
   exists on main, and both are out of scope, so they are dropped from the doc.
5. Not in the card description: V2 automated-message and loop detection is broken by the same defect and fixed by this change (§1, §6).
