# T0-2 — Billing: late approved hourly time

Reviewer question: **"Is approved hourly time dated inside an already-invoiced period billed on the next
invoice, visibly, and are voided/cancelled windows handled correctly?"**

Card: CM T0-2 (`963783ee`) · wave 2, standalone fix straight to main (no flag)
Depends on T0-1 (merged to main) · Reference: `feature/co-managed-it` @ `2d00cb6f0e` (base `7e8d87a948`)
Owned paths: `~/cm-redelivery/manifests/T0-2.md` · Charter: PLAN.md §1/§3, T0-standalone §1 item **B2**

The defect: a time entry approved *after* the invoice for its service period has been generated is silently
never billed — no error, no line, no notice. The reference also mishandles windows belonging to voided and
cancelled invoices. The answer this plan has to make true is: **billed exactly once, on the next invoice,
visibly** — with the three window shapes (billed, voided, cancelled) each proven by an integration test
carrying exact amounts.

### Mandatory strip

entirely rather than ported. The card's own sentence for this is "change nothing beyond the listed fixes";
the strip is the first instance of it.

## 2. Windows: what counts as "closed"

The whole correctness of this card sits in one predicate, so state it once:

| Invoice status of the period's invoice | Window | Late entry dated inside it |
|---|---|---|
| `finalized` / `sent` / `paid` / `partially_paid` / `overdue` (a real issued invoice) | **closed** | Billed on the next invoice, flagged late |
| `void` | **not closed** | Bills as ordinary time on the next invoice — no "late" flag, no second window |
| `cancelled` / `draft` / none | **not closed** | Same: ordinary billing |

The reference's bug is that it treats *any* invoice row for the period as a closed window, so a voided or
cancelled invoice suppresses the entry a second time. The loader must join on the invoice **state**, not on
the existence of a row. Draft invoices are not closed either — they have not been issued, and re-generating
them picks the entry up the normal way.

Two further rules that follow from "exactly once":

- **One closed window per entry.** If a period was invoiced twice (void then re-issue), only the live
  invoice closes it; the voided one must not contribute a second OR-term.
- **No double-billing inside the same run.** The next invoice must take each entry at most once even if it
  is reachable through two windows; assert by amount, and assert a second generation run after a successful
  one produces no late line (idempotency).

## 3. Product decision taken at this desk: bounded lookback

The reference has no lookback at all — every historical approved, uninvoiced, late entry bills on the next
invoice, unbounded. That is not shippable: a tenant with years of history would get one catastrophic
invoice. Card instruction is explicit that the Design Session settles it, with a bounded lookback as the
default:

- **Lookback: 90 days before the invoice period's end**, defined in **one** exported constant in
  `lateHourlyTime.ts` (`LATE_TIME_LOOKBACK_DAYS = 90`) and applied in the loader, never duplicated in the
  UI or the batch scanner.
- **Entries older than the lookback do not silently vanish.** They are outside the billed set but remain
  visible in the notices panel as "outside lookback" so an operator can see them, and they are counted in
  the backlog report.
- **Tenant-configurable later — not now.** No tenant flag, no settings surface, no capability gate. The
  constant is the seam; a follow-up card turns it into a settings value.
- **Backlog report first.** A per-tenant report (entries that would bill late, and entries outside lookback)
  is produced before rollout, per the card's release note. It is a script/query and an ops artifact, not
  product code and not evidence media in the PR.

## 4. Where the late charge joins the invoice

The late entries must resolve through the same path ordinary hourly time uses, or amounts drift:

- `computeTimeBasedCharges` gains the late set as an additional input; it does **not** gain a second rate
  resolver. Rates, contract-line selection, bucket/override handling and rounding all come from main's
  existing resolution.
- The invoice line carries the entry's own description plus the suffix `(late time, service period
  <start>–<end>)`, using the period of the **invoice that closed the window**, not the date the entry was
  approved.
- `describeTimeCharge` (invoiceService) is where the suffix text is built, so the preview, the PDF and the
  API agree on wording; `invoiceAdapters.ts` only maps it.

## 5. The Automatic Invoices smoke finding

The screen hides service periods ending after today unless the date filter is manually widened, so an
operator setting up a run for the current period does not see it. **Decision: fix it in this card**, because
the late-time work makes the period picker load-bearing (the notices panel points at "the next invoice",
which is usually the in-progress period). The fix is the default filter's upper bound: include periods whose
start is at or before today and whose end is in the future, i.e. default to "current and past periods"
instead of "periods fully in the past". It is a one-line predicate in `AutomaticInvoices.tsx`, no new
component.

If during implementation this turns out to require more than the default predicate (e.g. a server-side
filter contract), **document it instead** and leave the behavior as is — the card allows either, and a
half-fixed picker is worse than a documented one.

## 6. Acceptance (bar A, plus the review rider)

**A — integration tests with exact amounts** (`server/src/test/integration/billing/lateApprovedHourlyTime.integration.test.ts`, ~522 lines in the reference):

1. **Late inside a billed period.** Invoice the period; approve a later-dated entry inside it; next invoice
   bills it exactly once, with the exact expected amount asserted (not "greater than zero").
2. **Voided window.** Void the period's invoice, then approve/detect the entry: it bills as ordinary time on
   the next invoice, once, and **not** with the late suffix.
3. **Cancelled window.** Same as voided.
4. **Lookback.** An entry older than 90 days is not billed and is reported as outside lookback.
5. **Idempotency.** Re-running generation after a successful run adds nothing.
6. Unit: `lateHourlyTimeNotices.ui.test.tsx` (panel renders the entry and its closed period),
   `invoiceAdapters.test.ts`, and the five `invoiceGeneration.*` selector tests updated only where the
   input shape changed (1 line each in the reference — keep them 1 line).

**R — review rider**: video, *approve old-dated time after an invoice exists → notice appears → next
invoice bills it exactly once*. The guide must show the invoice line with the `(late time, service period …)`
text legible.

**CI**: unit + affected Nx lanes, server unit shards, integration shards 1–4 green.

## 7. Risks

| Risk | Handling |
|---|---|
| Unbounded history bills at once | 90-day lookback constant, single definition; outside-lookback entries surfaced and reported |
| Double billing (re-run, or two windows for one period) | Idempotency test + one-closed-window predicate + exact-amount assertions |
| Void/cancel windows re-suppressed | Window joins on invoice state, not row existence; three separate integration tests |
| Perf: OR per closed window; tenant-wide scan with per-client loop | Scope the scan by client and batch it; index the entry lookup on (approved-at/date, contract line, invoiced link) |
| Charge amounts drift from ordinary time | Route through `computeTimeBasedCharges`/`chargeResolution`; no second rate resolver |
| File overlap with T0-1 (billingEngine, computeTimeBasedCharges) | Rebase after T0-1 is on main before raising the PR; 3-way hunks, never whole-file |
| Co-managed coupling sneaks back in with the loader | `joinTimeEntryBillingWorkContext` UNION arm stays out; `coManagedInvoiceJourneyCases` dropped |

## 8. Deliberately not done

- No tenant flag or settings UI for the lookback (constant is the seam).
- No capability gate, release-version string or flag of any kind — straight to main.
- No co-managed time-work references, no co-managed invoice journey cases.
- No second billing engine, no parallel rate resolution.
- No ledger, census or evidence-media machinery in the PR.
- No backfill of historical unbilled time: the backlog report tells the operator what exists; billing past
  the lookback is a separate decision.

## 9. Implementation notes (as built)

- **Automatic Invoices default period filter: documented, behaviour unchanged.** The picker's `to` bound is
  applied server-side to the period *end* column (`getAvailableRecurringDueWork` -> `DATE(period_end) <= to`) and
  the same value is the readiness date (`asOf`) for every row. Showing in-progress periods (start <= today,
  end in the future) therefore needs a server-side filter contract change (a start-bounded predicate separate
  from `asOf`), not a default predicate in `AutomaticInvoices.tsx`. Per section 5 that case is documented, not
  half-fixed. Operators can still widen the date filter. The notices panel is independent of this filter.
- **Scan scoping: done.** `filterBillingPeriodsWithPotentialUnresolvedWork` was already one batched read, but its
  time-entry query was tenant-wide over the date span while the usage read was client-scoped. The time-entry read
  now carries the same scope (`tickets.client_id` / `projects.client_id` in the listed clients); the in-process
  per-client window match is unchanged. The mocked `recurringDueWorkReader` and `nonContractDueWork` suites got the
  minimal emulation lines for the new nested `whereIn`/`orWhereIn`. The serial per-period
  `calculateUnresolvedNonContractChargesForExecutionWindow` call is unchanged. The late-time notices are one batched
  query per request (`findLateApprovedHourlyTime`), optionally scoped by client, loaded on mount and after each
  generation refresh rather than on paging or filter changes.
- **Closed statuses on main:** `finalized`, `sent`, `paid`, `partially_paid`, `partially_applied`
  (main's partial status), `overdue`. Main's void action sets `cancelled`, so void and cancelled are the same
  state in the DB; the tests cover a void-action window and a directly cancelled window.
- **Backlog report:** `npx tsx scripts/billing/report-late-approved-hourly-time.ts --tenant <uuid>` prints the two
  counts (would bill late / outside lookback) per tenant and per client, using the product's own loader.
- **Limitation:** windows are read from materialized `recurring_service_periods`; a line with none yet has no
  closed window and its time bills through its own generation as before.
