## 0. Resolved product decision (XO, this session)

**G4(b): a mapped blank Tags cell on a contact CSV re-import does NOT clear the contact's existing tags.** A blank cell means "no opinion"; only a non-blank cell states the contact's tag set, and then it replaces it.

Rejected alternative (one line, for the record): *blank clears* — the reference branch's behaviour (`buildContactCsvImportRows` sends `tags: ''`) — rejected because a re-export of a subset of columns, or a spreadsheet that drops an empty trailing cell, would silently strip every tag on the tenant's contacts.

Consequences, binding on the implementation:
- Tags presence remains *column-mapping driven* (an unmapped Tags column never produces a `tags` key), and the cell *adds* a second condition: `tags` is set only when the mapped cell's trimmed value is non-empty.
- A blank cell produces no `tag_mappings` delete, no tag write, and no tag events — byte-identical to the unmapped case.
- The failed-records download keeps writing a Tags column only when the import carried one; with this decision that condition is also what makes a re-import of the failure file safe.

The transactor a `trx.transaction(cb)` callback receives carries `parentTransaction` and `executionPromise` (knex 3.1.0: resolves when the savepoint is released, rejects when it is rolled back to). ## 11. Risks and open observations

1. **A savepoint that swallows tag failures reports the row as successful** (`console.error`, matching main's warn-and-continue). Accepted: main already imports the row and loses only the tags, and the alternative — failing the whole row — changes CSV import semantics on a standalone fix. Recorded in the guide as "the contact is imported; the tags are not".
2. **`createTagsForEntityWithTransaction` publishes nothing for a tag text that already exists and is already mapped** — unchanged; not this card.
3. **`ClientService.handleTags` (`ClientService.ts:1359`) writes `tag_mappings` on a bare connection inside its caller's transaction.** Not a hang today (no prior mapping lock in the create path) but non-atomic: a client update that rolls back keeps its tags. Same family as G2; one-line class of bug; deferred to a follow-up so this card keeps its bar.
4. **`vite-tsconfig-paths` is only declared in `ee/server`** and reaches `packages/tags` today only through root hoisting. Declare it in `packages/tags/package.json` devDependencies rather than relying on the hoist; if the resolver is rejected, the fallback is to alias `@alga-psa/*` in the tags vitest config.
5. **`TagManager` still keeps a local `tags` state through `useReconciledTags`; the TagContext sync effect now writes through `commitBase`.** Two sources of truth remain (base + pending ops) by design; the effect must not call `onTagsChange` on a content-equal refresh, or it will loop with parents that echo the prop back. A1's equal-content case is the guard.
6. **G4(a)'s `mergeContactsById` only fixes the list's in-memory append.** If the list is paginated and the updated contact is not on the current page, the merge is a no-op for it and the next fetch is authoritative — accepted, and R2 records it.
