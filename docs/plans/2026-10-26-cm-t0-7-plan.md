- **Citus**: `ensureSequentialMode` is taken from `server/migrations/20261020120000_add_default_payment_terms_to_billing_settings.cjs:1-10` (a `DO` block guarded on `pg_extension`), and the backfill is per-tenant so each `UPDATE` is single-shard; sequential mode is belt-and-braces for the `ALTER TABLE` propagation.
- **Re-dating**: newest migration on main is `20261025080000_staging_task_fks_no_cascade.cjs`; the reference's `20261019120000` is interleaved and is re-dated to `20261026090000` and `20261026090100` (D §1.4: never keep a branch timestamp older than main's).
- **"Migrations: 1"** in the card description counts the reference's one file. PLAN.md §3 wins: `NOT VALID` and `VALIDATE` live in separate files (migration-lint rule 2). Two files, one logical migration.
- **NULL means active**: sign-in treats any falsy `is_inactive` as active (`packages/auth/src/lib/nextAuthOptions.ts:1691+` authorises by email, then truthiness), while seat counts read `is_inactive = false`. The backfill to `false` preserves the sign-in meaning and makes those rows countable; that is why seat usage may rise.
- **N-1 compatibility**: the schema makes `NULL` unwritable while the previous colour still serves. Old `updateUser` happily wrote whatever the caller sent, and the old mapping turns 23502 into `Missing required user field`. Real UI paths send booleans, so the exposure is crafted calls only (recorded in Risks).
- **Rollback**: traffic flip to the previous colour. The check and the constraint are additive; `down` never resurrects NULLs (a down-migration is never run in prod).

### 5.1 SQL sketch

```js
// A — 20261026090000, transaction: true
await ensureSequentialMode(knex);                       // DO $$ IF citus THEN SET sequential $$ END $$
await knex.raw(`SET LOCAL lock_timeout = '2s'`);
if (await knex.schema.hasColumn('users', 'is_inactive')) {  // guards a replay on an older schema
  await knex.raw(`ALTER TABLE users ALTER COLUMN is_inactive SET DEFAULT false`);
  for (const { tenant } of await knex('tenants').select('tenant')) {   // single-shard batches
    let moved;
    do { moved = await knex.raw(`UPDATE users SET is_inactive = false
      WHERE tenant = ? AND is_inactive IS NULL
        AND user_id IN (SELECT user_id FROM users WHERE tenant = ? AND is_inactive IS NULL LIMIT 5000)`, [tenant, tenant]); }
    while (rowCount(moved) === 5000);
  }
  if (!await hasConstraint('users', 'users_is_inactive_not_null')) {
    await knex.raw(`ALTER TABLE users ADD CONSTRAINT users_is_inactive_not_null
      CHECK (is_inactive IS NOT NULL) NOT VALID`);
  }
}
// B — 20261026090100, exports.config = { transaction: false }
if (await hasConstraint('users', 'users_is_inactive_not_null'))
  await knex.raw(`ALTER TABLE users VALIDATE CONSTRAINT users_is_inactive_not_null`);
await knex.raw(`ALTER TABLE users ALTER COLUMN is_inactive SET NOT NULL`);   // metadata-only
await knex.raw(`ALTER TABLE users DROP CONSTRAINT IF EXISTS users_is_inactive_not_null`);
```

### 6.2 O3 — team members: `addUser`, role by id, no shared password
Defect: `onboardingActions.ts:285` (`hashPassword(member.password || 'TempPassword123!')`), `:294` writes it, `:302-306` looks the role up as `role_name = member.role.toLowerCase()` (every seeded role is `Admin`, `Technician`, … so the lookup misses), `:315-327` falls back to `roles.where({msp:true}).orderBy('role_name').first()` — alphabetically `Admin`. `:429`, `:446` are the bulk twin; `:494-498` persists the successful members *including `password`* into tenant onboarding progress; `:384-403` pre-slices by `getLicenseUsage` and ignores pending invitations; `OnboardingWizard.tsx:218-219` filters only `createdTeamMemberEmails`, so "Next" re-creates an invited member with a known password.
Fix: both actions delegate to `addUser` (`packages/users/src/actions/user-actions/userActions.ts:518`) with `roleId` resolved by exact `role_name` from `roles.where({msp:true})`; a missing password or unknown role is refused with a message; `addUser` supplies the permission check (`user:create`), platform-wide internal email uniqueness and seat admission (its own inline license block, `userActions.ts:592-650`, returning `LICENSE_LIMIT_REACHED`/`SOLO_PLAN_LIMIT`). Invitations already exist on main (`TeamMembersStep.tsx:183-205` → `sendUserInvitation`), so the replacement for the shared temp password is **the invitation the step already sends**: the invitee sets their own password at acceptance. The wizard's Next guard skips `invitedTeamMemberEmails` and stops when an email-mode member was never sent. Progress is written without `password`. `getOnboardingLicenseUsage` reports `used` = active internal users + pending invitations (`user_invitations` where `used_at IS NULL AND expires_at > now()`, tenant-scoped), counted by `countPendingInvitationSeats` — the same helper `sendUserInvitation` uses for `reservedSeats`; the `licenseStatus` returned by `addSingleTeamMember`/`addTeamMembers` reads the same number. An invitee who accepts gets `used_at` set and becomes an active user, so they are counted once. Reservation semantics, by design: when seats remain only because of pending invitations the step reports the limit reached and blocks a direct-create save that `addUser` (active users only) would itself admit; those seats belong to the invitees. The co-managed seat branch is stripped.
Restored invariant: role chosen by the administrator is the role granted; no account is created with a password the administrator knows; seat admission is the same on both creation paths.

### 6.3 O2 — who may run workspace setup
Defect: none of `saveClientInfo:115`, `addSingleTeamMember:246`, `addTeamMembers:373`, `createClient:528`, `addClientContact:656`, `setupBilling:738`, `configureTicketing:833`, `saveOnboardingStepPosition:1186`, `completeOnboarding:1204` checks a permission; `server/src/app/msp/layout.tsx:103-109` sets `needsOnboarding` for every internal user; `MspLayoutClient.tsx:115-124` forces the redirect and `:157` re-fetches as a fallback; `onboarding/page.tsx:24-28` loads the wizard.
Model: **one permission, `settings:update`**, checked in **every write action** (authoritative — the action is reachable as a server action without the wizard) and rendered as a report in `getWorkspaceSetupAccess` used by the **RSC** (`layout.tsx`, with `canRunOnboarding` also pushed into the client fallback) and by the onboarding page. The gate is `isLicensedUserType(user.user_type)` **and** `settings:update`: `settings:update` is also held by `client:Admin` (permissions match resource+action within the caller's own portal), so the permission alone would let a client-portal admin run setup and create internal users. `isLicensedUserType` (`'internal'`) is the test `msp/layout.tsx` applies to a session; `service` principals hold no UI session, so `isMspPrincipalUserType` was judged too wide. Every caller goes through `canRunWorkspaceSetup` (nine actions + `getWorkspaceSetupAccess`, which feeds `layout.tsx` and `onboarding/page.tsx`). Reason for `settings:update` over `user:create`: the wizard writes tenant settings, a client, a contract line and ticket defaults, not only users.
Failure shape: actions return `{success:false, error:'Only an administrator can complete workspace setup.'}` rather than throwing a 403 — the wizard renders inline action errors, and a thrown error inside a server action surfaces as a generic client exception. The RSC **redirects to `/msp/dashboard`** rather than `notFound()`: the route exists for every tenant, and 404 would be a lie the reviewer has to explain; the dashboard is where the non-admin's work actually is. No 403 page: a full-page forbidden screen for a setup wizard is a dead end.
Restored invariant: a technician cannot create users, rewrite ticket defaults, or mark the tenant onboarded.

### 6.4 O4 — the setup email change
Defect: `onboardingActions.ts:133` writes `users.email` — the credentials sign-in identity (`nextAuthOptions.ts:1649,1691`) — with no format and no global uniqueness check.
Validation: only when the trimmed, lower-cased value differs from the caller's current email: `isValidEmail` (already imported from `@alga-psa/core`), then `User.findUsersByEmailAndType(newEmail, 'internal')` and refuse if any hit has a different `user_id`. Domain is not restricted (no tenant email-domain policy exists for internal users on main — unverified that any policy module exists; none is imported by this path); uniqueness is per `user_type = 'internal'` because the same address may legitimately be a `client` user (matching `findExistingUserByEmailGlobally`, `userActions.ts:371-395`).
TOCTOU: the check runs immediately before the update, inside the write's transaction callback, but the read itself goes through `User.findUsersByEmailAndType` on the admin connection (`packages/db/src/models/user.ts`), because it must see every tenant — so it is **not** part of the write's transaction. The remaining window runs from that read to the write's commit. Moving the read into the transaction would not close it either: at READ COMMITTED a concurrent uncommitted claim is invisible, and there is **no database unique constraint on `users.email`** (uniqueness is app-level everywhere), and a Citus-distributed `users` (on `tenant`) cannot carry a cross-tenant unique index on `email`. Two concurrent setup changes therefore still have a narrow window. It is narrowed, not closed; recorded in Risks. No re-verification email is sent — the change is a signed-in administrator's own identity, and the reference behaviour (immediate write) is kept so sign-in keeps working with the address just typed.

### 6.5 O5 — a start number never reissues a ticket number
Defect: `onboardingActions.ts:852-868` writes `last_number = 0, initial_value = start` whenever the setup form carries a start number. `generate_next_number` (`server/migrations/20250220165247_update_generate_next_number_function.cjs:24-36`) issues `GREATEST(last_number+1, initial_value)`, so after the reset any number at or below the issued high-water mark is handed out again.
Mechanism: keep the allocator (a counter row serialised by `pg_advisory_xact_lock(hashtext(tenant||entity_type))`) and stop rewinding. Rewind `last_number` to 0 **only when the tenant has no `tickets` row**; otherwise write `initial_value = start` alone, which is a monotone floor. Add `SELECT pg_advisory_xact_lock(hashtext(?))` for `'<tenant>TICKET'` at the top of the numbering block, so a concurrent `generate_next_number` cannot slip between the ticket-existence probe and the update — the reference does not take this lock, and without it a concurrent create can still be rewound (see §7). Not a ledger row and not a sequence: `next_number` is already the allocator of record, and a second allocator would fork numbering for every other entity type.
Cost of a reissue: two tickets share a `ticket_number`, client-facing replies, invoice/contract references and search all resolve to the wrong ticket; it is not repairable by a later renumber because the number is already in outbound mail.

### 6.6 O6 — `is_inactive` is a strict boolean
Defect: `users.is_inactive` is nullable (`server/migrations/202409111020_add_is_inactive_field.cjs:4`, `DEFAULT false`, no `NOT NULL`); `userActions.updateUser:1187` writes whatever it is given, and the seat check at `:1080` and every seat count (`get-license-usage.ts:31-36`, `internalUserLicenseGuard.ts:52-58`) filter `is_inactive = false`, while sign-in tests truthiness. So `null` (or the string `'false'`) is a working, uncounted account.
Fix: refuse `'is_inactive' in userData && typeof !== 'boolean'` with `code: 'INVALID_ACTIVE_STATE'` before any write, and map that code to the existing generic string in the three profile forms. SQL shape as §5. Backfill value `false` = active.
Budget: `withLockRetry` scopes its `SET LOCAL lock_timeout = '2s'` to the one statement (prior value read and restored on both the success and rollback paths; `RELEASE SAVEPOINT` does not undo `SET LOCAL`), and each backfill batch runs through it, so a row held for >2s retries that batch instead of aborting the migration — up to `LOCK_ATTEMPTS = 3` attempts, i.e. a lock held for ~6s or more still fails the statement and the whole migration (its transaction rolls back; the run is repeatable). Every failed attempt, including the last, rolls back its savepoint and restores the prior `lock_timeout` before retrying or propagating. `20261026090100` sets no `lock_timeout`, so it has nothing to leak. `SET DEFAULT` is catalog-only; `ADD CONSTRAINT … NOT VALID` is catalog-only; the only scan is `VALIDATE`, under SHARE UPDATE EXCLUSIVE; `SET NOT NULL` uses the validated check and does not rescan (PG12+); the data change is per-tenant ≤5 000-row batches with `lock_timeout = '2s'` and retry, so a busy `users` table (hot: every auth lookup) never holds a long queue. Preflight: `SELECT tenant, count(*) FROM users WHERE is_inactive IS NULL GROUP BY tenant ORDER BY 2 DESC;` must be run before the release note because it predicts the seat-usage delta.
Rollback: forward-only; previous colour runs on the new schema, and only a crafted `NULL` write regresses (23502 → `Missing required user field`).

### 6.7 O11 — seat check on reactivation: **yes**
Take it. It is ~10 lines using an existing helper, and without it the seat invariant holds only on create and invite while deactivate→reactivate is an unbounded free seat. Placement: in `updateUser`, after the email/`existing` read and before `User.update`, only on the **inactive→active transition** (`existing.is_inactive === true && userData.is_inactive === false`) and only for `user_type = 'internal'`, calling `checkInternalUserLicenseLimit(trx, tenant)` with no options. That last part diverges from the reference, which fires whenever `is_inactive === false` — that would refuse an unrelated edit (a phone number) by an already-active user on a tenant at its limit.
Error code: pass through the guard's own `LICENSE_LIMIT_REACHED` / `SOLO_PLAN_LIMIT`; both must be added to `UpdateUserErrorCode` (`userActions.ts:71-80`), and the settings UI then shows the same message as create.
Requires `existing` to also select `is_inactive` and to be read whenever `is_inactive` is present, not only for email/timezone.
Restored invariant: an internal user only occupies a seat the tenant has.

## 10. Risks / open questions

1. **Email TOCTOU** (§6.4): no DB constraint, so two concurrent changes can still race. Closing it needs a cross-tenant identity table or a coordinator advisory lock; `pg_advisory_xact_lock` on the app's tenant-scoped connection may execute on a worker, not the coordinator — unverified, so not relied on.
2. **`username` is not updated** with `email` by `saveClientInfo`; sign-in reads `email` (`nextAuthOptions.ts:1649`), but any other consumer of `username` keeps the old value. Unverified whether one exists; left as main behaviour.
3. **`settings:update` is broader than "is an administrator"**: any custom role granted it can run setup. Accepted (it is the same grant the reference chose, and the alternative would be a new permission plus a global catalog backfill, which PLAN §3 forbids for a T0 card).
4. **`VALIDATE` on a large `users`** takes a full scan under SHARE UPDATE EXCLUSIVE; the upgrade-order CI job must time it. If it exceeds the deploy budget, split the `VALIDATE` into its own deploy (H §2's two-deploy variant).
5. **Seat-usage delta** is unknown until the preflight query runs; a tenant with many NULL rows may lose available seats at upgrade time, which is the release note's warning.
6. **O5 residual**: numbers from deleted tickets can be reissued. The advisory lock closes the concurrent-creation race but not this; a strict never-reuse rule would need a high-water column that survives ticket deletion.
7. **O2 test file** from the reference also asserts co-managed step refusal; removing those cases leaves the file shorter than the reference and must not be read as a regression.
8. The staggering means this card cannot be merged concurrently with T0-11/T0-9a on one host; the migration re-date must be re-checked at merge time against the newest main migration.
