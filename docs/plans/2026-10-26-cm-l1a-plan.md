## 6. Acceptance bar

Automated (green at HEAD):
1. **Provisioning idempotency** — same `operationId` twice ⇒ one tenant, one allocation, one invitation, one `requested` event; a differing fingerprint ⇒ `OPERATION_CONFLICT`.
2. **Seat guard** — invite beyond `allocation.seats` ⇒ `CO_MANAGED_SEAT_LIMIT`; accept when committed seats exceed the allocation ⇒ `CAPACITY_UNAVAILABLE`; reactivating an active technician reserves nothing.
3. **Awaiting-acceptance guard** — action/API/multipart refused with `CO_MANAGED_NOT_ACTIVE`; RSC render and the two acceptance actions allowed; cache invalidated on accept/decline/terminate.
4. **Product-surface denial matrix** — for `co_managed`: billing/quotes/accounting/contracts/marketing/integrations `not_found`; tickets/boards/portal/projects/docs allowed; `/msp/co-managed` `not_found`.
5. **Focused Temporal provisioning test** — bootstrap → invitation → `pending_acceptance`; cancel → `cleanup_requested` → `terminated` with seats released once; retry after failure resumes only the next step.
6. **Resolver tests** — `admits` false for flag-only and for Emerald; `serves` true for relationship/entitlement/product code; both false under `FORCE_CAPABILITIES=co-managed:off`.
7. **Zero extra queries for `psa`** — hot-path query budget snapshot unchanged, `co_manag%` denylist clean, equality asserted per step.
8. **Emerald** — flag on, not participating: native behaviour unchanged, empty overview, Enable gated by entitlement.

## Annex A — Design decisions

### A.1 Data model
Six tables, all new, all carrying `tenant`, all distributed `colocate_with => 'tenants'`, **no foreign keys at all**: `reserveCoManagedWorkspace` inserts the relationship *before* the customer `tenants` row exists, so an FK to `tenants` would make the reservation impossible, and cross-tenant FKs are deliberately not modelled. Invariants live in CHECKs plus app code; no triggers (Citus skips them).

| Table | Key | Columns that survive the squash | Constraints / indexes |
|---|---|---|---|
| `co_management_relationships` | PK `(tenant, relationship_id)` | `sponsor_tenant`, `sponsor_client_id`, `state`, `visibility_mode`, `escalation_board_id` (folded), `revision`, `accepted_by`, `accepted_at`, `ended_at`, timestamps | `tenant <> sponsor_tenant`; `state IN ('provisioning','pending_acceptance','active','terminated')`; `visibility_mode IN ('board_scope','escalation_only')`; `revision > 0`; `(accepted_at IS NULL) = (accepted_by IS NULL)`; `state <> 'active' OR accepted_at IS NOT NULL`; `(state = 'terminated') = (ended_at IS NOT NULL)`; unique partial `co_management_one_live_sponsor (tenant) WHERE ended_at IS NULL`; index `(sponsor_tenant, tenant)` |
| `co_managed_entitlements` | PK `tenant` (sponsor) | `source`, `source_reference`, `capacity`, `signed_license`, `source_version` (folded), `verified_at`, `valid_until`, `lapse_started_at`, `read_only_after`, `revision`, `updated_at` | `source IN ('hosted','self_host','admin_grant')`; `capacity >= 0`; `revision > 0`; `source <> 'self_host' OR signed_license IS NOT NULL`; `(lapse_started_at IS NULL) = (read_only_after IS NULL)` |
| `co_managed_allocations` | PK `(tenant, allocation_id)` | `operation_id`, `request_fingerprint`, `customer_tenant`, `relationship_id`, `seats`, `state`, `released_at`, timestamps | `seats >= 1`; `tenant <> customer_tenant`; fingerprint `^[0-9a-f]{64}$`; `state IN ('reserved','active','released')`; `(state='released') = (released_at IS NOT NULL)`; **unique `(tenant, operation_id)`** (the idempotency record); unique partial `co_managed_one_live_allocation (tenant, customer_tenant) WHERE state <> 'released'` |
| `co_managed_provisioning_operations` | PK `(tenant, operation_id)` | `allocation_id`, `customer_tenant`, `relationship_id`, `requested_by`, `escalation_board_id`, `customer_board_id`, `customer_client_id`, `administrator_invitation_id`, `request_fingerprint`, `request` jsonb, `state`, `step`, `error_code`, `invitation_sent_at`, `invitation_delivery_error` (folded), timestamps | unique `(tenant, customer_tenant)`; `state IN ('queued','provisioning','pending_acceptance','failed','cleanup_requested','cancelled')`; `step IS NULL OR step IN ('tenant','seeds','settings','administrator_invitation')` |
| `co_management_relationship_events` | PK `(tenant, event_id)` | `relationship_id`, `actor_tenant`, `actor_user_id`, `event_type`, `revision`, `scope` jsonb, `scope_fingerprint`, `created_at` | unique `(tenant, relationship_id, revision, event_type)`; `revision > 0` |
| `co_management_board_scopes` | PK `(tenant, relationship_id, board_id)` | `can_collaborate` | boolean not null |

Lock order, shared by every writer including workers and L2/L7a: **sponsor entitlement `FOR UPDATE` → sponsor `tenants` `FOR SHARE` → provisioning operation `FOR UPDATE` → customer relationship `FOR UPDATE` → customer `tenants` `FOR NO KEY UPDATE` (seat admission only)**. `FOR NO KEY UPDATE` is deliberate: it serialises admissions without blocking the `email_sending_logs` insert a send on its own connection needs.

### A.2 Lifecycle state machine
Four states, reference names kept. The brief’s “suspended” is not a state: suspension is derived from the entitlement (`grace`/`read_only` in `readState`) and L7a owns any new state. “Ended” is `terminated` + `ended_at`, retained for export.

| Transition | From → to | Actor | Guard | Event (type, revision) |
|---|---|---|---|---|
| reservation | ∅ → `provisioning` | sponsor admin | sponsor eligible, capacity, one live sponsorship, fingerprint | `requested`, rev 1; idempotency key `(relationship,'requested',1)` — retry with the same `operation_id` returns the existing row |
| prepared | `provisioning` → `pending_acceptance` | worker | step `administrator_invitation` complete; owner, board, invitation, destination present | `prepared`, rev 1; `finalize…` returns early when already `pending_acceptance`, so a replay writes nothing |
| accept | `pending_acceptance` → `active` | customer admin holding `co_management:manage` in the customer workspace | `revision` + `scopeFingerprint` match, capacity, allocation `reserved`, sponsor still `psa`/Pro, no other live relationship | `accepted`, rev+1; idempotency key `(relationship,'accepted',revision,actor,scope_fingerprint)` (reference receipt re-read, kept verbatim) |
| decline | stays `pending_acceptance` | customer admin | same revision/fingerprint check | `declined`, rev+1; then `requestCoManagedProvisioningCleanup` sets the operation `cleanup_requested`, which the review screen already renders as `cancelled` |
| cancel | any pre-active | sponsor admin | operation not `active`, cleanup eligible | `cancelled`, rev+1 |
| cleanup complete | → `terminated` | worker | customer tables empty, residual proof | `terminated`, rev+1 |
| scope change | `pending_acceptance` | sponsor admin | same relationship lock | `reprepared`, rev+1 (L2 fills the mutation path) |

Revision moves only on a scope-affecting transition; `unique (tenant, relationship_id, revision, event_type)` makes every transition safe under retry.

### A.3 Provisioning
Two workflows, three activities, one durable idempotency record.

- `coManagedProvisioningWorkflow` → `bootstrapCoManagedCustomer` then `deliverCoManagedAdministratorInvitation`; `startToCloseTimeout 10m`, `maximumAttempts 5`, backoff 5s→1m. `coManagedProvisioningCleanupWorkflow` → `cleanupCoManagedCustomer`.
- The operation row **is** the idempotency record: `runCoManagedProvisioningStep` takes the lock order, returns `{skipped:true}` when `requested <= completed`, refuses `requested > completed + 1`, and writes `state/step` in the same transaction as the step’s data. “Tenant exists but step unrecorded” is therefore impossible; they commit or roll back together.
- Tenant already exists: `createTenantInDB(..., {coManagedOperation})` refuses unless `customer_tenant === input.tenantId`, `state ∈ {queued,provisioning,failed}`, `step === null`, and the workspace name / administrator email / seats match the operation; a mismatch throws rather than minting a second tenant. Once `pending_acceptance`, bootstrap returns before any step.
- Failure: `recordCoManagedProvisioningFailure` sets `failed` + `PROVISIONING_FAILED` and **keeps the reservation**; retries continue; `OPERATION_CLOSED` is non-retryable.
- Invitation delivery is three-phase (retain → send with no transaction open → re-retain and acknowledge only if the token is unchanged) because holding `FOR UPDATE` on the customer `tenants` row while `email_sending_logs` inserts on another pooled connection is an unbreakable deadlock.
- Decline writes `declined`, requests cleanup and starts the cleanup workflow; cleanup deletes the unactivated workspace, then sets `terminated` and `released` exactly once (guarded by `state='cleanup_requested'` and `whereNot('state','released')`).

### A.4 Awaiting-acceptance guard
Placement: `withAuth` calls `assertCoManagedWorkspaceUsable(user.tenant, options)` after authentication and before the action body; `authenticateApiKeyRequest` calls the same check before building the API context. Both raise `coManagedAcceptancePendingError()` (`CoManagedLifecycleError`, `code: CO_MANAGED_NOT_ACTIVE`).

Denied: every browser-invoked server action (`next-action` header), every multipart submission, and every request whose middleware-stamped `x-pathname` starts with `/api/`. Not denied: server-rendered review screen and layout, the get/accept/decline actions, and the preference reads the screen needs (`allowBeforeCoManagedAcceptance: true`). Product-surface denial is separate and unconditional for `co_managed` customers and does not depend on this guard.

Cache: `isCoManagedAwaitingAcceptance` retains only stable negative answers per process. Pending answers are re-read on every request, so a committed acceptance is visible immediately across bundles and processes, including after an earlier pending read completes. Transition invalidation remains after commit; it is not needed for pending-answer freshness. For a `psa` tenant the first probe costs one query per process and every later request costs zero, so the guard adds no statement to the `withAuth` hot-path step — asserted by snapshot equality (Annex B).

### A.6 Permission catalog
Two entries in `catalog.cjs`:

```
{ resource:'co_management', action:'read',  msp:true, client:false,
  capabilities:['co-managed'], products:['psa','co_managed'],
  defaultGrants:{psa:['msp:Admin'], co_managed:['msp:Admin']} }
{ resource:'co_management', action:'manage', ... same shape ... }
```

No migration inserts them for existing tenants (DO-NOT-PORT #27). `admitCoManagedPermissions(trx, sponsorTenant)` runs inside the first successful `reserveCoManagedWorkspace` transaction: insert both `permissions` rows for that tenant, grant them to its `msp:Admin` role, idempotent via `onConflict(...).ignore()` plus insert-if-missing. The customer workspace gets them from its own onboarding seeds (`02_permissions.cjs`, `03_role_permissions.cjs`), which run inside the provisioning transaction with `onDrift:'throw'`.

Role-editor filter: `PermissionRoleService.listPermissions` drops rows whose capability the tenant is not served for (`permissionCapabilities.ts` → `servedCapabilities(tenant)` → the same `serves` resolver). It matters even though unserved tenants normally hold no such rows: an ended sponsorship or a kill switch leaves rows in place (nothing is deleted), and they must not surface in the editor. Server-side, one call per list request, answered from the participation cache.

Dependency: `co_managed` in `PRODUCTS` and in each entry’s `products` array is L0a’s work. Without it `reconcileAllTenants(..., {product:'co_managed'})` throws `Unknown product "co_managed"`, provisioning fails at `seeds`, and the customer Admin never receives `co_management:manage`, so acceptance is impossible. Annex B carries a red test for exactly that.

### A.7 Cross-tenant identity kernel
Four symbols in `packages/co-managed/src/sharedWorkIdentity.ts` (`CoManagedHomeActor` is defined there for L1a and widened by L2):

| Symbol | Shape | Role |
|---|---|---|
| `CoManagedHomeActor` | `{ tenant; userId }` | the only identity shape policy code accepts; always the authenticated home tenant |
| `CoManagedSessionActor` | `CoManagedHomeActor & { kind:'session'; sessionId }` | built by `browserActor` from `getSession()`, never from a request body |
| `CoManagedSharedWorkError` | `code = 'CO_MANAGED_SHARED_WORK_FORBIDDEN'` | the single refusal for an unverified cross-tenant identity |
| `isCoManagedUuid` | type guard | rejects non-UUID tenant/user/record ids before any query |

Invariant: `browserActor` requires `session.user.tenant === tenant` and a matching `user_type`, so an actor’s `tenant` is whatever workspace the credential signed into. A `co_managed` workspace’s users live under the customer tenant, so their actor carries the customer tenant; the sponsor is reached only as data (`relationship.sponsor_tenant`, through a customer-scoped query) and never as an actor. `customerAdministrator` additionally requires an active internal user and `tenants.product_code='co_managed'` in the actor’s tenant, so an MSP admin cannot present as a customer admin. Every entry point re-runs `snapshotCoManagedSessionActor` / `snapshotCoManagedAuthenticatedActor`, and `isCoManagedSharedWorkError` matches on name+code rather than `instanceof` so the bundled and source copies of the package classify refusals identically.

## Annex C — Risks / open questions

1. **Catalog dependency.** If L0a’s `co_managed` catalog tagging is not on `main`, provisioning fails at `seeds` and the customer Admin cannot accept. The Annex B catalog test turns that into a red build rather than a recorded-run surprise.
2. **`co_management_board_scopes` ownership.** Shipping it here means L2 adds policy columns expand-only instead of owning the create. Fallback if L2 objects: a `proposed_boards` JSONB on the relationship, which loosens the fingerprint-to-table correspondence.
3. **`PermissionRoleService` is outside the manifest.** The role-editor filter lands in `server/src/lib/api/services/PermissionRoleService.ts`; it needs coordinator sign-off, or it must move to the RSC that feeds `packages/auth/src/components/settings/policy/RoleManagement.tsx` — unverified which one the editor actually reads.
4. **`admin_grant` is a policy shortcut.** `admits` accepts an unsigned row; that is what makes the card demonstrable without Stripe and is also a self-service lever on appliances. L8a must replace it; until then the kill switch is the only lever.
5. **Decline vs cancel.** A declined relationship stays `pending_acceptance` until cleanup, and only the operation state distinguishes it. If L7a wants customer-visible decline history, it needs a real relationship state.
6. **Table-manifest breadth.** Six keys here versus ~60 in the reference; the deletion/merge gates will fail on each later card until its keys land. The deletion worker must tolerate unknown table names during that window.
7. **`productSurfaceRegistry` typing.** Adding `co_managed` to `Record<ProductCode, …>` maps requires L0a’s `ProductCode` widening first, or the file does not typecheck. Unverified until L0a lands.
8. **Invitation link host.** Delivery builds the URL from `NEXT_PUBLIC_BASE_URL || NEXTAUTH_URL || HOST`; a missing value fails the activity after bootstrap, leaving the workspace `pending_acceptance` with no delivered invitation. L5 owns retries; this card exposes one manual resend.


## Deployment mitigation: native customer authorization

The initial customer catalog omitted native permissions. The mitigation extends
the catalog's co-managed product membership and default grants without a global
backfill. `ticket_attachment:read/create` grants are resource-scoped; they do not
grant the document library. `knowledge_base:read` is shared by action/API readers,
with a separate published-only portal reader. The shared policy lives in
`packages/documents/src/lib/documentPermissions.ts`; its byte-query predicate
preserves the PSA statement count. Document byte routes also enforce consent.
Both API-key validator classes enforce consent before changing key state.

Additional owned hunks are the document/portal readers and byte routes, KB API
controller, auth key validator, document package export, and the focused
`coManagedNativeAccess.integration.test.ts` suite/config. These extend existing
entry points; there are no new routes, migrations or sharing capabilities.
