# Internationalization (i18n) Architecture

AlgaPSA uses **i18next** with **react-i18next** for internationalization. Both the MSP portal and Client Portal are fully internationalized with feature-based namespace splitting and lazy loading.

### Which namespace to use

| String location | Namespace |
|----------------|----------|
| Generic button/label used everywhere (Save, Cancel, Delete) | `common` |
| Client portal nav, auth, dashboard, profile | `client-portal` |
| Ticket/project/billing/document UI used by both portals | `features/*` |
| MSP nav, sidebar, header | `msp/core` |
| MSP feature page (time entry, dispatch, assets, etc.) | `msp/<feature>` |

### Route-to-namespace mapping

Namespaces are lazy-loaded per route. The mapping is defined in `ROUTE_NAMESPACES` in `packages/core/src/lib/i18n/config.ts`. When adding new routes, register them there so the correct namespaces are preloaded.

## How to Use Translations

### In React components

```tsx
import { useTranslation } from '@alga-psa/ui/lib/i18n/client';

export function MyComponent() {
  const { t } = useTranslation('msp/time-entry');

  return (
    <div>
      <h1>{t('page.title')}</h1>
      <button>{t('actions.save')}</button>
      <p>{t('messages.success.created', { name: itemName })}</p>
    </div>
  );
}
```

### Locale-aware formatting

Use `useFormatters()` instead of hardcoded date/number/currency formatting:

```tsx
import { useFormatters } from '@alga-psa/ui/lib/i18n/client';

export function InvoiceRow({ invoice }) {
  const { formatDate, formatCurrency, formatNumber, formatRelativeTime } = useFormatters();

  return (
    <tr>
      <td>{formatDate(invoice.date, { month: 'short', day: 'numeric' })}</td>
      <td>{formatCurrency(invoice.amount, 'USD')}</td>
      <td>{formatNumber(invoice.tax, { style: 'percent' })}</td>
      <td>{formatRelativeTime(invoice.created_at)}</td>
    </tr>
  );
}
```

> **Country-driven date shape:** `formatDate` resolves the date's **numeric shape** — digit order (DMY / MDY / YMD), field separator, and 12/24-hour cycle — from the tenant or client's **country** configuration, not from the display locale. Language continues to supply names only (month names, weekday names, AM/PM wording). See [Country-Based Date Formatting](#country-based-date-formatting) below for the full model.

**Migration from hardcoded patterns:**

| Old pattern | New pattern |
|------------|------------|
| `new Date(x).toLocaleDateString('en-US', opts)` | `formatDate(x, opts)` |
| `` `$${amount.toFixed(2)}` `` | `formatCurrency(amount, 'USD')` |
| `amount.toFixed(2)` (for display) | `formatNumber(amount, { minimumFractionDigits: 2 })` |
| Hardcoded `"Today"`, `"Yesterday"` | `formatRelativeTime(date)` |

### Server-side formatting

```typescript
import { formatCurrency, formatDate } from '@alga-psa/core';

formatCurrency(100.50, 'fr', 'EUR');  // "100,50 EUR"
formatDate(new Date(), 'de');          // digit order determined by tenant country, not language
```

### Error and toast messages

Which pattern applies depends on whether the message crosses a request boundary.

#### Pure libraries — carry the key, translate at the edge

Code that runs in the browser and has no serialization boundary never returns bare prose.
`packages/validation` is the reference implementation, in two shapes.

Field validators return the structured `FieldValidation` (`normalize → validate → advise`),
which carries a `ValidationMessage` — key, English default, params — beside the English text.
The rendering component resolves it:

```tsx
const { t: tValidation } = useTranslation('common');  // messages live under common:clients.validation.*

const result = translateFieldValidation(validateEmailAddressField(email), tValidation);
setFieldErrors(prev => ({ ...prev, email: result.error || '' }));
setFieldWarnings(prev => ({ ...prev, email: result.warnings }));
```

Validators that answer with a single string instead — `validatePassword`, the contact phone
row rules — take the i18next-shaped `Translator` as an optional last argument:

```ts
export function validatePassword(password: string, t: Translator = englishFallback): string | null {
  if (!password) {
    return t('common:auth.validation.password.required', { defaultValue: 'Password is required' });
  }
  // …
}
```

Those keys are fully namespaced (`common:…`) so the caller's bound namespace does not matter,
and the English default keeps every un-migrated call site working. Do **not** wrap these
libraries in a lookup map keyed by English prose — the key is the seam, in both shapes.

#### Server actions — attach a key, translate at the boundary

Server actions attach a stable key to the error they already return. The `withAuth` /
`withOptionalAuth` wrapper resolves that key to the user's locale before the payload
crosses to the client. **Client render sites do not change** — an existing
`toast.error(result.actionError)` starts showing translated text on its own.

```ts
export type ActionMessageErrorShape = {
  readonly actionError: string;              // English at construction, localized by the boundary
  readonly messageKey?: string;              // e.g. 'msp/clients:errors.duplicateName'
  readonly messageParams?: Record<string, string | number>;
};
```

The action side is one extra argument; `actionError` stays synchronous, so no call site
grows an `await`:

```ts
return actionError(
  'A client with this name already exists',
  'msp/clients:errors.duplicateName',
  { name },
);
```

The wrapper does the rest:

```ts
// packages/auth/src/lib/withAuth.ts
const result = await runWithTenant(user.tenant, () => action(user, ctx, ...args));
return localizeActionError(result);   // no-op unless the payload carries a messageKey
```

`localizeActionError` (`packages/auth/src/lib/localizeActionError.ts`) resolves the locale
once per request through the already-`cache()`d `getServerTranslation`, reads the key's
namespace off disk, and rewrites `actionError` / `permissionError` in place. Because it
reads namespaces from disk it is **not** constrained by `ROUTE_NAMESPACES` — any namespace
works. It keeps `messageKey` on the payload after translating, so the operation is
idempotent when a wrapped action calls another wrapped action, and so log lines and any
remaining client-side branching have something stable to key off.

An action that runs outside a request scope (workflow workers, pg-boss jobs) degrades to
English rather than throwing: locale resolution try/catches to the default locale. An
action outside `withAuth` — an anonymous token flow, say — calls `localizeActionError`
itself at its own return.

The boundary rewrites three payload shapes, not two. Plenty of actions predate
`actionError` and still report failure as `{ success: false, error }`; those attach
`messageKey` to the object literal they already return and the boundary rewrites `error`
in place, on the same no-op-without-a-key contract:

```ts
return {
  success: false,
  error: 'Current password is incorrect',
  messageKey: 'common:errors.password.currentIncorrect',
};
```

Spread `ActionResultMessageKey` into the action's declared result type so the extra fields
are part of the contract rather than a stray property. A failure branch that forgets the
key renders English on an otherwise translated page — which is exactly how the profile
password form kept saying "Current password is incorrect" in German while the client-side
validators beside it translated correctly.

Do **not** resolve the key on the client. That needs a new helper adopted at ~1,100 render
sites, every site that misses it silently keeps rendering English, and a key whose
namespace is not listed for the current route renders raw.

**For an action that is not migrated yet**, one that already returns a typed error *code* can be
localized today by mapping the code — never the prose. `UserManagement` does this:

```ts
const PORTAL_INVITE_ERROR_KEYS: Partial<Record<PortalInvitationErrorCode, string>> = {
  PERMISSION_DENIED_INVITE: 'users.messages.error.permissionDeniedInvite',
  CONTACT_NOT_FOUND: 'users.messages.error.contactNotFound',
  // …
};

const key = PORTAL_INVITE_ERROR_KEYS[result.errorCode];
```

The map is keyed by a union type, so adding a code without a message is a type error, and
rewording the English cannot break it. If an action does not yet return a code, add one —
that is the migration, and it is the same work Category 1 formalises.

#### Deprecated: English→key lookup maps

```tsx
// Do not add these.
const errorMap: Record<string, string> = {
  'Permission denied': t('errors.permissionDenied'),
};
toast.error(errorMap[result.error!] || t('errors.saveFailed'));
```

This was the documented pattern and still exists in a few components. It makes the English
prose the error's identity, so rewording a message silently drops every caller through to
the generic fallback, and it cannot be validated by `validate-translations.cjs` or the
pseudo-locale run. The same coupling already causes real breakage elsewhere:
`packages/tickets/src/actions/ticketActionErrors.ts` classifies errors by matching 52
English prefixes, and `isPermissionError` does `.includes('Permission denied')` — so
translating a message at its source breaks error *handling*, not just display.

Existing maps are migrated to `messageKey` as each package moves. Do not add new ones, and
do not add one for a pure library — use the translator argument instead.

> Migration status, per-package sequencing, and the prose-as-discriminator prerequisite are
> tracked in [`ee/docs/plans/2026-08-18-error-message-i18n/PLAN.md`](../../ee/docs/plans/2026-08-18-error-message-i18n/PLAN.md).

### Enum labels from shared constants

Shared enum labels (e.g. `BILLING_FREQUENCY` → Monthly / Quarterly / Annually, `CONTRACT_LINE_TYPE` → Fixed / Hourly / Usage Based, status badges, Yes/No) must not ship as hardcoded English strings inside `*_DISPLAY` / `*_OPTIONS` constant files. The labels are baked in at module load, bypass `t()`, and are invisible to both the audit test suite and `validate-translations.cjs` — only pseudo-locale visual QA catches them, and only on screens someone remembers to visit.

The project uses a **localized option-hook pattern**: the constant file owns the values and the TypeScript types, a colocated hook produces the localized option list, and every consumer imports the hook instead of the constant.

```ts
// Source of truth: values only
export const BILLING_FREQUENCY_VALUES = ['monthly', 'quarterly', 'annually'] as const;
export type BillingFrequency = typeof BILLING_FREQUENCY_VALUES[number];

// Published hook: returns localized options
export function useBillingFrequencyOptions() {
  const { t } = useTranslation('features/billing');
  return BILLING_FREQUENCY_VALUES.map((value) => ({
    value,
    label: t(`enums.billingFrequency.${value}`),
  }));
}

// Companion formatter for table/cell renderers
export function useFormatBillingFrequency() {
  const { t } = useTranslation('features/billing');
  return (value: string) => t(`enums.billingFrequency.${value}`, { defaultValue: value });
}
```

Consumers call the hook at the top of the component body and pass the result into `<CustomSelect>`, column `render` callbacks, badges, etc. The route that renders any consumer must have the chosen namespace listed in `ROUTE_NAMESPACES` or the hook returns the raw key.

**Where to put the keys:**

| Blast radius | Namespace |
|---|---|
| Single feature area | `msp/<feature>.json` or `features/<feature>.json` under `enums.<enumName>.*` |
| One domain, many features | `features/<domain>.json` under `enums.<enumName>.*` |
| App-wide (Yes/No, status, priority) | `common.json` under `enums.*` |

Inline hardcoded option arrays inside components (`const userTypeOptions = [{ value, label: 'Technician' }, ...]`) are the same anti-pattern with a smaller blast radius and should be migrated the same way — or deleted if they are dead code.

Full recipe, reviewer checklist, audit greps, and the current migration backlog live in [`.ai/translation/enum-labels-pattern.md`](../../.ai/translation/enum-labels-pattern.md).

## Country-Based Date Formatting

Date **numeric shape** — the order of day, month, and year fields, the separator between them, and whether the clock uses a 12- or 24-hour cycle — is determined by the **country** associated with the tenant's or client's company location, **not** by the UI display language. Language continues to control names only: month names, weekday names, and AM/PM wording.

This separation means that a French-speaking tenant whose company is registered in Australia sees Australian date order (`DD/MM/YYYY`) rather than French order. A US-based tenant whose technicians work in German still sees `MM/DD/YYYY`. Changing the display language never reshuffles date digits.

### How country is resolved

`resolveDateFormatCountry` (in `packages/tenancy/src/lib/tenantDefaultCountry.ts`) returns a `CountryDateFormat` through the following priority chain:

| Context | Source |
|---|---|
| Client portal users | Their client's primary location country → tenant default country |
| MSP users | Tenant default country (from the MSP's own company location) |
| Fallback | `SYSTEM_DATE_FORMAT` (ISO-like `YYYY-MM-DD`, 24-hour) when no country is set |

The MSP's country is configured on its default company location under **Settings > General > Your Company**. Each client's country comes from the client record's primary location.

### The CountryDateFormat type

```typescript
export type CountryDateFormat = {
  order: 'DMY' | 'MDY' | 'YMD';
  separator: '/' | '.' | '-';
  hour12: boolean;
  // date-fns compatible format strings
  datePattern: string;   // e.g. 'dd/MM/yyyy'
  timePattern: string;   // e.g. 'HH:mm'
};
```

The full mapping from every ISO 3166-1 country to its `CountryDateFormat` lives in `packages/core/src/lib/i18n/countryDateFormat.ts`. It is checked-in and never fetched at runtime. An unrecognized or placeholder country code (`XX`) falls back to `SYSTEM_DATE_FORMAT`.

### DateFormatProvider

The resolved `CountryDateFormat` is injected server-side by the MSP and Client Portal layouts into a `DateFormatProvider` context (a sibling to `CurrencyFormatProvider`). All date pickers, time fields, and the shared `formatDateValue` formatter read from this context automatically.

```tsx
// Reading the resolved format directly (rarely needed)
import { useDateFormat } from '@alga-psa/ui/lib/dateFormat/useDateFormat';
const { order, separator, hour12 } = useDateFormat();
```

Components that render or parse dates should call `useDateFormat()` or use the shared `DatePicker` / `DateTimeField` components, which apply the country format automatically. Do not call `Intl.DateTimeFormat(locale)` to determine digit order — that derives from locale, which is now wrong for any tenant whose country differs from their display language.

### Pitfalls specific to country date formatting

- **`en-AU` locale is removed.** It existed solely to piggyback Australian date ordering on a fake language variant. Country now owns that responsibility. If you see `en-AU` anywhere in config or tests, replace it with the standard `en` locale plus an `AU` country configuration.
- **Do not infer date order from locale.** `Intl.DateTimeFormat(locale).resolvedOptions()` still exposes a format, but it is wrong for any tenant whose country differs from their UI language. Always read from `useDateFormat()` or `formatDateValue`.
- **Ticket display settings no longer include a date format pattern.** The per-tenant date-format pattern setting in ticketing display has been replaced with a `showWeekday` boolean. The numeric date shape is no longer a per-tenant choice — it follows company country.

## How Locale Resolution Works

### MSP Portal (internal users)

1. User language preference (`user_preferences` table)
2. MSP org default locale (`tenant_settings.settings.mspPortal.defaultLocale`)
3. System default (`'en'`)

MSP translation is unconditional. The former `msp-i18n-enabled` feature flag has been removed; locale resolution always follows the preference chain above.

### Client Portal

1. User language preference
2. Client default locale (`clients.properties.defaultLocale`)
3. Tenant client portal default (`tenant_settings.settings.clientPortal.defaultLocale`)
4. Cookie / browser language
5. System default (`'en'`)

### Emails

Currently locale-resolved for **client portal users only**. MSP internal users receive English emails regardless of preference.

Resolution hierarchy (client users): User preference > Client preference > Tenant client portal default > Tenant default > English. Falls back to English if no template exists for the resolved locale.

**Translation coverage:** en, fr, es, de, nl have full coverage. Italian and Polish are partial — missing project, SLA, time entry, and billing-misc email templates. See `docs/email/email-i18n-implementation-summary.md` for details.

## Pseudo-Locale Visual QA

Two pseudo-locales exist for visual testing. Each accents the English source
character by character and wraps it in locale-specific markers, so a pseudo
string stays readable, stays unique, and cannot be mistaken for English:

- `xx` — `⟦Şȧṽḗ ƈħȧƞɠḗş⟧`
- `yy` — `〖Şȧṽḗ ƈħȧƞɠḗş ····〗`, padded ~40% wider to surface layout truncation

`{{interpolation}}` tokens and `<tags>` pass through untouched. Values are
deliberately *not* a single fill string: identical fills collide when a
component uses a translated label as a React key, which corrupts sibling lists.

The transform lives in `tools/i18n/lib/pseudo-locale.mjs`. Regenerate the packs
with `node scripts/generate-pseudo-locales.cjs` — never hand-edit `xx`/`yy`.

**QA process:**
1. Switch to locale `xx` in the language picker
2. Navigate the feature area, and deliberately trigger its error paths —
   an error message is only visible to this check when it is actually raised
3. Every user-visible string should be accented and bracketed by `⟦…⟧`
4. Any string still showing plain English was not extracted — fix it

Dates, numbers, and currency will NOT be accented — they come from `useFormatters()`.
Date digit order in particular follows the **country** configuration, not the pseudo-locale.

## CustomTabs and Translation

`CustomTabs` uses a required `id` field for matching (URL sync, state, Radix values). The `label` property is display-only and safe to translate:

```tsx
const tabs = [
  { id: 'general', label: t('tabs.general'), content: <GeneralTab /> },
  { id: 'billing', label: t('tabs.billing'), content: <BillingTab /> },
];
```

Always store/compare active tab state using `id`, never `label`.

## Adding a New Language

1. Add the locale code to `packages/core/src/lib/i18n/config.ts` in `supportedLocales` and `localeNames`
2. Copy `server/public/locales/en/` to `server/public/locales/<code>/` and translate all files
3. Create email template migrations (see `server/migrations/20251228123000_add_polish_email_templates.cjs` for reference)
4. Create internal notification template migrations (see `server/migrations/20251228120000_add_polish_internal_notification_templates.cjs`)
5. Add language to `languageNames` mapping in `server/src/components/settings/notifications/EmailTemplates.tsx` (3 locations)
6. Run `node scripts/generate-pseudo-locales.cjs` and `node scripts/validate-translations.cjs`
7. Test in browser with both portals

Note: adding a new language does not affect date numeric format. A new language's date digit order is still determined by the tenant's country, not the language code.

## Common Pitfalls

1. **Wrong import path** — use `@alga-psa/ui/lib/i18n/client`, not a server path
2. **Hardcoded locale in formatting** — use `useFormatters()`, not `toLocaleDateString('en-US')`. Also: do not derive the date's digit order, separator, or 12/24-hour cycle from the locale — language no longer determines numeric date shape. Use `useDateFormat()` or the shared `formatDateValue` formatter, which both read country configuration automatically.
3. **Missing route in ROUTE_NAMESPACES** — if `t('key')` returns the key itself, the namespace likely isn't loaded for that route
4. **German/Dutch text overflow** — these translations are 30-50% longer than English; test layouts
5. **Forgetting toast/error messages** — `toast.success()`, `toast.error()`, `setError()` calls are easy to miss
6. **Missing aria-labels and tooltips** — accessibility text must also be translated
7. **Currency symbol placement** — use `formatCurrency()` which handles per-locale placement
8. **Enum labels from `*_DISPLAY` / `*_OPTIONS` constants** — labels imported from a constant file never reach `t()` and never appear in the audit suite. Use the [enum-labels option-hook pattern](../../.ai/translation/enum-labels-pattern.md) (`useXOptions()` / `useFormatX()`) instead. Applies to inline `const fooOptions = [{ value, label: 'Xyz' }, ...]` arrays inside components as well.
