# PRD — Record the on-wire Message-ID for Resend sends

Date: 2026-11-11
Status: ready for implementation
Origin: Perceptive IT (Dan Cudjoe) email threading report, 2026-10-19

## Summary

Email sent through Resend leaves with a Message-ID assigned by Amazon SES, not the one AlgaPSA put on the message. AlgaPSA records its own generated id in `email_sending_logs.rfc_message_id`, so the id recipients see and reply to is stored nowhere. Inbound header matching can never match a reply to a Resend-sent notification, and the `In-Reply-To` / `References` AlgaPSA writes on later notifications point at ids that do not exist on the wire, so mail clients do not group a ticket's notifications.

Resend has exposed the real id as `message_id` since 2026-07-08. This plan records it for every Resend send and makes the stored thread headers use it.

## Problem and findings

Production evidence, tenant `bc9aa7be-6c93-4bb9-8077-692b56670624`, ticket TR0008 (2026-10-10):

- All five `email_sending_logs` rows are `provider_type = resend` with `rfc_message_id` of the form `<uuid@perceptiveit.net>` (generated by `buildGeneratedRfcMessageId` in `packages/email/src/BaseEmailService.ts`).
- The customer's reply to row 81117 carried `In-Reply-To: <010001a127f5d259-604177f1-76f4-4180-8b8f-7dcfb8a08ccf-000000@email.amazonses.com>`. That id appears in no column of any log row for the tenant.
- `ResendEmailProvider.sendEmail` (`packages/email/src/providers/ResendEmailProvider.ts`) returns only `response.data.id` as `providerMessageId`. `BaseEmailService` then falls back to the `Message-ID` header it generated (`rfcMessageId: result.rfcMessageId ?? getHeaderValue(emailMessage.headers, 'Message-ID')`).
- Commit `115a58ccf6` (2026-10-21, alga-2026-0002798) fixed the same defect for SES over SMTP only, by parsing the `250 Ok <id>` reply in `SMTPEmailProvider` (`resolveSesOnWireMessageId`).
- `resolveReplyTargetFromOutboundMessageId` (`shared/services/email/processInboundEmailInApp.ts`) compares `rfc_message_id` with only `.trim()` applied, while every other Message-ID lookup uses `rfcMessageIdLookupForms`. This did not cause the report but is the same lookup and is inconsistent.

Resend facts (changelog "Message ID for sent emails", 2026-07-08; API reference "Retrieve email"):

- `GET /emails/:email_id` returns `message_id`.
- `GET /emails` (list) returns `message_id` per row.
- Every `email.*` webhook payload includes `message_id`; `email.sent` fires when the email is accepted for delivery.
- Not documented: whether `POST /emails` returns it, whether it can be null shortly after a send, and whether it is byte-identical to the on-wire header.

## Goals

- Every successful Resend send ends with the on-wire Message-ID in `email_sending_logs.rfc_message_id`.
- A reply whose `In-Reply-To` or `References` names that id resolves to the right ticket or comment thread.
- Later notifications for the same ticket or thread reference on-wire ids, so recipients' mail clients group them.
- Recording an on-wire id is one provider-agnostic operation, used by the synchronous path and the asynchronous path alike.

## Non-goals

- Changing reply-token matching. It already works and stays first.
- Populating `inReplyTo` / `references` in `GmailAdapter.getMessageDetails`. Production recorded them as null for Gmail replies on 2026-10-10; whether Gmail still uses that path is unverified. Track separately.
- Diagnosing why one inbound Gmail message for this tenant was never ingested, or the tenant's Gmail `unauthorized_client` watch failure.
- Microsoft Graph and non-SES SMTP sends.

## Users and primary flows

- A contact replies to a ticket notification from a client that strips the quoted body (so no reply token). The reply attaches to the ticket by header match.
- A contact receives "Ticket Created" and then "New Comment" for one ticket. Their mail client shows them as one conversation.

## Requirements

### On-wire id reconciliation

- One operation records the on-wire Message-ID for a send identified by tenant and `provider_message_id`. It is idempotent, never overwrites an on-wire id with a different one silently (log and keep the first), and keeps the generated id in `metadata` as `generatedRfcMessageId`, matching what the SMTP SES path stores.
- The same operation rewrites every persisted copy of the generated id that feeds later thread headers. The implementer must trace them all; known ones are `comment_threads.email_references`, `comments` reply-context `email_message_id` written by `BaseEmailService`, and the ticket's stored reference chain in `tickets.email_metadata.references`. The per-ticket root anchor is the customer's inbound id or an AlgaPSA-generated root; if a generated root was itself sent as a message through Resend, it follows the same rule.
- `SMTPEmailProvider`'s SES handling keeps working unchanged or is moved onto the same operation. No third variant.

### Resend send path

- After a successful `POST /emails`, the provider obtains `message_id` and returns it as `rfcMessageId`. Use the send response if it carries it; otherwise `GET /emails/:id`. A missing or null value is not a send failure: the send succeeds with the generated id recorded, and the webhook path corrects it.
- The extra call must not turn a successful send into a retried send. Failures fetching the id are logged and swallowed.

### Resend webhook path

- `mapResendWebhookToWorkflowEvents` / the route at `server/src/app/api/email/webhooks/resend/route.ts` handle `email.sent` (and read `message_id` on the other `email.*` events) and call the reconciliation operation with the tenant from the signed `alga_tenant_id` tag and `email_id` as `provider_message_id`.
- Existing delivered / bounced / complained / unsubscribed publishing is unchanged. An event with no `message_id` is a no-op for reconciliation.
- Tenant derivation keeps the existing trust rules in `resendWebhookEvents.ts`; reconciliation only ever touches rows of that tenant whose `provider_message_id` matches.

### Inbound lookup

- `resolveReplyTargetFromOutboundMessageId` matches using `rfcMessageIdLookupForms`, so bracketing and domain case cannot cause a miss.
- A reply naming either the on-wire id or the generated id resolves, since `References` already sent to customers contain generated ids.

### Backfill

- A one-off, re-runnable backfill sets on-wire ids for existing `provider_type = resend` rows from `GET /emails` (list) or per-id retrieve, through the reconciliation operation. It is tenant-scoped, rate-limit aware, and safe to stop and resume. Rows Resend no longer returns are left as they are.

## UX / UI notes

None. No user-visible surface changes.

## Data / API / integrations

- No schema change expected: `rfc_message_id`, `provider_message_id` and the index `idx_email_sending_logs_tenant_provider_message` exist.
- `email_sending_logs` is tenant-distributed (Citus). All reads and writes carry the tenant.
- Resend webhook subscription must include `email.sent`. Check the live endpoint's subscribed events; record the result in the scratchpad.

## Security / permissions

- Webhook input is attacker-controlled until the signature verifies; reconciliation runs only after `verifyResendWebhookSignature` passes.
- A webhook must not be able to repoint another tenant's send: match on tenant and `provider_message_id` together.

## Verification

- Before coding the send path, do one live Resend send in a dev environment and record in the scratchpad: what `POST /emails` returns, how soon `GET /emails/:id` has `message_id`, and whether it equals the `Message-ID` header of the delivered message.
- Round-trip test: Resend send, then an inbound reply whose `In-Reply-To` is the on-wire id and whose body has no reply token, lands on the ticket (extend `server/src/test/unit/email/outboundInboundThreadRoundTrip.test.ts`).
