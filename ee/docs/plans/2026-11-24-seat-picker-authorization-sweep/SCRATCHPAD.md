## Implementation and verification notes (Draft Implementation pass)

Every finding was reconfirmed against the branch before the change; none was already fixed.

| Finding | Confirmed gap | What changed |
| --- | --- | --- |
| F001 | `createTicketCategory` had no permission check; the Add Ticket form always offered "add new category". | Server: `evaluateBoardMutationPolicy(user, 'update')` (principal + `ticket_settings:update`) and a target-board existence check run before any read or write. Form: the control is rendered only when `checkCurrentUserPermissions` grants `ticket_settings:update`. The seat role holds no `ticket_settings` grant, so a stock seat is refused by both. |
| F002 | `applyAssociationTargetSearchScope` scoped only portal users; an MSP principal (a seat) got every client, contact and ticket. The contact loader selected `c.*` for every contact. Upload-time `assertAuthorizedAssociationTarget` accepted any MSP principal for client / contact / ticket. | `narrowToKernelReadable` compiles the kernel read scope (clients, contacts) and the ticket list's own narrowing (tickets) into the search query before search, count and page; `isKernelReadable` is the same predicate as an existence probe for the target check. Contact loader goes through the same scope and selects only the columns an option renders. Portal rules (`directClientScope`, `ticketScope`) are untouched. |
| F003 | Only the ticket branch of `searchPickerWorkItems` was narrowed. Task, interaction and ad hoc branches were not; the bundle parent (`mt`) and the task's effective service were joined unconditionally. | Project task branch: the owning project's read scope (a seat: its client's shared projects) compiled into the branch query, so rows and count agree. Interaction branch: client read scope for bundle-narrowed users; not built for a seat. Ad hoc branch: not built for a seat; `createWorkItem` refuses a seat. Bundle parent joined through a viewer-readable derived table, so an unreadable parent projects NULL id and number. Closed project fields (`service_id`) are not selected. MSP assignees of a task are released to a seat only when in its assignable audience. The picker hides the interaction / ad hoc controls for a seat (`getWorkItemPickerOptions`). |
| F004 | Add Ticket, filters and the ticket screen all read every board of the tenant; the status and category loaders took any board id. | One authority function, `resolveOperationBoardIds(action)`, returns the boards an operation permits (built-in resolver rules for that action, intersected with bundle rules for that action). `getBoardsForOperation` serves Add Ticket (`create`), `getTicketFormOptions` serves filters (`read`), and the ticket screen's destination list uses `update`. `getTicketStatuses`, `getTicketCategoriesByBoard`, `getTicketCategories`, `getAllCategories` and the administrative `getAllBoards` follow the board for a resolver-governed caller; the administrative listing is unchanged for everyone else. |
| F005 | The assignee controls were fed the people projection (who the caller may SEE). | The server marks each projected person `assignable: false` when `resolveSeatAssigneeAudience` excludes them (no marker for an unrestricted caller). Classic (`TicketInfo`, `TicketProperties`) and Bento (`BentoHero`, `TicketBentoLayout`) primary and additional assignee controls use `assignableAgentsOf`; mentions and displays keep the whole projection. `assertActorMayAssign` is unchanged. |
| F006 | `watcher_ids` were checked only for existence and `user_type`; the create response returned `attributes.watch_list` with every stored email, board defaults included. | Selected watchers are checked against the caller's people projection (`assertAssigneesInActorProjection`). The response is projected by `projectTicketWatchListForCaller`: a restricted caller is returned only listed people and only the fields the projection releases. The stored row is untouched. |
