# Attachment draft revision review

The work order is the primary specification. No approved full-feature design plan was present in this checkout; PRD.md records that absence. This feature remains separate from mitigation card 4e6f8956-4609-49e9-90a7-6daaf858983b and PDF-link PR #3319. No delivery date is promised.

## Inspect first

1. **Authorization:** `shared/lib/ticketCommentAttachments.ts`, `client-documents.ts`, `ticketCommentAttachmentEmail.ts`, and the signed download route. The portal global query applies lifecycle, public publication, client and board visibility before pagination, counts and folder discovery. An additional document association cannot bypass it. Email bytes use current canonical document authorization, including document visibility and existing account permissions. Guest recipients must remain eligible contacts for the same client/ticket; disabled or restricted accounts cannot fall through to guest access.
2. **Transactions and lifecycle:** the recovery migration, shared claim/reconciliation and publication-intent functions, shared TicketModel, portal/MSP/REST actions, and scheduled handler. Attachment claims and publication intent commit with the comment. Immediate events reuse the scheduled publication infrastructure and stable event identity. After-commit failure leaves a pending intent for startup and recurring recovery. Inbound transactional outbox behavior remains. Portal replies now actually submit through the shared Comment model and preserve the parent thread.
3. **Email recovery:** Resend adapter → Base/TenantEmailService → sendEventEmail → EventEmailRetryQueue. Explicit non-delivery retains error classification and permits retry; sent recipients cannot repeat. Unknown acceptance leaves `sending`, `requires_reconciliation`, error code and message, and the queue archives reconciliation entries rather than silently reporting success. Atomic Redis processing leases retain payloads across interrupted workers. Both event-bus implementations scope deduplication to the channel so a global consumer cannot suppress email/internal notification channels.
4. **Cleanup:** tracked new/reply/edit/thread-drawer uploads, cancellation during upload, and `cleanupCommentAttachmentDrafts.ts`. The worker checks document and file references, persists deletion work before physical deletion, and rechecks file sharing under a transaction lock on each retry. Shared content is preserved and excluded from subsequent draft-cleanup batches. Storage deletion accepts the locking transaction.

## Implemented behavior

- Images remain inline; PDFs, videos and supported storage file types use downloadable file blocks. No embedded PDF viewer or video player. Comment and ticket Documents associations persist together.
- All composition sessions track unclaimed uploads. Cancel waits for in-flight uploads, withdraws completed drafts, and keeps the editor open if withdrawal fails. Upload failures do not publish comments or send email. Drafts expire after 24 hours. The recurring sweep processes at most 100 expired drafts per tenant; exclusively owned documents and storage are removed, while shared documents/files are retained. Attached removed/deleted content stays as revoked history rather than being physically collected.
- Create/edit reconciles only same-tenant/ticket, actor-owned, unexpired drafts under locks. Removal, deletion, canceled scheduling and internal visibility revoke access. Edits and visibility changes do not resend previously delivered files. Scheduled attachments become public only at publication.
- Public initial publication selects only that comment's eligible documents, deduplicates inline CID images by document ID, and applies provider size/type limits. A one-hour signed fallback link explains the omitted file. Existing matching users can download directly; contacts without accounts verify a six-digit email code. Codes expire within ten minutes/the original link expiry, bind to an HttpOnly browser nonce, permit five attempts, and redeem once. Current authorization is checked before code delivery and again before bytes.
- Verification pages use same-origin referrers so native form POSTs work; downloads use no-referrer/no-store and attachment disposition. Portal file sizes are normalized from PostgreSQL bigint strings to prevent the global Documents page from crashing.

## Diagnosis and remaining limits

- The old live failure lacked diagnostic metadata. Reproduction found the synthetic tenant's Redis email bucket at roughly -2.2 million tokens, generating an impractical delay before SMTP. Only that invalid tenant bucket was repaired; a current UI event then recovered through the retry queue and sent once. The prior event's exact historical provider response cannot be reconstructed. The independent channel-deduplication defect also suppressed email after a global consumer processed the stable event ID; both copies are fixed and behaviorally tested.
- Other worktrees share the database and default Redis streams. Live coverage used isolated event/retry prefixes and a temporary CE/PgBoss process to ensure the current code consumed its events. The original environment file is unchanged, and the registered dev-server is restored at completion. The corrupt tenant bucket is intentionally not restored.
- EE Temporal scheduling was not exercised: this local environment cannot resolve/reach `temporal-frontend.temporal.svc.cluster.local`. Real Resend/Graph sends and a Citus-distributed migration were not run; controlled provider transport/capability tests cover classification and limits without paid sends. PgBoss scheduled and recurring execution passed live.
- Ambiguous SMTP/HTTP acceptance requires operator reconciliation; there is no reconciliation UI or automatic provider-status lookup. The ledger and Redis reconciliation records intentionally retain that state and prevent blind resends. Providers permanently disabled or recovery schedules that fail to install also require intervention and are logged. New tenant recovery schedules are installed on application initialization.
- Internal files are never included in email, including staff email. Staff can use authorized application document access. External watcher addresses without current tenant/client eligibility receive no files. Shared cleanup preserves content permanently once another relationship owns it. Deleted/edited attached history is retained with access revoked.
