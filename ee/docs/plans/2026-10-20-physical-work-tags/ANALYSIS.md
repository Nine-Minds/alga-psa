# Physical work tags, equipment custody, and project logistics — capability analysis

Source: PSA ticket **alga-2026-0002683** ("AlgaPSA Feature Proposal – Physical Equipment Tracking, QR Labels, and Service Logistics"), from an MSP customer. The ticket has a ~5,100-word Markdown proposal attached (`AlgaPSA_Physical_Work_Tags_Custody_and_Project_Logistics_Feature_Proposal_2026-10-10.md`). Read it from the ticket's documents through the PSA MCP (`GET /api/v1/tickets/{id}/documents/{documentId}`) if you need the original wording. This file is the code-grounded answer to it, audited against `main` at `a62fafbcb5` (2026-10-20).

## The request in one paragraph

An MSP has a client's defective Dell dock on its warranty shelf while Dell decides on coverage. The ticket holds the story, but nothing ties the physical box to it. They want to:

1. Print a small QR label from the ticket (and from assets, stock units, RMAs and projects) that opens the right record when scanned.
2. Track client-owned equipment in the MSP's custody: where it is, who has it, and who owes the next action. Client-owned items must never become sellable stock.
3. Stage project hardware in labelled boxes with manifests, reserved but not consumed.
4. Keep vendor (Dell) conversations on the ticket, separate from customer-visible and internal ones.

Their invariants:
- Printing has no side effects: no stock, billing or ownership change.
- QR codes are not secrets; RBAC applies after the scan.
- Customer property is never stock.
- Reservation is distinct from consumption.
- No duplicate ledger.

## Verdict

It's a good fit, and an old non-goal coming due: the inventory remediation plan deferred "client-owned/consignment stock, bins, barcode hardware" as **D10** (`ee/docs/plans/2026-07-01-inventory-review-remediation/PRD.md:35`).

How each part fits:
- **Parts 1 and 2:** build these first. They reuse a lot of existing code and together cover the customer's Dell scenario end to end.
- **Part 3:** fits, but it is its own inventory change (project reservations), and it depends on a bug fix (see "Bugs found").
- **Part 4:** a platform change to the comment-thread model. It belongs with the multi-party / co-managed conversation work, not here. Until then, vendor case numbers can go on the ticket as external links.

## What exists

### Printing and PDF

- **Browser print exists, but doesn't fit labels.** App-wide print is `window.print()` plus CSS:
  - Components: `packages/ui/src/components/PrintButton.tsx` (`usePrintAction`, `<PrintButton>`), `PrintableRegion.tsx`, `PrintOptionsDialog.tsx`.
  - Styles: `server/src/app/print.css`. It has no `@page size`, so the printer dialog decides the paper size.
  - Used on asset detail (`packages/assets/src/components/AssetDetailHeader.tsx`), tasks, and the ticket, asset and task lists. **The ticket detail screen has no print action.**
- **Server PDF exists and is the base to build on.** It renders HTML with Puppeteer and calls `page.pdf`:
  - Service: `packages/billing/src/services/pdfGenerationService.ts` (`generatePDF`, `generatePDFBuffer`); browser pool in `browserPoolService.ts`.
  - Template AST: `packages/types/src/lib/invoice-template-ast.ts`, evaluated by `packages/billing/src/lib/invoice-template-ast/evaluator.ts` and rendered by `react-renderer.tsx` / `server-render.ts`. `image` nodes take an expression `src`, so a data URL works.
- **The generic document-type registry is where a work-tag type goes.**
  - Registry: `packages/billing/src/lib/document-templates/registry.ts`. Today `DocumentType` is `'sales-order' | 'packing-slip' | 'pick-list'`.
  - Storage: the `document_templates` table (tenant, `document_type`, `version`, `templateAst`), with tenant/standard resolution in `resolution.ts`.
  - Designer: the `/msp/document-templates/[type]` page.
  - Provenance: `documents.source_template_id` / `source_template_version` / `rendered_locale` (`server/migrations/20260812090000_add_document_render_provenance.cjs`).
  - Model to copy: the packing slip and pick list in `packages/billing/src/lib/sales-order-template-ast/otherDocuments.ts`, generated by `getSalesOrderHtml` and the `server/src/app/api/inventory/sales-orders/[id]/document/route.ts` route.
- **Blockers for labels:**
  - Page size is fixed. `packages/types/src/lib/invoice-print-settings.ts` allows only `Letter | A4 | Legal`; `resolveInvoicePdfPrintOptions` emits only `format`, never `width`/`height`; `preferCSSPageSize` is never set.
  - The AST has no barcode or QR node.
  - One PDF holds one record: there is no batch or n-up sheet layout.
  - The registry, adapters and route are wired to sales orders. Inventory cannot import billing, which is why the SO document route lives in `server/`.
  - `DesignerDocumentKind` (`packages/billing/src/components/invoice-designer/utils/documentKind.ts`) covers only invoice, quote and sales-order.
- **Branding exists.** `enrichWithTenantClient` uses `packages/billing/src/lib/adapters/tenantPartyAdapter.ts` `fetchTenantParty` to supply name, address and logo. Richer branding is in `packages/tenancy/src/actions/tenant-actions/tenantBrandingActions.ts`. The sales-order adapter hard-codes `logo_url: null`.

### QR codes, barcodes and scanning

- **QR generation:** `qrcode@^1.5.4` is in root and `server/package.json`, used by `server/src/components/dashboard/MobileAppCard.tsx` and the MFA authenticator. There is **no Code 128 generator** (no bwip-js or jsbarcode); `pdf-lib` is present but only merges PDFs.
- **Mobile scanning exists.** `expo-camera` is used in:
  - `ee/mobile/src/features/inventory/components/ScanView.tsx` (the scanner)
  - `SerialAccumulator.tsx`
  - `ee/mobile/src/screens/ServerEntryScreen.tsx`

  Supported symbologies (qr, code128, ...) are listed in `ee/mobile/src/features/inventory/barcodeTypes.ts`.
- **What a scan resolves to:**
  - The chain is `GET /api/v1/inventory/lookup?code=` → `ApiInventoryController.lookup()` → `InventoryService.lookup()` (`server/src/lib/api/services/InventoryService.ts` ~303).
  - It matches product barcode/SKU, unit serial/MAC, and asset serial/`asset_tag`.
  - **It does not parse URLs**, so a QR code holding a ticket link resolves to nothing today.
- **Mobile deep links are partial.**
  - `ee/mobile/src/navigation/linking.ts` handles the `alga://` scheme and `https://algapsa.com`. Only `ticket/:uuid` and `project-task/:uuid` are routed, via `normalizeHostedTicketUrl`.
  - Server app-link files: `server/src/app/.well-known/apple-app-site-association/route.ts` and `assetlinks.json`, generated by `server/src/lib/mobileAppLinks.ts`. They claim only `/msp/tickets/*`, and only when the mobile app env vars are set; self-hosted domains get 404.
  - Mobile has detail screens for TicketDetail, AssetDetail, StockUnitDetail, StockProductDetail, ProjectTaskDetail and others. There is no Project, RMA or box screen.

### Record URLs and sign-in

- **No shared "record → URL" function.** The same mapping is written separately in:
  - `packages/search/src/indexers/*.ts` (`url:`)
  - `server/src/lib/utils/notificationLinkResolver.ts`
  - `ee/packages/microsoft-teams/src/lib/teams/buildTeamsFullPsaUrl.ts`
  - `ee/mobile/src/urls/hostedUrls.ts`

  A work tag would be a fifth copy, so extract one shared resolver first.
- **Canonical routes:**
  - `/msp/tickets/{uuid}`. It accepts UUIDs only: `TICKET_ID_PATTERN` in `server/src/app/msp/tickets/[id]/page.tsx`.
  - `/msp/assets/{id}`
  - `/msp/projects/{id}` (tasks: `/msp/projects/{pid}/tasks/{tid}`)
- **Stock units and RMAs have no detail routes.** Search emits `/msp/inventory/units?unitId=`, but no manager reads `unitId`/`soId`/`poId`. `/msp/inventory/rma` filters only by `?status=`.
- **Sign-in round trip exists.** An unauthenticated `/msp/*` request goes to `/auth/signin?callbackUrl=` (`server/src/middleware.ts` ~495–525) and comes back after login.
- **No short-link or record-reference route exists** (`/share/[token]` is for documents only).
- **Ticket-number lookups:** `findTicketByNumberAction` in `packages/tickets/src/actions/ticketBundleActions.ts`, and the REST `ticket_number` filter.

### Inventory, RMA and assets

All inventory code is in `packages/inventory/src/{lib,actions,components}`, with REST in `InventoryService.ts`.

- **`stock_locations` is flat.** `location_type` is `warehouse|van|office|other`, with no hierarchy and no bins.
- **`stock_units` assumes MSP stock.**
  - `status` is one of `in_stock|allocated|in_transit|on_loan|delivered|returned|in_rma|retired`.
  - `service_id` is NOT NULL and points at a catalog product.
  - There is no ownership column: every unit is implicitly MSP stock.
- **`stock_movements` is the append-only ledger.**
  - On plain Postgres a trigger enforces this; on Citus it is app discipline only.
  - Every write goes through `recordStockMovement` (`lib/movements.ts`).
  - Chain of custody for a unit is built from the ledger (`queryUnitDetail`, `UnitHistoryDialog.tsx`), but only for MSP stock.
- **Receiving can't be reused for intake.** `lib/receive.ts` always creates sellable `in_stock` units and updates average cost, so reusing it for client-owned intake would break the customer's invariant.
- **RMAs** (`rma_cases`; logic in `packages/inventory/src/actions/rmaActions.ts`):
  - Supports standard and advance-replacement tracks, vendor case reference `rma_reference`, `vendor_id`, and dead-unit aging.
  - `openRma` and `openAdvanceRma` require `returned_unit_id`, and `loadUnit` throws without a stock unit. **A client-owned device that was never stocked can't be put on an RMA**, even though the table already has `asset_id`/`client_id`.
  - **No pre-authorization state:** the first status is `open` or `awaiting_return`.
  - **No `ticket_id`** and no shipping or tracking fields.
- **Loaners** (`actions/loanerActions.ts`) are the existing "custody without sale" pattern: they change unit status with no COGS and no invoice.
- **Ticket and project materials consume stock immediately.**
  - `packages/inventory/src/lib/materials.ts` `addMaterial` calls `recordStockConsumption` (`lib/consume.ts`) in the same transaction.
  - There is no reserved or staged state for tickets or projects.
  - Serialized units become client assets through `lib/assetLink.ts` `createAndLinkDeliveredAsset`.
- **Sales-order allocation is the model to copy for project staging.** `actions/salesOrderActions.ts` `confirmSalesOrder` calls `allocateLine`, which goes through `lib/levels.ts` `applyAllocationDelta`. Non-serialized stock uses `reserved_quantity` (soft) or `held_quantity` (hard); serialized units move to status `allocated`.
- **Assets:**
  - `assets.client_id`; `status` from `asset_statuses`; `location` (free text) and `location_id` (FK to `client_locations`, so a client site only).
  - Procurement fields: `vendor_id`, `warranty_end_date`, `service_id`, `stock_unit_id`.
  - **No ownership field and no custody concept.**
  - History: `asset_history` (`change_type` + `changes` jsonb) and `asset_assignments` (people over time).
  - Grouping: `asset_groups` (`bundle|shared_workspace`).
  - Ticket links: `asset_associations`.
  - Events: `packages/assets/src/lib/assetChangeEvents.ts`.
- **Not found anywhere:** containers, boxes, shipments, tracking numbers, carriers. Kits (`kit_components`) are a pricing bill of materials, not physical packaging.

### Comment audiences

- **Two audiences today.** Comments have `is_internal` (internal authors only) and `author_type`. Threads (`comment_threads`, `server/migrations/20260513100000_create_comment_threads_schema.cjs`) have a thread-level `is_internal`, and replies inherit it.
- **The client portal** filters on both flags (`packages/client-portal/src/actions/client-portal-actions/client-tickets.ts`).
- **One-off Cc/Bcc** (`metadata.email_recipients`) is allowed on public comments only, so a vendor Cc'd today sees the client-visible conversation.
- **No vendor or third-party audience** and no per-thread participant lists.
- **External links can carry the vendor case today.**
  - Tables: `external_entity_links` and `tenant_external_systems`, which supports `custom:<slug>` systems with a URL template (`server/migrations/20260913120000_create_external_entity_links.cjs`).
  - UI: `packages/tickets/src/components/ticket/TicketExternalLinksSection.tsx`.
  - A vendor case such as a Dell case number fits as a custom external system.

### Permissions

- **RBAC resources** in play: `ticket`, `asset`, `inventory`, `purchase_order`, `cycle_count`, `stock_transfer`, `vendor`, `project`, `project_task`.
- **Record-level checks** sit on top of RBAC:
  - Tickets: `authorizeTicketRead` (`packages/tickets/src/actions/ticketActions.ts` ~309, using the authorization kernel in `packages/authorization/src/kernel`).
  - Assets: `authorizeRecord` (`packages/assets/src/actions/assetActions.ts` ~2409).
- **MCP** self-fetches `/api/v1/*` with the caller's key, so REST RBAC applies to it as well.

## Design calls this analysis recommends (confirm in each card's design session)

1. **Label rendering is a document type, not a new engine.**
   - Add a `work-tag` type, or one type per label class, to the document-template registry.
   - Add custom page dimensions (inches/mm) to print settings and set `preferCSSPageSize`.
   - Add a `barcode` AST node that renders server-side to inline SVG or PNG: QR through `qrcode`, Code 128 through a new dependency such as bwip-js.
   - Add a batch path that renders N records into one PDF, either one label per page (thermal printers) or n-up on a letter sheet (Avery-style).
2. **Two label classes:**
   - **Permanent identity labels** (asset, stock unit) encode the record's canonical URL.
   - **Temporary work tags** (ticket, RMA, project/task, box) encode the work record.

   Printed labels are snapshots; a scan always shows live data.
3. **QR content is the canonical web URL** from one shared resolver, e.g. `https://<host>/msp/tickets/<uuid>`. It is not a token, and RBAC applies after the scan.
   - The web gets this round trip for free (sign-in redirect plus `callbackUrl`).
   - Mobile needs the scanner to recognise its own host's URLs and route them in-app.
   - Self-hosted installs can't rely on universal links, so the in-app scanner path is the one that must always work.
4. **Custody belongs on assets, not in a new handling system.**
   - The Dell dock is normally already a client asset (often synced from the RMM).
   - Add ownership (`client` | `msp`) and a custody record: holder, MSP-side location (a stock location plus free-text bin/shelf), next-action party and follow-up date.
   - Add an append-only custody event history beside `asset_history`.
   - For items with no asset (accessories, walk-ins), intake creates a lightweight client asset in a "held" status. It never creates a `stock_units` row.
   - This is the main open product decision; see question 1 in `PLAN.md`.
5. **RMA learns client-owned devices.**
   - `openRma` accepts `asset_id` with no `returned_unit_id`.
   - Add a pre-authorization `warranty_review` status, `ticket_id`, and shipping and tracking fields.
   - Approval moves the same case into the existing standard or advance track, so its history is preserved.
6. **Project staging copies sales-order allocation** onto project materials, with a reserve → stage → consume flow. Boxes become a new `staging_containers` record with members and a manifest PDF.
7. **Vendor conversations go to the multi-party thread model.** That work is already in flight as the XO card "Ticket conversations: vendor email threads, AI participation, sharing and synthesis" (`feature/ticket-conversations-vendor-email-threads-ai-par`). The audit above describes `main` before that card merges. Interim: vendor case as an external link, and RMA `rma_reference` linked to the ticket.

## Bugs found during the audit (separate cards, not part of this feature)

1. **Ticket and project materials can consume stock reserved for sales orders.**
   - `packages/inventory/src/lib/consume.ts:141` checks `quantity_on_hand < quantity` and ignores `reserved_quantity` / `held_quantity`.
   - A material add can therefore take stock already soft- or hard-allocated to a sales order. Serialized picks are safe because they require `in_stock`.
   - Project staging (card 6 in `PLAN.md`) builds on this code, so this fix should land first.
2. **The inventory scan lookup returns assets without an asset permission check.**
   - `InventoryService.lookup()` matches `assets.serial_number` / `asset_tag` and returns asset summaries.
   - The controller checks only `inventory` read; there is no `asset:read` or record-level check.
   - A user with inventory read but no asset access can enumerate assets by serial number or tag.
   - This matters more once QR scanning becomes the way people find records.
