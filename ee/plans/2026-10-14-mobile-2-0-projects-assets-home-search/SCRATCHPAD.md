### Review round (2026-10-16)

- **Citus + `onConflict().merge()`**: `AssetAuditService.markItem` wrote `marked_at: trx.fn.now()` in the merge object. Citus: "functions used in the DO UPDATE SET clause of INSERTs on distributed tables must be marked IMMUTABLE". Every expected asset already has a snapshot row, so every mark takes the ON CONFLICT path and **no device could be marked on hosted** — invisible to mocked knex and to plain-PG CI. Bound `new Date().toISOString()` instead (the `TicketService` convention), and the test knex's `fn.now()` now returns SQL rather than a string so T117 fails if it comes back. Same trap as `reference_citus_immutable_upsert`.
- `inSnapshot = Boolean(existing)` was true for an `unexpected` row too, so re-scanning an out-of-scope device promoted it to `present` (inflated `present_count`, wrote it an `audit` history row). Snapshot membership is `existing.result !== 'unexpected'`.
- **Audit scope**: the setup screen defaulted the location row to "All of this client's devices" but sent `location_id: null`, which `start()` reads as `whereNull('location_id')` — only the location-less assets. The PRD makes the location required, so the row now reads "Pick a location" and Start waits for one ("No location" stays as the explicit location-less choice).
- **The expected count has to be built the way the server builds the scope.** `/api/v1/assets` takes one `status` and has no null-location filter, so the preview sums one dry count per status slug (the slugs partition the assets) with the location applied, and reports no count for "No location" rather than a number that disagrees with the snapshot. A `location_id=none` sentinel on the assets list would make that case countable too — a server change this card did not take.
- **`project_tasks.estimated_hours` is a bigint of MINUTES** (migration 20251205120000 renames nothing; the client portal divides by 60, and mobile's detail row already formats it with `formatMinutesDuration`). Create task was sending typed hours, so "2" stored two minutes.

### Operator round: category/subcategory on mobile (2026-10-19, F095–F097)

- **The reported bug is a close-rule interaction.** `board_close_rules.required_fields` can list `category_id`/`subcategory_id` (`CLOSE_RULE_REQUIRED_FIELDS`), and `TicketService.update` runs `enforceTicketCloseRules` on the open→closed transition, so a gated board rejected every close from a client that cannot set those columns. Mobile had neither a reader nor a writer: the v1 ticket PUT accepted the fields, but nothing in the app sent them.
- **Why a new route.** `/api/v1/categories/ticket` (ApiCategoryController) is gated on `ticket_settings:read`, which by default only Admin, Manager and Technician hold — a Dispatcher or Project Manager would have been 403'd on the picker and still unable to resolve. `GET /api/v1/tickets/categories` is the sibling of `/tickets/statuses` and `/tickets/priorities` (both added for mobile): `ticket:read`, optional `board_id`, selecting exactly what `getTicketCategoriesByBoard` selects (`display_order`, then name). Configuration stays on the settings surface.
- **The pair has to be nullable.** `updateTicketSchema` derives from the create schema, where `category_id`/`subcategory_id` are non-nullable, so re-classifying from "Hardware › Laptop" to a childless "Network" could not drop the old child and would have left a subcategory belonging to another parent. Both are now `uuidSchema.nullable().optional()`, the same treatment `contact_name_id` already documents.
- **Selection mapping copies the web.** `TicketInfo.handleCategoryChange` (pattern ticket-category-selection) stores the parent in `category_id` and the child in `subcategory_id`, and highlights `subcategory_id || category_id`. `features/ticketDetail/ticketCategory.ts` is that rule as pure functions, so the phone and the web agree about what a tap means.
- `GET /api/v1/tickets/{id}` joined `categories as cat` but never the subcategory, although `ticketWithDetailsResponseSchema` has always declared `subcategory_name` — the detail row would have read "Hardware" for a ticket filed under "Hardware › Laptop". One extra left join fixes it for every consumer.
- **Spec artefacts were patched, not generated.** `generate-openapi.ts` still dies on `DEFAULT_RATE_CONFLICT_MESSAGE` (pre-existing, reproduced on the asset-branch baseline), so the six committed documents were edited with the generator's own serializers (`JSON.stringify(doc, null, 2)` / `YAML.stringify(doc)`) after proving each file round-trips byte-identically; the new path and schema sit exactly where registration order puts them. `npm run mcp:registry:generate` was deliberately **not** committed: from these specs it also rewrites 715 lines of asset-branch drift that belongs to that branch's own regeneration.
