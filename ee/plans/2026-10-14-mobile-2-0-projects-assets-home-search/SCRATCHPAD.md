### Operator round: category/subcategory on mobile (2026-10-19, F095–F097)

- **The reported bug is a close-rule interaction.** `board_close_rules.required_fields` can list `category_id`/`subcategory_id` (`CLOSE_RULE_REQUIRED_FIELDS`), and `TicketService.update` runs `enforceTicketCloseRules` on the open→closed transition, so a gated board rejected every close from a client that cannot set those columns. Mobile had neither a reader nor a writer: the v1 ticket PUT accepted the fields, but nothing in the app sent them.
- **Why a new route.** `/api/v1/categories/ticket` (ApiCategoryController) is gated on `ticket_settings:read`, which by default only Admin, Manager and Technician hold — a Dispatcher or Project Manager would have been 403'd on the picker and still unable to resolve. `GET /api/v1/tickets/categories` is the sibling of `/tickets/statuses` and `/tickets/priorities` (both added for mobile): `ticket:read`, optional `board_id`, selecting exactly what `getTicketCategoriesByBoard` selects (`display_order`, then name). Configuration stays on the settings surface.
- **The pair has to be nullable.** `updateTicketSchema` derives from the create schema, where `category_id`/`subcategory_id` are non-nullable, so re-classifying from "Hardware › Laptop" to a childless "Network" could not drop the old child and would have left a subcategory belonging to another parent. Both are now `uuidSchema.nullable().optional()`, the same treatment `contact_name_id` already documents.
- **Selection mapping copies the web.** `TicketInfo.handleCategoryChange` (pattern ticket-category-selection) stores the parent in `category_id` and the child in `subcategory_id`, and highlights `subcategory_id || category_id`. `features/ticketDetail/ticketCategory.ts` is that rule as pure functions, so the phone and the web agree about what a tap means.
- `GET /api/v1/tickets/{id}` joined `categories as cat` but never the subcategory, although `ticketWithDetailsResponseSchema` has always declared `subcategory_name` — the detail row would have read "Hardware" for a ticket filed under "Hardware › Laptop". One extra left join fixes it for every consumer.
- **Spec artefacts were patched, not generated.** `generate-openapi.ts` still dies on `DEFAULT_RATE_CONFLICT_MESSAGE` (pre-existing, reproduced on the asset-branch baseline), so the six committed documents were edited with the generator's own serializers (`JSON.stringify(doc, null, 2)` / `YAML.stringify(doc)`) after proving each file round-trips byte-identically; the new path and schema sit exactly where registration order puts them. `npm run mcp:registry:generate` was deliberately **not** committed: from these specs it also rewrites 715 lines of asset-branch drift that belongs to that branch's own regeneration.

- **The Assets tab search box was a no-op end to end.** `listAssets` sent `search=` and `assetListQuerySchema` accepted it (it is on `baseFilterSchema`), the controller spread it into `filters`, and then `AssetService.list` dropped it on the floor: that method is a complete override with ~50 hand-enumerated `filters.X` branches and no `search` branch, and it never calls `BaseService.applyFilters` — the *only* place `searchableFields` is consumed. New `assetServiceListSearch.test.ts` pins the narrowing, the tenant scope, composition with `client_id`, and the no-search case; its stub implements grouped `where(cb)` + `whereILike`/`orWhereILike` so the OR grouping itself is covered, not just the presence of a clause. Deliberately **not** mirrored as device-side narrowing: a predicate on the phone would have to cover exactly the same six columns or it would *drop* valid server matches (search "Dell" returns manufacturer hits, which `AssetListItem` does not type), and `AssetListItem` exposes only four of them. Build 39 pointed at a server older than this fix therefore still sees an unnarrowed list — the same degradation rollout note 2 already records for the status registry.
- **`asset_audits` / `asset_audit_items` were missing from `TENANT_TABLES_DELETION_ORDER`.** They were registered in `packages/db/src/lib/tenantTableMetadata.ts` and the `tenantDb.cjs` snapshot (what the plan asked for) but not in `ee/temporal-workflows/src/activities/tenant-deletion-activities.ts`. ### Review round 5 (2026-10-19) — the Priority row never named a priority

- **`priority_name` was typed, documented and never selected.** The Details card rendered `task.priority_name`, but `ProjectService.getTaskById` joins phases, projects, status mappings, statuses, users and three service-catalog aliases and never `priorities`, while selecting `project_tasks.*` (which carries only `priority_id`). ### Review round 6 (2026-10-19) — the category picker was empty on ITIL boards

- **A board's categories are not always keyed by `board_id`.** `/api/v1/tickets/categories` filtered `where board_id = <board>` unconditionally, but `ItilStandardsService.copyItilCategoriesToTenant` inserts the standards **once per tenant** with `board_id` set to whichever board enabled ITIL *first*, and its existence check is tenant-wide (`category_name` + `parent_category`), so it never copies a second set. Every later ITIL board therefore owns zero rows in `categories`: the picker read "No categories", and a board whose `required_fields` include `category_id`/`subcategory_id` stayed unresolvable from the phone — the operator's exact complaint, just one board over from where this round-2 surface fixed it. The web has the rule in two places (`getTicketCategoriesByBoard`, and the form hydration in `optimizedTicketActions` whose comment already says "This must match getTicketCategoriesByBoard"); the route is now the third: read `boards.category_type`, filter `is_from_itil_standard = true` for `itil`, else `board_id`. Custom boards keep the web's exact behaviour (board-scoped, ITIL leftovers not excluded) rather than a cleaner rule the picker would then disagree with.
- A missing `boards` row falls back to the `board_id` filter instead of the web's `throw new Error('Board not found')`: the ticket's own board always exists, and 500-ing a read that used to answer would be a worse failure than the empty list it replaces.
- **The sibling `/tickets/priorities` route is deliberately untouched.** It is unfiltered tenant-wide (`item_type = 'ticket'`), so the `priority_id` close rule is always satisfiable; it does offer ITIL priorities on a custom board, which `optimizedTicketActions` filters out, but that inaccuracy predates this card and blocks nothing.
- Coverage is behavioural, not source-shaped: `ticketCategoriesRoute.test.ts` drives the real `GET` over a recording fake knex so it asserts **which column** was filtered, and it fails on the pre-fix route with `expected [] to deeply equal ['itil-parent','itil-child']` — the empty picker itself. One source assertion joins the existing contract test so a future rewrite cannot quietly drop the branch. No spec regen: the route's path, parameter and permission are unchanged.
- **Confirmed on real data, not just the fake.** The card's own clone (`server_mc2`) holds three `category_type = 'itil'` boards and 70 ITIL categories, and counting both filters per board shows the bug and the fix in one table: board "ITIL Support" returned **0** rows under `board_id` and returns **35** under the ITIL flag — the empty picker, reproduced — while the board that enabled ITIL first returned **187** (its own custom categories plus the standards it was stamped with) where the web's picker shows 35. So the old filter was wrong in both directions: empty on later ITIL boards, over-full on the first one. Both now agree with `getTicketCategoriesByBoard`. Each branch's SQL was also executed against the live schema, which the mocked knex cannot do: `boards.category_type` is `text`, `categories.is_from_itil_standard` is `boolean`, and both queries plan and run.

### The additivity gate needs declared exceptions (2026-10-27)

The sixth is `/paths/~1api~1v1~1assets/get/extensions/x-unapplied-validated-filters` losing its `search` entry because the filter is now actually applied; that list names validated-but-ignored filters, so an entry can only leave it when the filter starts working.
